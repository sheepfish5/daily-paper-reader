## 摘要
自回归大语言模型推理会反复调用目标模型以一次生成一个 token，这使得生成过程对 GPU 内存移动和顺序执行较为敏感。本研究在 NVIDIA A10G GPU 上受控的单请求部署中，评估了双 token 多 token 预测（MTP）相对于自回归解码的表现。一个包含 360 个请求的基准测试覆盖了纯文本、推理密集型以及工具调用类工作负载；同时，使用运行时遥测、Nsight Systems、PyTorch Profiler 以及选定的 Nsight Compute 测量来解释观察到的性能表现。MTP 在所有提示上使输出吞吐量提高了 1.91 倍至 2.19 倍，并将首次输出时间缩短了 10.0%–14.2%。平均接受长度的中位数范围为每次验证迭代 2.370 至 2.595 个 token。性能分析表明，MTP 引入了更长且更复杂的执行路径，包括提议、采样、注意力、收集和归约操作。然而，每生成一个 token，它对所选重复 CUDA Graph 的执行次数减少了 56.4%–78.1%。占主导的 MTP GEMM 内核并不比占主导的自回归 GEMV 内核更快，并且两者的选定实例都接近 A10G 的内存带宽上限。这些结果表明，MTP 通过摊销提升了推理性能：更大的 token 推进量充分减少了重复的 GPU 执行，从而抵消了额外的推测执行开销。

## Abstract
Autoregressive large language model inference repeatedly invokes the target model to generate one token at a time, making generation sensitive to GPU memory movement and sequential execution. This study evaluates two-token multi-token prediction (MTP) against autoregressive decoding in a controlled single-request deployment on an NVIDIA A10G GPU. A 360-request benchmark covered plain-text, reasoning-intensive, and tool-calling workloads, while runtime telemetry, Nsight Systems, PyTorch Profiler, and selected Nsight Compute measurements were used to explain the observed performance. MTP increased output throughput by \(1.91\times\) to \(2.19\times\) across all prompts and reduced time to first output by 10.0--14.2\%. Median mean acceptance length ranged from 2.370 to 2.595 tokens per verification iteration. Profiling showed that MTP introduced a longer and more complex execution path, including proposal, sampling, attention, gathering, and reduction operations. However, it required 56.4--78.1\% fewer executions of the selected repeating CUDA Graph per generated token. The dominant MTP GEMM kernel was not faster than the dominant autoregressive GEMV kernel, and selected instances of both approached the A10G memory-bandwidth limit. These results show that MTP improved inference through amortization: greater token progress reduced repeated GPU execution sufficiently to outweigh the additional speculative-execution cost.

## 1. 核心问题与整体含义

- **背景**：自回归（AR）LLM 推理逐 token 生成，每个新 token 都依赖完整前缀，形成单 token 前向传播循环，严重受限于 GPU 显存带宽，而非计算能力。
- **动机**：推测解码（Speculative Decoding）通过一次目标模型执行并行验证多个候选 token，有望突破该带宽瓶颈；多 token 预测（MTP）则提供模型原生的多步预测能力。
- **核心问题**：MTP 的实际收益不能仅从解码算法推断——它引入了额外的推测工作，最终 wall-clock 性能取决于"更大的 token 进展"能否抵消"额外推测执行成本"。
- **整体含义**：本文在受控单请求部署下，跨应用层、运行时层、GPU 内核层系统评估双 token MTP 与 AR 解码的性能差异，揭示加速的真正来源。

## 2. 方法论

- **核心思想**：使用专用 MTP drafter 模型（`google/gemma-4-E4B-it-assistant`）提出 2 个候选 token，目标模型（`google/gemma-4-E4B-it-qat-w4a16-ct`，量化目标模型）并行验证并按前缀顺序接受/纠正，在保持目标分布不变的前提下减少重复目标模型调用次数。
- **关键理论公式**：
  - 接受概率：\(a_i(x_i)=\min(1,\;p_i(x_i)/q_i(x_i))\)，拒绝时后续候选全部丢弃，并从修正分布 \(p'_i(x)=\text{norm}(\max(0,p_i(x)-q_i(x)))\) 重采样替代 token。
  - 期望接受长度：\(E[N]=1+\alpha+\alpha^2+\cdots+\alpha^\gamma=(1-\alpha^{\gamma+1})/(1-\alpha)\)；本研究中 \(\gamma=2\)，故 \(1\le E[N]\le 3\)。
  - 理论加速比：\(S_{\text{theory}}=E[N]/(1+\gamma c)\)，其中 \(c\) 为一次 draft 步相对一次 target 步的成本系数。
- **研究方法设计**：
  - 严格分离**干净基准测试**（量化性能结果）与**profiler 插桩执行**（解释执行行为）。
  - 使用运行时遥测（接受率）、Nsight Systems（GPU 执行节奏与内核构成）、PyTorch Profiler（运行时操作层级）、Nsight Compute（选定内核微架构）四层证据。
  - 定义了归一化指标：每 token 内核启动数 \(K_{\text{token}}\)、每 token 重复 CUDA Graph 执行数 \(G_{\text{token}}\)、每 token 内核总时长 \(T_{\text{kernel/token}}\)、重复执行组节奏 \(T_{\text{group}}\)、实现级比值 \(r=T_{\text{MTP group}}/T_{\text{AR group}}\)（明确不等同于理论系数 \(c\)）。
  - 实验协议 v1.2 冻结并用 SHA-256 校验，配对实验标识符链接等价 AR/MTP 运行。

## 3. 实验设计

- **场景/负载**（三类，每类 3 个固定提示）：
  - **纯文本**：生成恰好 8 行自由诗，每行 6–12 词。
  - **推理密集**：基于 Amdahl 定律的确定性数值计算，要求严格 FINAL 格式答案。
  - **工具调用**：给定固定工具 schema，要求恰好一次 `get_weather` 调用，禁用并行工具调用。
- **Benchmark 规模**：\(2\text{ mode}\times3\text{ workload}\times3\text{ prompt}\times20\text{ repetition}=360\) 个请求，每模式 180 个。
- **对比方法**：
  - **Autoregressive**：量化目标模型直接生成，无推测。
  - **MTP**：同一目标模型 + 专用 MTP drafter，\(\gamma=2\)。
- **环境**：vLLM 0.24.0，OpenAI 兼容流式 API，Python 3.12，温度 0、top-p 1.0、seed 42、最大 1024 输出 token、max_model_len 8192、max_num_seqs 1、BF16 KV-cache、chunked prefill、prefix caching、GPU 内存利用率 0.80。
- **测量指标**：TTFO、端到端延迟、输出吞吐（TPS）、语义阶段关联时长、完成长度；输出吞吐计算中减去首个 completion token 以对齐测量区间。

## 6. 主要结论与发现

- **应用层收益**：MTP 在所有提示上提升输出吞吐 **1.91×–2.19×**；TTFO 降低 **10.0%–14.2%**；提示级中位 E2E 加速 1.91×–2.27×；工具调用因完成长度一致成为最稳定的对比场景。
- **接受行为**：中位平均接受长度 **2.370（纯文本）–2.595（工具调用）**；位置 1 接受率 74.3%–84.5%，位置 2 为 62.8%–75.9%，第二候选接受率始终低于第一候选。
- **接受 ≠ 加速**：吞吐增益小于接受长度，说明接受是必要条件而非充分条件，必须计入推测路径成本。
- **GPU 执行机制**：MTP 执行路径更长更复杂（提议、采样、统一注意力、向量化收集、分段归约、拒绝/采样），重复执行组节奏延长 16.8%–19.7%；但每 token 的重复 CUDA Graph 执行减少 **56.4%–78.1%**，主矩阵内核调用减少 **56.4%–77.7%**，每 token 内核总时长减少 **52.0%–75.5%**。
- **内核层面**：主导 MTP GEMM（2.784 ms）并不比 AR GEMV（2.777 ms）快；两者均接近 A10G 带宽上限（575.07 vs 579.04 GB/s，达 95.93% vs 96.59%），MTP 未从内存受限转向计算受限。
- **核心结论**：MTP 通过**摊销**获益——更大的 token 进展减少了重复 GPU 执行次数，其收益超过额外推测执行成本，而非单个内核更快。

## 7. 优点

- **跨层分析方法论**：应用层 → 运行时层 → GPU 内核层 → 微架构层的完整证据链，将性能结果与执行机制明确分离。
- **严格的实验控制**：冻结协议 v1.2 + SHA-256 校验、独立 systemd 服务、warm-up 控制、profiler 检测拒绝机制、配对实验 ID。
- **解释边界清晰**：明确区分内核启动数与逻辑解码步、CUDA Graph 执行数与接受长度、内核总时长与端到端延迟，避免过度解读。
- **归一化指标设计合理**：以完成 token 数为分母，使不同工作负载间可比；定义实现级比值 \(r\) 并明确其与理论系数 \(c\) 的差异。
- **诚实的敏感性分析**：对 plain-text E2E 结果因完成长度差异给出警告，并用输出有效子集验证推理密集型结论的稳健性。
- **可复现性**：代码、文档、完整基准与 profiling 归档公开。

## 8. 不足与局限

- **配置覆盖窄**：仅 1 组 Gemma 4 target–drafter 配对、1 张 A10G、固定 \(\gamma=2\)、单请求服务、每工作负载 3 个提示；无法推广到其他模型、硬件、推测深度、批大小和并发部署。
- **遥测粒度粗**：接受率数据为约 10 秒聚合窗口，多个请求可能混入同一窗口，无法逐请求归因。
- **Profiling 样本少**：每工作负载/模式仅 1 个匹配 profiler 请求；Nsight Compute 仅刻画 1 个 GEMM 和 1 个 GEMV 实例，代表性有限。
- **理论模型未闭合**：无法从 trace 中隔离 draft 步与 target 步成本，因此理论系数 \(c\) 无法经验估计，只能做方向性对应而非精确预测。
- **观测单元非逻辑单元**：PyTorch 生成上下文和 CUDA Graph 执行是实现的观测单位，非逻辑解码步，不能直接推断推测接受长度。
- **未探索维度**：未涉及推测深度缩放（\(\gamma\) 扫描）、批处理/并发、其他硬件、训练或微调影响；未来工作明确提出推测深度缩放为重要方向。
