## 摘要
测试时扩展近来已成为一种提升 LLM 推理能力的强大方法：它通过在推理期间分配额外计算，显著提高数学、编程等挑战性任务的准确率。为加速对推理路径的探索，近期研究提出了推测执行。然而，我们表明，支持推测执行会给 LLM 服务系统带来两个独特挑战：(1) 候选路径搜索空间爆炸；(2) 针对候选路径的频繁且细粒度的验证任务。为解决这些挑战，本文提出 SpecScale，一个面向高效推测执行的服务系统。我们引入三项技术来协调延迟与计算开销之间的权衡：(1) 对低质量候选路径进行早期剪枝；(2) 对冗余候选路径之间的计算进行去重；(3) 推迟细粒度验证任务。我们在包括 MATH 和 Olympiad 在内的挑战性推理基准上评估 SpecScale。结果表明，SpecScale 显著优于非推测方法和近期的推测方法，在保持答案质量的同时大幅提升吞吐量并降低延迟。

## Abstract
Test-time scaling has recently emerged as a powerful approach for improving LLM reasoning by allocating additional computation during inference, substantially enhancing accuracy on challenging tasks such as mathematics and coding. To accelerate the exploration of reasoning paths, recent studies proposed speculative execution. However, we show that supporting speculative execution poses two unique challenges for LLM serving systems: (1) an explosion in the search space of candidate paths and (2) frequent, fine-grained verification tasks for candidates.   To address these challenges, this paper proposes SpecScale, a serving system for efficient speculative execution. We introduce three techniques to reconcile the trade-off between latency and computational overhead: (1) early pruning of low-quality candidate paths, (2) deduplicating computation across redundant candidate paths, and (3) deferring fine-grained verification tasks. We evaluate SpecScale on challenging reasoning benchmarks, including MATH and Olympiad. Our results show that SpecScale significantly outperforms both non-speculative and recent speculative approaches, delivering substantial improvements in throughput and latency while preserving answer quality.

# 论文总结：Taming Speculative Search for Test-Time Scaling in LLM Serving（SpecScale）

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 领域的训练时扩展（training-time scaling）面临算力成本高、难以持续的瓶颈。测试时扩展（test-time scaling）成为一条正交路径——不改模型参数，而是在推理阶段分配更多计算，通过生成多条推理路径并用奖励模型验证，在数学、编程等复杂推理任务上显著提升准确率。
- **问题聚焦**：论文聚焦于**外部式测试时扩展**中的 **beam search + 过程奖励模型（PRM）** 范式，其流程为“扩展–验证–选择”（expand–verify–select）循环。
- **结构性低效**：由于不同候选路径生成长度不一，朴素执行必须等待所有候选完成才能统一验证，导致每个步骤都存在显著的空闲等待时间。实验显示等待时间中位数占总执行时间的 **20–55%**，且问题越难占比越高。
- **推测执行的引入与副作用**：推测执行（speculative execution）让已完成步骤的候选路径立即继续扩展，无需等待落后者，可有效消除等待时间。但论文指出，这给 LLM 服务系统带来两个独特挑战：
  1. **候选路径搜索空间爆炸**：推测会探索远多于非推测的候选路径，放大解码计算量并加剧 KV 内存压力（beam=4 时活跃候选从约 3 条增至约 6 条）。
  2. **频繁、细粒度的验证任务**：每条候选独立触发验证，小而不规则的 prefill 任务既浪费 GPU，又反复打断解码步骤，验证次数可达到基线的 **2–3 倍**。
- **整体含义**：若缺乏系统级支持，推测执行的开销可能超过其收益；在高并发服务场景下，naive speculation 的延迟甚至会反超非推测基线。

## 2. 方法论：核心思想与关键技术

**核心思想**：围绕“延迟 vs. 计算开销”的权衡，提出 SpecScale 服务系统，通过**早期剪枝、计算去重、惰性验证**三项技术协同优化推测执行。

### (1) 早期剪枝（Early Pruning, EP）
- **依据**：beam search 每步只保留 top-𝑘 候选。一旦已验证候选数超过 𝑘，任何分数低于当前第 𝑘 名的候选都不可能进入最终 top-𝑘 集合，因此可立即剪枝，无需继续推测扩展。
- **满分终止策略**：PRM 输出 [0,1] 浮点分数，1.0 表示满分。当获得满分的候选数达到 𝑘 时，可直接确定最终选择并剪除所有剩余路径（同分无法区分优劣，无需继续比较）。
- **效果**：在不影响最终答案的前提下显著降低总计算量，且能更早结束搜索。

### (2) 计算去重（Computation Deduplication, CD）
- **问题**：多条候选共享相同 token 前缀（实验测得每步 **25–50%** 的 token 是公共的），但现有系统将每条候选实例化为独立序列，重复执行相同前缀的前向计算。
- **方法**：**按需分支（on-demand branching）**。将多条候选合并为一条带“潜在大小（potential size）”的序列；对当前前缀只做**一次解码前向**，从同一 logits 中独立采样多次；将采样结果按相同 token 分组，每组生成一个子序列并赋予其基数作为潜在大小。
- **概率等价性**：该构造与独立运行多条采样在概率上等价，但解码计算量只与**唯一前缀数**成正比，而非候选总数。
- **与 KV 前缀共享的区别**：现有前缀 KV 缓存/共享仍需每条候选各做一次前向；CD 直接对相同候选合并前向并共享 logits。
- **工程细节**：不同序列的潜在大小不同，无法一次性批量采样，因此按潜在大小分组进行批量采样以保持效率。该技术同样适用于非推测方法。

### (3) 惰性验证（Lazy Verification, LV）
- **方法**：将每条候选的验证请求入队缓冲，周期性批量 flush，利用 PRM 为 prefill-only 工作负载、吞吐随 batch 增大的特性提升 GPU 利用率。
- **三重触发策略**：
  1. **Token 阈值**：当队列中总 token 数超过阈值时 flush。通过离线 profiling 确定阈值（实验发现吞吐在 **2,048 token** 附近饱和）。
  2. **兄弟组完成**：同一父节点下的所有候选完成当前步骤时立即一起验证，避免相对非推测基线的额外延迟。
  3. **每样本延迟上限**：跟踪每条样本验证被推迟的次数，超过小上限（实验设为 **6**）即 flush，防止低负载下过度推迟。
- **权衡**：推迟越久批次越大、效率越高，但会削弱推测执行的延迟收益；三策略共同寻找平衡点。

### 系统实现
- 轻量级 LLM 服务框架，集成连续批处理（continuous batching）、PagedAttention、前缀 KV 缓存与共享、基于 FlashInfer 的融合注意力内核。

## 6. 主要结论与发现

- **推测执行的代价**：naive speculation 在高并发下会因搜索空间爆炸和频繁小验证而性能劣化，延迟甚至反超非推测基线；推测验证次数可达基线的 2–3 倍。
- **SpecScale 的收益**：
  - MATH 数据集上（Qwen2.5-7B-Instruct + PRM），吞吐量达 naive speculation 的 **2.18×**、FastTTS 的 **1.87×**。
  - 相比非推测基线，MATH 上 8 beams 时吞吐提升 **1.51×**（3B）与 **1.43×**（7B）。
  - 服务性能上，SpecScale 在相同延迟预算下可服务更多请求（更高 goodput）。
- **技术贡献分解**：
  - **EP** 主要降低候选路径数量与生成开销，但受模型满分率影响（Qwen 比 Llama 更易获满分，故收益更大）。
  - **CD** 在大模型/大 beam 下收益更明显（小模型计算资源未充分利用时收益有限）。
  - **LV** 通过高效批处理进一步降低验证开销，虽引入少量等待，但整体延迟最低。
- **质量保持**：准确率与非推测基线差异在 −1.01 至 +2.97 个百分点之间，波动在随机性范围内，答案质量基本无损。
- **可扩展性**：beam size 32 时，SpecScale 延迟约 **195ms**（非推测约 330ms），同时 KV 内存降低约 **22%**；并发 128 时仍持续提升吞吐，而基线与 FastTTS 在约 64 并发时饱和。
- **阈值敏感性**：lazy verification 的 token 阈值在 2,048 时吞吐最优（1.09×–1.14×），增至 4,096 反而低于基线。

## 7. 优点

- **问题识别精准**：首次系统性地刻画了推测执行在 LLM 服务场景下的两大独特挑战（搜索空间爆炸、细粒度验证），并用数据（候选数、token 延迟、验证次数）充分佐证。
- **技术设计正交且互补**：EP 减少无用路径、CD 消除冗余前向、LV 优化验证批处理，三者分别作用于搜索、解码、验证三个环节，可渐进叠加。
- **理论保证清晰**：EP 的第一策略（低于 top-𝑘 即剪枝）在标准 beam search 下**不改变最终选择**；CD 通过潜在大小与分组构造，保持与独立采样**概率等价**。
- **工程落地性强**：集成主流服务优化，重实现 FastTTS 并验证一致性，阈值通过离线 profiling 确定，易于迁移到其他模型/硬件。
- **评估维度全面**：吞吐、延迟、KV 内存、准确率、消融、敏感性、可扩展性均有覆盖，结论相互印证。

## 8. 不足与局限

- **硬件与场景覆盖有限**：所有实验仅在**单张 A100 80GB** 上完成，未验证多卡/分布式场景或不同 GPU 型号（如消费级或边缘设备）的适用性。
