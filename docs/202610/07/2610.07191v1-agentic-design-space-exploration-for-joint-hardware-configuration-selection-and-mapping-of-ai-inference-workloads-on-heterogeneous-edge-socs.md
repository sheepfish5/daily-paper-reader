## 摘要
现代边缘片上系统（SoC）集成了CPU、GPU和NPU等异构处理单元（PU），它们各自具有不同的性能和能耗特性。在实时延迟与能耗约束下将AI推理工作负载部署到这些SoC上，需要联合地将工作负载映射到PU，并配置每个PU（例如选择活动核心数和运行频率）。这一联合空间呈组合式增长，使得穷举搜索不可行。大多数先前关于设计空间探索（DSE）的工作采用黑盒优化（BBO），如进化搜索，其中每次评估仅返回延迟和能耗等聚合指标。近期由LLM引导的DSE也依赖同样稀疏的反馈。我们观察到，这限制了其效率：它无法提供对设计空间的洞察，也无法说明某个设计选择为何表现如此，并且使LLM的推理能力在很大程度上未被利用。我们提出TraceDSE，一种智能体式DSE流程，用于在异构SoC上为AI推理执行联合工作负载映射和PU配置选择。TraceDSE是一个由更丰富反馈（以系统执行轨迹的形式）驱动的迭代式提议者-评论者循环。LLM提议者智能体生成候选映射和PU配置，以供硬件评估。配备程序化轨迹分析工具的LLM评论者智能体分析这些轨迹，以识别瓶颈并提出有针对性的改进建议。这一循环能够更深入地洞察每个设计点，产生更高质量的决策，并实现更有效的搜索。在英特尔Meteor Lake SoC上的四个AI推理工作负载（不同复杂度的模型和一个多模型流水线）上，TraceDSE始终优于两种最先进的BBO工具，相比NSGA-II将帕累托前沿超体积最多提升35%，相比贝叶斯优化最多提升68%，同时所需的硬件评估次数减少约6-9倍。

## Abstract
Modern edge Systems-on-Chip (SoCs) integrate heterogeneous processing units (PUs) such as CPUs, GPUs, and NPUs, each with distinct performance and energy characteristics. Deploying AI inference workloads on them under real-time latency and energy constraints requires jointly mapping workloads to PUs and configuring each PU (e.g., selecting the number of active cores and the operating frequency). This joint space grows combinatorially, making exhaustive search infeasible. Most prior work on design space exploration (DSE) applies black-box optimization (BBO) such as evolutionary search, where each evaluation returns only aggregate metrics such as latency and energy. Recent LLM-guided DSE relies on the same sparse feedback. We observe that this limits its efficiency: it offers no insight into the design space or the reasons a design choice performs the way it does, and it leaves the reasoning abilities of LLMs largely unused. We present TraceDSE, an agentic DSE flow that performs joint workload mapping and PU configuration selection for AI inference on heterogeneous SoCs. TraceDSE is an iterative proposer-critic loop driven by richer feedback in the form of system execution traces. The LLM proposer agent generates candidate mappings and PU configurations for hardware evaluation. The LLM critic agent, equipped with programmatic trace-analysis tools, analyzes the traces to identify bottlenecks and suggest targeted refinements. This loop yields deeper insight into each design point, higher-quality decisions, and a more effective search. Across four AI inference workloads (models of varying complexity and a multi-model pipeline) on an Intel Meteor Lake SoC, TraceDSE consistently outperforms two state-of-the-art BBO tools, improving Pareto frontier hypervolume by up to 35% over NSGA-II and up to 68% over Bayesian optimization, while requiring ~6-9x fewer hardware evaluations.

## 1. 核心问题与整体含义（研究动机与背景）

- **应用背景**：AI 推理正广泛部署于手机、可穿戴设备、智能眼镜、AR/VR 头显等边缘设备，这些设备普遍搭载集成 CPU、GPU、NPU 的异构 SoC。为在实时延迟与能耗约束下高效部署，需要同时解决两个耦合的设计问题：
  - **工作负载映射空间**：将神经网络计算图（DAG）的每个节点分配到哪个 PU 上执行。同一节点在不同 PU 上存在显著不同的延迟–能耗权衡（论文举例：某节点在 Intel Meteor Lake 上 GPU 46.7ms/1.40J、NPU 51.3ms/1.04J、CPU 51.5ms/3.81J）。
  - **PU 配置空间**：CPU 的 P-core/E-core 类型与活动核心数、GPU/NPU 的工作频率、NPU 的活动 tile 数等运行时可配置项。
- **组合爆炸**：两个空间取笛卡尔积后规模巨大。例如 HRNet（98 节点）部署到 3 个 PU、每个 PU 仅 2 种配置，候选解约 3⁹⁸ × 2³ ≈ 4.6×10⁴⁷；而单次硬件评估需 30–60 秒，穷举搜索完全不可行。
- **现有方法的共同缺陷**：无论是黑盒优化（BBO，如进化搜索、贝叶斯优化）还是近期兴起的 LLM 引导 DSE，其迭代循环中反馈都只有**聚合指标**（端到端延迟、能耗）。作者指出这种稀疏反馈限制效率，原因有二：
  - 无法揭示设计空间的规律，也无法说明某个设计选择为何表现如此；
  - 未发挥 LLM 的推理能力——LLM 本可从更丰富的信息中做出更高质量决策。
- **核心洞察**：硬件评估能产生远比聚合指标更有价值的**执行轨迹（execution trace）**，包含每个节点的执行时间/能耗、跨 PU 数据传输时间、PU 利用率等。例如 Inception 某 block 的轨迹显示关键路径节点被映射到 CPU 成为瓶颈、GPU 上有排队节点而 NPU 空闲——这些信息直接提示"将排队节点迁移到空闲 PU"和"增加 CPU 活动核心数"两项改进，而聚合指标无法推导出这些结论。
- **整体意义**：论文提出以执行轨迹作为丰富反馈、由双 LLM 智能体驱动闭环搜索的 DSE 范式，在真实边缘 SoC 上同时提升搜索质量、样本效率与可解释性。

## 2. 方法论：TraceDSE 的核心思想与关键细节

### 2.1 问题形式化
- 工作负载表示为 DAG *G*，节点集 *N*，边表示数据依赖；平台提供异构 PU 集合 *P*，完整配置空间 *H = H₁×…×H|P|*。
- 映射 *m: N → P*；给定 *m* 与配置 *h ∈ H*，调度器产生满足依赖的调度 *S(G, h, m)*。
- 优化两个目标：延迟 *L(h,m) = Makespan(S)*，能耗 *E(h,m) = Pow(h,m) · L(h,m)*。
- 用超体积 *HV(F)* 衡量帕累托前沿 *F* 的质量，目标是在延迟–能耗空间中发现非支配解以最大化 *HV(F)*。

### 2.2 框架总览（迭代式 evaluate–analyze–refine 闭环）
- 由两个 LLM 智能体——**提议者（proposer）**与**评论者（critic）**——通过迭代循环连接，另有**搜索状态**作为共享记忆。
- 终止条件：连续 *T* 次迭代（实验中 T=5）超体积相对提升低于阈值 *ε*（实验中 0.5%）。

### 2.3 关键组件
- **节点画像（Node Profiling，一次性）**：将全部节点分别映射到每个 PU 并以最大资源配置运行一次，得到每个节点在各 PU 上的延迟/能耗，即"画像先验"。作用有二：(1) 为提议者热启动提供先验；(2) 使评论者能在不额外做硬件评估的情况下，通过替换节点的画像延迟来估计重映射的端到端延迟影响。
- **提议者智能体**：每轮生成一批候选（映射 + PU 配置 + 解释性推理陈述）。输入包括：
  - 首轮：工作负载 DAG、PU 配置空间、优化目标、画像先验；
  - 后续轮次追加：帕累托前沿（指引新候选应改进的目标空间区域）、探索摘要（记录已评估区域以避免重复）、上一轮评论（逐候选反馈 + 建议改动）。
- **调度器与评估器**：调度器用 HEFT（Heterogeneous Earliest Finish Time）按候选映射做 DAG 调度；评估器在目标平台执行，输出端到端延迟、能耗、各 PU 能耗占比，以及**执行轨迹**（每节点的 PU 归属、起止时间戳、计算时间、跨 PU 数据传输延迟）。
- **评论者智能体**：分析轨迹并产出三部分评论——(1) 逐候选反馈（哪些设计选择驱动了当前指标，哪些应保留/修改）；(2) 跨迭代综合观察（如某节点–PU 映射持续表现不佳）；(3) 对映射与配置的推荐改动。其配备 6 个可自主选择调用的程序化工具：
  1. 关键路径提取（节点及其延迟与总延迟占比）；
  2. 延迟瓶颈排序（按延迟降序的 Top-k 节点及在替代 PU 上的估计加速）；
  3. PU 利用率与空闲区间分析；
  4. 单节点细粒度检查（计算时间、调度与通信延迟、各 PU 上的估计延迟）；
  5. 能耗分解（各 PU 占总能耗百分比）；
  6. 延迟估计（预测某映射/配置改动后的延迟）。
- **搜索状态**：记录已评估候选、帕累托前沿与探索摘要，平衡"精炼（refinement）"与"探索（exploration）"。

## 3. 实验设计

- **推理运行时**：OpenVINO。
- **LLM**：Gemini 3.1 Pro Preview（temperature 1.0，thinking level high），同时用于提议者与评论者。
- **PU 配置空间**（5 个参数的合法组合）：CPU 核心数 ∈ {1,…,16}、CPU 核类型 ∈ {P-core, E-core}、超线程 ∈ {on, off}、NPU turbo ∈ {on, off}、NPU tile 数 ∈ {1, 2}。每个节点映射到 CPU/GPU/NPU 之一。
- **四个评测工作负载**（并行度各异）：
  - Depth Anything V2（28 节点，基本串行）；
  - HRNet（98 节点，重复的 fork–join 并行）；
  - ImageBind（72 节点，四条并行编码链汇聚为联合嵌入）；
  - 基于语音的 VQA 流水线（Whisper-Small + CLIP ViT-L/14 + Qwen2.5-3B，71 节点，音频与视觉编码器并行汇聚到 LLM 解码器）。
- **对比基线（3 个）**：
  - 随机搜索；
  - NSGA-II（种群 16，均匀交叉）；
  - 多目标贝叶斯优化（TPE，原生支持混合连续–类别参数空间）。
- **公平性设置**：每个基线在目标 SoC 上运行固定 12 小时墙钟预算；所有方法从相同的 3 个种子候选出发（全节点映射到单一 PU、最大资源配置），且种子候选计入各自预算。
- **评价指标**：按 benchmark 归一化的超体积 *gHV ∈ [0,1]*（以所有方法帕累托最优候选中的最大延迟与最大能耗为参考点）、硬件评估次数、墙钟时间。
