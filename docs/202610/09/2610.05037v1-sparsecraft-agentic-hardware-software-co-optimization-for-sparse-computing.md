## 摘要
稀疏加速器设计空间通常依据解析模型进行搜索，因此一个设计点是否被接受取决于模型预测的结果，而非硬件的实际表现。SparseCraft 通过在一个闭环 CHIA 循环中引入语言模型弥合了这一差距。在 15 次迭代的每一次中，模型读取上一次迭代的实测结果，并通过 MCP 工具服务器编辑 Gemmini 加速器的 Chisel RTL、内存配置和稀疏内核调度；任何候选设计只有在经过合法性检查、展开、周期精确仿真、对所有输出与黄金参考进行逐位比对并通过综合之后，才被计入。该测试框架将每次测量转化为下一项工作任务：一个经诊断的瓶颈及匹配的策略指导、已尝试设计的历史记录，以及模型自身预测的评分；第二个模型则修复未能通过门控的修改。在 $512 \times 512$ 的 GraphChallenge 稀疏 DNN 层上，该闭环相比块稀疏 Gemmini 基线实现了周期数降至 1/2.1、片外流量降至 1/9.8 和面积减少 22.8%，同时建模 perf/W 提高 5.61 倍，EDP 降至 1/11.8。优化手段跨越三个层面：使稠密操作数常驻的调度消除了 9.8 倍的流量，模型用 Chisel 编写的零门控 MAC 和零行跳过单元降低了能耗，调整存储器大小则减少了面积。

## Abstract
Sparse-accelerator design spaces are usually searched against analytical models, so a design point is admitted on what a model predicts rather than on what the hardware does. SparseCraft closes that gap with a language model inside a closed CHIA loop. In each of 15 iterations the model reads the measured outcome of the previous one and edits the Chisel RTL, the memory configuration and the sparse-kernel schedule of a Gemmini accelerator through MCP tool servers, and no candidate counts until it has been checked for legality, elaborated, simulated cycle-accurately, checked bit-for-bit on every output against a golden reference, and synthesised. The harness turns each measurement into the next work order, a diagnosed bottleneck with matching strategy guidance, the history of tried designs and a score of the model's own prediction, and a second model repairs changes that fail a gate. On a $512 \times 512$ GraphChallenge sparse-DNN layer the loop reaches 2.1x fewer cycles, 9.8x less off-chip traffic and 22.8% less area than the block-sparse Gemmini baseline, with 5.61x higher modelled perf/W and 11.8x lower EDP. The levers span three layers: a schedule that keeps the dense operand resident removes 9.8x of the traffic, a zero-gated MAC and a zero-row skip unit that the model wrote in Chisel cut energy, and resizing the memories cuts area.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景缺口**：稀疏加速器的设计空间通常以**解析模型**作为搜索目标，一个设计点是否被接受取决于"模型预测了什么"，而非"硬件实际做了什么"，预测与真实行为之间存在鸿沟。
- **现有 LLM 硬件工作的局限**：语言模型已能生成可编译、可通过仿真的硬件描述代码，能设定加速器参数、优化加速器内核，但大多**一次性生成**、以解析模型评分，或**只调一层**（RTL 或软件），缺乏跨迭代、可承担后果的闭环协同设计。
- **稀疏性使问题天然跨层**：在本文工作负载中，块稀疏内核虽跳过了空块，但被占用块密度仅 **6.25%**，导致为 524,288 个有效 MAC 发出 8,388,608 个 MAC（约 16 倍浪费）。要回收这些浪费，必须**同时**改动 RTL、存储与调度。
- **整体含义**：SparseCraft 将 LLM 作为闭环 CHIA 框架中的一个节点，让其在**实测反馈**（而非解析模型）驱动下，跨软件调度、RTL 电路、存储配置三层自动协同优化 Gemmini 稀疏加速器。

## 2. 方法论

### 2.1 核心思想
- 在 CHIA（智能体式软硬件协同设计开源框架）中构建**封闭回路**：LLM 提出设计 → 门控阶梯验证 → 实测结果转为下一轮"工作任务" → 再提出设计。
- **预算固定为 15 次迭代**，由计数器而非模型终止流程；"不可变输入"（合法性规则、Pareto 准入、能耗模型、指标解析器、内核）每轮做哈希校验（N74）。
- 无人类提出、编辑或挑选设计；测试框架、能耗模型与基准固定且已哈希。

### 2.2 两个 LLM 角色
- **提议者（Proposer, N10）**：Claude Opus 5 以 Claude Code 智能体形式运行；**移除所有内置工具**，仅能调用三个由 CHIA 提供的 MCP 工具：
  - bash 工具（限定于 Chipyard 构建容器，仅允许写 3 个文件：设计点参数、PE、零位图单元）；
  - status 工具（返回上一实测设计）；
  - history 工具（返回所有已尝试设计及其结果）。
- **修复者（Repairer, N73）**：第二个 LLM，接收"收缩后的证据"、提议者声明的机制、两份设计状态与历史修复尝试，返回修复后的树（重跑整条阶梯）或报告 **NOT ACTIONABLE** 并给出根因。修复尝试上限为每轮 3 次。

### 2.3 提示结构
- 系统提示由共享片段（可写集合、执行规则、反馈模式、输出契约）组合而成，保证事实定义唯一、前缀字节稳定以利缓存。
- 每轮工作任务按序提供：父设计状态 → 实测诊断与计数器 → 针对该瓶颈选出的策略模块 → 编号流程（先读后写、单次改动、验证、编译）→ 模型自己未尝试的候选。
- 回答必须解析为三段：候选列表、已实现并编译的**单一变异**、对时间/能耗/面积/时钟的**预测（better / flat / worse）**，由测试框架对实测结果打分。
- 修复者提示额外加入调试方法（沿门控阶梯逐项验证、一次一改）、按判决分类的故障手册，以及"只修能命名的根因，否则报 NOT ACTIONABLE"的置信协议。

### 2.4 设计状态与合法性
- 设计为**类型化记录**：**28 个硬件字段**（阵列几何、暂存器与累加器容量与分 bank、DMA 与队列参数、稀疏机制）+ **6 个调度字段**；仅改调度可复用缓存的精化结果。
- **合法性（N20）在构建前以微秒级检查 27 条命名规则**：Gemmini 生成器不变量、硬件与内核之间的容量与调度耦合、稀疏元数据预算、面积预算；另有两条规则锁死工作负载与稠密调度标志。
- **N13** 拒绝可写集合之外的编辑；**N21** 拒绝已评估过的重复设计。

### 2.5 模型可构建的两个 RTL 机制
- **T-A：零门控 MAC**——当 PE 的操作数为零时保持不动，使乘法器不翻转，降低能耗。
- **T-B：零位图单元（ZBU）**——抑制对稀疏操作数全零行的暂存器读取。

### 2.6 测量与门控阶梯
- 精化 + Verilator 构建（N30/31）产生 Rocket + Gemmini 的**周期精确仿真器**；内核（N32）仅遍历稀疏操作数的非零 16×16 块。
- 仿真（N50）给出周期数、片外字节数与 Gemmini 硬件计数器；**tripwire** 拒绝低于读取输入所需流量的结果。
- **N41 等价性检查**：将全部 **32,768 个输出**与主机端计算的黄金结果逐位比对，确保调度错误不会同时出现在两侧。
- 综合（N52）：yosys + OpenSTA on NanGate45，与仿真**并行**运行；面积为综合逻辑面积 + 估算 SRAM 面积；所有设计在固定 **2.0 ns 时钟**下评估；能耗（N53）由实测计数器建模。

### 2.7 准入、诊断与修复
- **N60 准入**：仅当没有已准入设计在时间、能耗、面积三项上同时不劣于它时才接纳（**Pareto 非支配**）；被拒绝者精确回滚（含 RTL）。
- **N61 诊断**：依据 DMA 等待与阵列活动计数器，将瓶颈标为 memory / compute / idle / balanced，该标签决定下一轮工作任务选取哪些策略模块。
- **N71 分类**：失败门控被分类，基础设施故障**从不进入模型**；N72 收缩证据后交给修复者。
- 算法 1 给出完整流程：`for i=2..T` → 校验不可变输入 → PROPOSE → LADDER → 若失败且可修复则在 R≤3 内循环 EVIDENCE/REPAIR → 若通过且 ADMIT 则更新父设计，否则回滚 → 记录并给预测打分 → 重新诊断。

## 6. 主要结论与发现

- 相比块稀疏 Gemmini 基线（表 I，it.1 vs it.15），最终设计达成：
  - **周期数** 106,650 → 50,862（**2.1× 更少**）；
  - **片外字节** 3,211,264 → 327,680（**9.8× 更少**）；
  - **面积** 4.035 → 3.115 mm²（**−22.8%**）；
  - **能耗** 95.67 → 17.04 μJ（**5.61× 更少**）；
  - **功耗** 0.449 → 0.168 W（**2.68× 更低**）；
  - **性能** 4.92 → 10.31 GOPS（**2.1×**）；
  - **perf/W** 10.96 → 61.5 GOPS/W（**5.61×**）；
  - **perf/area** 1.22 → 3.31 GOPS/mm²（**2.72×**）；
  - **EDP** 20.41 → 1.73 nJ·s（**11.8× 更低**）。
- 两者均**未产生错误输出**。
- **杠杆跨三层**：软件层让稠密操作数常驻（消除 9.8× 流量）；RTL 层由模型手写 Chisel 的零门控 MAC 与零行跳过单元（降低能耗）；存储层重设容量（减少面积并意外地大幅缩短周期）。
- 模型**首步选择软件层**、且**方向性预测 30/36 正确**，说明实测反馈回路能有效引导跨层决策。
- 仿真占关键路径 75%，说明**周期精确仿真（而非 LLM 推理）才是闭环的主要瓶颈**。

## 7. 优点

- **方法论层面**：
  - 用**真实硬件实测**（周期精确仿真 + 逐位等价性 + 综合）替代解析模型作为接受判据，从根本上消除"模型预测与硬件行为脱节"的问题。
  - **门控阶梯（N13–N53）** 层层设防：可写范围限制、去重、合法性、编译、精化、仿真、32,768 输出逐位比对、综合——确保只有"真实可行"的设计才被计入。
  - **双 LLM 分工**：提议者

提议者负责"提出设计 + 声明机制 + 给出可打分的方向性预测"，修复者只在证据被收缩、根因可命名时介入，形成**"生成—诊断—修复"的责任分离**；修复者被明确授权输出 `NOT ACTIONABLE`，避免模型为"显得有用"而编造修复。
  - **失败即数据**：基础设施故障从不进入模型上下文，被拒设计连同拒绝原因（重复、违反规则、Pareto 被支配）全部记录，使"模型犯错"与"流程出错"可区分。
  - **提示工程的工程化**：共享片段保证事实定义唯一、前缀字节稳定以利缓存；每轮工作任务按"父状态 → 实测诊断 → 针对性策略模块 → 编号流程 → 未尝试候选"的固定结构注入，把"探索"约束在受控轨道上，降低长程智能体的漂移风险。
  - **预算由外部计数器固定**（15 次迭代），而非由模型自行决定何时停止，杜绝"自我宣告收敛"。

- **系统与实验层面**：
  - **跨三层同时见效**且各层贡献可归因：软件层（it.2）解决片外流量、RTL 层（it.3/it.4）解决能耗、存储层（it.8/it.9/it.15）同时改善面积与周期，三条杠杆的作用域清晰、互不混淆。
  - **反直觉发现的保留**：it.8 缩小暂存器反而使周期下降 36%，与模型预期不符——论文如实报告而非事后合理化，说明该框架具备"发现人类直觉之外设计点"的能力。
  - **Pareto 准入 + 精确回滚**保证迭代单调不劣化，最终前沿是 15 次尝试中真实可达点的非支配集合，而非"最优一次"的幸存者偏差。
  - **能耗由实测计数器建模**而非峰值功耗估算，避免了"面积换能耗"类结论的常见夸大。

## 8. 局限与不足

- **泛化性证据薄弱（最核心局限）**：
  - 仅 **1 个工作负载**（`n1024-l1.mtx` 的 512×512 左上块）、**1 个加速器**（Gemmini）、**1 个阵列配置**、**1 次运行**。稀疏矩阵的块占用模式、密度分布、维度都会显著改变最优设计点，论文无法说明所得设计点是否可迁移。
  - 模型首步即选软件层、并在 it.5 因"内核 16×16 分块锁死阵列尺寸"而失败，说明**搜索空间实际上被内核与规则大幅裁剪**，"LLM 自主协同设计"的自由度可能被高估。

- **对比基线不足**：
  - 全程为**自比对**（it.1 vs it.15），未与任何**自动化 DSE 方法**（贝叶斯优化、遗传算法、随机搜索、逐层网格搜索）在同一预算下横向比较。因此无法回答"LLM 智能体是否比传统搜索更高效"这一关键问题——而这恰恰是本文标题的核心主张。
  - 也缺少 **LLM 消融**：如去掉实测反馈（改用解析模型打分）、去掉修复者、去掉 Pareto 准入、去掉预测打分等，均未做受控实验，无法定位收益来源。

- **统计显著性缺失**：LLM 采样具有随机性，论文未报告多种子重复、未给置信区间或方差，单次轨迹可能高度依赖运气（模型首步选对软件层即已锁定大部分收益）。

- **成本与效率未正面讨论**：
  - 328 分钟活跃时间、17 次 LLM 会话、15 轮仿真，但**未给出与基线 DSE 方法的成本对比**（例如同等墙钟时间下随机搜索能走多少点）。若随机搜索在 328 分钟内能评估数百个设计点，LLM 的"少样本高效"优势需要更强的论证。
  - 未给出 token 消耗、API 成本、失败重试的经济代价。

- **可复现性缺口**：未说明 CPU/内存/容器资源配额；未提供提示全文（仅描述结构）；模型版本以代号出现（Claude Opus 5、N10/N73 等），第三方难以精确重放。

- **机制层面的解释力有限**：对"为什么 it.8 缩小暂存器会缩短周期"缺乏硬件层面的机理解释（如是否减少了 DMA 搬运粒度、改变了 bank 冲突或 TLB 行为），停留在现象描述。

- **方法适用范围**：框架依赖"可编译—可仿真—可综合—可逐位校验"的完整阶梯，对于**缺少周期精确模型或黄金参考**的领域（模拟电路、模拟/混合信号、新型器件）难以直接套用。

## 9. 启示与可延展方向

- **把"实测"而非"模型"作为接受判据**，是本文最具迁移价值的思想：任何"生成式硬件/系统设计"工作都应回答"这个设计点真的被构建并测量过吗"。
- **门控阶梯可作为通用模板**：可写范围 → 去重 → 合法性 → 编译 → 精化 → 仿真 → 逐位等价 → 综合，每一级都是一个廉价的"否决权"，把 LLM 的幻觉挡在物理世界之外。
- **瓶颈画像值得借鉴**：仿真占关键路径 75%，提示后续工作应优先做"仿真加速"（更快的周期模型、代理模型引导预筛），而非一味提升模型能力或增加迭代次数。
- **值得补做的实验**：多矩阵（不同密度/块结构）、多阵列尺寸、多种子重复、与传统 DSE 的同预算对比、以及逐组件的消融。

## 10. 总体评价

SparseCraft 的贡献**主要在于方法论与流程严谨性，而非绝对性能数字**。它把 LLM 从一个"代码生成器"改造为闭环优化器中的一个受约束节点：所有中间结论都必须经过构建、仿真、逐位校验与综合的检验，失败被分类、回滚可精确、预算由外部固定。相比大量"用 LLM 生成 RTL 后靠解析模型打分"的工作，其可信度有量级上的提升。

但论文的核心主张——"智能体式闭环协同设计优于既有 DSE"——**并未被实验设计所验证**：单工作负载、单次运行、无横向基线、无消融，使得 2.1× 性能、5.61× 能效的提升只能说明"这条特定轨迹有效"，而不能说明"该框架普遍有效"。文中那些反直觉的发现（缩小暂存器提速、模型预测 30/36 命中）是很有价值的定性线索，却因样本量为 1 而无法上升为结论。

**一句话定位**：这是一篇**流程贡献扎实、验证范式先进、但实证覆盖明显不足**的可行性演示（proof-of-concept）论文；若补上多场景、多基线与消融实验，其方法论主张才具备被广泛接受的基础。
