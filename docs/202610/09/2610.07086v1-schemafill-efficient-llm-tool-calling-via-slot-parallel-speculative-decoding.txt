# ABSTRACT 

LLM agents interact with external systems by generating structured tool calls. Given a user request, conversational context, and a catalog of tool schemas, a tool-calling model must select tools and generate their arguments, potentially pro-ducing multiple calls in a single response. Standard autoregressive decoding gen-erates these calls token by token, incurring substantial latency for requests involv-ing multiple calls or many argument fields. The explicit argument structure offers opportunities for parallel generation, but later argument values may depend on preceding fields and calls, so independently generated values can differ from the target model’s output. We present SchemaFill, a framework for efficient LLM tool calling through slot-parallel speculative decoding. SchemaFill generates future slot values concurrently as candidates, without requiring advance knowledge of the actual call sequence or argument values. Candidates spanning multiple fields and calls are concatenated for verification by the target model under the actual output prefix. Only verified tokens are committed, and the target supplies correc-tions when candidates disagree. This applies target verification while exploiting parallelism across slots and calls. On Glaive and BFCL, SchemaFill achieves up to a 4.05 × improvement in end-to-end throughput over autoregressive decoding. Code is available at https://github.com/Czzzk/SchemaFill .

# 1 INTRODUCTION 

LLM agents extend language models from producing text to acting on external systems (Yao et al., 2023; Schick et al., 2023). Given a user request, conversation history, and a catalog of available tools, an agent may need to query a database, invoke a software service, or coordinate several ac-tions. Tool calling connects the model’s decision to such operations: the model selects an available function and supplies the information required to invoke it (Liu et al., 2024). Function-calling eval-uations therefore test whether an agent can choose and parameterize actions from natural-language requests (Patil et al., 2025; Li et al., 2023). To make those actions executable, the agent cannot communicate them only as free-form text. A tool runtime expects a machine-readable object whose tool names, argument keys, value types, and nesting satisfy predefined interface schemas (Willard & Louf, 2023; Dong et al., 2025; Geng et al., 2025). This structured object is the contract between the model and the runtime: it can be parsed, validated, routed to the selected tools, and executed without another semantic interpretation step. Generating it requires the model to decide which tools to invoke, how many calls to emit, their order, and the exact argument values; one response may contain different tools or repeat the same tool several times (Qin et al., 2024; Patil et al., 2025). Current tool-calling models usually generate the entire response autoregressively, one token at a time (Xia et al., 2026). Much of that response has explicit structure, including call wrappers, argu-ment keys, and typed value slots, yet AR decoding treats it as one flat token sequence (Zheng et al., 2024). The model must finish earlier fields and calls before reaching later slots, so requests with many fields or multiple calls incur substantial decoding latency (Chen et al., 2023; Xia et al., 2026).

The direct-parallel baseline follows the skeleton-then-parallel-fill idea of Skeleton-of-Thought (Ning et al., 2024), with the correct skeleton supplied in advance. Direct slot-parallel generation faces two problems: the realized tool-call sequence and argument slots are unknown when drafting begins, and indepen-dently drafted values may differ from what the tar-get would generate under the actual preceding out-put. Figure 2 shows the second problem even with an oracle skeleton: deviations from target AR ac-cumulate as more fields and calls are generated independently. Keeping the speedup while com-mitting only target-consistent tokens is the central challenge. These disagreements become output errors if inde-pendently drafted slot values are committed with-out checking them against the target under the pre-ceding fields and calls. To retain parallel gen-eration while preserving the target response, the drafted values must remain candidates until the tar-get decides which tokens to accept. Speculative decoding provides this accept-or-correct mecha-nism: the target verifies proposed tokens under the actual output prefix, accepts matches, and supplies a correction at the first mismatch (Leviathan et al., 2023; Chen et al., 2023). Conventional speculative decoders draft a continuation of the cur-rent prefix (Li et al., 2025); applying the same verification rule to future slots would let their values be drafted concurrently without committing disagreements to the response. We introduce S CHEMA FILL , which combines parallel drafting of future slots with target verification across fields and calls (Figure 1). From the request and tool catalog, it forecasts possible call posi-tions and slots without assuming the realized calls or values. Isolated branches draft slot values in parallel while the committed output advances. The runtime packs ready values with proposed tool names, field keys, and structural text for shared target verification. All packed tokens remain specu-lative until accepted by the target under the actual output prefix. Our contributions are threefold: • We present SchemaFill, a framework for slot-parallel speculative decoding of structured tool calls. It drafts future argument values concurrently and packs them with structural text across fields and calls, while the target verifies every token under the actual output prefix. • We design a shared verification runtime that evaluates concurrent drafts in one target forward pass while isolating branch attention and reusing verified KV states. • We achieve up to a 4.05 × mean end-to-end speedup over autoregressive decoding and outper-form existing speculative decoding baselines on G LAIVE and BFCL. 

# 2 RELATED WORK 

Tool Use, Function Calling, and Structured Generation. Tool-use research studies how lan-guage models select APIs, decide when to invoke them, and produce executable arguments: Tool-former learns these decisions from self-supervised API annotations (Schick et al., 2023), Gorilla adds retrieval-aware training for large and changing API collections (Patil et al., 2024), and Tool-LLM/ToolBench scales to thousands of real-world APIs and multi-tool solution paths (Qin et al., 2024). API-Bank and BFCL evaluate tool selection and structured arguments in tool-augmented and single-/multi-call settings (Li et al., 2023; Patil et al., 2025), while grammar-constrained meth-ods enforce valid output languages or schemas (Geng et al., 2023; Dong et al., 2025). These works improve tool-use capability or structural validity; SchemaFill addresses the inference cost of gener-ating an already structured response, using public schema metadata to propose slots while retaining target verification and target control over tools, fields, ordering, and values. 

Speculative Decoding. Early methods use a lightweight drafter to propose future tokens for target verification (Leviathan et al., 2023; Chen et al., 2023). SpecInfer verifies draft trees (Miao et al., 2Under review as a conference paper at ICLR 2027 2024), EAGLE and EAGLE-3 draft from target features (Li et al., 2024; 2025), and Medusa uses multiple decoding heads to propose candidate continuations (Cai et al., 2024). Lookahead Decoding generates and verifies parallel token continuations without an auxiliary drafter (Fu et al., 2024). De-spite different proposal mechanisms, these methods work on continuations of the current serialized prefix. SchemaFill applies target verification to a different unit of parallel work: values for possible fields and tool calls beyond that prefix. 

Schema-Aware Tool-Call Acceleration. ToolSpec is the closest prior work to our setting: it com-bines schema proposals, retrieval, and token recycling to accelerate tool calls (Xia et al., 2026). SchemaFill instead prepares argument values for future fields and forecast call positions, and packs those candidates with proposed structural syntax across call boundaries. Branches can prepare can-didates early, but their local acceptance never commits text to the final response; every proposed value is checked again under the actual output prefix. This distinction lets us evaluate slot-parallel drafting while preserving the target’s freedom to select tools, fields, ordering, and values. Together, these lines of work leave open how to apply target-verified speculation when the candidate units are noncontiguous slots in a structured multi-call response. SchemaFill addresses this gap by drafting possible argument slots across fields and calls, packing them for shared verification, and extending the response only with target-consistent tokens. The next section defines the tool-call setting and target verification rule, then examines why independently generated slot values cannot be committed directly. 

# 3 SETTING AND MOTIVATION 

3.1 STRUCTURED MULTI -C ALL GENERATION 

An LLM agent processes a user request x in conversational context c, which may include earlier messages and tool results. Some requests can be handled directly; others require information from, or actions by, an external system. For the latter, the agent uses tool calling: it expresses the needed operation as a structured call that a runtime can execute. The runtime supplies a catalog T of available tools, each with a name, description, and argument schema St defining how it can be called. The model receives the request, context, and full catalog in the prompt P = P (x, c, T ).Given P , the model generates an ordered call sequence. For each call, it chooses a tool, selects its argument fields, and supplies their values from x and c. The sequence may contain multiple calls or repeated use of one tool:

# 4 METHOD : S CHEMA FILL 

4.1 METHOD OVERVIEW 

SchemaFill follows a forecast–draft–verify loop. From the request, dialogue context, and full tool catalog, the method identifies possible argument slots and begins drafting later values before their serialized positions are reached. These drafts remain provisional. When a candidate becomes rele-vant, SchemaFill packs it with the required structural text after the current output prefix and lets the target accept or correct the resulting sequence in the same order as ordinary autoregressive decoding. We call the authoritative output path the committed stream and the provisional value paths specula-tive branches ; the implementation refers to them as MAIN and SIDE, respectively. Building on tree-based speculative verification (Miao et al., 2024), SchemaFill manages the target-KV lifecycle shown in Figure 3. The physical arena is shared by MAIN and SIDE branches, but logical ownership and attention visibility remain branch-specific. The public-prefix region stores the common prompt context; the persistent verified region stores the authoritative target-accepted history accumulated across verification rounds; and the scratch region holds the current batch of 6Under review as a conference paper at ICLR 2027 unverified candidate rows. Free capacity is managed separately from these logical regions so that temporary tree paths can be created without making them part of the committed stream. The lifecycle follows the stages in the figure. (1) Read shared context: each branch attends to the public prefix and verified history with only its visible ancestors and private tokens; shared physical storage does not merge branch histories. (2) Batched target verification: MAIN and active SIDE candidates are placed in one structured verification tree. The MAIN path is causal across its packed fields and calls, while the visibility mask prevents it from attending to private SIDE paths and masks sibling SIDE paths from one another. Candidate rows remain scratch until the target accepts them. (3) Resolve and update branch paths: accepted rows extend only their owning path. A MAIN correction extends the committed output, whereas a SIDE correction remains provisional; rejected suffix rows are discarded. A SIDE value is never grafted directly into MAIN state: when used as a MAIN proposal, it is verified again under the true prefix. This reuse of verified history avoids repeated re-prefill while preserving the target’s serialized acceptance rule. Drafter KV and captured target features remain separate branch-owned state rather than additional authoritative target history.

Greedy consistency at temperature zero. Fix a prompt P and a deterministic tie-breaking rule for gθ .
