## 摘要
LLM 智能体通过生成结构化工具调用来与外部系统交互。给定用户请求、对话上下文和工具模式目录，工具调用模型必须选择工具并生成其参数，并可能在单次响应中产生多个调用。标准自回归解码会逐 token 生成这些调用，对涉及多个调用或大量参数字段的请求造成显著延迟。显式的参数结构为并行生成提供了机会，但后续参数值可能依赖于前面的字段和调用，因此独立生成的值可能与目标模型的输出不同。我们提出 SchemaFill，一个通过槽位并行投机解码实现高效 LLM 工具调用的框架。SchemaFill 并发生成未来槽位值作为候选，而无需预先知道实际调用序列或参数值。跨多个字段和调用的候选会被拼接起来，由目标模型在实际输出前缀下进行验证。只有经过验证的 token 才会被提交，当候选不一致时由目标模型提供修正。这在对槽位和调用进行并行化的同时，应用了目标模型验证。在 Glaive 和 BFCL 上，SchemaFill 相比自回归解码，端到端吞吐量最高提升 4.05 倍。代码见 https://github.com/Czzzk/SchemaFill。

## Abstract
LLM agents interact with external systems by generating structured tool calls. Given a user request, conversational context, and a catalog of tool schemas, a tool-calling model must select tools and generate their arguments, potentially producing multiple calls in a single response. Standard autoregressive decoding generates these calls token by token, incurring substantial latency for requests involving multiple calls or many argument fields. The explicit argument structure offers opportunities for parallel generation, but later argument values may depend on preceding fields and calls, so independently generated values can differ from the target model's output. We present SchemaFill, a framework for efficient LLM tool calling through slot-parallel speculative decoding. SchemaFill generates future slot values concurrently as candidates, without requiring advance knowledge of the actual call sequence or argument values. Candidates spanning multiple fields and calls are concatenated for verification by the target model under the actual output prefix. Only verified tokens are committed, and the target supplies corrections when candidates disagree. This applies target verification while exploiting parallelism across slots and calls. On Glaive and BFCL, SchemaFill achieves up to a 4.05$\times$ improvement in end-to-end throughput over autoregressive decoding. Code is available at https://github.com/Czzzk/SchemaFill.

# SchemaFill 论文深度总结

## 1. 核心问题与研究动机

- **背景**：LLM 智能体（Agent）通过生成结构化工具调用（tool call）与外部系统交互。给定用户请求、对话历史和工具模式（schema）目录，模型需选择工具、生成参数，并可能在单次响应中输出多个调用（multi-call）。
- **核心痛点**：标准自回归（AR）解码逐 token 生成整个 JSON 调用对象，即使调用包装、参数字段名、类型结构等大量内容具有显式结构性，仍被当作扁平 token 序列处理。当请求涉及多个字段或多个调用时，必须完成前序字段/调用才能到达后续槽位，造成显著解码延迟。
- **并行化的机会与风险**：参数结构天然支持并行填充（如 Skeleton-of-Thought 思路）。但后续参数值可能依赖前面的字段和调用，独立生成的值会与目标模型在实际前缀下的输出产生偏差。
- **关键实证**：论文用 BFCL 诊断实验证明，即使给定 oracle 调用/字段骨架，独立生成槽值的 AR 偏差会随槽位数累积——参数数从 1 增至 8 时，偏差响应比例从 3.0% 升至 49.5%；调用数从 1 增至 3 时从 6.7% 升至 43.3%。
- **核心挑战**：如何在保持并行生成加速的同时，只提交与目标模型一致的 token，避免把偏差变成输出错误。

## 2. 方法论

### 2.1 核心思想

SchemaFill 将"预测未来槽位值"视为一种新的投机解码并行单元，采用 **forecast–draft–verify** 循环：

- 从请求、上下文和完整工具目录中**预测可能的调用位置与参数槽位**，无需预知真实调用序列或参数值。
- 由 **SIDE 分支**（speculative branches）并行起草未来槽位值，保持为临时候选。
- 当候选变得相关时，将其与结构文本（工具名、字段键、标点、闭合符）打包，交给**目标模型在真实输出前缀下统一验证**。
- 只有被目标接受的 token 才进入 **MAIN 提交流**（committed stream），不一致处由目标提供纠正。

### 2.2 关键技术细节

**(a) 元数据引导的工具与槽位预测**

- 使用 BM25 对工具公开元数据（名称、描述、schema 字段名与描述）进行词法排序：`π = rank_{t∈T} BM25(q, d_t)`。
- 循环排序列表并截断为前 B=3 个调用组，按渲染 schema 的键顺序展开为槽位，记录声明类型与是否必需。
- 预测仅分配起草计算资源，目标模型仍决定实际工具、字段、顺序和值；若验证结构排除某预测槽位，调度器将其退休。

**(b) SIDE 投机起草**

- 对活动槽位 `s_i = (j_i, t_i, f_i)`，构造包含调用位置提示、工具/字段前缀和分支私有历史的本地上下文 `H_i`。
- 使用 EAGLE-3 作为起草器：`v̂_i = D_φ(P ⊕ H_i)`，各分支共享公共提示，注意力掩码隔离其他分支的私有历史。
- 本地接受或纠正只推进该临时分支，**本地接受永不直接写入响应**。

**(c) 跨调用打包（cross-call packing）**

- 当 MAIN 到达某字段时，打包器将 SIDE 已准备的值放在真实 MAIN 前缀之后，并提议其间的工具名、字段键、标点和闭合文本：
  `Z_t = S_0 ⊕ v̂_1 ⊕ S_1 ⊕ ... ⊕ v̂_k ⊕ S_k`
- 目标将 `Z_t` 作为一条因果 MAIN 路径检查，token 可跨字段和调用边界互相注意，但不注意 SIDE 私有历史。
- 贪心解码下按公式 2 接受最长匹配前缀，不匹配时提交纠正并丢弃剩余后缀及其 KV 行。

**(d) KV 缓存管理**

- 物理 arena 由 MAIN 和 SIDE 共享，但逻辑归属与注意力可见性按分支隔离。
- 三个逻辑区域：公共前缀区、持久验证区（权威已接受历史）、scratch 区（当前未验证候选行）。
- 生命周期：读取共享上下文 → 批量目标验证（结构化验证树）→ 解析并更新分支路径（被接受的行使对应路径扩展，被拒绝后缀行丢弃）。
- SIDE 值绝不移植进 MAIN 状态，必须在新前缀下重新验证，避免重复预填充同时保持目标序列化接受规则。

**(e) 理论保证**

- 附录 B 证明：温度 0 贪心解码下，SchemaFill 精确输出与贪心 AR 相同的 token 序列。
- 温度随机采样下，使用标准投机采样接受概率 `α_u(v) = min{1, p_u(v)/q_u(v)}` 和残差纠正分布，可保证与串行采样分布一致。

## 3. 实验设计

### 3.1 数据集 / 场景

- **Glaive**：从 Glaive Function Calling 数据集采样 650 个测试样例（平均 1.00 参考调用、1.93 个顶层参数字段）。
- **BFCL v3**：选取 3 个最适合评估并发工具调用的类别（executable-parallel、parallel、parallel-multiple），共 450 个请求（平均 2.96 调用、7.46 字段）。
- **附加诊断**：从更广 BFCL 发布中为调用数 1–4 各随机采样 100 个自然请求（共 400 个）。

### 3.2 Benchmark 与指标

- 任务：生成一个含 tool calls 列表的 JSON 对象，每个条目含工具名和 arguments 对象。
- 指标：
  - **E2E TPS**：端到端吞吐（提交 token 数 / 总耗时）。
  - **Acceptance Length (AL)**：每次目标验证调用提交的 token 数。
  - **AR agreement**：与自回归输出的一致性。
  - **Nodes/Verify**：池化验证树规模。

### 3.3 对比方法

- **AR**：自回归单 token 参考基线。
- **EAGLE-3**：学习式 token 树投机（无槽位预测/跨调用打包）。
- **ToolSpec**：最接近的 schema 感知加速方法（提案+检索+token 回收）。
- **Parallel Fill**：Skeleton-of-Thought 式并行填充（给定 AR 骨架）。
- **SchemaFill**：本文方法。

## 6. 主要结论与发现

- SchemaFill 在两个数据集上均取得最高吞吐：Glaive 340.60 TPS（3.73× AR），BFCL 375.71 TPS（4.05× AR）。
- 相对 EAGLE-3 提升 1.51×/1.87×，相对 ToolSpec 提升 1.75×/1.56×。
- AL 达 6.21（Glaive）/6.42（BFCL），分别为 ToolSpec 的 2.35×/1.96×，显著降低目标验证频率。
- 消融显示三个组件均有贡献：schema-guided MAIN path（+48.07% TPS）、SIDE drafting（+11.04%）、cross-call packing（+13.69%）。
- 调用数扩展：性能在 2–3 个调用时达峰（438.62–443.54 TPS，AL 7.98–8.06），4 个调用时 AL 降至 7.54、TPS 降至 410.72，提示槽位起草器质量限制了进一步接受增益。
- 温度 1 下仍有 3.58×/3.87× 加速；跨 4 个目标模型均保持 3.57×–4.04× 相对 AR 的加速。
- 核心洞见：工具调用结构可支持并行投机，但无需假设参数独立——目标模型在每个 token 提交前验证，从而在加速的同时保持输出一致性。

## 7. 优点

- **输出一致性保证**：附录 B 给出贪心一致性的归纳证明和随机采样的分布一致性证明，方法在理论上有严格保障，不是"近似加速"。
- **新并行单元**：将投机验证从"当前序列化前缀的延续"拓展到"跨字段、跨调用的非连续槽位"，是对投机解码范式的有意义扩展。
- **不依赖真实调用序列**：预测机制仅用公开 schema 元数据和 BM25，无需预知实际调用布局，实际工具/字段/顺序/值仍由目标决定。
- **分支隔离与 KV 复用设计精细**：共享物理 arena 但逻辑归属和注意力可见性隔离；SIDE 值绝不直接移植 MAIN，必须在新前缀下重验，兼顾效率与正确性。
- **实验较全面**：多数据集、多基线、多目标模型、两个温度、消融、调用数扩展、KV/时间开销、运行方差均有覆盖。
- **对加速来源的分解清晰**：通过 4 阶段累积消融量化每个组件的边际贡献。

## 8. 不足与局限

- **实验覆盖有限**：
  - 主实验仅 Qwen2.5-7B-Instruct 一个目标模型；BFCL 只选 3/25 类别，结果仅代表所选样例和类别。
  - 跨目标评估为单次启动，未做重复均值±标准差；消融中 B/C 阶段仅一次 BFCL 启动。
  - 单卡 batch size 1，未验证批处理/高并发服务场景。
- **性能上限受起草器质量制约**：4 个调用时 AL 和 TPS 下降，说明槽位起草器质量限制了进一步接受增益；预测预算 B=3 固定，调用数超过预算时需 rebind 机制。
- **预测开销与失败风险**：BM25 预测虽耗时占比极小（0.027%），但若预测偏差大，SIDE 计算可能浪费；文中未系统报告预测命中率或浪费率。
- **KV 开销**：有效 KV 平均增加 24.65%（模型+缓存整体增加 0.28%），并有约 100.68 MiB 可复用公共前缀快照，长上下文/大 batch 下开销可能放大。
- **依赖本地训练的 EAGLE-3 头**：每个目标模型需单独训练草稿头（跨目标实验中各自训练），部署成本不为零。
- **偏差风险**：AR 偏差诊断使用 AR 选择的布局，属描述性分析而非端到端泛化性能；Parallel Fill 的 AL 不适用，其吞吐包含给定骨架的填充与重建成本，与 SchemaFill 的可比性需谨慎解读。
- **应用限制**：方法假设工具 schema 公开可得且结构清晰；对无 schema、自由文本式工具调用或高度动态的工具目录，预测机制可能失效。
