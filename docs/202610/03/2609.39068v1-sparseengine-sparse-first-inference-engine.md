## 摘要
长上下文 LLM 智能体累积的交互历史会给 KV 缓存内存和注意力计算带来压力。尽管稀疏注意力能降低这些开销，但异构的缓存表示与工作流阻碍了其与现有推理引擎的集成，而先前的稀疏服务抽象仅支持特定布局或工作流。我们提出 SparseEngine，一个从头构建、稀疏优先的推理引擎，其共享生命周期契约让每种方法能够控制自身的 KV 表示与计算，同时与通用服务基础设施协调状态转换。SparseEngine 支持四大类别下的 15 种方法，并通过 Chain Cache 实现跨请求状态管理，Chain Cache 可从保留的历史中恢复 KV 驱逐方法；以及可控的 Prefix-Cache Pruning，可在保留逻辑前缀匹配的同时，从选定的历史区域中移除 KV。在保持方法质量的同时，SparseEngine 在采用 KV 驱逐时实现超过 10 倍的吞吐量提升，在相同并发度下解码速度比 vLLM 快 2.5 倍以上，并在智能体基准测试上实现超过 2 倍的端到端加速。代码见 https://github.com/CURRENTF/SparseEngine。

## Abstract
Long-context LLM agents accumulate interaction histories that strain KV-cache memory and attention computation. Although sparse attention reduces these costs, heterogeneous cache representations and workflows hinder integration with existing inference engines, while prior sparse-serving abstractions support only specific layouts or workflows. We present SparseEngine, a ground-up, sparse-first inference engine whose shared lifecycle contract lets each method control its KV representation and computation while coordinating state transitions with common serving infrastructure. SparseEngine supports 15 methods across four categories and enables cross-request state management through Chain Cache, which resumes KV-eviction methods from retained history, and controllable Prefix-Cache Pruning, which removes KV from selected history regions while preserving logical-prefix matching. While maintaining method quality, SparseEngine delivers over 10x higher throughput with KV eviction, over 2.5x faster decoding at matched concurrency than vLLM, and over 2x end-to-end speedup on agent benchmarks. The code is available at https://github.com/CURRENTF/SparseEngine.

- **背景趋势**：LLM 正演变为自主、多轮智能体，推理负载变得本质上有状态。在编码、研究、推理等迭代工作流中，上下文历史通过反复的工具调用与推理链迅速膨胀，造成 KV 缓存容量与注意力计算延迟的**双重 GPU 瓶颈**。
- **已有缓解手段**：稀疏推理方法通过选择性注意力或压缩 KV 存储降低成本，但它们在**KV 表示方式**与**更新时机**上差异巨大，又必须运行于共享的请求调度与缓存复用基础设施之上。
- **核心矛盾**：现有引擎把接口围绕特定缓存布局或工作流组织——Vortex 暴露页为中心的算子、SPIN 用 GPU–CPU 流水线管理分区、Tangram 专攻非均匀 head-wise KV 保留。这些接口适配部分方法却限制其他方法：Quest 需要 query 相关的页选择，H₂O 还需要持久化注意力分数与生成过程中的物理 KV 驱逐。
- **中心问题**：**共享服务基础设施与方法特定的 KV 状态/计算控制之间，抽象边界应该划在哪里？**
- **论文主张**：SparseEngine 将该边界设在**共享生命周期契约**上，让稀疏方法定义自己的计算工作流与 KV 表示；细粒度钩子协调方法特定计算与状态更新，公共接口把这些方法接入注意力执行与调度。并在此基础上引入 **Chain Cache**（跨轮次复用保留的 KV）与**可控 Prefix-Cache Pruning**（在不破坏逻辑前缀匹配的前提下裁剪选定历史区间）。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心思想：生命周期契约
- 不预设某一种计算流程（如 SPIN 的 Index→Offload→Select→Retrieve→Attention，或 Vortex 的 Cache Update & Summary→Page Selection→Attention），而是锚定一个关键不变量：**模型原生模块执行顺序**。
- 沿该顺序暴露细粒度钩子，让每个稀疏方法注册回调、组合自己的工作流，而**无需修改模型实现**（避免 LlamaSnapKV、Qwen3H2O 这类方法专用模型分支）。

### 2.2 三大架构组件
- **SparseController 中的细粒度生命周期钩子**
  - 覆盖 prefill 与 decode，扩展点包括：Step 准备、Norm+QKV 之后、Attention 前后、FFN/MoE、Layer-End、Step-End。
  - 由初始化时选定的 `SparseMethodRuntime` 实现方法回调，组合跨 prefill chunk、decode step 与 Transformer 层的评分、选择、状态更新操作。
  - 例：prefill 阶段 `finish_step` 支持 H₂O 基于累积注意力的 chunk 级驱逐，以及 SnapKV 在最后一个 prompt chunk 后的选择与驱逐；decode 阶段 `build_decode_selection` 执行 Quest 的 query 相关页选择，`finish_step` 更新 H₂O 累积分数并在线驱逐；`on_layer_end` + `build_decode_selection` 让 OmniKV、DeltaKV 复用观测层索引。
- **方法定制的 CacheManager**
  - 拥有方法特定的状态与存储：定义 KV 表示、物理布局、位置映射，以及分配/写入/更新/释放操作，并维护与 KV 状态配套的持久元数据。
  - 明确区分**物理驱逐**（更新保留槽映射与上下文长度，把丢弃槽归还分配器）与**逻辑选择**（仅改变注意力读取哪些驻留条目）。
  - 例：SnapKV 压缩与 H₂O 驱逐联合更新保留位置、方法统计与可用容量；OmniKV 对驻留 KV 施加跨层选择；KIVI 管理量化 KV 页、量化元数据与非量化残差区。
- **AttentionView**
  - 连接方法自有缓存表示与注意力执行，形式化为：
    - `View_{ℓ,t} = BuildView(C_{ℓ,t}, I_{ℓ,t})`
    - `o_{ℓ,t} = Attention(q_{ℓ,t}, View_{ℓ,t})`
  - 其中 `C_{ℓ,t}` 为持久缓存状态，`I_{ℓ,t}` 标识被选中的 token 或页；View 描述可访问数据及其物理布局，供兼容的注意力后端使用。
  - 支持对选中、压缩、量化或临时重建的 KV 做注意力：Quest 的 View 含选中 KV 页，OmniKV 的 View 按跨层选择引用驻留 KV，DeltaKV 的 View 按需暴露重建后的 KV。

### 2.3 执行流程与调度接口
- 调度器按 prefill chunk 处理 prompt，再逐 token 反馈解码；通过 `MemoryOracle` 查询方法特定的容量与预留需求，并协调多 GPU rank 执行。
- 每个 Transformer 层内：生命周期钩子运行方法选择逻辑，CacheManager 通过 AttentionView 暴露所需 KV；Layer-End 钩子跨层协调状态，Step-End 钩子在下一次前向之前应用缓存更新。
- **MemoryOracle 与准入公式**：稀疏方法的注意力预算并不决定其内存需求（Quest 可只读少量页却保留大缓存；驱逐方法可能临时持有 prompt KV；压缩方法需要重建空间）。调度器按命名资源预算判定：
  - `c_j(r) ≤ B_j` 对所有上报资源 j 成立才准入，并在考虑下一个请求前扣除预留。
  - 例：PyramidKV 可为每层上报独立的保留槽预算；DeltaKV 上报全注意力层、参考条目、保留原始 KV 三类预算并预留重建空间。

### 2.4 跨请求状态管理（扩展能力）
- **Chain Cache（链式缓存）**
  - 面向多轮智能体轨迹，使**基于驱逐**的方法（SnapKV、KVzip、H₂O）也能跨轮复用压缩状态。
  - `ChainCacheIndex` 把会话与其逐层保留 KV、方法特定元数据、逻辑 token 前缀关联起来：**逻辑前缀仍可用于匹配，即使部分物理 KV 已被移除**。
  - 每个会话有 `chain_id`；续接请求必须匹配此前处理的逻辑前缀（不要求每个匹配 token 都有驻留 KV），然后只 prefill 未处理的后缀；空闲链按 LRU 回收。
- **基于稀疏性的 Prefix-Cache Pruning（前缀缓存裁剪）**
  - 应用提交完整 `token_ids` 序列与零基边界裁剪区间 `[L, R)`，定义 `T = {i | L ≤ i < R}`；由 SnapKV/KVzip 等评分策略在 `T` 内选保留位置并返回掩码；缓存管理器只对无活跃引用或在途传输的空闲块应用该掩码。
  - 设 `P` 为逻辑 token 前缀、`R` 为有驻留 KV 的位置，保留选中位置 `I ⊆ R ∩ T` 后：
    - `P' = P`（逻辑前缀不变）
    - `R' = (R \ T) ∪ I`
  - 即释放被排除的物理槽但保持逻辑前缀，后续请求仍能匹配同一前缀而只复用其保留 KV。

### 2.5 关键实现细节
- Attention View 载荷区分显式 KV 张量与 MLA 潜变量/位置张量，允许注意力实现声明其支持的表示；临时重建槽在层消费后释放，持久 KV 归 CacheManager 所有。
- 支持 CUDA Graph：cache manager、method runtime 与注意力实现提供地址在 replay 间稳定的缓冲区，step preparation 更新槽映射、长度等可变输入，图与布局兼容性在配置执行路径时检查。

- **尚可改进之处**：
  - **超参与预算敏感性刻画不足**：多数实验采用方法默认或少量档位（如 SnapKV 的 Low/Mid/High），缺少对"稀疏预算—质量—吞吐"帕累托前沿的系统扫描，读者难以判断某方法在给定精度目标下应取何种预算。
  - **硬件与并行配置耦合**：部分结论在特定 TP/EP 组合下取得（如 GLM 用 TP=EP=2、H20 用 2 卡），跨并行度、跨 GPU 代际的可迁移性未做独立验证，可能与缓存布局、通信开销强相关。
  - **评测规模与评判方式**：SWE-bench Lite（300 任务）与 Claw-Eval（182 纯文本任务）虽为公开基准，但相对真实生产流量仍属小样本；Claw-Eval 依赖单一 LLM 评判，存在评判偏差风险，未报告人工一致性校验。
  - **成本透明度**：未汇总推理实验的总 GPU 机时、能耗或吞吐归一化成本，复现与横向成本比较缺少统一口径。
  - **架构覆盖不均衡**：MLA（GLM-4.7-Flash）与混合线性注意力（Qwen3.6-27B）主要出现在质量或特定场景，未与全部 15 种稀疏方法交叉验证，部分组合的适用边界仍不清楚。
  - **长尾场景**：极长上下文（>200K）与高并发叠加时的调度公平性、Chain Cache 的 LRU 淘汰对多会话交织负载的影响，缺少压力测试。

### 5.x 小结
总体而言，实验在**机制多样性、模型架构跨度、质量—效率双维度**上具备较强说服力，公平性设计（原方法实现对照、方法匹配对比、统一测量协议）明显优于多数引擎类工作；其不足主要在于**超参敏感性、成本口径与评测样本规模**，属于"结论方向可信、边界条件待补"的充分性水平，而非决定性缺陷。

## 6. 局限性与批判性讨论

- **抽象层次的固有取舍**：将边界设在"生命周期契约"上，虽最大化了方法自由度，但也意味着引擎无法对方法内部的计算/状态语义做全局优化（如跨方法的统一重排、批量融合）。自由度换来了通用性，代价是失去部分跨方法协同优化空间。
- **钩子开销与工程复杂度**：在每层、每步暴露细粒度钩子，理论上带来额外的调度与状态检查开销；论文以吞吐/加速数据间接表明开销可控，但未给出钩子调用本身的微基准剖析。
- **正确性论证偏经验**：Chain Cache 的"逻辑前缀可匹配、物理 KV 可缺失"是核心创新点，但其对注意力数值等价性的影响主要靠下游质量指标间接佐证，缺少形式化或逐层误差分析。
- **Prefix-Cache Pruning 的边界条件**：裁剪仅作用于无活跃引用或在途传输的空闲块，这在低并发下易满足、高并发下可能限制裁剪机会，论文未量化"可裁剪窗口"随负载的变化。
- **公平比较的残余偏差**：以"原方法实现"为质量参照是优点，但原实现与 SparseEngine 集成版在 kernel、量化、并行策略上未必完全对齐，质量差异可能混入实现差异而非方法本身差异。
- **可复现性**：模型变体众多（14 个）且含若干较新模型，配置矩阵庞大，论文未提供完整配置清单与脚本，外部复现门槛较高。

## 7. 结论与启示

- **核心结论**：共享服务基础设施与方法特定 KV 状态/计算控制之间的抽象边界，应划在**生命周期契约**而非缓存布局或固定工作流上。SparseEngine 据此统一承载动态稀疏、KV 驱逐、KV 压缩、KV 量化四类共 15+ 方法，并在质量上忠实于原方法、在吞吐上相对 vLLM 等基线取得加速。
- **两项扩展能力**：Chain Cache 让基于驱逐的方法也能跨多轮会话复用压缩状态（逻辑前缀与物理 KV 解耦），Prefix-Cache Pruning 在保持逻辑前缀匹配的前提下裁剪历史区间——二者共同补足了"有状态智能体推理"这一现有引擎薄弱环节。
- **对系统研究的启示**：
  - 稀疏推理引擎的设计重点应从"支持哪些方法"转向"以何种不变量组织方法"，模型原生模块执行顺序是一个被验证可行的锚点。
  - 内存准入需与方法注意力预算解耦，用**命名资源预算 + MemoryOracle** 表达异构需求（保留槽、重建空间、参考条目等），比单一 KV 字节数更贴合真实约束。
  - 多轮智能体的缓存复用要求"逻辑前缀"与"物理驻留"可分离，这可能是未来 KV 缓存管理的通用范式。
- **适用场景判断**：最契合多轮、工具调用密集、长上下文且需在同一引擎内切换多种稀疏策略的服务场景；对单轮短上下文或方法单一的部署，收益可能不足以抵消钩子与集成复杂度。

## 8. 一句话评价

SparseEngine 以"生命周期契约"重新划定了稀疏推理引擎的抽象边界，用细粒度钩子 + 方法定制 CacheManager + AttentionView 统一了四大类 15+ 稀疏方法，并以 Chain Cache 与可控前缀裁剪补齐跨轮有状态推理的短板，是一项**抽象设计有洞见、实验覆盖较扎实、但成本口径与边界条件尚待补全**的系统性工作。
