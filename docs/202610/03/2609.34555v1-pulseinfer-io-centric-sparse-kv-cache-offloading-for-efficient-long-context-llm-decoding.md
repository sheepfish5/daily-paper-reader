## 摘要
长上下文 LLM 服务日益受限于解码阶段：庞大的 KV 缓存限制了批大小，并使 GPU 利用率不足。稀疏 KV 缓存卸载通过将大多数历史 KV 块存储在 CPU DRAM 中，并仅按需召回选定的块，从而扩展有效容量。然而，我们发现现有卸载系统将瓶颈转移到了 CPU-GPU 召回 I/O：召回量在不同层、解码步和请求之间差异很大，而按注意力头稀疏选择将召回碎片化为许多小型 PCIe 传输。本文提出 PulseInfer，一个以 I/O 为中心的稀疏 KV 缓存卸载系统。PulseInfer 通过可中断的逐层调度隐藏可变的召回延迟，通过 IO-Adaptive Offloading Admission 自适应调整卸载决策，并使用 SoloHead 稀疏选择与 gather-scatter I/O 引擎合并碎片化传输。PulseInfer 在 SGLang 上实现，相比 SGLang 将解码吞吐量提升最高 4.7 倍，相比最佳现有卸载基线提升最高 2.6 倍，同时将 TPOT 降低最高 76%，并保持近乎无损的准确率。

## Abstract
Long-context LLM serving is increasingly bottlenecked by decode, where large KV caches limit batch size and underutilize GPUs. Sparse KV cache offloading expands effective capacity by storing most historical KV blocks in CPU DRAM and recalling only selected blocks on demand. However, we find that existing offloading systems shift the bottleneck to CPU-GPU recall I/O: recall volume varies widely across layers, decode steps and requests, while headwise sparse selection fragments recalls into many small PCIe transfers.   This paper presents PulseInfer, an I/O-centric sparse KV cache offloading system. PulseInfer hides variable recall latency with interruptible layer-wise scheduling, adapts offloading decisions with IO-Adaptive Offloading Admission, and coalesces fragmented transfers using SoloHead sparse selection and a gather-scatter I/O engine. Implemented on SGLang, PulseInfer improves decode throughput by up to 4.7x over SGLang and 2.6x over the best existing offloading baseline, while reducing TPOT by up to 76% and preserving near-lossless accuracy.

# PulseInfer 论文总结

## 1. 核心问题与研究动机

- **背景**：长上下文 LLM 服务中，上下文窗口从数千扩展到数十万乃至百万 token，推理成本重心转移到解码阶段（可占端到端 90% 以上时间）。解码是**内存容量受限**的：KV 缓存随序列长度线性增长（如 Qwen-3 14B 单条 128K 序列需 20GB KV 缓存），GPU 只能容纳少量并发请求，批大小受限，GPU 利用率低下。
- **既有方案**：稀疏 KV 缓存卸载（ArkVale、PQCache、InfiniGen）将大部分历史 KV 块放在 CPU DRAM，仅保留摘要（digest）和热块在 GPU，按需召回被选中的块。
- **核心发现**：卸载把瓶颈从"GPU 显存容量"转移到了"CPU–GPU 召回 I/O"。作者识别出两个根因病理：
  - **召回量动态变化**：召回 token 数随解码步、层、请求、批次剧烈波动（单请求内呈右偏长尾分布，层间中位数召回量差异可达 5×）；真实工作负载（Mooncake、ServeGen）请求长度跨三个数量级且随时间漂移，导致静态卸载阈值与固定一层预取流水线失效。
  - **召回粒度太细**：逐 KV head 独立选择导致大量 8KB 级别的小而分散的 PCIe 传输，PCIe 5.0×16 理论 64GB/s 下实测仅约 6GB/s；同时每头 digest 常驻 GPU 显存，削弱卸载的显存收益。
- **后果**：同步召回（ArkVale/PQCache）GPU 利用率约 35%，一层预取（InfiniGen）约 45%；混合批次中短请求被长请求的召回 I/O 队头阻塞，TPOT 增加达 5×；在真实 trace 下现有卸载系统甚至不如不卸载基线。

## 2. 方法论

### 2.1 核心思想
以 I/O 为中心重新设计稀疏 KV 卸载，把召回 I/O 视为**一等可调度事件**，分解为三个目标：**Hide（隐藏）、Control（控制）、Coalesce（合并）**。

### 2.2 Hide：可中断逐层调度（IRQ）
- 将请求分为**正常批次**（较短、KV 常驻 GPU、无召回 I/O）与**卸载批次**（较长、KV 主要驻 CPU，仅保留 sink token、local token 和热 middle token 在 GPU）。
- 类比 OS 中断模型：卸载批次在某层完成稀疏选择后提交召回传输请求并**让出 GPU（yield）**，调度器立即切到正常批次执行；正常批次在**每个层边界**检查召回 I/O 是否完成，未完成则继续推进下一层，完成后切回卸载批次。
- 关键性质：**重叠深度**（一次召回等待期间执行的正常批次层数）由实际 I/O 完成时间动态决定，而非固定窗口；正常批次与卸载批次 I/O 隔离，消除短请求队头阻塞。
- **半同步中断检测**：纯同步（每层边界 CPU–GPU 同步）会排空 GPU 流水线；纯异步（CPU 持续入队 + 轮询）会延迟上下文切换。IRQ 折中——提交正常批次某层的 attention 与 FFN kernel 后，只同步等待 attention kernel 完成，利用 GPU 仍在执行 FFN 的时间窗检查 I/O 完成状态并决定下一个入队任务，兼顾高利用率与低切换延迟。

### 2.3 Control：IO 自适应卸载准入（IOAA）
- 吞吐量模型：设正常批大小为 $B_n$、卸载批大小为 $B_o$、重叠深度为 $m$，则
  $$\text{Throughput} \propto \frac{m}{m+1}\cdot B_n + \frac{1}{m+1}\cdot B_o$$
  即吞吐近似正比于两批大小的加权平均，$B_n$ 权重更大；但增大 $B_o$ 可释放显存、扩大总批大小，同时也会抬高 $m$、稀释 $B_o$ 的收益。
- **准入即搜索**：把 $n$ 个等待请求的正常/卸载分配建模为二叉搜索树，每个节点决定一个请求的去向，叶节点用上式评估吞吐并取最优。
- **剪枝规则**：① 超出剩余显存预算的分支立即剪枝；② 长度单调性规则——若较长请求进入正常批次，则较短请求不再考虑卸载。30 个等待请求时平均仅访问 3.16 个节点。
- **重叠深度画像**：$m=\lceil t_{io}/t_{layer}\rceil$，$t_{io}$ 随 $B_o$ 近似线性增长、$t_{layer}$ 随 $B_n$ 变化平缓。离线在 $(B_o, B_n)$ 离散网格上画像 $m$，运行时插值估计候选分配的重叠深度。

### 2.4 Coalesce：SoloHead 与 Gather-Scatter 传输
- **SoloHead 稀疏选择**：
  - 依据注意力头特化（retrieval head 关注中段语义丰富 token，streaming head 主要关注 sink/local token），定义 **Middle Attention Mass（MAM）**：对每个 KV head，计算其映射的 query heads 在中段 token 上的平均注意力权重。
  - 每层只保留 **MAM 最高**的一个检索头存储 block digest，由它选出 top-k block 集合供该层**所有 KV head 共享**。
  - 效果：把逐头小传输合并为逐层 token-wise 传输，消除逐头 digest 显存开销，并因规避 streaming head 的噪声选择而提升精度。
  - 用逐层 logit 差异 $D_L = \mathrm{KL}(p_{full}, p_{sparse}^L)$ 验证：SoloHead 接近 headwise 与 average，而用最低 MAM 头（reversed）差异最大。
- **Gather-Scatter I/O 引擎**：将 DRAM 中分散的 KV block 先 gather 到连续的 pinned CPU staging buffer，再用**一次大 DMA** 传到 GPU staging buffer，最后用轻量 GPU scatter kernel 写回 KV 缓存。>512 blocks 时有效带宽比多线程 `cudaMemcpyAsync` 高 2× 以上。
- **零同步 I/O 提交**：用一块 CPU–GPU 共享的 UVM 小缓冲存放 ready 标志与选中 block 索引，选择 kernel 写完后由专用 CPU 轮询线程检测并异步提交召回任务，使主推理线程无需等待召回任务构造/提交。

## 6. 主要结论与发现

- PulseInfer 在所有模型与负载上取得最高解码吞吐：相比 Vanilla 提升 **1.5×–4.7×**，相比最佳卸载基线提升 **1.1×–2.6×**；TPOT 相比 InfiniGen 降低 **16.0%–76.4%**。
- 输入越长收益越大：Qwen-3 14B 上 Vanilla 从 16K 到 64K 吞吐从 324 降到 81 tok/s，PulseInfer 仅从 488 降到 380 tok/s。
- GPU 利用率接近 Vanilla（约 95%），总批大小达 Vanilla 的 4.7×，正常批与卸载批各自都超过 Vanilla 批大小。
- 短请求隔离有效：<8K 请求 TPOT 仅比 Vanilla 增 1.5×，而现有卸载基线增 6.7–8.3×。
- IOAA 在两个真实 trace 上均优于任意固定阈值，且最优固定阈值因 trace 而异，说明静态策略无法泛化。
- PCIe 带宽降至 0.4× 时，PulseInfer 仍快于 Vanilla，而 InfiniGen 仅在满带宽下才与 Vanilla 持平。
- 精度近乎无损：多数任务与 Full Attention 持平，Qwen-3 上甚至略优；改用最低 MAM 头（reversed）则显著掉分，验证 MAM 有效区分检索头与流式头。

## 7. 优点

- **问题定位精准**：把"召回 I/O"而非"KV 选择算法"确立为核心瓶颈，并用图 2–8 的实测（GPU 利用率、TPOT 分组、逐层召回 CDF、请求长度漂移、PCIe 粒度带宽）系统刻画两条根因，动机扎实。
- **跨层协同设计**：算法层（SoloHead 共享 top-k）与系统层（gather-scatter、零同步提交）联合优化传输粒度，而不是单点改进。
- **OS 类比优雅且落地**：IRQ 将"进程/中断"映射到"批次/召回完成"，半同步检测在同步与异步之间取得可量化的折中，兼顾 GPU 流水线填充与切换时延。
- **控制策略有理论支撑**：IOAA 建立在显式吞吐模型与重叠深度画像之上，剪枝规则使搜索代价极低（30 请求平均 3.16 节点），且能随负载漂移自适应。
- **精度不降反升的解释合理**：通过 MAM 规避 streaming head 的噪声选择，并用 KL 散度逐层定量验证，而非仅报告端到端分数。
- **工程完整**：在 SGLang 上约 9K 行实现，消融逐组件量化贡献，敏感性与可扩展性分析齐备。

## 8. 不足与局限

- **基线复现风险**：ArkVale、InfiniGen、PQCache 均由作者在 SGLang 上自行实现，"to the best of our ability"暗示可能存在实现差距，绝对加速比需谨慎解读。
- **硬件与部署范围有限**：仅单机 4 卡、PCIe 5.0×16 环境；未覆盖 NVLink、多节点、跨机 KV 池等更复杂拓扑；MiniMax M2.5 用 4 卡张量并行，其相对收益反而更小，说明结论对并行度敏感。
- **对 Vanilla 的延迟代价**：TPOT 相比 Vanilla 平均增加 2.2×，论文明确将此视为吞吐换延迟的有意取舍，但在延迟敏感（如交互式）场景下该权衡未必可接受。
- **画像依赖与离线开销**：MAM 头选择与重叠深度 $m$ 均依赖离线画像，跨模型/硬件需重新画像；论文未报告画像成本，也未讨论模型更新（换权重）后的迁移性。
- **精度评测范围较窄**：仅 LongBench 的 9 个数据集、thinking budget 2048，未覆盖 128K+ 超长上下文、多轮 agent 历史、代码/工具调用等论文自身强调的关键场景；也未报告精度对 k 值（middle token 预算）的敏感性。
- **潜在偏差**：主分析实验集中于 Qwen-3 14B + ServeGen，结论是否在 MoE/大规模模型上同样成立缺乏同等深度的机制验证；合成负载虽声称匹配 ServeGen 特征，但仍是构造数据。
- **假设边界**：IRQ 依赖正常批次提供足够计算量来吸收召回 I/O，当负载几乎全为长请求（正常批次不足）时，重叠深度 $m$ 会显著增大，吞吐可能退化，论文未针对该极端分布给出实验。
