## 摘要
高性能 GPU 内核对于现代机器学习系统至关重要，然而自动生成既正确又高效的内核仍然具有挑战性。现有的基于大语言模型的方法面临两大局限：与模型当前能力相匹配的高质量训练数据稀缺，以及内核正确性与性能之间固有的权衡。为应对这些挑战，我们提出 KernelZero，一个协同演化框架，通过两个专门模型持续改进 GPU 内核生成：一个 Proposer 从 API 集合生成 Torch 模块，一个 Coder 将其转换为 CUDA 或 Triton 内核。KernelZero 采用前沿驱动的模块生成机制，基于 Coder 当前的薄弱环节持续产生与能力相匹配的训练模块。它进一步引入了正确性感知组相对策略优化（Correctness-Aware Group Relative Policy Optimization，CA-GRPO），仅在正确性足够可靠后才优化性能。通过交替优化 Proposer 与 Coder，KernelZero 形成了一种自动课程，实现了有针对性的、训练高效的能力提升。实验上，KernelZero-7B 在 CUDA 上超越了 Claude-4.5-Sonnet，在 Triton 上超越了 DeepSeek-V4-Pro。在 KernelBench 第 1 级和第 2 级上，其 CUDA pass@1 分数分别达到 75.8% 和 69.6%，pass@10 达到 100% 和 97%。在 Triton 上，其 pass@1 分数分别达到 77.2% 和 72.5%。

## Abstract
High-performance GPU kernels are essential to modern machine learning systems, yet automatically generating kernels that are both correct and efficient remains challenging. Existing LLM-based approaches face two major limitations: the scarcity of high-quality training data aligned with the model's current capabilities, and the inherent trade-off between kernel correctness and performance. To address these challenges, we propose KernelZero, a co-evolution framework that continuously improves GPU kernel generation through two specialized models: a Proposer that generates Torch modules from API sets and a Coder that translates them into CUDA or Triton kernels. KernelZero uses a frontier-driven module generation mechanism to continuously produce capability-aligned training modules based on the Coder's current weaknesses. It further introduces Correctness-Aware Group Relative Policy Optimization (CA-GRPO), which optimizes performance only after correctness becomes sufficiently reliable. By alternating the optimization of the Proposer and Coder, KernelZero forms an automatic curriculum that enables targeted and training-efficient capability improvement. Empirically, KernelZero-7B surpasses Claude-4.5-Sonnet on CUDA and DeepSeek-V4-Pro on Triton. On KernelBench Level 1 and 2, it achieves CUDA pass@1 scores of 75.8% and 69.6%, respectively, with pass@10 reaching 100% and 97%. On Triton, it achieves pass@1 scores of 77.2% and 72.5%, respectively.

- **核心研究问题**：如何以有针对性的方式训练模型，高效提升 GPU 内核生成性能？

## 二、方法论

### 2.1 整体框架：双模型协同演化

- 将内核生成建模为两个显式接口模型的协同演化：
  - **Proposer $P$**：输入一组 Torch API $a \in A$，生成可运行的组合式 Torch 模块 $m \sim \pi_P(\cdot|a;\theta_P)$。
  - **Coder $C$**：输入模块 $m$，生成对应的 CUDA 或 Triton 内核 $k \sim \pi_C(\cdot|m;\theta_C)$。
- 形成两阶段映射 $a \xrightarrow{P} m \xrightarrow{C} k$：Proposer 探索算子组合空间，Coder 将其实现为高效底层实现。
- **交替优化策略**：两个模型轮流更新，各自用自身奖励（$r_P$ 或 $r_C$）通过 GRPO 优化，另一模型保持固定。

### 2.2 Proposer：前沿导向的模块生成

- **API 列表采样**：从真实 Torch 模块构建 API 共现分布，采样 API 子集作为输入，兼顾真实性与多样性。
- **三重验证检查**：
  1. **AST 检查**：静态分析验证计算图与采样 API 集一致。
  2. **可运行检查**：调用 `get_init_inputs` / `get_inputs`，在 CUDA 设备上执行，丢弃编译或运行错误模块。
  3. **数值稳定性**：过滤产生 NaN/Inf 的模块。
- **前沿奖励（FO-GRPO）**：对模块 $m$ 从 Coder 采样 rollout 组，计算平均正确率 $\bar{l}$；奖励设计为在成功率接近 0.5 时最大：
  - $R_p(m) = 1 - 2|\bar{l} - 0.5|$（有效模块），$\rho < 0$（无效模块惩罚）。
  - 鼓励生成既非平凡也非不可能、恰位于 Coder 能力前沿的模块。

### 2.3 Coder：正确性感知的高性能内核生成

- **冷启动蒸馏**：总结四条 GPU 优化原则（**Tiling、Fusion、Pipeline、Reordering**），用教师模型（gpt-oss-120B）按这些原则生成带思维链的推理轨迹，仅保留功能正确的样本进行 SFT。
- **CA-GRPO（正确性感知组相对策略优化）**：
  - 计算组级正确率 $Acc_G$，定义阈值函数 $T(G)$：当 $Acc_G \geq \alpha$ 时 $T=1$，否则 $T=0$。
  - 归一化加速比得分：$S^G_i = \frac{S(k_i) - \min(S(G_c))}{\max(S(G_c)) - \min(S(G_c))}$。
  - 最终奖励：$R^G_i = 1 + T(G)\cdot\beta\cdot S^G_i$（若正确），否则为 0。
  - 核心思想：**先学正确性，待可靠后再引入性能优化**，避免早期奖励设计不稳定。

## 六、主要结论与发现

- **核心结果**：KernelZero-7B 在 CUDA 上超越 Claude-4.5-Sonnet，在 Triton 上超越 DeepSeek-V4-Pro。

## 七、优点

- **方法创新性**：
  - 提出双模型协同演化框架，将内核生成拆解为「模块提案—内核编码」两个显式接口，形成无需人工构建任务的自动课程。

  - CA-GRPO 通过组级门控机制解耦正确性与性能信号，解决早期训练不稳定的问题。
- **训练效率**：仅 7B 参数即超越多个大模型，冷启动蒸馏注入编译器优化原则，提升样本利用效率。

## 八、不足与局限

- **性能提升的限制**：
  - CUDA Level 2 的 fast 结果偏低（fast 1@1 仅 2.4%），因生成的 CUDA 内核不调用 cuDNN/cuBLAS，面对厂商库支持的卷积/GEMM 难以超越。

- **实验覆盖**：
  - 仅在 KernelBench 上评测，未涉及 FlashInfer-Bench 等其他评测框架。
  - 部分基线（如 Dr.Kernel）缺少 pass@5/10 与 fast 指标，对比维度不完全对称。
  - 未报告多次运行的标准差或显著性检验。
- **潜在偏差风险**：
  - Proposer 的 API 共现分布来自真实 Torch 模块，可能对特定 API 组合存在分布偏好，影响泛化到分布外算子。
  - 冷启动数据来自 cudaLLM 的 71,996 个实例，其数据覆盖范围可能限制模型能力边界。
- **应用限制**：
  - 训练成本依然不低（Proposer 更新需 12 张 GPU，Coder 更新需 8 张），且需交替多轮。
  - 生成的 CUDA 内核性能受限于不使用外部高性能库，实际部署场景可能更倾向于调用库函数。
  - 未讨论跨硬件平台（如 AMD、其他 NVIDIA 架构）的迁移能力。
