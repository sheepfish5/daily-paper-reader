## 摘要
请求调度是大规模集群中服务智能体大语言模型（LLM）工作负载的关键挑战。有效的调度器必须保持长共享前缀上的键值缓存（KVC）复用，满足令牌级延迟服务等级目标（SLO），并最小化GPU资源占用。现有调度器难以协调这些需求：请求合并可能牺牲缓存局部性并增加预填充/解码干扰，从而损害SLO达成与资源效率。我们提出PackServe，一种旨在降低资源成本同时满足智能体LLM服务延迟SLO的调度器。PackServe使用紧凑的白盒模型预测预填充/解码干扰下的延迟。在这些预测指导下，它将请求打包到更少的服务实例上，同时保持KVC复用和SLO约束，以可用延迟余量换取更高的单实例吞吐量。在64块NVIDIA H20 GPU上的评估表明，在30毫秒和50毫秒TPOT目标下，PackServe分别比最先进的调度器少用高达16.8%和24.6%的GPU小时，同时满足目标TPOT目标。PackServe也已部署在我们由超过1000块GPU组成的生产集群中，与原始生产调度器相比，将资源占用降低了34.7%。

## Abstract
Request scheduling is a key challenge in large-scale clusters serving agentic large language model (LLM) workloads. An effective scheduler must preserve key-value cache (KVC) reuse across long, shared prefixes, meet token-level latency service-level objectives (SLOs), and minimize GPU resource footprint. Existing schedulers struggle to reconcile these requirements: request consolidation can sacrifice cache locality and increase prefill/decode interference, compromising both SLO attainment and resource efficiency. We present PackServe, a scheduler designed to reduce resource costs while meeting latency SLOs for agentic LLM serving. PackServe uses compact white-box models to predict latency under prefill/decode interference. Guided by these predictions, it packs requests onto fewer serving instances while preserving KVC reuse and SLO constraints, trading available latency headroom for improved per-instance throughput. Evaluation on 64 NVIDIA H20 GPUs shows that PackServe uses up to 16.8% and 24.6% fewer GPU-hours than state-of-the-art schedulers under 30-ms and 50-ms TPOT targets, respectively, while meeting the target TPOT objectives. PackServe has also been deployed in our production cluster comprising over 1000 GPUs, where it reduces the resource footprint by 34.7% compared with the original production scheduler.

## 2. 方法论

### 2.1 核心思想
- 采用**网关级（gateway-level）请求调度**，不修改引擎内部调度、不做请求迁移，以降低 MaaS 平台的集成与维护成本。
- 用**紧凑白盒性能模型**预测 prefill/decode 干扰下的 TTFT 与 TPOT，再据此进行 **KVC 优先的 SLO 感知请求打包**，用"可用延迟余量"换取"更高的单实例吞吐与更少活跃实例"。

### 2.2 容量分析（理论动机）
- 稳态近似下：`TPOT_real ≈ T_iter(b) / (1 − λ·T_pre)`，其中 `T_iter(b)` 为无干扰 decode 迭代时间，λ 为到达率，`T_pre` 为 prefill 时间。
- 由 Little 定律得 `λ = b / (b·T_pre + L_out·T_iter(b))`；纯 decode 吞吐 `μ_dec = b / T_iter(b)`，墙钟吞吐 `μ_wall = (1 − λ·T_pre)·μ_dec`。
- 结论：放宽 TPOT 目标可增大 batch，但到达率上升同时抬高 prefill 占用，**墙钟吞吐增益小于纯 decode 增益**。单实例微基准显示：30 ms 与 50 ms 两个工作点之间 decode batch 约翻倍，纯 decode 吞吐 +40.4%，而墙钟吞吐仅 +14.4%。
- 由此得出两条设计洞见：
  - **洞见 #1：KVC 复用应优先于请求打包**（丢失复用的 prefill 代价可能超过大 batch 的收益），但**不需要无条件最大化缓存命中**，有界的局部性损失可换来放置灵活性。
  - **洞见 #2：decode batch size 是吞吐–延迟权衡的关键控制变量**；排队中与正在 prefill 的请求不计入当前 decode batch，因此总在飞请求数不能指导合并。

### 2.3 性能建模（§5）
- **TTFT 分解**：`TTFT = T_pf + T_queue + T_overhead`，其中调度开销可忽略，重点建模缓存相关的 `T_pf`。
- **TPOT 分解**：`TPOT = T_dec + ΔPD`（无干扰 decode + prefill 引起的额外延迟，均按每输出 token 平均）。
- **Prefill 模型**（由 Transformer 注意力计算推导，含 N 个新 token、C 个缓存 token）：
  `T_pf(N, C; θ) ≈ α0 + α1·N + α2·N·C + α3·N²`（线性项对应逐 token 计算，NC 与 N² 项对应注意力交互；区分新旧 token 以体现长前缀复用的价值）。
- **Decode 模型**：`T_iter(B, S; θ) ≈ β0 + β1·B + β2·S`，其中 B 为活跃请求数、S 为总上下文长度；不含 prefill 干扰。
- **离线标定**：在空闲实例上按部署配置（模型、硬件、引擎设置）profiling：
  - Prefill profile 覆盖冷缓存（C=0）、chunk 对齐的缓存命中点（C = k·L_chunk）、最大输入边界（C+N = L_max），并额外加入经验 C、C² 项；命中样本需预热前缀并核验引擎报告的缓存 token 数。
  - Decode profile 通过变化并发与输出长度采样 (B, S)，优先使用引擎原生 FPM 指标，仅保留纯 decode batch；以 CUDA graph 捕获的 batch size 作为分段边界分别拟合线性模型。
- **在线校准**：针对大 batch 下 profiling 低估（上下文长度偏斜），为每个 decode-BS 分段维护**乘性 EMA 修正因子**；用连续纯 decode 前向的实测时长与基础模型预测之比更新，更新权重 0.02，比值裁剪到 [0.5, 2]，因子裁剪到 [1, 2]；调度时按投影 batch size 对应因子缩放 decode 项，prefill 干扰单独建模。

### 2.4 SLO 感知调度算法（§6，Algorithm 1）
1. **容量过滤**：筛选容量可行候选集 A；为空则拒绝请求。
2. **KVC 优先的重算控制**：对每个候选计算预测 prefill 时间惩罚 `W_{r,i}` 与最小者 `W_min`，以及请求的全缓存收益 `Z_r`（全未缓存与全缓存输入的 prefill 时间差）；保留满足 `ρ_{r,i} = (W_{r,i} − W_min)/Z_r ≤ η`（Z_r > 0）的候选构成 **KVC 可准入集 C**。η=0 仅保留最小重算代价候选，η 越大放置灵活性越高。用"归一化重算预算"替代固定缓存命中率阈值。
3. **SLO 准入**：对 C 中候选估计放置后 TPOT
   `TPOT_{r,i} = T_iter(B⁺_i, S⁺_{r,i}) + 1[A_i > 0]·T_pf(n_{r,i}, c_{r,i}) / max(1, L̃_out)`，
   其中 `B⁺_i = A_i + 1` 为准入后的潜在 decode 并发，第二项为到达请求自身 prefill 干扰，按近期输出长度中位数摊销；保留预测 TPOT < τ_TPOT 的候选构成 **T**。
4. **以 decode batch size 为中心的打包**：在 T 中优先选择**调度器跟踪的解码请求数更多**的实例（促进更大 decode batch）；并发相同时优先**预测缓存 token 更多**者（保留额外 KVC 复用）；再相同时优先**排队请求更少**者（限制排队延迟）。
5. **有界回退**：若 T 为空，则在 C 内退化为**缓存感知负载均衡**（原型中复用 LMetric），保留容量与重算约束但放宽 TPOT 检验。

### 2.5 实现
- 原型基于现有生产网关架构：轻量调度与性能模型模块约 **1.4K 行 Python**，共享调度基础设施约 **2.6K 行**；本地前缀树估计 KVC 复用，后端记录维护请求数与负载，沿请求/响应路径更新。
- 独立 profiler 约 **2.8K 行 Go**，用于采集 prefill/decode 测量以标定模型；生产环境将调度策略集成进现有网关。
