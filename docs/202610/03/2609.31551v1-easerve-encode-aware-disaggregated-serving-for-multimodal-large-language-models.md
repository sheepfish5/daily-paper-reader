## 摘要
将预填充（Prefill）和解码（Decode）两个阶段解耦到独立的 GPU 资源池，现已成为（纯文本）LLM 服务的标准优化方案。然而，多模态大语言模型（MLLM）增加了第三个阶段——编码（Encode），给资源分配带来了新的挑战。编码阶段将图像、视频或音频转换为语言模型可消费的嵌入，形成编码-预填充-解码（EPD）三阶段流水线。现有框架仅提供部分解决方案：纯文本 PD 系统缺少编码阶段，而 EPD 框架将其作为独立服务暴露，却未对下游请求流进行调控。该流水线还存在结构性的资源不均衡：每个请求都必须先经过编码阶段，下游工作才能开始，但按请求执行的方式使得编码 GPU 即使在高负载下也严重利用不足，从而使下游的预填充和解码工作进程处于饥饿状态。为解决这一问题，我们将编码阶段重新定位为 EPD 流水线的控制点，并揭示三个紧密耦合的维度：工作何时进入下游、预填充在何处执行，以及 GPU 如何共享。我们在 EAServe 中通过两个协同设计层实现了这一理念。其运行时管理负载自适应的微批处理、以速率控制的向共驻预填充工作进程的部分卸载，以及用于可预测共置的动态 SM 分区。配置层——混合自动选择（HAS）——通过基于各阶段容量画像剪枝不均衡的分配，并借助基于 TPE 的贝叶斯优化对剩余配置进行精化，从而在 GPU 分配、编码批大小和卸载比例的联合空间中进行搜索。在涵盖图像、视频和音频的三种 MLLM 架构上评估，EAServe 在相同 SLO 约束下，相比 NVIDIA Dynamo 和 vLLM 分别实现最高 4.3 倍和 1.7 倍的有效吞吐量（goodput）提升，在 EPD 流水线中保持更均衡且更高的 GPU 利用率，并比基线搜索方法更快达到接近最优的配置。

## Abstract
Disaggregating the two stages, Prefill and Decode, onto separate GPU pools is now a standard optimization for (text-only) LLM serving. However, multimodal LLMs (MLLMs), which add a third phase, Encode, pose new challenges for resource allocation. Encode turns images, video, or audio into embeddings that the language model can consume, yielding a three-stage Encode-Prefill-Decode (EPD) pipeline. Existing frameworks offer only partial answers: text-only PD systems lack Encode, while EPD frameworks expose it as a separate service without regulating downstream request flow. The pipeline also carries a structural resource imbalance: every request enters through Encode before downstream work can begin, yet per-request execution leaves the encode GPU severely underutilized even at high loads, starving the downstream Prefill and Decode workers. Addressing this, we reposition Encode as the control point of the EPD pipeline, exposing three tightly coupled dimensions: when work enters downstream, where prefill executes, and how the GPU is shared. We instantiate this in EAServe across two co-designed layers. Its runtime manages load-adaptive micro-batching, rate-controlled partial offload to a co-resident prefill worker, and dynamic SM partitioning for predictable co-location. The configuration layer, Hybrid Auto Selection (HAS), navigates the joint space of GPU allocation, encode batch size, and offload ratio by pruning unbalanced allocations with per-stage capacity profiling and refining the remainder through TPE-based Bayesian optimization. Evaluated on three MLLM architectures spanning image, video, and audio, EAServe delivers up to 4.3x and 1.7x higher goodput than NVIDIA Dynamo and vLLM, respectively, under identical SLO constraints, sustains more balanced and higher GPU utilization across the EPD pipeline, and reaches near-optimal configurations faster than baseline search methods.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：纯文本 LLM 服务中，将 Prefill 与 Decode 解耦到独立 GPU 池（PD 分离）已成为标准优化。多模态大模型（MLLM）额外引入 **Encode 阶段**，形成 **Encode–Prefill–Decode（EPD）三阶段流水线**。
- **核心问题**：现有方案存在缺口：
  - 纯文本 PD 系统没有 Encode 阶段；
  - EPD 框架（如 NVIDIA Dynamo）虽把 Encode 独立为服务，但按请求逐条执行，不调控下游请求流，GPU 分配由运维人员手工设定。
- **结构性资源不均衡**：所有请求必须先经过 Encode，下游才能开始；但单次编码前向计算量太小，难以打满现代 GPU。高负载下编码 GPU 仍大量空闲，下游 Prefill/Decode 却因编码队列积压而饥饿，尾延迟膨胀。
- **整体含义**：论文主张把 **Encode 重新定位为 EPD 流水线的控制点**，因为它天然控制三个耦合维度：
  1. 工作何时进入下游；
  2. 每个请求的 Prefill 在哪里执行；
  3. 共置场景下 GPU 如何共享。
- 这三个维度必须联合优化，单独调优会破坏其他维度；但联合空间过大，手工搜索不可行。

## 2. 方法论

### 2.1 核心思想

EAServe 是围绕 Encode 控制点构建的两层协同设计框架：

- **配置层 Hybrid Auto Selection（HAS）**：离线搜索部署配置 \(PC = (alloc, B, s)\)，即 GPU 分配、最大编码批大小、卸载比例。
- **运行时层**：三个编码感知机制，将 HAS 选出的配置落地并在线自适应：
  - 负载自适应微批处理；
  - 速率控制的部分卸载；
  - 动态 SM 分区。

### 2.2 关键技术与公式

#### （1）HAS：混合自动选择

- 目标：给定 GPU 预算 \(G\)、模型 \(M\)、工作负载 \(D\)、目标到达率 \(\Lambda\)，最大化吞吐：
  \[
  PC^\star = \arg\max_{PC} \text{Throughput}(PC)
  \]
  以平均 TTFT、平均 TPOT 作为平局裁决。
- **Stage 1：容量画像与剪枝**
  - 在不相交 GPU 子集上并行测量 Encode 饱和容量 \(C_E\)、单 worker Prefill 容量 \(C_P\)、Decode 容量 \(C_D\)。
  - 将各阶段建模为独立开队列服务器，利用率：
    \[
    \rho_\sigma = \frac{\Lambda / n_\sigma}{C_\sigma}, \quad \sigma \in \{E,P,D\}
    \]
    Prefill 考虑本地共置 worker 时：
    \[
    \rho_P = \frac{\Lambda}{C_P(n_P + n_L \alpha)}
    \]
  - 瓶颈平衡得分：
    \[
    score(a) = \max(\rho_E, \rho_P, \rho_D)
    \]
  - 依次过滤：丢弃 \(\rho_\sigma \ge 1\) 的不可行分配；剪掉得分超过最小值 1.2 倍的分配；保留 top-\(K\)（\(K=3\)）。
  - 同时为 Stage 2 生成搜索范围：\(B \le B_{\max}(a)=\lceil \Lambda/n_E\rceil\)，\(s\) 以负载均衡点 \(s^*(a)=C_{\text{remote}}/(C_{\text{remote}}+C_{\text{local}})\) 为中心，窗口 \(\pm 0.2\)。
- **Stage 2：TPE 贝叶斯精化**
  - 使用 Optuna + TPE 采样器，在混合类型空间（类别型 alloc、离散 \(B\)、连续 \(s\)）中做端到端试验。
  - 每个 trial 部署完整 E+P+D 系统并运行 benchmark，记录吞吐及平均 TTFT/TPOT。
  - 终止条件：top-3 吞吐差距 <1%，或连续 5 轮无改进。
  - 最终按字典序选择：吞吐优先，其次平均 TTFT，再平均 TPOT。

#### （2）负载自适应微批处理

- 问题：固定超时随负载漂移；队列长度触发无法区分短暂低谷与突发结束；连续批处理仅适用于自回归解码。
- **Poisson-gap 调度规则**：
  - 设单编码 worker 到达率 \(\lambda=\Lambda/n_E\)，目标填满概率 \(p\)。
  - 到达间隔服从指数分布，要求批内 \(B-1\) 个间隔均不超过 \(g\)：
    \[
    \Pr(\max\{X_1,\dots,X_{B-1}\}\le g)=(1-e^{-\lambda g})^{B-1}=p
    \]
  - 解得：
    \[
    \kappa = -\ln(1-p^{\frac{1}{B-1}}), \quad g = \frac{\kappa}{\lambda}
    \]
  - 阈值 \(g \propto 1/\lambda\)：高负载自动收紧，低负载自动放宽，无需按工作负载重调。
- 调度条件：批大小达到 \(B\)，或空闲间隔超过 \(g\)，或批年龄超过硬上限 \(A=1000\) ms。
- 论文使用 \(p=0.6\)，在 [0.5, 0.7] 内不敏感。

#### （3）速率控制的部分卸载

- 目标：通过卸载比例 \(s \in [0,1]\) 控制请求流向远端 Prefill 还是编码 GPU 上的本地 Prefill。
- 为何共置 Prefill 而非 Decode：软件 SM 分区无法隔离 HBM 带宽，Decode 会逐 token 流式读取 KV cache，会占满共享内存总线，因此 Decode 必须独占 GPU。
- **赤字计数器路由**：
  - 维护实数累加器 \(d\)，初始为 0；每来一个请求加 \(s\)。
  - 若 \(d \ge 1\)，走远端路径并 \(d \leftarrow d-1\)；否则走本地路径。
  - 性质：累计远端请求数始终在 \(ns \pm 1\) 内，长期精确收敛到 \(s\)；连续远端决策不超过 \(\lceil 1/(1-s)\rceil\)，连续本地决策不超过 \(\lceil 1/s\rceil\)。
  - 无需额外调参，使 HAS 选择的 \(s\) 能在运行时转化为可观测延迟。
- **Envelope 式嵌入传输**：将发往同一 Prefill worker 的嵌入合并为一个连续张量，通过 NIXL 单次传输发送，一个微批最多每个目标 Prefill worker 一次传输，而非每请求一次。

#### （4）动态 SM 分区

- 关键观察：Encode 延迟随 SM 分配增加先快速下降，随后饱和。存在“最小安全 SM 份额”。
- 做法：
  - 启动时离线建查找表：在少量 SM 分配级别（5 级）和 batch size 范围内 profile 编码延迟，记录每个 SM 级别可支持的最大 batch size。
  - 运行时每个微批查表：给 Encode 最小安全份额，剩余 SM 给本地 Prefill。
  - 通过 libsmctrl 写入 TPC mask，亚微秒级重配置，无需重启内核。
- 当 HAS 选择 \(s=1\) 时，本地 Prefill 不共置，动态 SM 分区退化为单租户编码分配，无额外开销。

  - HAS 与 Dynamo 手动 sweep 的“最佳配置”比较，虽在同一分配空间内，但手动调优的彻底程度难以完全保证。
