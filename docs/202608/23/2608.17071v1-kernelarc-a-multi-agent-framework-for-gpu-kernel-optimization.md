## 摘要
我们提出了KernelArc，一个面向异构工作负载的自主GPU内核优化的多智能体框架。策略专用智能体并行运行，并通过仅结论共享内存、确定性基准守卫，以及带有平台触发草稿的只读跨智能体状态进行协调。我们使用具有类别代表性的SOL-ExecBench工作负载，在NVIDIA H100和B200 GPU上评估了KernelArc。所得到的实现涵盖自定义BF16 GEMM、静态cuBLASLt Expert-API配置表、融合的混合专家反向传播、形状门控解码器层融合、原生NVFP4分组查询注意力，以及分页预填充注意力。在2026年7月30日记录的公开SOL-ExecBench排行榜快照中，这些提交在具有代表性的L1、L2、量化和FlashInfer任务上排名第一。这些轨迹支持了论文的核心动机：在固定的候选预算内，共享多智能体搜索可以拓展探索范围并达到更强的现有方案，而各个协调特性的价值取决于内核和优化阶段。

## Abstract
We present KernelArc, a multi-agent framework for autonomous GPU kernel optimization across heterogeneous workloads. Strategy-specialized agents run in parallel and coordinate through conclusions-only shared memory, a deterministic benchmark guard, and read-only cross-agent state with plateau-triggered drafting. We evaluate \kernelarc{} on NVIDIA H100 and B200 GPUs using category-representative SOL-ExecBench workloads. The resulting implementations span custom BF16 GEMM, static cuBLASLt Expert-API configuration tables, fused mixture-of-experts backward, shape-gated decoder-layer fusion, native NVFP4 grouped-query attention, and paged prefill attention. At the public SOL-ExecBench leaderboard snapshot recorded on July~30, 2026, these submissions ranked first on representative L1, L2, Quantization, and FlashInfer tasks. The trajectories support the paper's central motivation: shared multi-agent search can broaden exploration and reach stronger incumbents within a fixed candidate budget, while the value of individual coordination features depends on the kernel and optimization stage.

## 1. 核心问题与整体含义（研究动机与背景）

- **GPU内核优化的高难度**：现代 Hopper/Blackwell 架构暴露了大量底层高性能原语（如 `wgmma.mma_async`、TMA传输、异步屏障、SM100指令、NVFP4格式等），但真正获得有效加速需要跨布局、内存层次、寄存器压力、同步和启动开销进行充分协调，人工性能工程极其耗时且门槛高。
- **LLM智能体作为新路径**：LLM 驱动的自主内核优化智能体可以在“观察-编辑-评测-保留”循环中替代人工调优，已有 AutoKernel 等单智能体系统验证了可行性。
- **单智能体的根本局限**：单智能体一次只推进一条局部历史轨迹，在固定预算下容易“过度细化单一设计方案”，覆盖的算法族（GEMM策略、融合方式、DSL选择等）较少；在遇到平台期（plateau）时容易把“搜索轨迹的瓶颈”误判为“硬件瓶颈”。
- **KernelArc 的定位**：提出多智能体架构，让策略特化的智能体并行探索不同优化家族，通过“仅共享结论”的协调机制拓宽搜索广度，在固定候选预算内达到更强的现有最优方案（incumbent）。

## 2. 提出的方法论：核心思想与关键技术细节

### 2.1 形式化目标
- 以测量门控的方式求解：`k* = argmax_{k∈K} S(k; W, H) s.t. C(k,w)=1 ∀w∈W`
  - `K`：源码级实现空间（含结构调整，如替换为库调用、改DSL、融合epilogue、引入warp specialization等）；
  - `S`：基准评分（如各 shape 延迟的几何均值倒数）；
  - `C`：确定性正确性谓词（任一工作负载失败即不可行）。

### 2.2 核心架构组件
1. **策略特化并行搜索**：8个策略技能（library、memory、compute、fusion、precision、reduction、scheduling、custom-b200）+ 元技能（playbook-index 控制策略资格）；技能只是轻量种子文档，用于防止并发智能体坍缩到同一优化方向。
2. **仅结论共享内存（Conclusions-only memory）**：
   - Wins：成功优化记录（speedup、shape上下文、why-it-worked + before→after 伪代码），默认每内核类型保留16条，按速度提升降序；
   - Traps：失败死胡同记录，默认 FIFO 保留16条；
   - 字段限额（策略160字符，反思1200字符）防止冗长条目污染上下文；
   - 迭代计数器、心跳、进度日志不进入共享内存——保持确定性代码与生成式推理分离。
3. **外部确定性守卫（Guarded evaluation）**：
   - 级联门（Cascade gate）：廉价预检语法、入口点、可移植性（禁止 ctypes/subprocess/cpp_extension）；
   - 确定性基准：GPU 锁下执行，测聚合延迟；
   - 保留条件：全部 workload 通过且超过当前最优的设定比例边际才 KEEP；
   - 停止条件：平台期、目标达成、时间预算耗尽、候选数上限。
4. **平台触发草稿（Plateau-triggered drafting）**：连续非改进次数 `r ≥ r_draft` 时，强制智能体更换算法族/DSL/数据布局，而非继续局部精调。
5. **只读跨智能体状态**：内部 campaign leaderboard 暴露各智能体最优归档（guard bests），供其他智能体只读检查较强兄弟解。

### 2.3 算法流程（文字说明）
- **Algorithm 1（智能体循环）**：初始化基线 → 确定内核类型与合格策略 → 每轮迭代先回忆 wins/traps、可选读取 leaderboard 与兄弟归档 → 若 `r ≥ r_draft` 则起草新方向，否则按策略计划 → 生成候选编辑 → 提交守卫 → 根据 KEEP/ACCEPT/REVERT/REJECT 更新 `r` 与记忆 → 直到守卫 STOP。
- **Algorithm 2（启动器循环）**：将策略分组分配给各智能体 → 配置共享/私有内存路径 → 每智能体独立解决方案目录并仅通过守卫访问GPU → 若启用 leaderboard 则启动发布器周期扫描归档 → 智能体提前退出时在同一目录重启（守卫归档保证最优变体不丢失）。

## 3. 实验设计

### 3.1 实验场景与 benchmark
- **单智能体 GEMM 边界研究（深度 regime）**：H100 SXM 上 4096×4096 BF16 GEMM，8小时预算，给定的 Hopper 专用 CUDA playbook 作为启动指导。
- **SOL-ExecBench 多任务研究（广度 regime）**：B200 GPU，SM 时钟锁定、L2 flush、CUPTI 追踪。选取每类别一个代表任务：
  - L1-030：注意力输出投影 + 残差（16 shapes）；
  - L2-025：256专家 top-8 MoE 反向（16 shapes，FP32）；
  - L2-053：文本解码器层（自注意力 + MLP）；
  - Q-031：NVFP4 分组查询注意力（40 Q头/8 KV头）；
  - FI-014：分页预填充因果 GQA（30个变长 workloads）。

### 3.2 对比方法
- **单智能体 vs 多智能体**：同一任务上对比单智能体搜索平台值（L1-030: SOL 0.441）与 KernelArc 多智能体结果（SOL 0.481）。
- **消融**：FI-014 上比较三种配置：
  - Single：私有内存、无 leaderboard；
  - Multi-bounded：双智能体 + 共享内存（16条上限）+ 只读 leaderboard；
  - Multi-unbounded：同上但无内存上限。
- **基准对比**：PyTorch 参考实现、NVIDIA 优化基线（公开 SOL-ExecBench 排行榜）、匹配环境下的 cuBLAS 端到端基线。

## 4. 资源与算力

## 6. 主要结论与发现

1. **单智能体可达深度有限**：GEMM 研究从 4.6 TFLOPS 提升到 766 TFLOPS（超过匹配 cuBLAS 基线 3.2%，达理论峰值 77%），但依赖详细人工 playbook，且任务为单一固定 shape。
2. **共享多智能体可突破平台期并扩大探索**：L1-030 从单智能体 SOL 0.441 提升到多智能体 SOL 0.481（公开排行榜第一名快照）；FI-014 消融中 Multi-unbounded 的几何平均加速为 Single 的 2.04 倍、Multi-bounded 的 1.59 倍；Multi-bounded 也达 Single 的 1.28 倍。
3. **跨类别泛化能力强**：同一框架在 L1（库配置+残差异名融合）、L2（MoE 反向计数排序 + 批 GEMM + algebraic 梯度复用）、Q（原生 NVFP4 tcgen05 路径 + 融合 softmax-W 量化）、FI（分页 paged prefill 的混合 cuDNN/Triton 路径）均产生有效内核；L1-030/L2-025/L2-053/Q-031/FI-014 中除 L2-053未列速度外，表中速度提升最高达 61972.57×（相对 PyTorch 参考）与 143.78×（相对优化基线）。
4. **协调特征价值与阶段相关**：早期探索、平台逃逸、后期局部精调中，不同机制（共享内存、leaderboard、保留期限）起作用的程度不同；结论性共享可以防止重复死胡同并重定向相邻搜索，但无法给出通用最优配置。

## 7. 优点

- **架构设计清晰分离**：生成式 LLM（提出候选）与确定性守卫（评测、保留、归档、发布）严格分离，避免智能体自我确认偏差；确定性代码掌握状态机、停止条件和内部排行，可复现性强。
- **结论级共享而非历史共享**：共享只携带“wins/traps + 反思”，不携带迭代计数器等噪音，降低上下文污染且保留可迁移经验；保留期限可配置，提供灵活性。
- **策略特化 + 元技能资格映射**：8个策略技能加 playbook-index 资格约束，防止无关策略（如对 GQA 用 SM100 GEMM 策略）浪费预算。
- **实验设计诚实且有区分度**：明确区分“深度 regime”（单智能体 playbook 指导）与“广度 regime”（多智能体共享搜索），不将 GEMM 结果泛化为“普遍优于 cuBLAS”；给出成本-性能前沿，考虑了模型后端的经济性。
- **跨类别验证**：覆盖自定义 PTX/库配置/融合/量化/注意力等不同优化轴而非单一内核族，提升体系结构通用性的说服力。

## 9. 改进建议与未来方向

- **扩大任务抽样**：在 SOL-ExecBench 全部 235 个问题上做分层采样（每类别至少 5–10 个任务），以估计整体胜率并给出置信区间，而非仅展示 5 个代表任务的单点结果。
- **统一成本计量**：在相同美元预算、GPU 机时或 token 预算下比较单/多智能体，报告“性能-成本”前沿，避免候选数口径掩盖 LLM 推理开销差异。
- **逐步消融设计**：分别加入 leaderboard、共享内存、无界记忆、平台触发草稿，逐步累积各机制，量化每个组件的边际贡献，并检验其与任务类型、平台期的交互。
- **超参数敏感性分析**：对 `r_draft`、内存条目上限、字段字符限制、候选预算上限做扫描，或改为基于进度统计的自适应阈值；给出默认参数在不同任务上的鲁棒性区间。
- **增强守卫能力**：加入数值误差容差检查、多次运行方差检测、端到端真实任务验证；对 win 条目的反思做自动摘要质检（如与实测加速比一致性校验），降低误导风险。
- **开放实现细节**：公开确定性守卫代码、智能体提示词、wins/traps 完整日志、GPU 锁调度与归档机制，并披露 B200 总卡时与 token 消耗，便于社区复现和后续扩展。

## 10. 总体评价

KernelArc 在架构设计上进行了有价值的创新：用“策略特化并行搜索 + 结论级共享 + 平台触发草稿 + 确定性守卫”构建了一个兼顾探索广度与评估可信度的多智能体内核优化框架。它明确区分了深度优化与广度覆盖两种 regime，并通过 LEADERBOARD 披露了可学习的跨智能体状态，为自动内核优化提供了一条清晰、可扩展的技术路线。但论文当前的实验规模仍偏小、统计证据较温和、成本核算不够统一，其“优于单智能体”的结论更适合被解读为有前景的探索性结果，而非已稳固确立的普遍优势。
