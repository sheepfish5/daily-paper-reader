## 摘要
稀疏混合专家（MoE）语言模型通过每个令牌仅激活一小部分专家来减少算术运算，但部署时仍需存储和移动完整的专家库。我们提出了ExactMoE，一种推理设计，仅对路由专家应用对称分组128的四比特权重量化，以内核原生的MARLIN形式将这些专家存储在固定主机内存中，并通过可配置的GPU驻留槽缓存和融合分组MoE内核执行所有选定专家。路由器、注意力、嵌入、归一化层和语言模型头保持BF16。“精确”指的是完整的专家可用性和不变的top-k路由过程：不修剪、替代或强制在CPU上执行任何专家。这并不意味着与BF16模型数值相同。在OLMoE-1B-7B-0924-Instruct上，在单个NVIDIA L4上评估，16槽配置将峰值保留GPU内存从14.168 GiB降至1.836 GiB（降低87.04%），同时保留BF16解码吞吐量的81.85%。完全驻留的64槽配置达到31.923令牌/秒，而BF16为21.662令牌/秒，同时保留4.061 GiB。在12,450个零样本多项选择问题中，ExactMoE获得70.3534%的归一化准确率，而BF16为70.8996%，保留了基线准确率的99.23%。在匹配的16令牌消融中，融合分组执行比顺序W4参考快1.97倍。这些结果确定了完整专家MoE推理的实用内存-传输吞吐量边界。

## Abstract
Sparse mixture-of-experts (MoE) language models reduce arithmetic by activating only a small subset of experts per token, yet deployment still requires storing and moving the full expert bank. We present ExactMoE, an inference design that applies symmetric group-128 four-bit weight quantization only to routed experts, stores those experts in kernel-native MARLIN form in pinned host memory, and executes all selected experts through a configurable GPU-resident slot cache and fused grouped MoE kernels. The router, attention, embeddings, normalization layers, and language-model head remain in BF16. "Exact" refers to complete expert availability and an unchanged top-k routing procedure: no expert is pruned, substituted, or forced to execute on the CPU. It does not imply numerical identity with the BF16 model. On OLMoE-1B-7B-0924-Instruct, evaluated on a single NVIDIA L4, a 16-slot configuration reduces peak reserved GPU memory from 14.168 to 1.836 GiB (87.04%) while retaining 81.85% of BF16 decode throughput. A fully resident 64-slot configuration reaches 31.923 tokens/s versus 21.662 tokens/s for BF16 while reserving 4.061 GiB. Across 12,450 zero-shot multiple-choice questions, ExactMoE obtains 70.3534% normalized accuracy versus 70.8996% for BF16, retaining 99.23% of the baseline accuracy. In a matched 16-token ablation, fused grouped execution is 1.97x as fast as a sequential W4 reference. These results identify a practical memory-transfer-throughput frontier for complete-expert MoE inference.

## 1. 核心问题与整体含义

- **背景**：稀疏混合专家（MoE）模型通过每 token 只激活少数专家来降低计算量，但部署时仍需存储和搬运**完整专家库**，导致严重的 GPU 显存和主机-设备传输带宽瓶颈。
- **核心矛盾**：运行时必须在以下方案中取舍——在 GPU 上保留大型专家库、通过慢速存储层搬运专家、或缩小专家表示（带来量化误差）。
- **已有工作局限**：专家量化、混合精度、卸载系统等方法虽各自解决部分问题，但常伴随专家缺失、CPU 执行、临时 FP16 物化等不利特性。
- **ExactMoE 的定位**：在**不剪除任何专家、不改变 top-k 路由过程**的前提下，将专家权重以 W4A16 量化并以内核原生格式存储，通过 GPU 槽缓存和融合分组内核实现完整专家的高效推理。此处的「Exact」指系统层面保证完整专家可用性和路由忠实性，**不等同于**与 BF16 模型数值一致。

## 2. 方法论

- **总体框架**：仅对路由专家的投影矩阵（gate/up/down）进行分组 W4 量化，路由器、注意力、嵌入、归一化、语言模型头保持 BF16；在线推断时，原始路由器选择专家，token 按选定专家分组，通过缓存意识的分波（wave）融合内核执行。
- **专家量化公式**：
  - 对每个专家矩阵按输入维度分组（每组 128 权重），对称量化：
    - `s_i,g = max|W_i,j| / 7`
    - `q_i,j = clip(round(W_i,j / s_i,g), -8, 7)`
    - 反量化参考值 `Ŵ = s_i,g * q_i,j`
  - 全零组直接置零避免除零。
- **内核原生打包**：量化后的 q 权重和 FP16 scale 直接打包成 MARLIN 所需格式，离线一次完成；同一份打包数据同时存储在**固定主机内存**和**GPU 槽缓存**中，缓存缺失时只做异步复制，**不进行反量化和重新打包**，避免了临时 FP16 物化。
- **分级驻留与缓存管理**：
  - 每层有 C 个专家槽（k ≤ C ≤ E），记录全局专家到槽的映射和 LRU 时间戳。
  - 缓存缺失时替换当前波未保护的最近最少使用槽，并用 CUDA 事件防止覆盖尚未完成计算的槽。
  - 当 C=E 时完全驻留，禁用专家 ID 传输和替换。
- **分组完整执行**：
  - 当批量 token 激活的专家数超过 C 时，将活动专家集划分为若干 wave（每 wave ≤ C 个专家）。
  - 每个 wave：解析/加载专家到槽 → 构造全局专家 ID 到槽 ID 的映射（未激活专家映射到哨兵）→ 调用融合 MARLIN MoE 内核处理完整 token 矩阵 → 累加 wave 输出 → 记录完成事件。
  - 每 wave 仅做 2 次分组 GEMM（一次融合 gate/up，一次 down），而非逐专家调用；路由权重不跨 wave 重归一化，各 wave 不相交贡献求和还原式(2)。
- **内存估算**：路由专家参数约需 `48 + 16/128*8` 字节/参数；OLMoE 6.44B 路由参数打包后主机池实测 3.09 GiB。

## 3. 实验设计

- **模型与数据集**：

  - 质量评测：ARC-Easy（570）、PIQA（1838）、HellaSwag（10042），共 **12,450** 个零样本选择题；另加 WikiText-2 测试（120 段落）和 Dolly-15k 采样（120 条）的 teacher-forced 困惑度。

- **对比基准**：同一检查点的 **BF16 原模型**；内部顺序逐专家 W4 参考（消融用）。未复现任何外部 MoE 量化/卸载系统。
- **配置变量**：GPU 槽缓存容量 C ∈ {8, 16, 32, 64}，其中 64 为完全驻留；主卸载对比点为 C=16。

## 6. 主要结论与发现

- **内存-吞吐前沿**（持久热，OLMoE/L4）：
  - C=16：峰值保留显存从 14.168 → 1.836 GiB（**降 87.04%**），解码吞吐保留 BF16 的 81.85%（17.73 vs 21.66 tok/s），代价是每 128-token 请求中位 H2D 流量 21.44 GiB，TTFT 升高到 290 ms。
  - C=32：命中率 81.4%，吞吐 21.66 tok/s 几乎追平 BF16，显存仍降 81.8%。
  - C=64（完全驻留）：吞吐 31.92 tok/s（**比 BF16 高 47.4%**），显存 4.061 GiB（降 71.3%）。
- **质量保持**：归一化多选准确率 70.3534% vs 70.8996%，**保留 99.23%**；绝对下降 0.546 个百分点，bootstrap 区间 [-0.964, -0.137]，McNemar p=0.0112（统计显著但量级很小）。HellaSwag 主导下降；ARC-Easy/PIQA 点估计为正但区间含零。WikiText PPL 升 3.85%，Dolly PPL 降 1.46%（后者视为无退化迹象）。
- **融合消融**：相同 16 槽缓存下，融合分组执行比顺序 W4 参考**快 1.97×**（18.43 vs 9.36 tok/s），输出 token 完全一致。
- **批量扫描**：batch=8 时 W4A16 吞吐 90.02 tok/s > BF16 65.25 tok/s，且显存仅 1.86 GiB。

## 7. 优点

- **系统设计亮点**：主机与 GPU 使用**同一份内核原生打包表示**，缓存缺失路径极简（纯异步复制，无 FP16 物化、无重打包），独立于反量化工作区。
- **完整专家承诺**：不剪枝、不替换、不强制 CPU 执行，保持原始 top-k 路由，将「完整可用性」「路由忠实性」「数值等价性」三个概念明确分离，避免混淆。
- **工程可复用性**：借助 MARLIN 和 vLLM 融合 MoE 原语，通过波式分组执行把激活专家批量合并为两次 GEMM，扩展性好。
- **实验严谨**：报告统计显著性和置信区间，主动声明评价范围与局限，提供详细可复现性记录（固定模型/数据集/软件 commits、原始测量日志、校验和等）。
- **实用价值**：给出了清晰的内存-传输-吞吐权衡前沿，支持根据瓶颈选择缓存容量；全驻留时甚至超越 BF16 吞吐。

## 8. 不足与局限

- **泛化性有限**：仅单模型（OLMoE-1B-7B）和单 GPU（L4）验证，未复现外部 MoE 卸载/量化系统，不能宣称优于现有 serving 框架。
- **数值非等价**：W4 量化改变隐藏状态和后续路由决策，与 BF16 仅近似；质量保留（99.23%）有统计上可检测的微小下降。
- **硬件与格式约束**：依赖 MARLIN 兼容维度和 NVIDIA GPU；不同专家布局需填充/重打包/换内核，新架构需手工映射 checkpoint 张量。
- **显存节省依赖结构**：仅量化路由专家，注意、路由、共享组件等保持稠密 BF16，总节省取决于路由专家占比。
- **运行时依赖缓存命中**：专家复用率低时频繁缺失，卸载带来的吞吐优势可能消失；C=16 时 TTFT 明显劣化（79→290 ms）。
- **未覆盖部署场景**：无多 GPU 协调、无分布式缓存、无连续批处理调度器；权重更新需重新打包。
- **测量细节**：批量扫描每点仅单次测量，属描述性结论；请求间共享进程不能反映冷启动/跨机器波动。
