## 摘要
前沿的开权重模型日益普及，但服务它们的方式仍然主要假设数据中心基础设施。我们提出了FreeToken，一个边缘原生的MoE服务系统，它将个人机器视为一个统一的、弹性的推理平台，而非小型GPU。FreeToken协同设计整个服务栈，包括模型布局与加载、专家驻留、CPU-GPU执行、智能体状态复用以及运行时内存管理，围绕本地AI的两个现实：智能体工作负载不断改变其执行模式，以及边缘硬件暴露出的异构资源在不同机器间平衡各异。FreeToken并非采用固定的卸载策略，而是持续将计算和模型状态映射到实际可用的资源上。FreeToken支持超过20个MoE模型，以及从8GB笔记本GPU到单个工作站GPU的硬件上的真实编码和工具使用智能体。更重要的是，它改变了这些机器实际可服务的规模，从笔记本上的35B模型，到游戏台式机上的284B模型，再到单个工作站GPU上的753B GLM-5.2。FreeToken将开放权重转变为可部署的本地软件，使用户已有的机器成为前沿规模智能的实用平台。我们在flashml.ai发布该系统。

## Abstract
Frontier open-weight models are increasingly available, but serving them still largely assumes datacenter infrastructure. We present FreeToken, an edge-native MoE serving system that treats a personal machine not as a small GPU, but as a unified, elastic inference platform. FreeToken co-designs the full serving stack, including model layout and loading, expert residency, CPU--GPU execution, agentic state reuse, and runtime memory management, around two realities of local AI: agent workloads continuously change their execution pattern, and edge hardware exposes heterogeneous resources whose balance differs from machine to machine. Rather than committing to a fixed offloading strategy, FreeToken continuously maps computation and model state onto the resources actually available. FreeToken supports more than 20 MoE models and real coding and tool-using agents across hardware ranging from an 8GB laptop GPU to a single workstation GPU. More importantly, it changes what these machines can practically serve, from a 35B model on a laptop to a 284B model on a gaming desktop and the 753B GLM-5.2 on a single workstation GPU. FreeToken turns open weights into deployable local software, making the machines users already own a practical platform for frontier-scale intelligence. We release the system at flashml.ai.

## FreeToken：高效边缘原生MoE服务与带宽自适应执行——论文总结

### 1. 论文的核心问题与整体含义（研究动机与背景）

前沿开放权重模型（如DeepSeek-V4-Flash、GLM-5.2等）的能力虽已快速逼近闭源系统，但其服务方式仍默认依赖数据中心级GPU集群，动辄需要数百万美元的硬件投入。虽然开放权重使“谁都能获得模型”，但尚未解决“谁都能运行模型”的可及性问题。智能体（agent）应用的兴起使推理需求急剧增长，个人用户和小型团队难以承担云端API的持续使用成本。

MoE（混合专家）架构为边缘部署提供了新路径：每token只需激活少量专家，计算量大幅降低——例如DeepSeek-V4-Flash的284B参数中仅13B参与每个token的推理，这一活跃参数足迹可适配主流消费级GPU的显存。但完整专家池仍远超显存容量，必须在推理过程中动态从主存或磁盘加载。MoE因而同时创造了机遇与挑战：稀疏激活使计算可行，而完整专家池使高效服务变得困难。

现有边缘服务系统（如llama.cpp、KTransformers、Ollama）仅解决局部问题，存在三个核心短板：预填充（prefill）阶段破坏MoE工作集稀疏性——长提示跨层路由覆盖几乎全部专家，造成大量权重流式传输；解码（decode）阶段缺乏系统的缓存未命中处理策略——静态放置无法适应token级路由变化；边缘资源高度异构且动态变化——GPU、CPU、PCIe带宽、主机内存带宽在不同设备间差异极大，且资源常被并发应用抢占，固定策略无法适应。

FreeToken的核心主张是：将个人机器视为统一的弹性推理平台，而非小型GPU，通过协同设计整个服务栈，持续将计算和模型状态映射到实际可用的资源上，而非采用固定卸载策略。

### 2. 论文提出的方法论：核心思想、关键技术细节与公式

FreeToken的设计围绕“两条执行原则 + 一个弹性资源管理策略”展开，核心架构为两层级专家内存层次：CPU驻留完整专家池（唯一事实来源） + GPU上的弹性专家缓存（按（层，专家）逻辑标识管理）。

#### 2.1 带宽自适应执行（Bandwidth-Adaptive Execution）

这是整个系统的核心执行原则，将有限的边缘带宽从固定瓶颈转化为运行时调度信号。

**预填充阶段——全层双缓冲（Full-Layer Double Buffering）：**
- 从全局槽池分配两个全层缓冲区，GPU计算第l层路由专家的同时，专用传输流将第l+1层完整专家集载入另一缓冲区。
- 因预填充激活几乎全部专家，按完整层加载可在路由未知前启动传输，实现权重移动与计算持续重叠。
- 缓冲区在层间交换角色，与解码共享同一槽池，无独立预填充缓存或阶段交接。

**解码阶段——q*策略（公式化划分缓存未命中）：**
每个解码步的m个缺失专家M被划分为缓存填充集F（经PCIe传输至GPU）和CPU执行集C（在主存中原地计算）：

- M = F ∪ C，q = |F|
- 设S为单个专家字节数，B_P为PCIe专家传输带宽，B_H为主机侧专家处理带宽。PCIe传输饱和后剩余可供CPU执行的主存带宽为：B_R = max(B_H − B_P, 0)
- 两分支执行时间均衡：T_fill(q) ≈ qS/B_P，T_cpu(m−q) ≈ (m−q)S/(B_H − B_P)
- 均衡并发分支得到最优划分比：**q⋆ ≈ m · B_P/B_H**

该公式统一覆盖所有硬件平衡场景：当B_H接近B_P时，q⋆趋近于m，系统退化为纯按需填充。实际运行时始终保留至少一个填充，保证缓存持续预热。带宽参数在部署时实测获得，CPU分支先行启动，GPU与CPU计算结果精确合并，无算法近似。

#### 2.2 语义感知缓存（Semantic-Aware Caching）

**预填充阶段——语义锚点状态缓存：** 混合注意力模型中，循环层将完整前缀压缩为单一状态，无法部分复用。FreeToken维护一个循环状态检查点池，附着于前缀树的节点上，将稀疏的检查点预算花在“语义锚点”——特殊token边界（思维段、工具调用、工具输出、对话轮次）。这些正是智能体框架编辑上下文的位置（如OpenClaw移除思维块、OpenCode替换旧工具输出）。编辑后从最近的幸存锚点恢复，仅重算新增后缀。

**解码阶段——语义感知专家缓存（LRU）：** 解码路由展示出强时间局部性——相邻token常路由到重叠或近期使用的专家。FreeToken以全局共享LRU驻留空间取代加载时固定的静态放置，缓存内容持续跟随路由器选择的实时工作集：命中刷新recency，填充准入新选专家，驱逐最久未用者。

#### 2.3 弹性边缘资源管理（Elastic Edge Resource Management）

- **运行时缓存重构：** 因CPU驻留池是事实来源，GPU内存只影响性能不影响正确性。在任何调度器安全点，可在不重启引擎、不重载专家池的前提下，按修订后的运行时可显存预算重建GPU专家缓存。
- **快速引擎启动：** 将专家权重直接从磁盘读入最终主机布局后再钉住内存（避免先钉空缓冲造成页面归零浪费），首个请求以冷缓存服务，通过常规解码路径自然预热，消除启动预热。

#### 2.4 实现层面要点

- 所有路由相关控制保持在GPU上，以“图内数据”形式存入静态捕获的CUDA Graph：固定形状工作缓冲 + 设备端有效计数。
- 单遍内核完成专家去重、驻留分类、计算q、选择受害者（K个最近最少使用候选）、重写逻辑ID为物理槽ID。
- CPU执行分支亦被捕获入同一图，避免每token的Python调度开销。
- FTW格式将专家权重预合并为运行时bank布局，启动时并行直接I/O读取，跳过张量发现与重打包。

### 6. 论文的主要结论与发现

- **端到端性能：** RTX 5090上，FreeToken在Qwen3.6达77–83 tok/s、DSV4-Flash达22–25 tok/s，比最强基线分别高1.8–2.3×和1.5–1.9×。智能体工作负载下解码率稳定在单轮值的12%以内，而基线系统显著退化（KTransformers在DSV4上从W1到W2即损失31%）。
- **尾部延迟：** FreeToken最差轮次TTFT在所有单元均低于44秒，每个基线都在某处突破150秒（最严重达946秒），已越过真实智能体客户端的超时阈值。
- **跨硬件普适性：** 领先最强基线1.3×（3090）至2.1×（5090桌面）。8GB RTX 4060笔记本上服务35B模型达39.3 tok/s，超过Codex生产环境33 tok/s的中位数；RTX PRO 6000上GLM-5.2速度为llama.cpp的2.0×（14.9 vs 7.3 tok/s）。
- **机制归因：** 全层双缓冲使预填充传输受限（8K token块1.19-1.22s完成，达PCIe 5.0 x16实际上限）；全局LRU在相同容量下miss率（16%/39%）远低于静态放置（62%/89%）和预填充更新（41%/59%）。
- **宏观结论：** 开放权重能否落地取决于服务软件能否组合现有资源——边缘AI的边界由硬件容量与服务软件共同决定。

- **未充分讨论多租户/并发场景：** 弹性缓存的动态重构虽支持运行时显存变动，但评测中未系统展示GPU被其他应用抢占时的性能变化过程。
- **某些机制的性能边界未完全刻画：** 如仅保留一个填充时的CPU分支性能下限、前缀树与状态缓存联合最优放置等细节问题。
- **外部效度问题：** 论文基于2026年的模型与硬件（RTX 50系等），结论对更早或更晚世代硬件的泛化需谨慎。
