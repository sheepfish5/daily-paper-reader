## 摘要
传统上，GPU内核在供应商特定的编程模型中开发和优化以达到高性能，这导致软件难以优化并适应日益异构的计算系统。硬件无关的编程模型通过提高可移植性和可维护性，为GPU软件开发提供了一种更可持续的方法，但在不同架构上实现高效执行仍然具有挑战性。我们通过将自动调优集成到用Julia编写的硬件无关GPU内核中来应对这一挑战。我们重建了支持Julia的成熟Kernel Tuner自动调优框架，使得能够系统探索面向NVIDIA、AMD、Intel和Apple GPU的硬件无关GPU内核的配置。我们在NextLA.jl线性代数库中实现的硬件无关奇异值分解（SVD）上演示了这种方法。结果表明，自动调优对于在各种硬件上创建资源高效的硬件无关GPU内核至关重要。与中位数参数配置相比，最优配置将内核性能提高了3倍到7倍，展示了调优对高效硬件利用率的显著影响。

## Abstract
Traditionally, GPU kernels have been developed and optimized within vendor-specific programming models to achieve high performance, resulting in software that is difficult to optimize and adapt across increasingly heterogeneous computing systems. Hardware-agnostic programming models offer a more sustainable approach to GPU software development by improving portability and maintainability, but achieving efficient execution across diverse architectures remains challenging. We address this challenge by integrating auto-tuning into hardware-agnostic GPU kernels written in Julia. We rebuild the established Kernel Tuner auto-tuning framework with Julia support, enabling systematic exploration of kernel configurations for hardware-agnostic GPU kernels targeting NVIDIA, AMD, Intel, and Apple GPUs. We demonstrate this approach on hardware-agnostic singular value decomposition (SVD) as implemented in the NextLA.jl linear algebra library. The results show that auto-tuning is essential for creating resource-efficient hardware-agnostic GPU kernels across a variety of hardware. Optimal configurations improve kernel performance by a factor of 3x to 7x compared to median parameter configurations, demonstrating the substantial impact of tuning on efficient hardware utilization.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：现代 HPC 系统异构性越来越强，同一集群中可能包含 NVIDIA、AMD、Intel、Apple 等多个厂商的 GPU。传统 GPU 内核开发依赖厂商特定的编程模型（如 CUDA、HIP），只能针对单一硬件优化，跨平台时需要重复开发与维护，成本极高。
- **核心矛盾**：硬件无关编程模型（如 Julia 的 KernelAbstractions）能显著提升代码可移植性和可维护性，但**编写出在所有硬件上都能高效执行的内核仍然困难**——硬件的差异（计算能力、内存层次、带宽、缓存策略等）使得一组固定的内核参数无法在多个平台上同时达到最优。
- **已有工作的不足**：
  - 现有自动调优框架（如 Kernel Tuner、KTT、CLTune、OpenTuner）主要面向 CUDA、OpenCL、HIP 等厂商相关的编程模型，尚未覆盖硬件无关框架；
  - Julia 生态中 NextLA.jl 等库提供了可移植 GPU 线性代数内核，但参数选择依赖专家经验或手动暴力搜索，限制了搜索范围且耗时；
  - 可移植性与最优性能之间存在"性能差距"，有时需要完全重写才能达到厂商库的性能水平。
- **整体含义**：论文提出将自动调优与硬件无关 GPU 编程模型相结合，使"一次编写、全平台高效"成为可能，是推动可持续计算、降低跨平台开发成本的重要一步。

## 2. 方法论：核心思想与关键技术细节

### 2.1 核心思想
将成熟的 Python 自动调优框架 Kernel Tuner 扩展到 Julia GPU 生态，实现**跨语言集成**：Julia 负责硬件无关内核编写，Python 负责自动调优编排。两者通过 PythonCall/CondaPkg 桥接，避免重复代码库。

### 2.2 主要架构与组件

- **Julia 后端（Julia Backend）**：在 Kernel Tuner 中新增的 backend，通过 JuliaCall 在 Python 内嵌 Julia 运行时；
- **自动检测**：初始化时自动探测可用的 Julia GPU 后端（CUDA.jl、AMDGPU.jl、oneAPI.jl、Metal.jl）；
- **动态编译**：为每次调优动态构造 Julia 模块，隔离内核定义，避免命名冲突；
- **参数传递**：将调优参数转换为 `Val` 类型，利用 Julia 的编译期特化（compile-time specialization），使每个配置的差异完全暴露给编译器；
- **内存管理**：Python host 数组自动转换为 GPU 数组（deep copy 防止副作用）；
- **预热机制**：每个配置先执行一次 warm-up，排除 JIT 编译对计时的影响。

### 2.3 跨后端计时（Cross-Backend Timing）

| 后端 | 计时方案 |
|---|---|
| NVIDIA (CUDA) | GPU 流事件计时（CuEvent） |
| AMD (ROCm) | GPU 流事件计时（HIPEvent） |
| Apple (Metal) | 在 kernel 执行前后插入 command buffer 计算 GPU 时间 |
| Intel (oneAPI) | 退化为 host 侧计时（并给出警告） |

### 2.4 Julia 接口与包
- 提供 kernel launcher（负责参数传递、执行、同步、计时）；
- 用户可用纯 Julia 代码定义 kernel 和调优问题，也可混合使用 Kernel Tuner 的数据结构；
- 支持灵活的双向工作流：Julia 脚本可调优任何 Kernel Tuner 支持的语言编写的内核，Python 脚本也可直接调优 Julia 内核。

### 2.5 应用场景：SVD 内核调优
- 聚焦 NextLA.jl 中 SVD 算法的第一阶段——**稠密矩阵到带状矩阵的归约**，其中的核心是计算密集的 trailing matrix update 内核（Fused TSQRT/TSMQR）；
- 调优的搜索空间为 4 个参数：

| 参数 | 含义 | 取值范围 |
|---|---|---|
| Tilesize (TS) | 矩阵分块大小 | 8, 16, 32, 64, 128 |
| Tile height (TH) | tile 高度 | 8, 16, 32, 64, 128 |
| Split-K (K) | split-k 并行分裂数 | 1, 2, 4, 8, 16, 32, 64, 128 |
| Columns per block (CPB) | 每线程块的列数 | 1, 2, 4, 8, 16, 32, 64, 128 |

## 6. 主要结论与发现

1. **自动调优的必要性**：最优配置比中位配置快 2.7×～6.7×（不同 GPU 上），说明不经调优地选择任意参数会造成巨大的性能浪费；
2. **自动调优优于专家经验**：在 7 款 GPU 中有 6 款上自动调优找到的配置优于原始专家手动选择的配置（唯一例外是同样团队深度优化过的 A4000）；Apple Metal GPU 上此前根本没有好的专家配置；
3. **可移植 + 自动调优 = 资源高效**：硬件无关内核经过自动调优后，有潜力接近甚至超过手动优化的厂商特定实现，且大幅降低开发成本；
4. **平台差异符合预期**：数据中心 GPU（MI300X、H200 等）显著优于消费级 Apple M1 Pro，但论文强调的是"对每款硬件实现最优资源效率"，而非让所有硬件达到相同性能；
5. **跨语言集成的可行性**：Julia + Python 的混编方案没有阻碍调优流程，且避免了重复代码库，是语言生态间协作的正向案例。

## 7. 优点与亮点

- **首个 Julia 自动调优框架**：KernelTuner.jl 填补了 Julia GPU 生态中缺少正式自动调优工具的空白；
- **跨语言集成设计巧妙**：利用 PythonCall/CondaPkg 实现 Julia 与 Python 双向互操作，不引入重复代码，灵活性与可维护性俱佳；
- **硬件覆盖广**：同时覆盖 NVIDIA、AMD、Intel、Apple 四大 GPU 厂商，验证了硬件无关编程模型 + 自动调优在大范围异构硬件上的可行性；
- **针对不同后端设计了不同的计时方案**：对 NVIDIA/AMD 用 GPU 事件，对 Metal 用 command buffer，对 Intel 用 host 计时并给出诚实警告，体现了工程严谨性；
- **Val 类型传递参数**：利用 Julia 编译期特化使调优参数完全暴露给编译器，保证每个配置的性能真实性；
- **开源于 GitHub**：可复现、可扩展，便于社区使用与改进。

## 8. 不足与局限

- **实验规模有限**：只有一个应用（SVD 的单个内核）、一个矩阵规模（16384×16384）、一种精度（FP32）；对其他应用、数据规模和精度的推广性未知；
- **缺乏全流程（pipeline）调优**：tile size 作为管线参数被单独固定，没有与其他参数联合优化，论文也将其列为未来工作；仅优化单个内核而非完整 SVD 的实际端到端性能；
- **没有评估调优成本**：未报告搜索整个空间所需的 GPU 小时数、时间开销、收敛速度，实际使用时的调优开销可能较大；
- **缺少与其他调优工具的对比**：没有与 OpenTuner、KTT 等进行性能与效率的比较，无法定位 KernelTuner.jl 在同类工具中的相对优势；
- **Apple/Intel 计时方法受限**：Metal 用 command buffer 间接测量，Intel 退化为 host 计时，精度低于 CUDA/HIP 的事件计时，可能引入误差；
- **无消融实验**：没有单独验证"跨语言桥接"、"Val 特化"、"预热机制"等设计选择各自对性能的影响；
- **排名意义有限**：只做了单轮搜索空间遍历，未讨论不同优化策略（贝叶斯优化、遗传算法等)在 Julia 内核上的实际效果差异；
- **基准对比不系统**：未与 vendor 库（cuSOLVER / rocSOLVER）直接做端到端对比，因此"超越手动优化实现"的结论支持有限。
