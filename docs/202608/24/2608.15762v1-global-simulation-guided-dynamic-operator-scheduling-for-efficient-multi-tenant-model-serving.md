## 摘要
容器粒度调度使得容器内大量短暂的闲置片段未被利用。在SLA约束下，重新分配容器过于笨重，无法利用这种细粒度的机会；而算子级调度需要实时推理依赖关系、内存安全性和集群范围的执行动态。本文提出了SliceScheduler，一个面向多租户模型服务的动态算子级调度系统。其关键思想是暴露集群范围的算子执行状态，并支持对调度决策进行what-if推理。SliceScheduler由四个关键组件组成。首先，我们引入了全局映射图（GMG），这是一种统一抽象，捕获算子依赖、张量形状、资源映射和执行状态，提供具有明确资源语义的实时集群范围视图。其次，我们在GMG之上构建了一个全局模拟器，用于预测候选放置下的算子级执行和内存演变。第三，我们设计了一个增量式、基于模拟的调度模块，该模块选择放置方案以利用碎片化的空闲片段，同时避免内存违规并保持SLA。最后，我们开发了一个算子执行器，在GPU上实现调度决策，并协调计算和跨加速器传输。我们将SliceScheduler实现为PyTorch后端，并使用生产轨迹重放对其进行评估。实验结果表明，与现有方法相比，SliceScheduler将token吞吐量提高了1.10–2.29倍，同时将SLA违规保持在9%以内。SliceScheduler证明了算子级调度是提高多租户LLM服务GPU利用率的实用且有效的方法。

## Abstract
Container-granularity scheduling leaves abundant short-lived idle slices within containers unexploited. Reallocating containers is too heavyweight to utilize such fine-grained opportunities under SLA constraints, and operator-level scheduling requires reasoning about dependencies, memory safety, and cluster-wide execution dynamics in real time.   In this paper, we present SliceScheduler, a dynamic operator-level scheduling system for multi-tenant model serving. The key idea is to expose cluster-wide operator execution state and enable what-if reasoning over scheduling decisions. SliceScheduler consists of four key components. First, we introduce the Global Mapping Graph (GMG), a unified abstraction that captures operator dependencies, tensor shapes, resource mappings, and execution states, providing a real-time, cluster-wide view with explicit resource semantics. Second, we build a global simulator on top of GMG to predict operator-level execution and memory evolution under candidate placements. Third, we design an incremental, simulation-based scheduling module that selects placements to exploit fragmented idle slices while avoiding memory violations and preserving SLA. Finally, we develop an operator executor that materializes scheduling decisions on GPUs and coordinates computation and cross-accelerator transfers. We implement SliceScheduler as a PyTorch backend and evaluate it using production trace replay. Experimental results show that SliceScheduler improves token throughput by 1.10--2.29$\times$ compared to existing approaches, while maintaining SLA violations within 9\%. SliceScheduler demonstrates that operator-level scheduling is a practical and effective approach to improving GPU utilization for multi-tenant LLM serving.

# SliceScheduler 论文详细总结

## 1. 核心问题与研究动机（整体含义）

- **背景**：大规模多租户 LLM 推理服务中，GPU 资源利用率普遍偏低。现有主流的**容器级调度**（如 Kubernetes）只做“租户/容器粒度”的资源分配，无法感知和利用 GPU 上大量**短暂、细粒度的空闲片段**（idle slices）。
- **关键观察**：
  - 生产 AI 编程负载的轨迹重放显示：平均 GPU 利用率仅 64.0%，空闲片段中位时长为 2551 ms，p99 约 17.8 s；短于 p99 的空闲片段占总空闲时间的 95.6%。
  - 在线服务即使按 SLA 资源饱和供给，仍会因突发请求产生大量瞬时空闲。
  - 容器重新分配（预占、checkpoint、重调度、冷启动）开销达分钟级，无法适配秒级空闲片段。
- **核心问题**：如何将调度粒度下沉到**算子（operator/layer）级**，在不违反 SLA、不导致 HBM 内存溢出的前提下，动态利用集群中碎片化的短暂空闲 GPU 资源？
- **挑战**：
  1. 算子级调度缺少显式资源需求描述，容易造成 HBM OOM；
  2. 静态“算子→资源”映射无法预测集群执行随时间的动态演化；
  3. 跨 GPU 的算子放置会引入张量传输，需要实时控制和死锁避免。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- **暴露集群级算子执行状态**，对调度决策进行 **what-if 模拟评估**，再决定算子放置。
- 将 LLM 推理层（layer）视为调度单位，把低优先级离线请求“塞”进高优先级在线服务留下的空闲片段中。

### 系统架构（四层紧密耦合）
1. **GMG（Global Mapping Graph，全局映射图）**
   - 统一抽象：Shape DAG + Accelerator Set。
   - 节点 = 算子，携带张量形状、执行状态（unscheduled/issued/done）、输出张量形状、checkpoint 元数据。
   - 边 = 数据依赖。
   - 记录算子到加速器的映射、HBM 占用、全局时间戳，提供实时集群视图。
   - 采用“register-once, instantiate-many-times”模式，注册模板后反复实例化，形状可推导。

2. **Global Simulator（全局模拟器）**
   - 基于 GMG 快照重建每个加速器的执行队列和 HBM 张量驻留；
   - 采用**事件驱动模拟**：每次选取最早完成的算子作为事件，推进统一模拟时间线，触发后续算子启动；
   - 依赖**线性估计器**：
     - 传输延迟：`t = α·size + c`；
     - 算子执行时间：以 batched matmul 为例，`t = β1(bmnk) + β2(bmk) + β3(bkn) + β4(bmn) + β5`；
   - 持续用运行时反馈在线更新估计器，提高预测精度。

3. **Scheduling Module（调度模块）**
   - 维护两个 frontier：**scheduled frontier**（已调度且存在未调度后继的算子）和**unscheduled frontier**（可被调度且前驱已完成/已调度的算子）。
   - 使用 **Algorithm 1：Incremental Simulation-Based Scheduling**：
     - 若已 issued 算子数超过预算则返回；
     - 从 unscheduled frontier 选最高优先级算子，收集一个小的连通图批次；
     - 对每个候选分区（并行）克隆 GMG、应用放置、构建全局模拟器、执行模拟；
     - 丢弃导致 OOM 的放置；
     - 选择“预测平均算子完成时间最小”的可行放置。
   - 优势：自动偏好数据局部性（跨加速器传输会增加预测完成时间）、保护高优先级 SLA、细粒度负载均衡。

4. **Operator Executor（算子执行器）**
   - 每个加速器维护一个**本地算子队列**，按数据依赖驱动，而非按下发顺序；
   - 跨加速器张量传输被拆为 **Intent / Recv / Send** 三个操作，强制 Recv-before-Send 顺序，避免目的地缓冲区未就绪而失败/死锁；
   - **仲裁算法**：维护独立的通信图，选择无冲突的传输集合并发执行，事件驱动触发，避免本地协商导致的环等待。

### 实现
- 作为 **PyTorch 自定义后端**，用 TorchDynamo 捕获计算图并注册为模板；
- Master 运行在 host CPU，执行器基于 LibTorch 在 GPU 端运行；
- 调度粒度为“层”（将每层前向/反向合并为一个算子），避免 ATen op 粒度过细导致调度开销过大。

## 3. 实验设计

- 在线负载：Llama3-8B 推理服务，按轨迹的 TTFT/TPOT 驱动，重放 19:00–19:30 区间（含忙闲波动）。
- 离线负载：每秒 1 个请求，输入 2048 token，输出 15 token，作为低优先级填充工作负载。

### 环境
- 单台多 GPU 服务器：
  - 2× Intel Xeon Platinum 8468（共 96 CPU 核）；
  - 1600 GB 主机内存；
  - **8× NVIDIA A16 GPU，每张 64 GB**。

### 对比方法（Baselines）
- **Static-Online**：四个在线实例固定绑扎 GPU 对 (0,1), (2,3), (4,5), (6,7)。
- **Subset-Share**：优先级感知共享 [44]，离线实例固定于 4 GPU 子集。
- **Dual-Share**：干扰感知共享 [39]，两个离线实例分别固定于两个 4 GPU 子集。

### 监控指标

## 6. 主要结论与发现

- **SliseScheduler 能有效利用细粒度空闲片段**：相比 GPU 共享/固定共享基线，token 吞吐提升 **1.10×–2.29×**，SLO attainment 提升约 **9%**，GPU 利用率提高 **17%–38%**。
- **收益来源**：
  - 突破容器隔离限制，实现集群级细粒度负载均衡；
  - 比固定范围 GPU 共享（Full-Share）更好地对齐多 GPU 间空闲片段的时间重叠；
  - 通过优先级感知调度保护在线 SLA。
- **系统开销几乎可忽略**：SliceScheduler 运行 1000 次 prefill 的时间与 Direct Execution 基本一致（23.37s vs 23.39s），且比 Eager Execution 快 8%。
- **模拟器精度高**：算子/传输估计器 MAPE 分别为 0.32%/0.92%；端到端训练迭代时间预测误差仅 1.83%（SimAI 为 20.58%）。
- **模拟速度快**：约 176.8 ops/ms，比 SimAI 高约四个数量级。
- **可扩展性**：在 8 层合并为 1 算子、模拟吞吐 176.8、预测窗口 l=3、timeliness t=0.1 条件下，可扩展到约 64 GPU 的中小型集群。

## 7. 优点

- **问题定位精准**：明确指出容器级调度的结构性缺陷，并用生产数据量化空闲片段规模。
- **抽象设计统一**：GMG 同时表达依赖、形状、放置和运行状态，天然支持模拟和增量调度。
- **what-if 调度机制新颖**：将调度决策转化为可评估的模拟问题，兼顾全局最优性和实时性。
- **工程实现完整**：覆盖从图捕获、算子队列、跨 GPU 传输仲裁到反馈更新的完整闭环。
- **性能提升显著且不牺牲 SLA**：在真实轨迹重放上验证，SLA 违规率控制在 9% 以内。
- **模拟器轻量且准确**：线性估计器 + 事件驱动模拟在精度与速度上均优于 SimAI。

## 8. 不足与局限

- **实验规模有限**：仅单机 8 GPU，未在多机集群、更大量 GPU 下验证；可扩展性分析偏理论。
- **硬件单一**：仅 NVIDIA A16，未覆盖 A100/H100 等更强算力或不同带宽拓扑，结论的泛化性存疑。
- **无消融实验**：未逐项验证 GMG、模拟器、增量调度、传输仲裁等组件的独立贡献。
- **baseline 为自行实现**：作者自复现 GPU 共享方法（Subset-Share、Dual-Share、Full-Share），可能与原始系统在工程细节上有差异，公平性需谨慎评估。
- **工作负载定制化**：仅测试 Llama3-8B 一种模型，未涵盖更大 LLM、多模型混部、长上下文、不同批次策略等场景。
- **调度粒度依赖人工调整**：将层合并为调度单元（如 8 层一组）需要经验设定，未提出自适应粒度选择机制。
- **在线更新估计器存在冷启动问题**：早期训练样本不足时，模拟精度可能下降，论文未深入讨论。
- **SLA 度量单一**：只使用 p90 TTFT 阈值，未分析更严苛的 p99/p999 或 end-to-end 延迟违例。
