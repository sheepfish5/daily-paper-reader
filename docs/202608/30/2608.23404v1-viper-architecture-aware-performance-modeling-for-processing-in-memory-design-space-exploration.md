## 摘要
内存内处理（PIM）通过在内或近内存执行计算来减少数据移动开销，但其实际应用加速比高度依赖设计。不可卸载的主机执行、主机-PIM传输、有限的PIM容量以及设备编程延迟可能限制端到端加速比，因此快速的早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然有限：电路级和设备级工具无法捕获这些端到端PIM性能因素，而周期精确模拟对于迭代式DSE来说太慢。为解决这一差距，我们提出了VIPER，一个统一、轻量级且架构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次性能剖析，并将测得的主机行为与PIM感知的分析引擎结合，该引擎在候选设计间扫描PIM侧参数。它通过捕获主机-PIM传输、阵列访问、内存内计算、设备编程延迟和容量引起的分区，支持任务卸载和数据触发执行下的近内存处理（PNM）与使用内存处理（PUM），为迭代式DSE提供快速的架构感知性能估计，无需重复进行周期精确模拟。我们针对商用UPMEM系统和400多个周期精确的gem5配置验证了VIPER。VIPER先验地预测UPMEM卸载决策和盈亏平衡区域，并通过精细化的传输模型，在DPU扫描中捕获测得的峰值-滚降行为，平均加速比误差为12%（在256-DPU峰值前为6%）。与gem5相比，VIPER误差小于10%，同时将评估时间从数小时缩短至一分钟以内。UPMEM、ReRAM/FeFET交叉阵列和IMCRYPTO的案例研究表明，架构感知的DSE揭示了设备级评估所忽略的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 核心问题与整体含义

- **背景与动机**：处理中内存（PIM）通过在内或近内存执行计算来减少数据移动开销，但其端到端加速比高度依赖具体设计。不可卸载的主机执行、主机-PIM传输、有限PIM容量和NVM设备编程延迟等因素可能严重限制实际收益。因此，在早期设计阶段进行快速设计空间探索（DSE）至关重要。
- **现有工具缺陷**：
  - 电路/器件级工具（如IMAC-Sim、Eva-CAM）只评估阵列边界，无法反映主机交互、数据移动和容量问题；
  - 周期精确模拟（如gem5-SALAM、PIMSim）虽能建模全系统，但每个配置需数小时到数天，不适合迭代搜索；
  - 接口级模型（如LogCA、Gables）速度快，但把主机和内存系统抽象为平坦接口成本，无法表达PIM特有的容量分区、设备编程延迟和数据触发执行。
- **核心问题**：如何让设计者在硅片流片前，快速、准确地量化PIM设计在完整内存层次结构中的端到端性能收益？
- **整体含义**：VIPER提出一个统一、轻量且架构感知的解析性能框架，以AMAT为基础将PIM嵌入内存访问路径，覆盖PNM与PUM两种范式，支持任务卸载与数据触发两种执行模式，使PIM DSE能在数秒内完成，弥补了电路级粒度与全系统模拟之间的空白。

## 2. 方法论

### 核心思想
- 将PIM视为内存层次结构中的一个组件，而非简单的宿主连接加速器；
- 利用“应用的主机侧行为不随PIM设计变化”这一结构性特点，只剖析主机一次，固定CPU参数；然后通过解析引擎扫描PIM侧设计参数；
- 基于经典AMAT模型扩展，加入显式的PIM延迟项和容量分区项。

### 解析模型要点
- **任务卸载模型**：
  - CPU执行时间使用标准AMAT计算；
  - 总执行时间 = CPU部分 + PIM部分；
  - PIM部分包含PIM指令数、执行CPI、PIM访问次数与有效PIM内存延迟。
- **数据触发模型**：
  - 用`tPIM,mem`替换标准AMAT中的`tDRAM`；
  - 总执行时间仍由CPU指令数、CPI和PIM感知AMAT决定。
- **PIM时序分解**：
  - PNM任务卸载：`tPIM,mem = (tin + tarray + tout) / CC_PIM`；
  - PUM任务卸载：`tPIM,mem = (tin + tprog + tout) / CC_PIM`；
  - 数据触发PNM/PUM：额外包含`tcomp`，并乘以容量分区因子；
  - 容量分区：当工作集超过PIM容量`C_PIM`时，按`ceil(D_PIM / C_PIM)`重复整个流水线。
- **DSE流程**：
  - **剖析阶段**：使用Linux `perf`采集硬件计数器，得到指令数、执行CPI、缓存缺失率、内存访问率、时钟周期等固定CPU参数；
  - **扫描阶段**：设计者扫描PIM侧参数（指令数、CPI、延迟项、容量、时钟周期），直接由解析方程计算端到端时间，无需重复模拟。

## 3. 实验设计

### 验证场景与基准
- **任务卸载验证（gem5-SALAM）**：
  - 模拟平台：ARM MinorCPU in-order，默认缓存，DDR4-2400；
  - 加速器：GEMM集群（LLVM-IR建模），通过配置scratchpad延迟`m`区分PNM（m>0）与PUM（m=0）；
  - 工作负载：单层Llama2 transformer prefill（dim=128, hidden=256, 8 heads, batch=128）；
  - 扫描参数：GEMM tile size（6种）、PIM计算延迟`c`（7种）、scratchpad延迟`m`（8种），共336个配置。
- **数据触发验证（gem5扩展）**：
  - 在gem5缓存/内存控制器中注入可配置PIM延迟，模拟数据触发；
  - 11种配置（覆盖SRAM PNM、DRAM PNM、NVM PUM、HBM/存储类等不同延迟与容量）；
  - 12个基准：SPEC2017 CPU子集 + GraphBig（GitHub开发者社交网络数据集）。
- **真实PIM案例研究**：
  - UPMEM 2560-DPU服务器：验证Llama2 matmul卸载的端到端加速比预测；
  - ReRAM/FeFET交叉阵列（XBA）：结合DNN+NeuroSim电路级模拟器，研究容量与编程延迟影响；
  - IMCRYPTO：SRAM内AES-128，作为数据触发PUM网关，评估在内存加密的内存访问成本。
- **对比对象**：VIPER vs gem5周期模拟、VIPER vs 商用UPMEM实测、VIPER vs 电路级工具（NeuroSim）的差异。

## 6. 主要结论与发现

- VIPER在400+ gem5配置上平均误差低于10%，评估时间从6–30小时降至1分钟以内；
- 在UPMEM真实系统上先验预测了Amdahl天花板、盈亏平衡DPU范围（约35预测 vs 40–49实测）和卸载决策；修正传输模型后，可捕获峰值-滚降行为（峰值约256-570 DPU，而单调饱和预测被实测否定）；
- 架构感知DSE揭示：
  - **UPMEM类PNM**：存在最优DPU数量，超过该点增加DPU反而降低端到端加速比，原因是主机中介的传输与调度开销随DPU数增长；
  - **XBA（ReRAM/FeFET）**：内核加速比41–70×，但端到端最高仅2.96×；容量略小于工作集时性能急剧恶化（比更小容量更差）；编程延迟使ReRAM/FeFET在非驻留场景出现3倍差异，而器件级模拟完全看不到；
  - **IMCRYPTO**：数据触发式内存加密在实测配置下平均只增加1.5% AMAT（最差6.2%）；对编程延迟扫描显示只有CMOS和FeFET能满足最差10%预算，RRAM和PCM不适合作关键路径网关。
- 总体结论：早期PIM DSE必须架构感知，设备级评估会遗漏跨层交互导致的“悬崖式”性能变化。

## 7. 优点

- **统一性**：单一解析框架同时覆盖PNM与PUM、任务卸载与数据触发，无需为每种设计重新建模；
- **速度快**：一次剖析+解析计算，可在秒级扫描数百设计点，远超周期模拟；
- **准确性**：与gem5和真实UPMEM硬件对比验证，误差可接受且趋势预测可靠；
- **可操作性**：参数与具体设计决策直接对应（容量、技术延迟、时钟、指令数），适合早期“如果-怎么办”探索；
- **开源**：提供源码和评估脚本，可复现；
- **案例研究深刻**：UPMEM的峰值-滚降、XBA的容量悬崖、IMCRYPTO的技术筛选都是电路级工具无法发现的架构级洞察。

## 8. 不足与局限

- **未建模MLP**：AMAT顺序延假设不捕获内存级并行，导致OoO CPU下系统性高估，尤其是GraphBig等不规则访问负载；
- **容量模型简化**：用`ceil(D/C)`的一阶乘数近似容量分区，未考虑bank级并行、非均匀数据布局等二阶效应，设计者需自行调整有效容量；
- **数据触发验证不够细**：gem5验证中仅用一个聚合`tPIM,mem`，未单独验证`tarray`、`tprog`、`tcomp`各自精度；
- **传输模型依赖校准**：UPMEM先验预测使用恒定传输时间，高DPU数下明显低估传输开销；虽然修正后精度改善，但表明解析模型对复杂主机-PIM通信行为需要实测数据或更细交互模型；
- **仅关注性能**：未包含能量模型（作者列为未来工作），而PIM的能效优势是重要指标；
- **适用范围**：数据触发模型主要针对小、低延迟任务（如AES），对大型计算型触发任务可能不适用；
- **早期设计不确定性**：模型输入（如`tprog`、`tarray`）在流片前只能靠器件估计，误差会传导到最终性能预测。
