## 摘要
分块预填充流水线并行（CPP）是LLM推理的一项关键技术。然而，等大小的分块表现出不均衡的延迟，因为后面的分块需要关注更长的前缀KV缓存并产生更高的注意力成本，从而导致流水线气泡。现有方法通过动态分块调整（动态CPP，DCPP）来缓解这种不均衡，但我们的测量表明，这以调度开销换取了负载均衡，在长序列上变得不利。在本研究中，我们提出了虚拟流水线并行（VPP），它保持分块大小固定，并通过虚拟阶段优化流水线布局。一种V形虚拟阶段遍历将每个分块昂贵的中间阶段与其相邻分块的较轻头部和尾部阶段重叠，同时异步通信和流水线打包进一步减少了通信停顿和跨请求的排空气泡。我们在vLLM-Ascend中实现了VPP，并在16个Ascend 910C NPU上对三个基于MoE的LLM进行了评估，序列长度高达1M个token。在长序列上，VPP相对于DCPP将吞吐量提高了最多13.1%，在混合工作负载上提高了6.7%，同时在短序列上保持了性能。在一个512K-token的DeepSeek-V3.1预填充工作负载上，VPP将流水线气泡比率从6.4%降低到0.1%，与DCPP相比实现了98.0%的降低。

## Abstract
Chunked prefill pipeline parallelism (CPP) is a key technique for LLM inference. However, equal-size chunks exhibit imbalanced latency, as later chunks attend longer prefix KV caches and incur higher attention costs, leading to pipeline bubbles. Existing approaches mitigate this imbalance through dynamic chunk resizing (Dynamic CPP, DCPP), but our measurements show that this trades scheduling overhead for load balancing, which becomes unfavorable on long sequences. In this study, we propose Virtual Pipeline Parallelism (VPP), which keeps chunk sizes fixed and optimizes the pipeline layout through virtual stages. A V-shaped virtual-stage traversal overlaps each chunk's expensive middle stages with the lighter head and tail stages of its neighbors, while asynchronous communication and pipelined packing further reduce communication stalls and cross-request drain bubbles. We implement VPP in vLLM-Ascend and evaluate it on three MoE-based LLMs with sequences up to 1M tokens on 16 Ascend 910C NPUs. VPP improves throughput by up to 13.1% over DCPP on long sequences and 6.7% on mixed workloads, while preserving performance on short sequences. On a 512K-token DeepSeek-V3.1 prefill workload, VPP reduces the pipeline bubble ratio from 6.4% to 0.1%, achieving a 98.0% reduction compared with DCPP.

## 1. 核心问题与整体含义（研究动机与背景）
- **背景**：LLM 应用（Agent、多轮对话、工具调用、检索、推理）推动上下文长度不断增长，从几万到上百万 token。长序列的 prefill 阶段计算密集、耗时长，会阻塞后续解码与短请求，导致首 token 时延（TTFT）增加和调度抖动。
- **已有方案**：
  - **Chunked Prefill Pipeline Parallelism（CPP）**：将长 prompt 切分为等大小的 chunk，以 chunk 为流水线基本调度单元。但因果注意力下，越靠后的 chunk 需要处理越长的前缀 KV 缓存，计算量越大，因此等分 chunk 的执行延迟随 chunk 索引近似线性增长，导致流水线负载不均和气泡（bubble）。
  - **Dynamic Chunked Prefill Pipeline Parallelism（DCPP）**：动态调整 chunk 边界以均衡各 chunk 执行时间。但动态调整引入了调度开销、执行碎片化（更多 kernel 调用和 host 启动），在长序列下可能得不偿失。
- **核心问题**：如何在不引入动态切分开销的前提下，消除 CPP 中由前缀 KV 缓存导致的负载不均与流水线气泡，从而提升长上下文 prefill 的效率。
- **整体含义**：本文提出 **VPP（Virtual Pipeline Parallelism）**，保持 chunk 大小固定，通过**虚拟阶段 + V 形遍历**重新设计流水线布局，将不同 chunk 的重负载中间阶段与相邻 chunk 的轻负载首尾阶段重叠，从而在不需要动态切分的情况下平衡负载、减少气泡。该方案在 16 个 Ascend 910C NPU 上验证了有效性，为长上下文推理的 prefill 优化提供了新思路。

## 2. 方法论：核心思想、关键技术细节
### 2.1 核心思想
- 观察到固定大小 chunk 的延迟存在**近似线性增长规律**（由因果注意力的前缀 KV 成本主导），因此不通过动态调整 chunk 大小来消除不均匀，而是利用这种可预测性来构造**平衡的固定流水线布局**。
- 将模型按层切分为多个**虚拟阶段**，并**折叠映射**到物理流水线 rank 上，形成 V 形（fold-back）遍历路径。每个 chunk 的路径为：先在前向阶段运行，跨 rank 后在后向阶段返回，呈“V”字形。

### 2.2 V 形阶段遍历（V-shaped Stage Traversal）
- 以 2 个物理 rank（PP=2）为例：模型被切为 4 个虚拟阶段 s0, s1, s2, s3。边界阶段 s0, s3 放在 pp0，中间阶段 s1, s2 放在 pp1。
- chunk Ck 的遍历路径：s0(pp0) → s1(pp1) → s2(pp1) → s3(pp0)。即先从 pp0 到 pp1，执行两个中间阶段后再回到 pp0 执行收尾阶段。
- **负载匹配推导**：假设第 k 个 chunk 的单阶段延迟近似为 τ_k = (k+1)·t。pp1 执行 Ck 的两个中间阶段需要约 2τ_k = 2(k+1)t；与此同时 pp0 可以执行上一 chunk 的收尾阶段（延迟 τ_{k-1}=kt）和下一 chunk 的起始阶段（延迟 τ_{k+1}=(k+2)t），两者之和为 kt + (k+2)t = 2(k+1)t = 2τ_k，正好互相匹配。由此相邻 chunk 的轻量首尾阶段填充了当前 chunk 重型中间阶段造成的空闲窗口。
- 边界情况（C0）也通过 s0/C1 的延迟 τ_1=2t 与 pp1 的 2τ_0=2t 近似匹配。

### 2.3 VPP-Async：异步通信与计算重叠
- 在基础 VPP 中存在同步的跨 rank send/recv，导致通信暴露在关键路径上。
- 通过**重排本地阶段执行顺序**（交换 C_{k-1} 的收尾阶段 s3 和 C_{k+1} 的起始阶段 s0），使得每次传输发起时对端 rank 还有计算可执行，从而将通信隐藏在计算中，避免双向同时传输造成的等待。

### 2.4 VPP-Async + Pipelined Packing：跨请求排空气泡压缩
- 单个长请求的末尾存在不可避免的 drain 气泡（最后一个 chunk 完成遍历时某个 rank 无任务）。
- 在流式请求场景中，利用当前请求 R 的 drain 窗口，将下一个请求 R′ 的**前导 chunk**（其延迟最小，约 t）填入，使 R 的 drain 与 R′ 的 fill 重叠，减少跨请求空闲时间。

### 2.5 实现细节
- 在 vLLM-Ascend 上实现，基于 PyTorch 和 HCCL。
- 控制面（虚拟阶段调度器、折叠层分配、每 batch 流水线状态机）用 Python，注意力与 MoE kernel 复用现有实现。
- 支持不均匀层划分和用户指定层范围，提供双队列调度器（初始遍历队列 + 续跑队列），采用两个交替 HCCL 通信组避免死锁。VPP 由单一开关启用，关闭时回退到上游 vLLM。

## 5. 主要结论与发现
- **DCPP 的缺陷**：在长序列（如 512K）下，DCPP 的执行碎片化开销超过了负载均衡收益；相比 CPP，DCPP 计算时间增加 10.5%，暴露通信增加 36.1%，尽管气泡时间减少 47%，但总 TTFT 仍增加 4.6%。
- **VPP 的有效性**：
  - **长序列**：相对 DCPP，Qwen 提升 3.7%–8.7%（128K–512K），DeepSeek 提升 2.6%–13.1%（64K–512K），GLM 在 64K 处提升 8.5% 但随长度增加而收窄。
  - **混合负载**：相对 DCPP，DeepSeek 提升 6.7%，Qwen 提升 0.8%，GLM 提升 1.3%–1.6%；相对 CPP，DeepSeek 提升 13.8%。
  - **短序列**：整体与 DCPP 相当，在 DeepSeek 上最多提升 10.8%（4K 长度），在 Qwen 上最多下降 6.8%（归因于小模型调度开销摊销不足）。
  - **512K DeepSeek prefill**：VPP 将气泡占比从 6.4% 降至 0.1%（降低 98.04%），拉普拉斯等待几乎归零；计算时间减少 10.1%，非计算开销减少 28.1%，TTFT 总体降低 12.53%。
  - **通信权衡**：VPP 暴露通信时间比 DCPP 增加 35.05%（主要源于 AllGather 平均单次延迟增加），但通信与计算重叠量大幅提升，整体收益仍为正。
  - **稀疏注意力限制**：DSA 降低了 chunk 延迟的线性增长规律，导致 VPP 在超长上下文下的调度效率下降，但在 512K 以内仍保持正收益。
- **消融贡献**：相比 vanilla VPP，VPP-Async 降低端到端延迟 3.13%，再加入 Pipelined Packing 后累计降低 6.89%；气泡占比从 11.0% 降至 2.4%，跨请求气泡降低 33.2%。
- **Chunk size 敏感性**：大多数配置中 24K 表现最优，因为 24K 不会整除序列长度，最后的较小 chunk 在 drain 阶段与前面 chunk 重叠，减少尾部气泡；但在 64K 短长序列上（DeepSeek/GLM），chunk 越小越好（因 pipeline 未达到稳态）。

## 6. 优点
- **思路新颖**：放弃“动态调整 chunk 大小”这一主流路线，转而利用 chunk 延迟的可预测线性增长规律，通过**虚拟阶段折叠布局**在固定模式下实现负载均衡，避免动态调度开销。
- **理论推导与直觉清晰**：用简单的延迟模型（τ_k=(k+1)t）和等式推导说明了 V 形遍历为何能匹配两个 rank 的计算量，可读性强。
- **工程实现完整**：在 vLLM-Ascend 上落地，包含调度器、通信组设计、双队列机制，并支持开关回退，具有实际生产价值。
- **实验设计严谨**：
  - 覆盖短/长/混合负载，多个模型、序列长度和 chunk size 扫描。
  - 不仅有端到端收益，还通过 profiler 分解计算、气泡、通信来源，提供清晰的机制解释。
  - 消融实验分离了各组成部分的贡献，并专门讨论了稀疏注意力这个边界条件。
  - 开源实现，可复现性较好。

## 7. 不足与局限
- **硬件与框架局限**：实验只在华为 Ascend 910C NPU 与 vLLM-Ascend 上完成，未在 NVIDIA GPU 或更大规模集群上验证；通信与调度开销因平台而异，结论的普适性有待检验。
- **模型覆盖有限**：仅评测了 MoE 模型，未包含稠密 Transformer；且模型多为大规模（30B+），对中小模型或不同注意力架构（如稀疏注意力）的表现可能不同。
- **流水线规模小**：只测试了 2 个流水线 rank（PP=2），未评估更深流水线（如 PP=4/8）下 V 形遍历和虚拟阶段的扩展性；虚拟阶段数、折叠方式与 PP 深度的关系尚未深入分析。
- **前提依赖性强**：VPP 依赖“chunk 延迟近似线性增长”这一规律。当注意力成本不占主导（如 EP 禁用、稀疏注意力、或 MoE 通信成本高）时，负载匹配可能失效，气泡会重新出现。论文对此有讨论，但未提出完备的适配方案。
- **通信开销增加**：VPP 暴露通信时间高于 DCPP（+35%），增益主要来自通信隐藏，而非真正的通信量减少；在某些通信受限场景下，性能提升可能被侵蚀。
- **负载与场景覆盖**：长序列测试以单请求为主，混合负载使用合成的 GSM8K 分布，真实生产环境中的请求到达模式、多租户干扰等未充分模拟。
- **作者与平台利益相关**：所有作者来自华为技术及上海交大，且实验平台为华为自有硬件；虽然方法本身可复现，但独立第三方验证仍有必要。
- **对比范围**：未与更广泛的系统（如 Medha、gLLM、SGLang 的最新版本）进行端到端比较，仅与 CPP 和 DCPP（vLLM-Ascend 实现）对比，可能不足以全面反映 SOTA 水平。
