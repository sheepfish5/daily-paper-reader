## 摘要
GPU加速数据库系统越来越普遍，但查询特定的峰值性能往往仍然依赖于手写内核。现有的LLM内核基准测试集中在机器学习算子，未测试不规则、异构、数据移动密集的数据库风格算子。我们介绍了DataKernelBench，它将SQL转换为验证过的PyTorch TorchPlan程序，并通过执行引导修复评估LLM在CUDA或Triton中优化核心张量受限片段或整个查询的能力。在十个专有和开放权重模型上，使用H100 GPU，TPC-H SF10，最强的全查询CUDA配置实现了比TorchPlan基线2.11倍的加速，且完全通过率。我们发现，性能更优的实现通常使用内核融合和执行策略更改，更强的模型从全查询专业化中获益最多，并且工作负载上下文比硬件上下文更重要。为了处理大于GPU内存的数据，我们将TorchPlan扩展为使用Dask-cuDF在TPC-H SF100上按需加载分区，使用四个H100 GPU，实现了2.54倍的加速。项目页面：https://kerneldf.github.io/datakernelbench

## Abstract
GPUs increasingly accelerate database systems, but query-specific peak performance still often relies on hand-written kernels. Existing LLM kernel benchmarks focus on machine learning operators, leaving irregular, heterogeneous, data-movement-heavy database-style operators untested. We introduce DataKernelBench, which translates SQL into validated PyTorch TorchPlan programs and evaluates LLMs that optimize either the core tensor-bounded snippet or the full query in CUDA or Triton through execution-guided repair. Across ten proprietary and open-weight models on TPC-H SF10 with an H100 GPU, the strongest full-query CUDA configuration achieves $2.11\times$ speedup over the TorchPlan baseline at full pass rate. We find that higher-performing implementations commonly use kernel fusion and execution-strategy changes, stronger models benefit most from full-query specialization, and workload context matters more than hardware context. To handle data larger than GPU memory, we extend TorchPlan with Dask-cuDF for on-demand partition loading on TPC-H SF100 with four H100 GPUs, achieving $2.54\times$ speedup. ## 1. 核心问题与整体含义

### 研究动机与背景

- **GPU加速数据库的兴起**：随着AI基础设施投资激增，GPU在企业环境中日益普及。许多分析型工作负载（大规模扫描、谓词求值、连接、聚合）具备高度数据并行性和内存带宽需求，非常适合GPU加速。
- **现实瓶颈**：尽管Tensor Query Processing (TQP) 等方案能将关系操作映射为张量计算，从而在PyTorch等ML框架上运行数据库负载，但通用编译器（如`torch.compile`）在处理分析型查询时仍难达峰值性能——分析查询通常涉及不规则内存访问、复杂谓词、异构算子组合和查询特定的融合机会，因此峰值性能仍依赖手写专用GPU内核。
- **待回答的核心问题**：如果分析查询可以表达为张量程序，最新的代码LLM能否合成专用GPU内核，超越通用编译的性能？该问题具有实际意义——若LLM能胜任此任务，可大幅降低为高频查询编写和维护专用内核的工程成本。

### 研究空白

现有LLM内核基准测试（如KernelBench、TritonBench、MultiKernelBench）均聚焦于**机器学习算子**（密集、规则、同质），完全未测试数据库风格的查询——这类负载**不规则、异构、数据移动密集**，且要求严格语义正确性和数据相关控制流。DataKernelBench正是为填补这一空白而设计。

## 2. 方法论

### 核心思想

DataKernelBench将LLM内核合成问题构建为**两阶段基准流水线**：

1. **阶段一**：将SQL翻译为经过验证的PyTorch张量程序（即**TorchPlan**），作为基准的中间表示（IR）。
2. **阶段二**：让LLM在保持外部`run_query`语义不变的前提下，注入优化后的Triton或CUDA内核，通过执行引导修复循环提升性能。

### 关键技术细节

#### TorchPlan中间表示

每个TorchPlan包含两个核心函数：

- **`run_query`**：处理表访问、连接、投影、参数解析和输出格式化，属于数据帧层操作。
- **`_query_core`**：实现张量密集型的"热路径"（在aligned 1D GPU张量和Python标量上运行），作为内核特化的目标。

这一分解将数据帧层的"关系准备"与张量层的"热路径优化"分离，使基准测试可以控制特化范围。

#### 两个优化级别

- **`core`级**：模型只能修改`_query_core`和私有辅助函数，`run_query`必须保持不变。该级别贴近ML内核基准测试的设定。
- **`full`级**：模型可重写`run_query`、`_query_core`及辅助函数，但必须保留外部`run_query` API——这允许端到端查询的专业化（如改变连接策略）。

#### 两种GPU编程接口

- **Triton**：较易合成，可靠性更高，适合较弱模型。
- **CUDA**：性能上限更高，但更易出现编译/导入错误。
