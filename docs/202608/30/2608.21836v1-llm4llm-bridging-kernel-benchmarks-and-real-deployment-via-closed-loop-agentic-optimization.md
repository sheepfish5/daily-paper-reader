## 摘要
大型语言模型已成为低层代码和内核优化的越来越强大的智能体，但孤立的内核基准测试仅提供了对语言模型推理中至关重要的部署行为的近似。我们发现了一个基准测试到部署的差距：在独立测试台中看似正确且快速的候选内核，在集成到实际推理工作负载后，可能表现出不同的性能、安全性或相位行为。我们引入了LLM4LLM，一个部署感知的闭环优化框架，它从目标推理脚本开始，提取相位感知的优化任务，使用经验引导的片段式智能体进行搜索，并通过模型内验证接受补丁。在A100和H100 GPU上的十个语言模型推理工作负载中，LLM4LLM改善了每个评估模型的端到端延迟，在A100/H100上实现了3.91倍/6.98倍的几何平均加速；作为支持性的内核级证据，它在KernelBench Level 2上也达到了高达2.745倍的几何平均加速。

## Abstract
Large language models have become increasingly capable agents for low-level code and kernel optimization, but isolated kernel benchmarks provide only a proxy for the deployment behavior that matters in language-model inference. We identify a benchmark-to-deployment gap: candidate kernels that appear correct and fast in standalone harnesses can exhibit different performance, safety, or phase behavior after integration into a real inference workload. We introduce LLM4LLM, a deployment-aware closed-loop optimization framework that starts from a target inference script, extracts phase-aware optimization tasks, searches with an experience-guided episodic agent, and accepts patches through in-model validation. Across ten language-model inference workloads on A100 and H100 GPUs, LLM4LLM improves end-to-end latency for every evaluated model, achieving 3.91$\times$/6.98$\times$ geometric-mean speedups on A100/H100; as supporting kernel-level evidence, it also attains up to 2.745$\times$ GeoMean speedup on KernelBench Level 2.

### 一、核心问题与整体含义（研究动机和背景）

- **核心问题**：大型语言模型（LLM）虽已被广泛用于低层代码和 GPU 内核优化，但现有的**孤立内核基准测试**（如 KernelBench）只能提供“代理指标”，无法真实反映内核集成到实际推理工作负载后的行为表现。
- **基准到部署的差距（Benchmark-to-Deployment Gap）**：候选内核在隔离测试台中通过编译、数值校验且测得较快，但一旦接入真实推理脚本后，可能出现**性能反转**（如加速变减速）、**运行时失效**（如隐藏的内存越界导致 CUDA 错误）、**相位行为差异**（如 prefill 优化的内核无法迁移到 decode 阶段）等问题。
- **问题根源**：执行上下文不同，包括缓存状态（冷缓存 vs. 热缓存）、内存分配器状态、启动开销、形状守卫、与现代高性能内核的交互等，均会改变内核的实际表现。

### 二、方法论

#### 2.1 核心思想

LLM4LLM 提出一个**部署感知（deployment-aware）的闭环优化框架**，将真实推理脚本纳入优化回路：从用户提供的推理脚本出发，通过真实模型剖析、相位感知任务提取、经验引导的片段式搜索，最终在**完整模型中验证**后才接受补丁。

#### 2.2 技术细节与公式

1. **热点发现与相位感知任务提取**
   - 对目标推理脚本分层剖析，计算 workload-weighted hotspot score：

     s(m) = Σ_{p∈P} ω_p · t(m,p) / T(p)

   - 其中 m 为模块实例，p 为自回归相位（prefill / decode），t(m,p) 为该模块在相位 p 下的耗时，T(p) 为该相位总延迟，ω_p 为相位权重。
   - 每个任务包含代表性输入、输出参考、形状信息、模块族元数据、硬件范围与相位标签；prefill 和 decode 会在语义分离时被构建为独立任务，并附带调度模板。

2. **经验引导的片段式优化（Experience-Guided Episodic Optimization）**
   - 每个片段（episode）内经历“生成候选-编译-正确性检查-延迟测量-失败检查”的循环。
   - 搜索期验证效用函数：

     u(c, τ) = (t_ref(τ) / t_c(τ)) · 1{err(c, τ) ≤ ε, safe(c, τ)}

   - 片段结束时，将验证轨迹提炼为**紧凑经验**（valid tiling、boundary mask、相位谓词、失败模式、最优性能区间），归档完整转录，并用“任务规范 + 经验摘要”重启新片段，避免陷入局部修复，同时保留可复用知识。

3. **部署时间接受与打补丁（Deployment-Time Acceptance）**
   - 候选内核被插入真实模型实例后，须通过模型内正确性、运行时兼容性、形状守卫覆盖检查。
   - 接受准则：

     c⋆ = arg min_{c∈C_dep} ℓ(c)，且 ℓ(c⋆) ≤ 1 − δ

   - 其中 ℓ(c) = L(M[c], W) / L(M, W) 为归一化部署延迟，δ 为最小部署改进阈值。

### 五、主要结论与发现

- **端到端加速**：在 A100 / H100 上，10 个模型全部获得加速，几何平均加速比分别为 **3.91× / 6.98×**；其中 Mamba-130M 在 H100 上最高达 32.79×，RecurrentGemma-9B 在 A100 上最低也有 1.24×。
- **KernelBench Level 2**：LLM4LLM 达到 97% Pass（A100）、GeoMean 加速 **2.745×（A100）/ 2.628×（H100）**，在对比系统中取得最优 GeoMean。
- **相位感知与模型族差异**：不同模型族的优化目标不同——transformer 族以注意力为主，Mamba 族以状态空间混频器为主，RecurrentGemma 族以 RGLRU 循环核心为主；剖面优先的策略比固定“注意力优先”策略更合理。
- **消融结论**：
  - 采样多样性（Sample-10 vs Sample-1）是强基线；
  - 线性迭代修复（Iter-10）虽能达到 100% Pass，但往往会陷入局部最优；
  - **重启机制（restart）**显著贡献于最佳结果，超出单纯增加预算的收益。

### 六、优点

- **问题定义清晰**：首次系统性地刻画了“基准到部署差距”及其三种表现（性能转移失败、运行时失效、相位行为不匹配），并配以直观的可视化案例（图 1、图 2）。
- **方法新颖且自洽**：将真实模型剖析、相位感知任务提取、经验引导片段式搜索和部署时间接受整合为闭环，公式定义明确（s(m)、u(c,τ)、c⋆），设计逻辑连贯。
- **经验机制设计合理**：片段式重启既保留了有价值约束，又避免了劣质修复轨迹对后续搜索的干扰，附录案例分析（problem 97 从 1.03× 到 5.80×）有力佐证了该设计。
- **实验严谨**：区分孤立性基准表现与部署接受；统一正确性与加速比聚合口径；与 FlashAttention、Mamba fast path 等强库内核做作用域匹配对比，不夸大能力。
- **多 LLM 骨干兼容**：对 GPT-5.4、Claude Sonnet 4.6、GLM-5 三种不同特性的模型均适用，体现了方法的通用性。

### 七、不足与局限

- **应用范围受限**：仅支持单 GPU 推理，未覆盖张量并行、流水线并行、连续批处理（continuous batching）、多租户服务等真实生产场景，这些场景需要通信成本、调度交互、批级干扰等额外验收标准。
- **部署适应性有限**：补丁针对观察到的形状和相位区间定制，若实际部署时提示词分布、解码长度、批处理行为或模型配置有显著变化，需要重新剖析和重新验证。
- **优化成本未量化**：未报告搜索的 token 数、GPU 时数、经济成本等，仅定性承认搜索成本高，实际落地时可用性存疑。
- **内核级结果受基准滥用影响**：论文指出无约束 LLM 可能生成“基准利用型”候选（硬编码测试输出），因此将主要证据放在部署评估上——这本身是优点，但也暗示 KernelBench 对比结果的参考价值有限。
- **未包含分布式与更大规模**：所有实验在单 GPU 上完成，最大模型为 Qwen3-32B，缺少多卡/大规模模型（如 70B+）场景下的验证。
