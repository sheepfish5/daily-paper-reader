## 摘要
基于大型语言模型（LLM）的智能体应用通常面临高响应时间问题。投机解码是一种有前景的解决方案，可在不影响生成质量的情况下提高LLM智能体的推理效率。然而，最先进的投机解码算法在大批量大小下表现出显著的加速退化，限制了其在实际智能体应用中的部署效果。在本工作中，我们首先对LLM智能体的投机解码进行了系统分析，并确定了加速退化的两个主导因素：投机令牌的高拒绝率以及动态令牌预算的利用不足。基于这些观察，我们提出了AgentSpec，一种针对LLM智能体解决现有方法局限性的投机解码算法。AgentSpec引入了结构隔离草拟，将投机限制在智能体工作流的语义连贯片段中，减少无关语义路径的草拟，从而实现极低的拒绝率。此外，AgentSpec采用冗余感知的预算分配，利用智能体级信息更好地在智能体推理期间利用动态空闲令牌预算。我们在vLLM中对五个不同工作负载和来自四个不同LLM家族的四种模型进行了AgentSpec的实现与评估。我们的结果证明了AgentSpec相对于最先进方法的优越性。

## Abstract
Large language model (LLM)-based agent applications often incur high response time. Speculative decoding is a promising solution to improve the inference efficiency of LLM agents without impacting generation quality. However, state-of-the-art speculative decoding algorithms exhibit substantial speed degradation under large batch sizes, limiting their effectiveness to deploy in real-world agent applications. In this work, we first present a systematic analysis of speculative decoding for LLM agents and identify two dominant factors of speedup degradation: high rejection rate of speculative tokens, and under-utilization of dynamic token budgets.B ased on these observations, we propose AgentSpec, a speculative decoding algorithm that addresses the limitations of existing methods for LLM agents. AgentSpec incorporates structure-isolated drafting that constrains speculation to semantically coherent segments of the agent workflow, reducing the drafts of irrelevant semantic paths and achieving an extremely low rejection rate. Moreover, AgentSpec adopts redundancy-aware budget allocation that exploits agent-level information to better utilize the dynamically-free token budget during the agent inference. We implement and evaluate AgentSpec on five different workloads and four different models from four different LLM families in vLLM. Our results demonstrate the superiority of AgentSpec over state-of-the-arts.

## 二、论文提出的方法论

### 2.1 总体架构

AgentSpec 是一个**无草稿模型（model-free）**的投机解码算法，由两个核心组件构成：

### 2.2 核心组件一：结构隔离起草（Structure-Isolated Drafting）

**核心思想**：LLM智能体应用中，一个用户查询往往跨越多个语义块（如推理、工具执行、结果解释等）。在同一语义块内生成模式高度一致，而跨块、跨查询则存在显著语义偏移。现有方法从全局历史中检索草拟候选，导致高拒绝率。

**关键技术细节**：
- 要求智能体应用在发送请求时提供语义结构标识符 `Si = {ai, qi, Bi}`，包含：
  - `ai`：智能体应用标识符
  - `qi`：用户查询索引
  - `Bi`：语义块列表（由开始/结束字符串标签定义）
- 采用**缓存的token-to-string映射 M**，避免在解码过程中频繁调用分词器，实现高效的在线转换。
- 维护一个**轻量级基于字符串的下推自动机（PDA）P**，增量更新以跟踪当前活跃的语义块。
- 为每个语义块维护独立的**结构隔离缓存**，只从匹配的语义块中检索草拟候选，避免跨语义上下文的投机，显著降低拒绝率（从53.3%/88.7%/65.9%降至26.4%）。

### 2.3 核心组件二：冗余感知预算分配（Redundancy-aware Budget Allocation）

**核心思想**：应当将更多草拟token分配给接受潜力高的请求。在智能体工作负载中，与历史重复模式对齐的草拟更有可能被接受。

**冗余评分公式**：
```
g(c, n) = (c/n) · p(n)
p(n) = gmin + (1 - gmin)(1 - e^(1-n))
```
- `n`：从同一语义块和用户查询的历史中检索到的候选延续数量
- `c`：在最高频前缀上一致的延续数量
- `c/n`：候选之间的共识度
- `p(n)`：饱和项，用于在历史支持有限时降低不可靠估计的权重

**预算分配机制**：
- 批级总投机预算：`Bt = ⌊α·bz⌋`（`bz`为批大小，`α`控制总投机预算）
- 每请求草拟长度：`Li = max(|CT*i|, Bt·gi/Σgj)`，优先分配给冗余度高的请求，同时确保每个请求至少草拟其最置信的前缀。

## 六、论文的主要结论与发现

1. **AgentSpec 在所有智能体工作负载和全部4种LLM家族上均一致性地优于现有投机解码方法**（EAGLE-3、NGram、SuffixDecoding）。

3. **AgentSpec 在非智能体工作负载上同样有效**：Spec-Bench整体1.14×加速，检索增强子集最高1.40×加速。
4. **AgentSpec 在 MiMo-7B 上比 MTP 取得更高加速比**（如全部USACO上1.29× vs 0.73×）。
5. **AgentSpec 在不同最大批大小下保持稳健的效率**且在无思考模式（w/o think）下加速比更高（超过2.5×）。
6. **结构隔离起草是主要贡献来源**（消融实验显示比冗余感知预算分配贡献更大），两者结合达到最佳效果。

## 七、优点

- **问题定位精准**：通过建模 `ΔT(b) ≈ D(b)[(1-ρ(b))tA - tV(b)]` 清晰揭示拒绝率与预算利用两个瓶颈，动机扎实有据。
- **方法设计巧妙**：
  - 结构隔离起草利用智能体工作流的语义块结构，从根源上避免了无关语义路径的投机，拒绝率降低50%以上。
  - 冗余评分函数兼顾了共识度（c/n）与历史支持量（p(n)），设计合理。
  - PDA 与 token-to-string 缓存的设计有效解决了 tokenization 与字符串级语义块对齐的工程难点。
- **工程落地性强**：在 vLLM 生产级引擎中实现，扩展接口轻量（仅需三个额外参数）。
- **实验广泛且客观**：多模型、多工作负载、多基线的全面对比；所有基线来自官方实现，配置统一；报告了消融研究、延迟分析、分解分析、批大小/思考模式敏感性、多GPU平台验证。
- **无训练开销**：与 MTP、EAGLE-3 等需要训练草稿模型的方法不同，AgentSpec 无需额外训练，即插即用。
- **理论复杂度约束良好**：时间复杂度与 NGram 同阶（O(K·L)），空间复杂度同为O(H)，额外开销随语义块数量B≪H和请求数R为轻量级。

## 八、不足与局限

- **需要语义结构信息**：AgentSpec 需要智能体应用提供显式的语义块结构标识符（structure、query-id、agent-id），这要求智能体应用配合修改，可能阻碍在已有系统中的直接部署。虽有无语义结构的变体 AgentSpec(N)，但其加速效果可能依赖于工作负载中重复生成模式的可用性。
- **有效性依赖重复模式**：如果智能体工作负载中历史重复模式很少，草拟候选不足，结构隔离起草的优势可能大打折扣。
- **实验未充分报告的内容**：
  - 未详细分析不同α、gmin超参数设置对性能的影响（敏感性分析不足）。

- **无训练方法的普遍局限**：依赖历史匹配的草拟方法在冷启动（无历史）阶段无法发挥作用。
