## 摘要
LLM服务引擎在启动时一次性确定其键值（KV）缓存的大小，永久性地为最坏情况的预填充激活预留一部分内存。在解码主导的阶段，该预留内存处于空闲状态，但它不能交给KV池，因为它正是大型预填充所需的内存。我们询问该预留内存是否可回收，并构建了一个机制来测试它。我们的弹性KV缓存在解码期间将预留内存借给KV池，并在预填充之前归还，由调度器对下一批次的提前一步视图驱动。它在CUDA虚拟内存路径上实现为纯用户空间：每层将两个物理句柄映射到一个连续的虚拟范围，因此注意力内核保持不变，且无需驱动程序补丁。它在几毫秒内解除提交，并在几十毫秒内重新提交，支持CUDA图和前缀缓存，并且从不触发内存不足事件。相同内存的静态提交是不安全的，会在预填充突发时崩溃，这使得动态切换成为必要。在构建了该机制之后，我们测试了它所依据的前提，并报告了一个诚实的负面结果。只有在小的预填充块大小严重损害预填充延迟时，它才有意义。在将长提示注入实时解码负载的受控实验中，这种惩罚很小（中位首次令牌时间在8192和32768个令牌的块大小之间相差约1%），因为预填充受计算限制，而解码每步每个序列仅消耗约一个令牌。仅仅降低max_num_batched_tokens就能比控制器恢复更多的KV，且延迟几乎相同。预留内存在张量并行下也会稀释，从TP1时KV的16%降至TP4时的2.7%。我们精确地说明了回收预留内存仍然可能有帮助的情况，并将该机制作为可重用的用户空间弹性VMM分配器发布。

## Abstract
An LLM serving engine sizes its key-value (KV) cache once, at startup, permanently setting aside a reserve for the worst-case prefill activation. During decode-dominant phases that reserve sits idle, yet it cannot be handed to the KV pool because it is exactly the memory a large prefill needs. We ask whether this reserve is reclaimable, and build a mechanism to test it. Our elastic KV cache lends the reserve to the KV pool during decode and returns it before prefill, driven by the scheduler's one-step-ahead view of the next batch. It is pure userspace on the CUDA virtual-memory path: two physical handles mapped into one contiguous virtual range per layer, so the attention kernel is unchanged and no driver patch is required. It decommits in a few milliseconds and recommits in tens of milliseconds, works with CUDA graphs and prefix caching, and never triggers an out-of-memory event. A static commit of the same memory is unsafe, crashing on prefill bursts, which makes the dynamic toggle necessary.   Having built the mechanism, we test the premise it rests on and report an honest negative result. It only pays off if a small prefill chunk size badly hurts prefill latency. In a controlled experiment injecting long prompts into a live decode load, that penalty is small (median time-to-first-token differs by about 1% between chunk sizes of 8192 and 32768 tokens), because prefill is compute bound and decode consumes only about one token per sequence per step. Simply lowering max_num_batched_tokens recovers more KV than the controller does, at nearly equal latency. The reserve also dilutes under tensor parallelism, from 16% of KV at TP1 to 2.7% at TP4. We state precisely when reclaiming the reserve could still help, and release the mechanism as a reusable userspace elastic-VMM allocator.

## 1. 核心问题与整体含义（研究动机和背景）

- LLM 服务引擎（如 vLLM）在启动时一次性确定 KV 缓存大小：将 GPU 内存划分为模型权重、CUDA 图池、激活工作集和 KV 缓存。
- 引擎为了应对**最坏情况的大规模预填充（prefill）**，会永久性地预留一部分激活内存（prefill-activation reserve）。在解码（decode）主导的阶段，这块预留完全闲置，但因它是未来大预填充所需的内存，不能交给 KV 池。
- 这种"预留闲置 + KV 稀缺"并存的现象构成了一个看似有价值的优化机会：**能否在解码阶段把预留内存借给 KV 缓存，待大预填充来临前再归还？**
- 论文的核心追求是：构建一个可工作的弹性 KV 缓存机制来回收这块预留，并严格检验该机制所依赖的前提是否成立。
- 论文最终给出一个**诚实的负面结果**：机制本身体现了很高的工程水准且是必要的（静态回收不安全），但它试图回收的内存实际上并不值得回收——因为 vLLM 的 chunked prefill（分块预填充）已经弥合了"预填充吞吐 vs KV 容量"之间的权衡。

## 2. 论文提出的方法论

### 核心思想
- 将预填充激活预留视作一种"可弹性借用"的资源：**解码阶段借给 KV 池，预填充边界前归还**。
- 由调度器利用其"提前一步看到下一批次"的能力，决定何时提交（commit）和解除提交（decommit）弹性内存。

### 关键技术细节
- **连续性约束**：vLLM 的 KV 缓存是每层一个连续张量，FlashAttention 内核通过单个基址按块 ID 索引。任何弹性方案必须保持每层虚拟地址连续，否则需要改内核。
- **CUDA VMM 方案（核心机制）**：
  - 使用 `cuMemCreate`、`cuMemMap`、`cuMemAddressReserve` 等 CUDA 虚拟内存 API；
  - 每层预留一个虚拟地址范围，用**两个物理句柄**（base handle + elastic handle）映射到同一虚拟范围；
  - 基础句柄始终映射，弹性句柄只映射/取消映射虚拟范围顶部的一个子区间（2 MiB 对齐）；
  - 注意力内核、驱动均无需修改，纯用户态实现。
- **切换成本**：完整 3 GiB 预留（28 层）的解除提交约 3.8 ms，重新提交约 23.8 ms（对比朴素 whole-handle commit 约 180 ms），远小于解码阶段持续时间。
- **控制器逻辑**：
  - 调度器提前一步判断下一 batch 是否含 prefill；
  - decode-only 阶段提交弹性切片，扩大 `num_gpu_blocks` 并放行顶部弹性块；
  - prefill 边界前先排空相关块、同步、再解除映射；
  - 加入滞后（hysteresis）避免抖动。
- **已知 bug 与修复**：大预填充后首次重新提交会出现 OOM，原因是 torch caching allocator 持有已释放的预填充内存；调用 `empty_cache()` 可解决。
- **配套机制**：通过 torch pluggable allocator 透明支撑 KV 张量，并通过 block-pool gate 控制弹性块的分配。

## 6. 论文的主要结论与发现

1. **机制有效**：弹性 KV 缓存可在毫秒级切换预留内存，保持内核不变、驱动不变，支持 CUDA graphs 与 prefix caching，全程零 OOM。
2. **机制必要**：静态承诺（statically commit）同样的 3 GiB 内存是**不安全**的——在 62K-token 预填充突发上必然 OOM；只有动态切换能安全捕获全部预留。
3. **核心负面结果**：小 chunk 对 TTFT 的损害极小。chunk 8192 vs 32768 的中位 TTFT 仅差约 1%（4.97 s vs 4.91 s），远低于预期中的数倍差距。
4. **原因结构性**：prefill 是计算密集型的，chunked prefill 只是将相同总计算量拆分成更多步骤；decode 每步每序列仅消耗约 1 个 token，几乎不挤占 prefill 预算（280 tokens vs 8192 的 chunk 预算，约 3%）。
5. **更优解决方案已存在**：直接降低 `max_num_batched_tokens` 就能以几乎相同的延迟回收更多 KV 容量（375K tokens），优于弹性控制器（最多 364K）。
6. **TP 稀释**：预留占 KV 的比例从 TP1 的 16% 降至 TP4 的 2.7%；大模型必然需要高 TP，因此弹性回收在大模型场景下收益甚微。
7. **适用条件极窄**：可能有利的场景需要"小 chunk 严重抑制 prefill 吞吐 + KV 稀缺"同时成立，作者在测试硬件上未能构造出该条件。

- **硬件与模型覆盖过窄**：仅 A100-40GB 单卡 + Qwen2.5-7B，未在 H100、多卡集群、更大模型（如 70B/405B）上实测。

- **应用局限**：论文结论"降低 chunk size 即可"依赖预填充为计算密集这一前提，未来若注意力机制/推理架构发生改变（如线性注意力、稀疏注意力），该结论可能需要重新验证。
