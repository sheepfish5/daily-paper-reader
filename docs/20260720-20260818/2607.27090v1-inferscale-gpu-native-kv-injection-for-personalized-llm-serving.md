## 摘要
大型语言模型越来越多地部署带有持久化个性化上下文，例如累积的记忆档案或长对话历史，这些内容在用户的众多请求中共享。生产级记忆系统（如Mem0、MemGPT和Zep）会检索相关子集并将其注入提示中，迫使推理引擎反复预填充相同内容。随着检索预算的增长，即使底层记忆在请求间复用，首词元延迟（TTFT）也会增加。我们提出了InferScale，一个GPU原生的LLM记忆系统，用可复用的KV状态替代重复的提示预填充。InferScale预计算每条记忆事实的KV表示，将其与语义嵌入一同存储在GPU上，在服务时检索相关事实，并将其KV直接注入vLLM的分页缓存中。为了支持旋转位置嵌入下动态组合的记忆，我们引入了分块RoPE（Chunked RoPE），它在旋转前存储键，并在注入时应用服务时的位置。然而，独立编码记忆事实会丢失联合预填充时可用的跨事实上下文。我们通过上下文窗口编码（Context-Window Encoding）缓解这一问题，该编码将每条记忆事实与其前面的一小段对话上下文一同编码，而仅缓存目标事实的KV。InferScale通过vLLM的KV连接器接口实现，既不需要修改引擎，也不需要微调模型。在LoCoMo上的三个开放权重模型上，随着检索预算的增加，InferScale使TTFT几乎保持恒定：在k=50时，TTFT降低72-79%（3.6-4.8倍），准确率达到60.3%，而Mem0在无服务时重算的情况下为63.3%，并且在并发负载下提供3.7-4.5倍的吞吐量。因此，可复用的KV状态将记忆条件下的服务延迟与检索上下文大小解耦，同时保持应用质量。

## Abstract
Large language models are increasingly deployed with persistent personalized context, such as accumulated memory profiles or long conversation histories, that is shared across a user's many requests. Production memory systems (e.g., Mem0, MemGPT, and Zep) retrieve a relevant subset of this memory and inject it into the prompt, forcing the serving engine to repeatedly prefill the same content. As the retrieval budget grows, time-to-first-token (TTFT) increases even though the underlying memory is reused across requests.   We present InferScale, a GPU-native LLM memory system that replaces repeated prompt prefilling with reusable KV state. InferScale precomputes each memory fact's KV representation, stores it alongside a semantic embedding on the GPU, retrieves relevant facts at serving time, and injects their KV directly into vLLM's paged cache. To support dynamically assembled memories under rotary position embeddings, we introduce Chunked RoPE, which stores keys before rotation and applies their serving-time positions during injection. However, encoding memory facts independently omits the cross-fact context available during joint prefilling. We mitigate this with Context-Window Encoding, which encodes each memory fact together with a small window of preceding conversation context while caching only the target fact's KV.   InferScale is implemented through vLLM's KV-connector interface, requiring neither engine modifications nor model fine-tuning. Across three open-weight models on LoCoMo, InferScale keeps TTFT nearly constant as the retrieval budget increases: at k=50 it reduces TTFT by 72-79% (3.6-4.8x), achieves 60.3% accuracy versus 63.3% for Mem0 without serving-time recomputation, and delivers 3.7-4.5x the throughput under concurrent load. Reusable KV state thus decouples memory-conditioned serving latency from retrieved-context size while preserving application quality.

## 论文核心信息总结

### 1. 核心问题与整体含义（研究动机和背景）

- **研究背景**：生产级 LLM 记忆系统（如 Mem0、MemGPT/Letta、Zep）在服务用户请求时，需要检索用户相关记忆子集并将其作为**提示文本**注入，迫使推理引擎反复预填充相同的内容。
- **核心问题**：
  - 重复预填充导致**首字延迟（TTFT）随检索预算增长**，即使被检索出的记忆在不断复用。
  - 现有 KV 复用技术（如前缀缓存）假设复用 token 在提示中占据固定位置，而记忆系统是动态组装不同子集，因此不适用。
- **关键洞察**：在因果注意力下，**静态记忆事实的 KV 表示仅取决于事实本身，与未来的查询无关**；KV 可以在同一请求上被反复复用，而无需在每次请求时重新预填充。
- **整体含义**：可将“条件化”动作从 token 层迁移到 **attention 层**，将可复用 KV 直接注入分页缓存，从而解耦 **记忆条件服务延迟与检索上下文大小**，且理论上对输出分布精确等价。

### 2. 提出的方法论

#### 核心思想
- 提出 **KV Injection（KV 注入）**：不再将记忆作为 prompt 文本输入，而是把记忆事实的 KV 表示直接注入到 vLLM 分页 KV cache 中；每个事实预先编码一次，在多个请求中复用。
- 理论上：将每次请求的注意力计算从 `O((m+q)²)` 降为 `O(q(m+q))`，消去每个请求反复支付的 `O(m²)` 项。

#### 核心技术一：Chunked RoPE（分块 RoPE）
- **问题**：检索到的事实往往放在与原编码时不同的位置上，RoPE 将位置编码在 key 中，直接复用 KV 会产生错误注意力分数。
- **方案**：在旋转位置编码之前存储 keys，注入时按服务位置重新施转。
- **结论**：因 RoPE 的相对位置特性，事实可以编码一次、注入到任意 prompt 位置，并保持与 prompt 注入位置相同的注意力分数。

#### 核心技术二：Context-Window Encoding（上下文窗口编码）
- **问题**：独立编码事实会丢失相邻事实间的交互上下文，损害下游事实检索效果。
- **方案**：离线阶段将每个事实与其之前的若干对话轮次一起编码，但只缓存该事实本身的 KV。
- **优点**：保留本地上下文以恢复词义，同时保持事实独立可检索、可重用；上下文信息不参与服务时重复预填充。

#### 系统实现
- 在 GPU 上同时维护两套索引（共享 fact_id）：**Jasper 向量索引**（语义嵌入近邻搜索）与 **pre-RoPE KV 存储**（条件化模型注意力）。
- 基于 **vLLM KV-connector 接口**实现为插件：调度端声明“外部已有 KV”以跳过预填充，worker 端用内存复制将组合 KV 块复制到已分配的页 block 上，然后只预填充 query。
- 要求：**无引擎改动、无模型微调、无检索管线变更**。

### 3. 实验设计

- **数据集与基准**：LoCoMo 长对话 QA 基准，使用 10 会话子集，排除 adversarial/unanswerable 后包含 1,540 个可回答 QA 对（多跳、时序、开放域、单跳四类）。
- **对比方法**：Mem0（生产基线，Qdrant CPU 向量库 + Prompt 注入 + 每请求预填充）；同时对比 Jasper（GPU），以隔离向量后端的影响。
- **模型**：三款 7-8B 开放权重模型作主要评测，另加 Qwen3-14B 验证规模化鲁棒性。
- **主要变量**：检索预算 `k∈{5,10,20,50}`，编码窗口 `w∈{0,5,20,50}`（以对话轮次计，w=0 表示孤立编码）。
- **评测指标**：vLLM 引擎 TTFT、端到端 query-to-first-token、查询吞吐（QPS）、判断式准确率（LLM judge）、预处理时间、GPU 存储开销、CPU 卸载开销及经验等价性测试。

### 4. 资源与算力

- **硬件**：单台 NVIDIA RTX PRO 6000 Blackwell Server Edition，96GB GDDR7，峰值带宽 1597GB/s，PCIe 5.0 x16（峰值读取 64GB/s）。
- **软件**：vLLM v0.19.1，KV cache 为 bfloat16、16-token 页大小；未涉及多 GPU 或模型训练。
- **算力说明**：论文未明确给出 GPU 数量与训练时长；训练部分不相关（无微调，模型原样使用）。离线预处理（KV 编码）成本以“每会话秒数”列出，Llama-3.1-8B 全会话范围 38.91s（w=0）到 206.45s（w=50），属一次性成本。

### 5. 实验数量与充分性

- **实验规模**：覆盖 3 个主模型 ×4 个 k ×4 个 w（延迟/准确率/吞吐），另加一 14B 模型；附录对 GPU/CPU KV 存储、逐类准确率、全量延迟等给出了完整数据。
- **实验类别**：延迟对比、准确率对比、吞吐对比、GPU 内存占用、CPU 卸载、向量后端消融、经验等价性测试（9 用户×2 类查询）、位置独立性测试（表 20）。
- **充分性评价**：实验较全面、控制变量较充分（统一嵌入、原样使用模型、前缀缓存默认开启保证 Mem0 处最优情形），等效性测量在 bf16 非确定性下预期内出现少量偏差且可解释。
- **存在不足**：仅在 LoCoMo 单基准上评估，覆盖场景较窄；内存占用实验仅测单会话规模；多跳推理仍明显低于 prompt 注入上限；准确率曲线在三模型上的 w 取值并不完全一致，受离线预处理开销约束。

### 6. 主要结论与发现

- **延迟**：在 Llama-3.1-8B 上，k=50 时引擎 TTFT 仅从 16.6ms 增至 17.3ms（+4%），而 Mem0 从 33.2ms 增至 68.3ms（+106%）；TTFT 降低 72-79%（3.6-4.8×）。
- **吞吐**：100 并发用户时，InferScale 达到 100-135 QPS，Mem0 为 23-32 QPS，加速 3.7-4.5×，且吞吐与并发近似线性增长。
- **准确率**：w=0 时性能随 k 增长而退化；w≥20 时准确率恢复，k=50 时 Llama 上 60.3% vs Mem0 63.3%；小 k 时多数情况下可与 Mem0 持平或略超。
- **有效性与扩展**：模型规模更大时优势更强（Qwen3-14B 上 TTFT 5.0× 下降、端到端升 2.9×）；KV 存储可卸载至 CPU，TTFT 仅增加约 3ms 且吞吐不受损。
- **理论支撑**：KV 注入对联合编码上下文是精确等价（定理 3）；Chunked RoPE 对位置重定位保持精确（定理 6）；Context-Window Encoding 保存因果上下文（定理 8）。

### 7. 优点

- **理论牢固**：给出 KV 注入与 prompt 注入在因果解码器上精确等价的证明，机制本身非近似；仅因独立事实编码引入可量化近似。
- **工程落地好**：以 vLLM KV-connector 插件实现，不需要引擎修改、不依赖模型微调，保持与现有检索管线兼容。
- **可推广**：可扩展至 RAG、系统提示、工具描述等任何静态上下文反复条件化的场景。
- **设计合理**：检索/条件化双空间分离，以共享 fact_id 桥接；离线-在线分离使记忆编码仅付一次成本；CPU 卸载设计延长 GPU 容量瓶颈。

### 8. 不足与局限

- **准确率上限受制**：跨事实联合预填充仍是质量上限，多跳问题在 k=50 时差距可达 16 个百分点；InferScale 未完全消除独立编码的信息损失。
- **内存容量压力**：每会话 GPU KV 存储高达 1.8-4.8GB，显著限制单 GPU 可同时驻留用户数；虽可采用 CPU 卸载但引入每次请求数十毫秒延迟。
- **离线预处理成本**：上下文窗口越大离线编码耗时越长（最大 206s/会话），对频繁变化的动态记忆场景不利。
- **评测覆盖单一**：仅 LoCoMo 单基准、单一 GPU、7-8B 统一大小（14B 为补充测试），未充分验证多节点、多 GPU 或更大规模模型。
- **内存占用报告粒度粗**：正文仅报告平均每会话占用，未对不同 k、w 下内存变化给出明细。
