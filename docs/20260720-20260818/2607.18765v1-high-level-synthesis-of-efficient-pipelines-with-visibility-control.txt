# High-Level Synthesis of Efficient Pipelines with Visibility Control 

JUNGIN RHEE, KAIST, Korea 

MINSEONG JANG, KAIST, Korea 

JAEWOO KIM, Seoul National University, Korea 

JEEHOON KANG, FuriosaAI, Korea High-level synthesis (HLS) raises the abstraction of hardware design from concurrent register-transfer level (RTL) programs to sequential programs. Among the forms of parallelism HLS exploits, pipelining demands fine-grained control over pipeline structure and hazard resolution to achieve competitive power, performance, and area (PPA). However, existing tools either lack such control or sacrifice sequential semantics to provide it. We present an HLS tool that embeds fine-grained pipeline control in a sequential programming model, enabling rapid design-space exploration. The tool builds on visibility control , a novel programming abstraction that unifies hazard resolution strategies including stalling, bypassing, speculation, deferred commit, and register renaming. We evaluate on in-order RISC-V cores, histograms, and an AES accelerator. On RISC-V cores, we implement stall, bypass, speculation, and register renaming; on histograms, we implement scheduling strategies that previously required RTL or concurrent programming models. Compiled pipelines outperform HLS tools with sequential semantics and achieve PPA comparable to hand-written RTL. 

1 Introduction 

High-level synthesis (HLS) makes hardware design productive by automatically pipelining sequen-tial programs, overlapping successive operations. The tool absorbs the concurrency this overlap introduces, so the designer writes and reasons about a program with purely sequential semantics. How a given program is pipelined, which we call the pipelining strategy , determines a design’s power, performance, and area (PPA) through two decisions, creating a tradeoff space where no single strategy dominates. (1) The pipeline structure , the number of stages and their boundaries, fixes how deeply operations overlap. Adding stages shortens the critical path and raises clock frequency, but costs pipeline registers, area, and power. (2) Dependency hazard resolution keeps the pipeline correct when overlapping execution breaks a sequential dependency on shared state. Hazard resolution strategies span stalling, bypassing, speculation, deferred commit, and register renaming. Choosing a more aggressive strategy removes stalls and raises throughput, but costs area and power and can lower frequency. The Pareto-optimal choice depends on the program’s characteristics, the target workload, and the PPA budget. The designer must navigate the PPA tradeoff by exploring strategies, yet no existing HLS tool provides the three properties this exploration requires (Table 1a): (1) fine-grained control over the pipelining strategy, to express diverse candidate strategies, (2) efficient implementation , so that each explored strategy attains the PPA of hand-written RTL, and (3) sequential semantics , so that switching strategies cannot introduce concurrency bugs. Traditional HLS tools [16, 22, 23] keep sequential semantics but give up fine-grained control over the pipelining strategy. The compiler places stage boundaries, steered at most by indirect hints such as initiation intervals [1], and decides how each hazard is resolved either statically [23] or dynamically [16, 22]. Kanagawa [30] delivers fine-grained control over hazard resolution and an efficient implementa-tion but gives up sequential semantics. Designers manually manage concurrent accesses to shared state, choosing hazard resolution along four dimensions (Table 1b): (1) per-state resolution , where

This expressiveness pairs with an efficient implementation, since resolution is ordinary user code compiled with the whole design. However, that same code runs under concurrent semantics, so every rewrite for strategy exploration risks introducing concurrency bugs. PDL [38, 42] aims for all three properties, but falls short of each because it fragments hazard resolution across disjoint subsystems (§2.3). (1) It cannot express strategies that compose the four dimensions of Table 1b, such as per-address speculation, in which an instruction rolls back when the address it speculatively read is later written. (2) It cannot implement even expressible strategies efficiently, since each subsystem lowers to a conservative, hand-written RTL module in isolation. (3) Its guarantee of sequential semantics is fragile , resting on 18 code rules, many of them path-sensitive, that govern each subsystem and their interactions. The rules are onerous , since the designer must satisfy them by hand to pass the compiler, and unsound , since rule-compliant programs can still produce incorrectly synchronized pipelines. As a result of the expressiveness and implementation shortfalls, PDL-generated CPUs run 1 .2–1 .5× slower and consume 1 .8–4 .1×

more area than RTL designs (§7.1). 

Our approach . We present an HLS tool that delivers all three properties at once, enabling rapid pipelining strategy exploration (Table 1a). The key enabler is visibility control , a unified program-ming abstraction for hazard resolution. We make the following contributions. In §3, we introduce visibility control, which distills each hazard resolution strategy into two choices: what an earlier instruction exposes of its pending reads and writes on shared state, and how a later instruction reacts. Under stalling, for example, the earlier instruction that writes to the shared state (the writer) exposes nothing, and the later instruction that reads it (the reader) waits. Under bypassing, the writer exposes its value early, and the reader forwards it. 3

In §4, we instantiate visibility control in a sequential programming model that gives fine-grained control over the pipelining strategy. We base our model on speculative loop pipelining, where each iteration overlaps with subsequent iterations (§4.1). We resolve dependency hazards via Var , a unified primitive for visibility control (§4.2). We capture advisory state (e.g. , a branch predictor), which affects performance but not correctness, via SpecVar , a primitive that needs no hazard resolution (§4.3). In §5, we formalize the semantics of the target pipeline and sketch a proof of compiler correctness, stating that the pipeline refines the source program. In §6, we show how the compiler implements the chosen hazard resolution strategy efficiently. It factors the program-order comparison between in-flight instructions into one mechanism shared by every Var . It specializes each Var ’s hazard resolution to the pipelining strategy, generating only the necessary registers and combinational logic. In §7, we show across three case studies that the three properties let us explore pipelining strategies and thereby achieve competitive PPA. Our designs outperform those from sequential-semantics HLS tools (PDL, Vitis HLS, Dynamatic), and match or exceed hand-written RTL and Kanagawa designs, both built under concurrent semantics. On in-order RISC-V CPUs targeting a 7nm ASIC flow [37], our designs achieve 1 .2–1 .8× lower runtime and 1 .7–3 .9× smaller area than PDL’s. They match hand-written RTL in cycle count and maximum frequency, staying within 5% in area and 3% in power. On countif histograms, our designs match or exceed Kanagawa’s PPA across static, dynamic, and speculative hazard resolution strategies. On an AES accelerator, viewing the design as a sequential program surfaces two optimizations that reduce area over an RTL reference. In the supplementary material [2], we provide the appendix and artifact. 2 Background and Motivation 

We review dependency hazards and their resolution strategies (§2.1) and examine how PDL [42], the closest existing approach to our goals, implements a 5-stage CPU (§2.2). We then identify three shortcomings that motivate our design: inexpressible resolution strategies, inefficient strategy implementation, and a fragile guarantee of sequential semantics (§2.3). 

2.1 Dependency Hazards 

Dependency hazards arise when pipelined execution reorders operations on shared state, e.g. , the register file, program counter (PC), or control and status registers (CSRs) of a CPU. They violate sequential semantics in three forms: Read-After-Write (RAW) reads state before an earlier write commits, Write-After-Write (WAW) commits a write before an earlier one, leaving a stale value, and Write-After-Read (WAR) commits a write before an earlier read finishes. The simplest resolution strategy is to stall the pipeline until the hazard clears. However, stalling reduces throughput, motivating more aggressive strategies. RAW hazards can be resolved by: (1) bypassing , where the writer forwards its result to the reader before committing, at the cost of additional multiplexers and wiring, and (2) speculation , where the reader proceeds with a predicted value and recovers if the prediction is wrong, at the cost of recovery logic. A representative application of speculation is resolving CPU control hazards (RAW on the PC) by predicting the next PC and flushing the pipeline on misprediction. 2.2 PDL: Pipeline Structure and Hazard Resolution 

In PDL [42], the designer writes the datapath pipeline and obtains every other feature, such as hazard resolution, as an external service. Each service runs as a separate subsystem, and the datapath pipeline uses it by sending requests to its interface. New concerns attach as additional subsystems. For example, XPDL [38], a follow-up work, adds exceptions. PDL realizes this model in the 5-stage pipelined CPU of Fig. 1. The program (Fig. 1a) describes the datapath pipeline, and the compiler connects it to the subsystems PDL provides (Fig. 1b). 

Datapath pipeline . The datapath pipeline is the part the designer writes directly, by (1) designating the pipeline structure, (2) writing the combinational logic of each stage, and (3) sending requests to the subsystems. It is written as a recursive function cpu (Fig. 1a), parameterized by the program counter ( pc ) and the shared resources it accesses: the register file ( rf ), instruction/data memory (imem /dmem ), CSRs ( csrs ), and the branch history table ( bht ). The pipeline structure is designated by two constructs. The stage separators ( ---, L4, 11, 18, 24) mark the boundaries at which the compiler inserts pipeline registers. The recursive call cpu(npc) (L17) spawns a new instruction that runs concurrently from L2, overlapping the spawner’s remaining stages. Statements in a single stage are combinational, e.g. , computing the ALU result and the branch target (L13–14). The remaining statements are requests to the subsystems, such as the register file read request (L7). 5

We describe the three subsystems in turn: hazard locks (guarding memories such as rf and dmem ), speculation (drawing predictions from bht ), and exceptions (manipulating csrs ). 

Hazard locks . PDL resolves dependency hazards as resource contention using hazard locks . A lock tracks accesses at address granularity within its memory, e.g. , individual registers in the register file. Each access follows a three-operation protocol: (1) reserve records access intent in program order, 

(2) block stalls until the access is granted, after which a read or write executes, and (3) release 

commits the result to the shared state and frees the lock. For a given address, block grants access in 

reserve order. PDL provides multiple lock libraries written in RTL for distinct resolution strategies: Queue Lock (stall), Bypass Queue (bypassing), and Renaming Register File (register renaming). The protocol resolves a RAW hazard by serializing the concurrent accesses. For example, consider two back-to-back instructions where the first writes r1 and the second reads r1 . The read lock is acquire d in Decode (L7), where acquire is a shorthand combining reserve and block in the same stage. The write lock access is split across stages: reserve (L10) records the write intent in 

Decode , block (L25) defers the actual stall to Writeback , and release (L26) commits the write. Since the first instruction reserve s its write before the second acquire s its read, the acquire 

stalls until the first instruction’s access to the address is finished. 

Speculation . PDL provides a separate speculation API that coordinates instructions through a 

speculation table , an automatically instantiated shared resource tracking in-flight instructions’ speculative status. An instruction can spawn a speculative successor with a predicted PC using 

spec_call (L6), creating an entry in the speculation table. The prediction comes from an integrated RTL branch predictor, queried by bht.req (L6) for whether the branch is taken. In Execute , the branch is resolved and the spawner writes the result to the table. verify (L16) compares the predicted and the resolved value, marking the entry as killed on mismatch or committed otherwise, and bht.upd (L16) updates the predictor with the outcome. invalidate and call (L17) kill the entry and spawn the correct successor. The spawned instruction, in turn, reads the speculation table to learn whether it is killed. 

spec_check (L2, 5) terminates the instruction without blocking if its entry is killed, gating lock reservation and further speculative calls. spec_barrier (L12) blocks until the entry resolves, then terminates the instruction if killed, gating write-lock release. Both gates prevent a killed instruction from corrupting locks and the speculation table. 

Exceptions . Exceptions are handled in two final blocks that follow the pipeline body. The commit 

block (L26) executes on the normal path, releasing the write lock. The except block (L27–30) handles the exceptional path, calling abort (L28) to release the lock without committing, saving exception state to CSRs (L28–29), and redirecting to the exception handler via call (L30). 

2.3 Limitations of PDL 

The interfaces that keep PDL’s subsystems modular also keep them fragmented. This fragmentation makes PDL fall short of all three properties of Table 1a. The expressiveness and implementation shortfalls make PDL-generated CPUs run 1 .2–1 .5× slower and consume 1 .8–4 .1× more area than RTL designs (§1). The fragile guarantee of sequential semantics shifts the correctness burden onto the designer. 

Inexpressible resolution strategies . PDL cannot express strategies that compose the four dimen-sions of Table 1b, because it isolates speculation in a separate function-call subsystem: (1) per-state resolution : spec_call bundles all speculative arguments into an atomically verified entry, so a misprediction on one argument forces recovery on all others, (2) resolution policy : PDL cannot mix stall or bypass with speculation on one state, since hazard locks and the speculation API are 6 Trovato et al. 

separate subsystems, (3) per-address resolution : PDL speculation cannot distinguish addresses, since 

spec_call cannot express indexing, and (4) selectable observation stage : PDL pins the predicted value at spawn time, since spec_call(value) takes the prediction as a call argument. 

Inefficient strategy implementation . Even expressible strategies compile inefficiently, since each subsystem becomes a hand-written RTL module unaware of the others and of the pipeline structure. Specifically, the following overheads occur in the CPU of Fig. 1a: (1) four redundant ordering systems (three locks and a speculation module), each tracking program order and adding per-instruction metadata as pipeline registers, and (2) unnecessary order comparison, since systems rely on runtime comparators even when the program order can be statically determined from pipeline structure, e.g. , an instruction in Decode necessarily precedes one in Writeback . These overheads preclude using locks even for simple stall-only state, forcing XPDL to implement CSRs via exceptions. 1

Fragile guarantee of sequential semantics . PDL’s guarantee of sequential semantics is fragile, because each subsystem is correct only under static rules its interface assumes, 2 and the rules are both onerous and unsound: (1) The rules are onerous, both numerous and manual (§B.1). Eighteen rules, counted across PDL and XPDL, span per-subsystem constraints ( e.g. , reserve of a memory may occur inside at most one branch) and cross-subsystem interactions ( e.g. , speculative instructions must never release write locks). Many of the rules are path-sensitive ones that PDL’s compiler checks with an SMT solver, so a violated rule rarely admits a local fix. Each rejection therefore returns to the designer, who must restructure the pipeline’s control flow by hand. Moreover, the rule count compounds with every subsystem added. XPDL’s exceptions arrive as a third subsystem, and integrating them contributed more rules, such as the except block releasing all acquired locks. 

(2) The rule set is unsound (§B.2). For instance, two conditional release operations placed in different pipeline stages can commit out of order, producing a WAW hazard that the rules fail to reject. 

3 Hazard Resolution as Visibility Control 

We distill the hazard resolution strategies of §2.1 into a unified programming abstraction we call 

visibility control . We proceed in three steps: (§3.1) building intuition on three example pipelines, whose instructions resolve hazards by controlling when their pending effects become visible to later instructions, (§3.2) defining the abstraction, and (§3.3) implementing each strategy as code against that abstraction. Visibility control targets dependency hazards within a single pipeline, whatever shared state they arise on. 3 Stalling, bypassing, speculation, and deferred commit each arise from visibility control on a single shared state, and renaming arises from composing it on several states (§4.2).

3.2 Visibility Control as a Programming Abstraction 

Visibility control models the shared state that in-flight instructions load and store, together with the operations by which each instruction publishes its pending effects and observes those of earlier instructions. The shared state splits into a base state and per-instruction published states. The base state is the underlying storage that instructions ultimately commit to, e.g. , the register file and the program counter. 4 The published states expose each instruction’s pending stores and loads to later instructions, as LD did step by step in Fig. 2a.

4 Programming Dataflow Pipelines with Visibility Control 

We instantiate visibility control (§3) in a sequential programming model for dataflow pipelines. The model gives the designer control over both axes of the pipelining strategy (Table 1a), pipeline structure and hazard resolution. Whichever strategy is selected, the compiled pipeline refines the source program, preserving its sequential behavior (§5). The model comprises three abstractions: (§4.1) speculative loop pipelining controls the pipeline structure, mapping each loop to a pipeline whose internal stages are set by PDL [42]’s separators, (§4.2) the wrapper type Var controls hazard resolution per variable by instantiating visibility control, and (§4.3) the wrapper type SpecVar complements speculative loop pipelining and Var for advisory state, such as a branch history table (BHT) accessed freely from multiple stages. 

Source program . We realize the programming model in Rust, taking a program as specification and compiling it into a pipeline. Although the proposed abstractions are language-agnostic, Rust offers two advantages: an advanced type system that enforces state-transition rules (Fig. 3b), and rich testing frameworks that verify the source program. Target pipeline . We target a dynamically scheduled dataflow pipeline whose stage executions are governed by a latency-insensitive protocol [6]. The pipeline consists of stages, each a set of combinational operations, separated by pipeline registers. To model the flow of work through the stages, we use the standard token abstraction of dataflow circuits [22]. A token represents one dynamic instance of an execution and carries its in-flight values, advancing through pipeline registers in order. 

4.1 Speculative Loop Pipelining 

We compile each source loop into a pipeline that issues up to one token per cycle, each token executing one iteration. Figure 4b illustrates the token flow of the pipeline compiled from Fig. 4a. When token P reaches the loop head (step 1), it remains there as the parent token and issues one 

subtoken per iteration (step 2). Subtokens inherit the program order of their iterations: token 𝑖 

precedes token 𝑗 iff 𝑖 < 𝑗 . (We generalize program order to nested loops in §5.) We adopt PDL’s structural mapping to compile the loop body, making pipeline structure directly controllable through source changes. The pipeline separators sep() (Fig. 4a, L7, L13, L16, and L19) map to pipeline registers (step 3), and the if branch (L9–18) maps to a demultiplexer at the branch entry and a multiplexer at the join. The branch join enforces in-order exit : tokens leave the join in program order, so 4 stalls until the earlier 2 and 3 exit (step 4). The loop pipelining is speculative because token 𝑖 can start before the pipeline knows that source iteration 𝑖 exists. If an earlier token terminates the loop, the pipeline flushes all later tokens (step 5) because their iterations do not occur in the source execution. The compiler makes this flush safe by forcing each flushable token to stall before any irreversible action. After the flush, parent token P

leaves the loop head (step 6).

4.3 Programming Advisory State with SpecVar 

We introduce SpecVar<T> for advisory state. Its load returns an arbitrary value and its store is a no-op. This deliberately weak contract lets us compile SpecVar to a shared storage that tokens access without hazard resolution. Figure 11 illustrates dynamic branch prediction with a BHT using SpecVar . Each token predicts whether the next branch will be taken based on the BHT state in SpecVar (L7) and updates it with the actual outcome (L16). Correctness is independent of the arbitrary value returned by bht.load() .If the prediction matches the outcome ( br_taken == pred_taken ), the PC assigned at L9 is already correct. Otherwise, the token overwrites it with correct_pc (L12–14).

5.3 Correctness Proof Sketch 

We provide an informal correctness proof sketch that the formalized pipeline behavior refines the source semantics up to base-state commits. For a source program 𝑆 , let [[ 𝑆 ]] Rust be the source Rust semantics, Π the compiled pipeline from 𝑆 , and [[ Π]] Pipe be the semantics defined by the transitive closure of Π’s cycle-level transitions. The compiler maps 𝑆 to Π structurally; ordinary computations map to comb segments, visibility operations map to the corresponding segments, and source sequencing, conditionals, and loops map to 𝑃 1; 𝑃 2, if (𝑥, 𝑃 t, 𝑃 f ), and loop (𝑇 ?, 𝑛, 𝑃 ). The correctness condition is the refinement [[ Π]] Pipe ⊑ [[ 𝑆 ]] Rust : every sequence of committed Var 

base-state updates produced by [[ Π]] Pipe is permitted by [[ 𝑆 ]] Rust .The proof establishes the refinement by simultaneous induction over loop iterations. The in-duction maintains three properties. First, each load and a value-producing try_load in a live token with loop index 𝐿 returns the same value as iteration 𝐿 of [[ 𝑆 ]] Rust . Second, each live token with loop index 𝐿 stores and seals the same slot contents as iteration 𝐿 of [[ 𝑆 ]] Rust . Third, each base-storage location has a time 𝑡 , itself a loop index, such that the stored value equals the value after iteration 𝑡 of [[ 𝑆 ]] Rust . If a live token with loop index 𝐿 may later commit a slot to that location, 20 Trovato et al.

then 𝑡 ≺𝑃 𝐿 . If a token with loop index 𝐿 has already committed a slot to that location, then 𝑡 is no earlier than 𝐿 in program order. The load rules prove the first property from the other two properties. The Load-Stall rule blocks a token while an earlier token may still publish an unsealed write to the loaded address. The Load-Bypass rule therefore returns the latest preceding sealed slot at the address, which the second property identifies with the latest visible write in [[ 𝑆 ]] Rust . The Load-Direct rule applies when no preceding token can provide such a sealed slot, and the third property then identifies the base-storage value with the latest committed write before loop index 𝐿 . The try_load operation follows the same argument when it returns a value, and its empty result is permitted by the source semantics. The ordinary computation rules prove the second property from the first property. Apart from shared-variable operations, [[ Π]] Pipe and [[ 𝑆 ]] Rust use the same expression semantics. Equal loaded values therefore produce equal local computations, and equal local computations produce the same 

store and seal slot contents. The drop rules prove the third property. The Drop-Stall rule delays a token while an earlier token may still load, declare, or write a location whose commit could change the required base-storage time. The Drop-Ok rule commits sealed slots only after those earlier hazards are resolved, so assigning the current token’s loop index as the new time preserves the ordering conditions for every remaining live token. The composite segment rules preserve the control-flow order used by the three properties. Conditionals route each token through the branch selected by its token-local guard and join branch outputs in program order. Loops may issue subtokens before the corresponding source iterations are known to execute, but a break flushes the excluded subtokens before they can commit a Var update. Speculative loads fit the same induction because 𝑆 spec records every address read speculatively, and a later conflicting store prevents the affected token from reaching drop .

6.1 Program-Order Analysis 

The program-order analysis tracks program order with one runtime mechanism shared by every site that queries it, and decides the order at compile time wherever possible. In a naive implementation, every token would carry its loop index through the pipeline registers, and every query site would instantiate a dynamic comparator. The query sites comprise the Var accesses, the branch joins enforcing in-order exit, and the break s (§5.2). Since all these sites query one relation, the program order of tokens, one loop index per token serves them all. The tree structure of the loop indices then settles most of these queries at compile time. Figure 16b visualizes the tokens of Fig. 16a as a tree, whose edges connect each parent token to its subtokens. On this tree, deciding the lexicographic program order ≺𝑃 (§5.1) reduces to two local checks: for loop indices 𝐿 1 and 𝐿 2, 𝐿 1 ≺𝑃 𝐿 2 holds exactly when (1) 𝐿 1 is a proper prefix of 𝐿 2 (an ancestor, e.g. , [2] ≺𝑃 [2,1] ), or (2) the indices first diverge at some depth with 𝐿 1’s entry smaller ( e.g. , [2,2] ≺𝑃 [3] ). Two structural rules statically decide ≺𝑃 for most pairs of positions , the sep() s and loop heads where a token can reside across cycles: (1) a token in a loop head precedes any token within that loop’s body, by the ancestor relationship ( e.g. , [2] in the loop head ℎ2 of Fig. 16a precedes [2,_] ), and (2) a token 𝑇 1 precedes 𝑇 2 if 𝑇 1’s position is reachable from 𝑇 2’s and outside the body of the loop whose head 𝑇 2 occupies, since in-order exit (§4.1) preserves entry order across branches ( e.g. , [2,1] 

precedes [2,2] in Fig. 16a). For the remaining pairs, the compiler synthesizes a comparator only for the closest common loop , the innermost loop enclosing both positions. Since the pair’s indices agree above the closest common loop and first diverge at its depth, the comparator examines only the entries at that depth ( e.g. , comparing [2,2] and [3] reduces to 2 < 3 at depth 1). Statically decided comparisons allow the compiler to eliminate the unused loop indices from the pipeline registers. For the 5-stage pipelined CPU of Fig. 7, the two rules decide ≺𝑃 for every pair of positions, so the analysis eliminates all comparators and loop indices (Fig. 17). 

6.2 State-Reachability Analysis 

The state-reachability analysis specializes each hazard-resolution network to the published states reachable under the pipelining strategy. In a naive implementation, every token would carry the full published state 𝑆 pub of every Var through the pipeline registers, and every network would branch on all published states. Since every visibility operation executes at a fixed stage, most components of 𝑆 pub are statically known at each position. The compiler prunes each token’s 𝑆 pub to the components whose value at its position is not statically known, shrinking the pipeline registers that carry them. Specialized against the statically known components, each network collapses from the case analysis of Fig. 15 into fixed wires and bypass multiplexers. The compiler emits flush logic only for Var s whose 𝑆 spec can reach Speculative .For the 5-stage pipelined CPU, the only published-state component left at run time is rf ’s 𝑆 batch ,and its network collapses to bypass multiplexers (Fig. 17). pc ’s 𝑆 spec is statically Speculative (0),since every read observes the tentative value at address 0, pc ’s only element. No register carries 

𝑆 spec , and only the flush logic remains. The predicted value itself is written to pc ’s storage register by an eager tentative commit (§C.2).

7.3 AES Cipher Accelerator 

To evaluate our tool on non-pipelined designs, we implement an AES cipher accelerator supporting both 128- and 256-bit keys. We compare against the SecWorks AES core [32], a widely used 1,844-LOC open-source Verilog implementation. Both designs target an Artix 7 FPGA, synthesized with AMD Vivado 2025.1.1. 

Productivity . Productivity manifests in two forms: less code and surfaced optimizations. First, our implementation requires only 0 .30 × the LOC of the reference while preserving the sequential algorithmic flow (key expansion to encryption and decryption), whereas the reference defines operation order implicitly through concurrent module connections. Second, viewing the design as sequential code surfaces optimization opportunities. We identify and apply two such optimizations: 

(1) the encryption and decryption paths are mutually exclusive (an if /else branch in the source), enabling deduplication of shared states, (2) the program always initializes key memory before use (via an element-wise store loop), allowing us to eliminate redundant initialization logic.

8 Related and Future Work 

Table 5 compares our work against prior hardware design languages on their support for task-level (TLP), data-level (DLP), and instruction-level (ILP) parallelism, with the support classified into the following levels, ordered from the strongest to the weakest: ( ✓) declarative , where the designer specifies a high-level policy and the tool implements the underlying mechanism efficiently, (G#) partial , where the declarative interface cannot express every policy, ( Ó) automated , where the compiler infers both policy and mechanism, ( ✍) manual , where the designer implements the low-level mechanism directly, and ( ✗) no support .The declarative level separates the policy from the mechanism. The designer navigates the PPA tradeoffs by adjusting the policy, while the tool keeps the mechanism correct and efficient. Automated inference is most valuable on top of that separation ( ✓, Ó), exploring the policy space for the designer. The three intermediate levels each break the separation. A partial interface covers only some policies and reverts to manual implementation for the rest. Automated inference alone becomes a leaky abstraction, because the designer has no policy to adjust when the generated RTL is suboptimal. Manual implementation shifts the whole mechanism onto the designer. Task-level parallelism (TLP) . TLP concerns the concurrent execution of independent tasks. Prior HLS research supports it along a spectrum, from declarative constructs ( ✓) such as map-reduce streaming, communicating sequential processes, and async functions [8, 15, 17, 19, 23, 24, 30, 33, 41], down to automatic extraction or tuning of the parallelism ( Ó) [11, 16, 22–24, 39, 40]. 

Data-level parallelism (DLP) . DLP requires expressing parallel computation and defining a memory architecture that supplies data to the functional units. For the computation, HLS tools provide unrolling directives ( ✓) [8, 23, 27, 30, 33], map-reduce streaming ( ✓) [11, 17, 19, 24], and explicitly parallel constructs ( ✓) [15, 28], with automated design space exploration on top ( Ó) [11, 24, 39, 40]. For the memory architecture, they provide banking directives ( ✓) [8, 23, 24, 27, 33] and automated design space exploration ( Ó) [11, 24, 39, 40]. 

Instruction-level parallelism (ILP) . HLS tools with sequential semantics offer at most automated dependency hazard resolution. The majority provide no support at all ( ✗) [8, 23, 27, 33, 39, 40]. Dynamic HLS tools [16, 22] resolve hazards at runtime ( Ó), but they fix the pipeline structure and choose the resolution strategy, leaving the designer no control. SpecHLS [16] supports neither dynamic bypassing nor per-address stalling and cannot integrate branch predictors. Dynamatic [22] implements a load-store queue (LSQ) [20] and control speculation [21] as isolated subsystems. The isolation blocks store-to-load forwarding through the LSQ under speculation. Manual approaches ( ✍) give the designer full control over the pipelining strategy, at the cost of hand-implemented hazard resolution. At the base, HDLs [3, 10, 18] expose the cycle-level FSM directly. Several abstractions reduce the burden. Streaming and message-passing HDLs [15, 17, 19] simplify dataflow composition with latency-insensitive interfaces. Guarded-atomic-action languages [5, 9, 29] discharge rule-level conflicts through one-rule-at-a-time semantics. Timing-aware HDLs [28, 41] rule out structural and timing hazards through a type system. Kanagawa [30] 26 Trovato et al. 

programs each resolution strategy as ordinary user code in a shared-memory concurrent model. None of these abstractions automatically addresses dependency hazards on mutable shared state. PDL [38, 42] uniquely aims at declarative hazard resolution from a sequential program, but achieves it only partially ( G#). Fragmented into disjoint subsystems for hazard locks and speculation, it leaves composed strategies inexpressible, expressible strategies inefficiently implemented, and the guarantee of sequential semantics fragile (§2.3). 

Future work . We are mechanizing the proof sketch of §5. We are also developing advanced CPUs [7, 43], AI accelerators [14], and network accelerators [13, 25] as further case studies. These workloads demand TLP and DLP, and several [7, 13, 14, 25] further demand reordered execution of tokens. We are extending the model accordingly, integrating TLP and DLP from the prior literature and designing a disciplined concurrency that relaxes the in-order execution while preserving sequential reasoning.

B PDL’s Sequential Semantics 

This section provides detailed evidence for the fragility of PDL’s sequential semantics guarantee. We first enumerate the 18 rules that PDL and XPDL together impose on the programmer to preserve refinement between the pipeline and its sequential specification (§B.1), then demonstrate that this rule set is unsound (§B.2). 

B.1 Rules 

The sequential semantics guarantee of PDL and XPDL rests on 18 rules: 8 per-subsystem rules and 10 cross-subsystem interaction rules, of which the 8 rules governing the except and commit blocks arrive with XPDL’s exceptions. We enumerate these rules below, then show that they are unsound. The rules keep PDL’s own terminology, in which an in-flight instruction (§2.2) is called a thread. 

Per-subsystem rules . PDL defines the following rules for using each subsystem independently: 

(1) On every program path, each thread either spawns a single child thread (via a recursive call 

or verify statement) or terminates by output ting a value. 

(2) On every program path, every speculative call is eventually resolved via a verify statement. 

(3) On every program path, hazard locks must be used in the correct state-transition sequence of 

reserve , block , read/write, and release .

(4) All reserve operations must occur in “in-order stages”, which are the stages where threads are guaranteed to pass in their program order. 

(5) All release operations for write locks must occur in “in-order stages”. 

(6) All reserve operations for a hazard lock must execute atomically. That is, succeeding instruc-tions’ reserve operations should stall until the preceding instruction’s reserve operation completes. PDL provides lock region construct to group multiple reserve operations into a critical section that executes atomically. 

(7) A verify can only be called after spec_barrier() .

(8) A speccall requires prior execution of either spec_check() in the current pipeline stage or a 

spec_barrier() .

Cross-subsystem interaction rules . Because hazard locks, speculation, and exceptions are inde-pendent subsystems, their joint use requires 10 additional rules: 

(1) A reserve requires the prior execution of either spec_check() in the current pipeline stage or a spec_barrier() .

(2) release on write locks can be called after spec_barrier() .

(3) An instruction must release the lock before exiting the except block. 

(4) Reads are forbidden from asynchronous memory or other pipelines at the end of the except 

block. 

(5) A recursive call statement can only be in the last stage of the except block. 31 

(6) spec_check , spec_barrier , and spec_call statements are not allowed within the except or 

commit blocks. 

(7) Users must call spec_barrier before except or commit blocks. 

(8) Users can not call speccall within the except or commit blocks. 

(9) Write locks acquired in the pipeline body must be release d within the commit block and not before. 

(10) No stateful operations are allowed in the commit block, with the exception of calling release to a lock. Stateful operations include spawning new instructions, acquiring locks, and speculation-related operations. 

B.2 Unsoundness 

PDL’s refinement guarantee between the pipeline and its sequential specification is unsound, in that a rule-compliant program accepted by the compiler can still produce a pipeline with incorrect hazard resolution. Fig. 18a illustrates a PDL program exhibiting a WAW hazard that originates from two conditional 

release operations. Specifically, a thread with pc = 1 executes its release at L29, while the preceding thread with pc = 0 executes its release at L37. The multiple pipeline stages separating these two release operations cause the thread with pc = 0 to release the lock and commit its pc 

after the thread with pc = 1, violating program order. Because the PDL rules only verify whether each release statement is placed within in-order stages, this problematic code is not rejected. The execution trace in Fig. 18b confirms the violation. The “Release Start” for pc = 1 (line 1) executes before the “Release Start” for pc = 0 (line 3). Consequently, “Result is: 0000000” shows that the final result is 0, whereas the result from the sequential specification should be 1. 

C Compiler Implementation 

Our compiler translates Rust’s Mid-level Intermediate Representation (MIR) to synthesizable Verilog, targeting the Rust subset of §4. 

C.1 Overview 

A Rust function annotated with #[synthesize] is compiled into RTL in two phases. 

Phase 1: MIR to Structured IR . The compiler lifts the function’s MIR control-flow graph into a 

structured IR (SIR), a DAG in which control-flow constructs (loops and branches) are first-class nodes, analogous to the MLIR scf dialect [36]. SIR makes the nesting structure of loops and branches explicit, which the second phase exploits for pipeline generation and the program-order analysis of §6.1. 

Phase 2: SIR to Verilog . The compiler lowers SIR into two kinds of Verilog modules. The main pipeline module contains pipeline registers, branch demux/mux logic, and subpipelines generated from loops. Each instantiated Var is emitted as a dedicated module that encapsulates internal state registers and its hazard-resolution network (§6). The network authorizes or stalls load /drop 

requests and flushes speculative tokens when necessary, following the visibility-control policy of Fig. 3.

C.2 Optimizations 

Beyond the two analyses of §6, the compiler applies the following additional optimizations: (1) Lo-cal-memory minimization. Only live variables are stored as token-local memory, reducing the register footprint at sep() and loop boundaries. (2) Loop-index minimization. The compiler com-putes the maximum number of concurrent tokens per loop and sizes loop-index fields to the 33 

minimum required bitwidth. (3) Logic minimization. Standard hardware optimizations (common– subexpression elimination, copy propagation, constant folding, and mux/boolean simplification) are applied to the generated Verilog. 

Eager tentative commit . When a Var satisfies four conditions, the compiler can write tentative values directly to base state on store instead of carrying them in the token’s 𝑆 batch , and subsequent reads become plain base-state accesses rather than bypass scans: (1) Speculative reads only. Every inter-token read is a spec_load ; no conservative load accesses the Var . (2) Read-before-write ordering. The spec_load point precedes or equals the store point in the pipeline structure, so a preceding token always completes its read before any succeeding token writes. (3) Single address. All reads and writes target the same element. A flush triggered by a store corrects exactly the address that was speculatively read; with multiple addresses, a store at one address would leave other addresses contaminated. (4) Sole eager-commit Var . No other Var in the same loop pipeline uses this optimization. A flush corrects only the triggering Var ’s shared state; a second eager-commit 

Var would retain stale values from flushed tokens, and re-issued tokens reading those stale values would propagate the corruption through their own computations. The flush mechanism recovers from misspeculation because the very store that triggers the flush also writes the correct value to the sole shared-storage location, so re-issued tokens observe the corrected state. For pc in the 5-stage CPU (Fig. 7), all four conditions hold: every read is spec_load , the 

spec_load in Fetch precedes or shares a stage with every store (the prediction in Fetch, and corrections at the same or later stages such as Execute), pc is Var<T, 1> with a single element, and pc is the only speculative Var . The optimization eliminates pipeline registers for pc ’s 𝑆 batch ,the bypass multiplexer, and the rest of the hazard-resolution network. store writes the predicted next PC directly to a shared register and spec_load reads it, matching the standard RTL practice where each instruction updates the PC register in place. The optimization does not apply to rf ,whose later instructions use conservative load and therefore require Sealed -state bypass with stall-on-Tentative semantics. 

D Extended RISC-V Evaluation 

This section supplements §7.1 with per-benchmark CPI breakdowns (Table 6a) and same-frequency synthesis comparisons (Table 6b), followed by an analysis of the sources of PDL’s overhead. 

Sources of PDL overhead . Table 6b provides a same-frequency comparison between PDL’s 5-stage RISC-V CPU and ours under various configurations. This comparison is unfavorable to our design, as ours additionally supports exceptions and the Zicsr ISA extension, which PDL’s design lacks. When targeting PDL’s clock speeds, our processor uses 42–48% less area and 44–50% less power across the rv32i configurations. The gap instantiates the two implementation overheads of §2.3. First, PDL’s subsystems are four redundant ordering systems, each adding per-instruction metadata as pipeline registers. The speculation subsystem additionally maintains its speculation table because a speculative instruction keeps executing until it voluntarily checks its status at spec_check or 

spec_barrier (§2.2). Second, PDL performs unnecessary order comparison. Each lock compiles to a hand-written RTL module unaware of the pipeline structure, so it tracks the program order of all in-flight instructions with runtime comparators for priority calculation and arbitration. Our program-order analysis (§6.1) instead decides program order statically wherever possible.
