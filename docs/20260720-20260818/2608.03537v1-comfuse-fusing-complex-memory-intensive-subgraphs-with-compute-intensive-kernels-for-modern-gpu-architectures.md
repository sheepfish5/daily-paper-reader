## 摘要
现代深度学习工作负载日益包含异构计算图，这些图将计算密集型算子与内存密集型子图结合在一起。现有的深度学习编译器通常分别优化这些算子类别，产生刚性的融合边界，限制了跨算子优化和片上数据重用。我们观察到，下游内存密集型操作可以与计算密集型算子并发执行，从而将其执行隐藏在计算之后；然而，自动利用这一机会带来了新的编译挑战。在本文中，我们提出了 ComFuse，一个自动化的 GPU 编译系统，采用一种新颖的算子融合策略，为包含计算密集型算子和依赖丰富、内存密集型的逐元素归约子图的复杂图结构生成高性能内核。ComFuse 进一步支持背靠背 GEMM（B2BGEMM）模式的融合，将其适用性扩展到更复杂的计算-内存交互模式。此外，它自动将高层张量子程序降级为优化的融合内核，减少了对手动内核工程的需求。实验结果表明，ComFuse 生成的融合内核在 post-norm 工作负载和各种复杂计算场景中优于 TorchInductor 生成的内核，同时支持更灵活的融合模式。

## Abstract
Modern deep learning workloads increasingly comprise heterogeneous computation graphs that combine compute-intensive operators with memory-intensive subgraphs. Existing deep learning compilers typically optimize these operator classes separately, creating rigid fusion boundaries that limit cross-operator optimization and on-chip data reuse. We observe that downstream memory-intensive operations can execute concurrently with compute-intensive operators, allowing their execution to be hidden behind computation; however, automatically exploiting this opportunity poses new compilation challenges.   In this paper, we present ComFuse, an automated GPU compilation system that employs a novel operator fusion strategy to generate high-performance kernels for complex graph structures comprising compute-intensive operators and dependency-rich, memory-intensive elementwise-reduction subgraphs. ComFuse further supports the fusion of back-to-back GEMM (B2BGEMM) patterns, extending its applicability to more complex compute-memory interaction patterns. Additionally, it automatically lowers high-level tensor subprograms into optimized fused kernels, reducing the need for manual kernel engineering. Experimental results show that the fused kernels generated by ComFuse outperform those produced by TorchInductor across post-norm workloads and various complex computation scenarios, while supporting more flexible fusion patterns.

## 一、论文的核心问题与整体含义

**研究动机与背景**：
- 现代深度学习工作负载（如推荐模型、大语言模型）的计算图日益复杂，通常混合了**计算密集型算子**（如 MatMul）与**内存密集型算子**（如 ElementWise、Reduction）。
- 现有深度学习编译器（如 XLA、TVM、TensorRT 等）通常将这两类算子**分开优化**，在它们之间维持明确的“实例化边界”（materialization boundary）。
- 该边界导致 MatMul 的中间结果必须写入全局内存（GMEM），再由下游内存密集型算子重新加载，形成了“片上 → 片外 → 片上”的往返数据移动，造成大量内存带宽浪费，损失了中间值的片上时间局部性。

**核心问题**：
- 如何**消除计算密集型算子与内存密集型算子之间的数据边界**，实现联合融合（joint compute-memory fusion），从而：
  1. 让下游算子直接在片上消费 MatMul 输出，减少 GMEM 流量、最大化片上数据重用；
  2. 利用两类算子对硬件资源需求的互补性（Tensor Core vs. CUDA Core），将内存密集型处理**隐藏在张量核心计算之后**。

**整体含义**：
- 论文提出 **ComFuse**，一个自动化 GPU 编译系统，可自动将“计算密集型算子 + 依赖丰富的内存密集子图”融合为高性能内核，并进一步支持背靠背 GEMM（B2BGEMM）等复杂结构的融合。

## 二、方法论：核心思想与关键技术细节

### 1. 核心观察与总体思路
- 论文观察到：大多数 epilogue 归约只沿一个逻辑维度聚合数据，因此**同步边界局限于局部 tile 子集**，而非整个张量。
- 利用现代 GPU（Hopper/Blackwell）的 **Thread Block Clusters** 与 **Distributed Shared Memory (DSMEM)**，可在片上跨 CTA 边界直接交换中间值。

### 2. Stage-Stream Execution Model

**基本结构**：
- 以 Reduction 运算为**阶段边界**，将完整的内存密集子图分解为多个顺序执行的 DAG（有向无环图）。
- 每个 DAG 对应一个执行阶段（Stage），阶段内进行局部的 ElementWise 与 Reduction；阶段间通过归约结果与旁路中间数据连接。

**阶段内计算（Intra-DAG computation）**：
- 每个阶段 DAG 执行分两个阶段：**细粒度计算（compute phase）** 与 **tile 级归约（reduce phase）**。
- 在 compute 阶段，数据以 **Fragment**（单条向量化指令能处理的最大元素组）为粒度沿依赖边传播。
- 归约节点会拦截数据流：先做线程内聚合，再进入归约阶段。

**三层归约方案（Three-level Reduction）**：
1. **intra-warp**：通过寄存器级 butterfly shuffle 完成；
2. **intra-warp-group**：通过共享内存（SMEM）完成；
3. **inter-CTA**：沿逻辑归约维度进行跨 CTA 聚合。

**dual-mode 自适应聚合策略**：
- 参与 CTA 数（CN）**较少**时：采用 **peer-to-peer 跨广播策略**，各 CTA 通过 DSMEM 做去中心化的 all-to-all 广播，独立完成最终聚合。
- CN **较多**时：切换为 **leader-follower 聚合策略**，由一个 leader CTA 集中聚合，避免 DSMEM 拥塞。

**两个关键设计**：
- **跨 CTA 数据布局一致性**：不同 CTA 中相同 ID 的线程持有相同的逻辑行，通信端点直接使用统一索引规则解释 DSMEM 数据，消除重排/编码开销。
- **TMA 使能的批量数据移动**：使用 Tensor Memory Accelerator（TMA）指令在 DSMEM 地址间进行直接批量传输，降低指令开销、最大化带宽利用率。

**阶段间链接（Inter-DAG chaining）**：
- 每个阶段的终端 Reduction 节点不仅完成聚合，还负责管理后续 DAG（PostOp）的生命周期，驱动其 compute 与 reduce 阶段。
- 归约结果被广播以匹配 tile 维度，再分解为 Fragment 输入下一阶段。
- **SMEM 缓冲复用**：由于多阶段 DAG 顺序执行、任一时刻至多一个归约节点使用 SMEM 缓冲，ComFuse 将缓冲空间复杂度从 O(L) 降为 O(1)（L 为归约节点总数），支持任意数量的归约运算而不线性增加片上存储开销。
- **旁路数据通路**：相邻阶段间可传递可复用的中间结果（如 LayerNorm 中先算 x = α·Acc + Bias，后续阶段还要用 x − mean），避免重复计算。

**流水线调度（Pipeline Schedule）**：
- 采用 **PingPong Pipeline** 策略：一个 CTA 执行一个 tile 的 MainLoop（MatMul 核心计算）时，同时处理另一个 tile 的 Epilogue。
- 通过跨 tile 交错 MainLoop 与 Epilogue，在理想条件下将 Epilogue 延迟隐藏在 MainLoop 之后。

### 3. B2BGEMM 融合范式

**问题定义**：
公式化表示为：P = XW₁, S = F(P), O = SW₂，其中 F(·) 为中间内存密集操作。

**主要挑战**：
- GEMM1 的 tile 产出粒度与 GEMM2 的 tile 消费粒度不匹配：生产 GEMM2 的一个输出 tile 需要沿收缩维度 N₁ 跨越多个连续中间 tile 做点积累加。

**Cluster 协作数据流调度（Cluster-cooperative dataflow scheduling）**：
- GEMM1 阶段：沿中间矩阵 P 的输出空间划分工作负载，每个 CTA 计算一个本地 tile P_tile；Epilogue 通过 Stage-Stream Model 融合，生成 S_tile = F(P_tile)。
- S_tile 严格驻留在线程寄存器中，完全不经过 SMEM 或 GMEM 写回。
- GEMM2 阶段：集群内各 CTA 利用寄存器驻留的 S_tile 与预加载的 W2 权重 tile 计算部分累加 O_tile⁽ᶜ⁾ = S_tile⁽ᶜ⁾ · W2_tile⁽ᶜ⁾，最终在全局内存提交时聚合为完整输出 tile：O_tile = Σ_c O_tile⁽ᶜ⁾。

**Producer Warp Group**：
- 将 MatMul1 和 MatMul2 所需的 SMEM 缓冲**统一复用**：由于 W1_tile 与 W2_tile 需要相同的 SMEM 缓冲结构，ComFuse 用 MatMul1 的缓冲配置构建统一的多级循环 SMEM 缓冲，交替加载 X_tile、W1_tile 和 W2_tile，SMEM 开销保持在单个 MatMul 的量级。

**Consumer Warp Group**：
- 将执行流程重构为**四阶段流水线**：ML1 → Epi1 → ML2 → Epi2。
- 同一 CTA 内不同的 Consumer Warp Group 按此四阶段调度交错一个流水线阶段执行。

### 4. ComFuse 编译实现

- 基于 CUTLASS 实现，引入新的 **StreamReduction** 节点原语：
  SR Node = ⟨PostOp, ReduceOp, ReduceMode, K⟩。
- 编译流程为两步同态映射：**G_epi →(Φ) S →(Ψ) T**。
  - Φ：前端映射，将算子节点系统化为 Fusion Spec IR（五元组 S = ⟨N, E, τ, A, C⟩）。
  - Ψ：后端映射，将 IR 结构化展开为对应的 CUTLASS EVT 模板实例化。
- **归约子图切分**：遇到归约节点时递归构造嵌套 IR，通过回溯归约节点的原始输入数据，自然表达 LayerNorm、RMSNorm、Softmax 等模式，无需模式特定配方。
- **闭包性质**：Φ 域外的算子回退到标准编译路径，保证语义不丢失。

## 三、实验设计

### 1. 实验环境
- Python 3.10.19 + PyTorch 2.5.1 + CUDA 12.4
- 使用 CUDA Graphs 消除 host 端内核启动开销
- 50 次 warm-up + 500 次正式测量，取平均

### 2. 对比基线
- **TorchInductor**：PyTorch 2.0 默认编译器后端，启用了静态形状编译和 max-autotune。
- **TensorRT 10.3.0**：NVIDIA 高性能推理引擎，作为强工业基线；工作负载先导出为 ONNX 图再编译。

### 3. Stage-Stream 执行模型评估（三个代表性模式）
- **MBR**（MatMul-BiasAdd-RMSNorm）：相对简单的基于归约的内存密集 epilogue。
- **MBLR**（MatMul-BiasAdd-LayerNorm-ReLU）：线形变换 + 归一化 + 非线性激活。
- **MSTS**（MatMul-Scale-TanhSoftcap-Softmax）：注意力分数归一化，涉及非线性变换和计算密集的 Softmax 归约。

  ✦ 矩阵规模：MN=(8192, 512)、(8192, 1024)、(32768, 512)、(32768, 1024) × Batch Size ∈ {1, 4, 8, 16}。

### 4. B2BGEMM 融合评估（三个工作负载）
- **Self-Attention**（SeqLen=512, HeadDim=128）— Transformer 模型的密集注意力。
- **Target-Attention**（TargetLen=4096, SourceLen=256）— 非对称注意力。
- **DLRM Bottom MLP**（FeatureDim: 1024→512→128）— 推荐模型的连续矩阵乘法。

  ✦ Batch L（batch length）∈ {1, 8, 16, 32, 64, 128}，HeadNum ∈ {4, 8}。

### 5. 评价指标
- 端到端执行时间（相对 TorchInductor 归一化）。
- **Residual time** = Time(Total) − Time(MatMul)，用于隔离联合优化对内存密集子图的实际收益。

## 六、主要结论与发现

1. **ComFuse 在 Stage-Stream 场景中全面优于 TorchInductor**：在 MBR、MBLR、MSTS 三个模式下分别平均加速 1.08×、1.09×、1.07×，最高达 1.24×。
2. **与 TensorRT 相比具有竞争力**：在多数场景中实现相当或更好的性能。
3. **Residual-time 分析显示融合收益显著**：在较大 batch 下，内存密集子图可获得最高达 **9.93×** 的加速（MSTS 模式），说明 MatMul 执行能有效隐藏 epilogue 计算。
4. **B2BGEMM 融合效果显著**：Target-Attention 最高加速 1.97×，DLRM Bottom MLP 最高 1.23×，接近或达到 TensorRT 水平。
5. **小规模场景下融合收益受限**：当每个 CTA 分配的 tile 数量较少时，流水线无法进入稳态，调度开销占比较高，融合优势减弱。
6. **局限性的重要发现**：在 Self-Attention 场景中，TorchInductor 匹配到 FlashAttention 算子库，性能最佳；ComFuse 因 MatMul 与 Softmax 工作负载失衡而存在差距。这表明**融合并非总是最优**，需要根据算子特征、硬件异构性和流水线平衡进行自适应选择。

## 八、不足与局限

1. **对计算密集型算子本身的优化不足**：论文自承“缺乏针对计算密集型算子的更精细优化策略”，在特定工作负载下与最优基线仍有性能差距。

## 九、总体评价与启示

**理论贡献层面**：
- 论文不是对某一固定融合模式的事后修补，而是提出了一种以“归约节点为阶段边界”的统一融合抽象——Stage-Stream Execution Model，将计算密集算子与任意深度、任意多层归约的内存密集子图纳入同一套执行与调度框架。
- 该抽象揭示了计算密集与内存密集算子间“实例化边界”的成因及其消除路径，为深度学习编译器在 Hopper/Blackwell 时代如何利用 Thread Block Cluster 与 DSMEM 协同调度提供了新的设计范式。

**工程价值层面**：
- 基于 CUTLASS 的原型实现表明方案具备真实硬件上的落地能力；
- SMEM 缓冲 O(L)→O(1) 复用、dual-mode 自适应聚合、Producer/Consumer Warp Group 分工等具体设计务实且可复用，对同类系统（如融合注意力、融合规范化、MoE 内核）具有直接借鉴意义；
- 编译前端采用同态映射与闭包回退机制，使系统在扩展新算子时无须破坏已有优化路径，具备良好的可维护性与可扩展性。

**研究启示层面**：
1. **融合并非无条件最优**：Self-Attention 场景中 TorchInductor + FlashAttention 优于 ComFuse 的结果提示，融合编译系统应将“保持算子边界”视为一种合法的调度选项，并依据流水线平衡度、tile 数量与通信代价做自适应决策；
2. **跨 CTA 片上通信（Cluster/DSMEM）是消除全局内存边界的有效替代路径**，该思路有望推广至卷积、GNN、稀疏算子等更多领域；
3. **评价指标方法论值得推广**：residual-time 分析将端到端收益拆解为 “MatMul 本身变快”与“epilogue 被有效隐藏”两个来源，为融合优化类论文提供了更精细的归因手段。

**总体判定**：
这是一篇技术含量较高、方案系统完整、且有清晰实证数据支撑的编译系统论文。其核心思想（以归约为边界的联合融合、依赖分布式共享内存的跨 CTA 归约）具有明确的学术价值与工程实用价值。主要局限集中在实验完备性——缺少消融实验、未报告 GPU 型号、缺乏跨架构验证与最新系统对比——使得部分结论的普适性和归因精度受到一定限制。但综合来看，ComFuse 在问题定位、方案设计与实验方法上均达到高水平，值得被编译器与高性能计算社区重点关注。
