## 摘要
Top-k稀疏注意力使得长上下文大语言模型解码的计算成本低廉：每一步仅读取几千个选定的KV条目，而不是整个上下文。然而，服务系统通常将整个KV缓存保留在GPU HBM中，以便每个位置保持可选，因此请求的内存开销仍随其完整上下文长度增长——解码在计算耗尽之前很久就遇到容量墙，而KV缓存超过HBM的上下文根本无法服务。我们提出了HiSparse，一种用于稀疏注意力服务的精确、与索引器无关的层次化KV缓存。HiSparse将每个请求的完整KV历史保存在主机内存中，并通过小型固定大小的GPU缓存限制其解码占用空间；一个融合的CUDA内核在解码CUDA图内解决每一层的选择——命中检测、LRU替换和主机到设备的获取；并且，对于跨层共享选择的模型，精确的逐层预取隐藏了大约一半的剩余未命中开销。因为只有KV放置发生变化，所以模型输出保持不变。HiSparse已合并到上游SGLang中，并在H200、B200和GH200平台上对三种稀疏注意力系列（DSA、NSA和Quest）进行了评估：在长上下文工作负载上，它可将峰值生成吞吐量提高至4.7倍，同时保持可比的每令牌延迟，并在高负载下减少首令牌时间——而且一个无I/O的参考基准表明，解析机制本身不会增加可衡量的每令牌成本，使得主机-设备IO成为有界驻留的唯一代价。

## Abstract
Top-k sparse attention makes long-context LLM decoding cheap to compute: each step reads only a few thousand selected KV entries rather than the full context. Serving systems, however, typically keep the entire KV cache in GPU HBM so that every position stays selectable, so a request's memory bill still grows with its full context length--decoding hits a capacity wall long before it runs out of compute, and a context whose KV cache exceeds HBM cannot be served at all. We present HiSparse, an exact, indexer-agnostic hierarchical KV cache for sparse-attention serving. HiSparse keeps each request's full KV history in host memory and bounds its decode footprint with a small, fixed-size GPU cache; a fused CUDA kernel resolves each layer's selections--hit detection, LRU replacement, and host-to-device fetches--inside the decode CUDA graph; and, for models that share selections across layers, exact layer-wise prefetching hides roughly half of the remaining miss overhead. Because only KV placement changes, model outputs are unchanged. HiSparse is merged into upstream SGLang and evaluated across three sparse-attention families (DSA, NSA, and Quest) on H200, B200, and GH200 platforms: it improves peak generation throughput by up to 4.7x on long-context workloads while preserving comparable per-token latency and reducing time-to-first-token at high load--and a no-IO oracle shows the resolution mechanism itself adds no measurable per-token cost, leaving host-device IO as the only price of bounded residency.

## 一、论文的核心问题与整体含义

- **背景与动机**：Top-k 稀疏注意力（如 DSA、NSA、Quest）使得长上下文 LLM 解码的计算开销大幅降低——每步只读取 k 个被选中的 KV 条目。然而，现有服务系统为了“任何位置都可能被未来选中”，仍然将完整 KV 缓存常驻 GPU HBM，导致单请求内存开销随完整上下文长度线性增长。
- **核心问题**：解码过程在计算资源耗尽之前，先被 GPU 显存容量卡住，即“容量墙”（capacity wall）。当 KV 缓存超过 HBM 时，长上下文请求甚至无法被服务。这意味着稀疏注意力降低了计算成本，却没有降低内存成本的一字节。
- **论文含义**：HiSparse 通过“将逻辑可用性与物理驻留解耦”来突破容量墙：完整 KV 保存在主机内存，GPU 只保留固定大小的热点缓存，从而让长上下文稀疏解码吞吐不再受 GPU HBM 容量限制，同时不改变模型输出。

## 二、方法论

- **核心思想**：构建一个精确（exact）、与索引器无关（indexer-agnostic）的两级 KV 层次结构：
  - **主机 KV 池（Host KV Pool）**：保存每个活跃请求的完整、权威 KV 历史，使用 pinned DRAM。
  - **GPU 缓存（Hot Device Buffer）**：每个请求、每一层只保留最多 B 个逻辑位置对应的 KV 记录槽位；B 为配置参数且 B ≥ k，与上下文长度无关。
- **关键设计组件**：
  1. **页表与 LRU 元数据**：维护“逻辑位置 → GPU 槽位/仅主机”的映射；每次解码步后更新 LRU 顺序，命中条目提升到 MRU 端，未命中新取条目排在命中后，以保留多次复用条目。
  2. **融合 Miss-Resolution 内核（RESOLVE）**：一个 CUDA kernel 完成五个阶段：
     - 将选中位置装入 shared-memory 哈希表；
     - 并行探测所有 GPU cache 槽位，标记命中/可驱逐；
     - 并行扫描选择 victim 并更新 LRU；
     - 通过 GPU-assisted IO（`ld.global.nc.v2.b64`，直接向量化非一致性 load）从 pinned host 内存批量获取缺失 KV；
     - 更新页表并输出与 top-k 顺序对齐的物理槽位向量 `top_k_device_locs`。
  3. **解码 CUDA 图集成**：RESOLVE 被捕获在 SGLang 稳态解码 CUDA graph 中，避免多次 launch 延迟。
  4. **写穿透（Write-through）**：新生成 token 的 KV 直接写入 GPU cache 保留槽，再由后台流异步写回主机池，保证后续 fetch 可用。
  5. **精确逐层预取（Exact Prefetch）**：针对跨层共享索引选择的模型（如 GLM-5.2 的 IndexShare），锚层（anchor layer）发出选择后，即可提前知道其共享层的选择位置；RESOLVE 记录“miss plan”，由 side stream 的 copy-only kernel 预取到共享层缓存，共享层跳过解析直接等待事件，从而将 IO 与中间层计算重叠。
  6. **索引器无关接口**：只消费每个请求每层输出的“逻辑位置集合”，不关心 DSA/NSA/Quest 如何生成选择，因此无需重训练或改模型。
- **有界内存占用**：解码侧 KV 内存为 `N_batch · N_layers · B · W_KV · s`，而不是 `N_batch · N_layers · L_ctx · W_KV · s`。例如 GLM-5.1 在 128K 上下文、B=4096 时，每请求从 13.09 GB 降至约 0.4 GB（约 30 倍压缩）。

## 六、论文的主要结论

- **吞吐增益**：HiSparse 通过有界 GPU 驻留大幅提升长上下文解码吞吐：
  - GLM-5.1（DSA，8×H200）：32K 输入吞吐提升 3.1×，160K 提升 2.9×；
  - Qwen3+Quest（GH200）：32K 提升 3.6×，200K 提升 4.7×；
  - DeepSeek-V4-Flash（NSA，2×B200，32K）：端到端提升 2.1×，decode-only 提升 2.9×；
  - GLM-5.2（IndexShare，8×H200，32K）：峰值吞吐从 618 提升到 1727 tokens/s（2.8×），带预取时达到无 IO oracle 上限的 85%。
- **延迟影响**：在吞吐重叠区间，TPOT 与基线相当（例如 DSv4-Flash 并发 16 时 15.9 vs 16.0 ms）；高负载下 HiSparse 的 TTFT 显著更低。
- **开销归因**：no-IO oracle 在低并发下与基线 TPOT 基本一致，说明 RESOLVE 机制本身（哈希探针、victim 扫描、LRU 更新、gather）几乎没有每 token 成本；HiSparse 的 TPOT 代价全部来自主机-设备 IO。
- **预取效果**：精确预取在匹配并发下将 TPOT 降低 13–15%，隐藏约一半剩余 IO 开销；锚层自身 miss 导致的剩余结构性开销约占 27%。
- **内存容量可转移**：有界驻留既能转化为更大 batch，也能在极端上下文下实现“HBM 放不下”的请求在 host 容量范围内可服务。

## 七、优点

- **精确性**：只改变 KV 放置，不改变选中位置、注意力分数或输出，模型输出完全不变。
- **索引器无关**：统一消费逻辑位置集合，可同时支持 DSA、NSA、Quest 等训练式/训练无关选择器，无需重训练。
- **生产级落地**：已合并进上游 SGLang，约 2200 行 Python + CUDA kernel，并考虑了 CUDA graph 捕获、多流事件、disaggregation 兼容等工程细节。
- **工程机制精巧**：融合 RESOLVE 内核、GPU-assisted IO、LRU 保留局部性、计划-IO 精确预取，共同把 miss 开销压到很低的水平。
- **实验设计严谨**：引入 no-IO oracle 作为性能上界，使“解析机制零成本、IO 是唯一代价”的结论有直接证据；同时用 Bélády 最优策略定位 LRU 与理论上限的差距。
- **结论具有系统指导意义**：通过懒调度能力分析指出模型共享选择、更快互连等 co-design 方向。

## 八、不足与局限

- **TPOT 开销**：在同步解析时，低并发下每 token 仍暴露约 7–8 ms 的主机 IO 开销；即使有精确预取，也只剩约 3 ms。这说明 HiSparse 本质上是“用内存容量换带宽流量”。
- **适用边界**：在短上下文或低并发、非容量受限场景下，HiSparse 几乎没有收益并可能引入额外开销，论文也承认此时应关闭该功能。
- **第二层容量限制**：在 Grace 类平台（GB200/GB300）上，CPU LPDDR 容量与 HBM 可比甚至更小，主机层不再是“远大于第一层”，容量乘数会大幅缩小；论文未在这些平台上进行端到端验证。
- **极端上下文未实测**：1M token 级别的请求可用性是推导出来的，没有专门实验验证 host 池、页表和 IO 路径在该规模下的实际表现。
- **动态调整缺失**：B 为静态配置参数，论文明确将动态扩缩容或按请求调整留作未来工作。
- **对比不充分**：未与 ESS、ECHO 等最相关系统进行直接实验对比，只以文字说明差异。
- **预取依赖模型结构**：投机预取（相邻层推测）在非共享索引模型中几乎无效，说明该方法高度依赖“共享索引选择”这类模型 co-design 条件。
