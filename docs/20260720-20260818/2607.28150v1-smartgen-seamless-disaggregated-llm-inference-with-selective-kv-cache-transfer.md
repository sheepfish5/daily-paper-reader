## 摘要
将大型语言模型（LLM）推理的预填充和解码阶段分离到两组不同的节点上，在当今的LLM服务系统中被广泛采用。然而，这种架构对在租用云实例上自行部署LLM提出了重大挑战，因为在分离节点之间传输大量键值（KV）缓存很容易使有限的节点间网络带宽饱和。在本文中，我们提出通过跨两个阶段选择性传输必要的KV缓存条目来缓解网络瓶颈。实现选择性KV缓存传输面临两个挑战，即预填充阶段的准确KV选择，以及解码阶段的高效KV获取。为了解决这些挑战，我们设计了SmartGen，一个KV缓存传输引擎，通过三条数据传输路径实现无缝的分离式LLM推理。具体来说，我们利用1）基于剖析的主动传输路径，在预填充阶段识别并推送必要的KV缓存条目到解码节点；2）并行按需传输路径，在解码阶段同时获取远程和本地KV缓存条目；以及3）推测性传输路径，最终将所有KV缓存传送到解码节点。实验结果表明，与典型的全量KV缓存传输方法相比，SmartGen将到第二个令牌的时间减少了高达4.3倍，同时提供相当的后续解码性能和准确性。

## Abstract
Disaggregating the prefill and decoding stages of large language model (LLM) inference into two separate sets of nodes is widely adopted in today's LLM serving systems. However, such an architecture poses significant challenges for self-hosted LLM deployments on rented cloud instances, since transferring enormous key-value (KV) caches between disaggregated nodes can easily saturate the limited inter-node network bandwidth. In this paper, we propose to mitigate the network bottleneck by selectively transferring essential KV cache entries across the two stages. There are two challenges to achieve selective KV cache transfer, i.e., accurate KV selection during the prefill stage, and efficient KV fetching during the decoding stage. To address these challenges, we design SmartGen, a KV cache transfer engine that allows seamless disaggregated LLM inference with three data transfer paths. Specifically, we leverage 1) a profile-based proactive transfer path to identify and push essential KV cache entries to the decoding node during the prefill stage, 2) a parallel on-demand transfer path to simultaneously fetch remote and local KV cache entries during the decoding stage, and 3) a speculative transfer path to finally deliver all KV caches to the decoding node. Experimental results show that SmartGen reduces time-to-second-token by up to 4.3x compared with the typical full KV cache transfer approach while offering comparable subsequent decoding performance and accuracy.

## 1. 核心问题与整体含义

**研究动机与背景：**

- 大型语言模型（LLM）推理通常被分为两个阶段：**预填充阶段（prefill）** 与**解码阶段（decoding）**，两者计算特性迥异（前者为计算密集，后者为访存密集）。
- 主流 LLM 服务系统将这两个阶段**部署到不同的节点上**（即 P/D 分离式架构），以实现灵活的资源分配和高吞吐。
- 但这种架构在**云租用实例（自托管）**场景下面临严峻挑战：预填充与解码节点之间需要传输庞大的 KV 缓存（key-value cache），而廉价云 GPU 实例的网络带宽通常有限（如 10–35 Gbps），KV 缓存传输极易导致网络饱和。
- 论文通过实测指出，在 48K tokens 的长上下文场景下，KV 缓存传输耗时可达预填充计算耗时的 **6.5×**；在更极端的 60K tokens 与 15 Gbps 带宽下，最大可达 **7.1×**。KV 缓存传输导致的"阶段转换停顿"（stage-transition stall）可占整体任务完成时间的 **42.2%**，显著损害用户体验（增大 time-to-second-token，TTST）。
- 核心思想：既然 KV 缓存本身存在**动态稀疏性**——并非所有 KV 条目在解码阶段都同等重要——那么**只选择性传输必要的 KV 条目**即可缓解网络瓶颈，但面临两大挑战：
  1. **预填充阶段准确识别重要 KV 条目**：现有稀疏注意力算法依赖解码阶段的 query 或 hidden states 来判断重要性，预填充时无从得知；
  2. **解码阶段高效获取缺失 KV 条目**：远程获取会引入网络往返延迟，进入注意力计算的每个迭代的关键路径，累积开销显著。

## 2. 方法论：核心思想、关键技术细节

**整体设计：SmartGen — 重要性感知的 KV 缓存传输引擎**

SmartGen 将所有 KV 缓存条目分为**三类**，并对应设计**三条数据传输路径**：

### (1) 基于剖析的主动传输路径（Profile-based Proactive Transfer）

- **目标对象**： universally important 的 KV 条目（无论输入 prompt 如何都被认为是重要的）。
- **关键洞察**：重要 KV 条目在序列中具有**位置相似性**——不同数据集、不同 prompt 长度下，重要 KV 条目倾向于出现在 KV 缓存矩阵中相对一致的位置区域。这意味着可以用一个校准数据集离线建模 token 重要性分布，泛化到同长度范围内的在线请求。
- **离线剖析**：在推理过程中统计每个 KV 条目被解码阶段 KV 选择算法选中的频率，将每层 KV 缓存沿序列维度划分为 M 个 KV 块（M=1K），按平均选择频率计算每个块的重要性 I_l,m：

  > I_l,m = (1/|E(B_l,m)|) · Σ_{e∈E(B_l,m)} S(e)

  其中 S(e) 是条目 e 在离线剖析解码阶段被选中的次数；第 0、1 层注意力层的 KV 缓存永远被标记为重要（l=0 或 1 时设 I=∞）。

- **可传输块数估算**：根据剖析得到的预填充计算耗时 T_p 与全量 KV 缓存传输耗时 T_t，计算可安全重叠进预填充计算的最多 KV 块数：

  > K_r = L·M · [ (L−1)/L · T_p / T_t ] = M·(L−1)·T_p / T_t

  即选择 top-K_r 个最重要的 KV 块，在预填充阶段用 **one-sided RDMA WRITE** 直接推送到解码节点的 CPU 内存 KV 缓存池；同时更新解码端的 KV mask。

### (2) 并行按需传输路径（Parallel On-demand Transfer）

- **目标对象**： context-dependent 的 KV 条目（只对特定 query 重要，预填充阶段无法预测）。
- **核心思想**：将本地 KV 缓存加载与远程 KV 获取**解耦并行化**，把网络往返从关键路径中移除。
- **Mask-based index splitting（基于掩码的索引拆分）**：解码节点 GPU 上为每个注意力层预分配一个 int8 格式的 KV mask 矩阵（形状 B×N），元素为 0（padding token）、1（本地已有）、2（位于远程节点）。预填充节点推送 KV 块后通过 GDR 更新对应 mask 值（与 KV 数据写入合并为一个 RDMA 往返，利用门铃批处理保证顺序性）。解码时，GPU 上的 KV 选择算法生成 KV 索引后，通过轻量算子将索引拆分为本地索引与远程索引。
- **Reordering-based KV gathering（基于重排序的 KV 聚集）**：利用"KV 条目沿序列维度的排列顺序不影响注意力结果"这一特性（因位置信息已在 KV 中编码），将远程 KV 条目在每个 head 的选中行内排序到连续位置（mask 值降序排列），从而解码节点可通过 RDMA 以**行块连续接收**而非逐条传输，并进一步利用 RDMA NIC 的 **DMA scatter 能力**将收到的连续块分发到离散行，大幅减少 I/O 次数（最多减少 20×）。

### (3) 投机性传输路径（Speculative Transfer）

- **目标对象**：剩余的 less important KV 条目。
- **关键洞察**：解码节点在注意力计算时间段内，CPU 与 RDMA NIC 处于空闲状态，可用来做后台传输而不干扰前台的按需获取。
- **机制**：解码节点在每层注意力计算开始时通知预填充节点"网络空闲"，预填充节点按照重要度降序（由式 1 定义）通过 RDMA WRITE 继续推送未传输的 KV 块。每轮**限制传输块数**（speculative ratio，默认 10%）以避免干扰前台远程 KV 获取，约 10 个解码迭代即可将全部剩余 KV 缓存送达，此后 TBT 收敛到理想情况（全量本地化）。

**关键辅助数据结构：** 每层一个 KV mask（B×N int8），内存开销小（例如 64K tokens + Qwen3-14B 时总计仅 2.5 MB）。

**算法核心（Algorithm 1：KV 索引拆分与重排序）**：
1. 从 KV mask 中按 KV 索引取值得到掩码序列；
2. （可选）每行按掩码值降序排序；
3. 按掩码值 1/2 拆分为 local_index 和 remote_index。

## 6. 主要结论与发现

1. **大幅降低阶段转换停顿**：与全量 KV 缓存传输相比，SmartGen 将 TTST 降低最高 **4.3×**（GovReport 数据集），同时保持可比的后续解码性能与精度。
2. **解码性能接近理想情况**：SmartGen 的 TBT 接近全量本地 KV 缓存（理想情况），显著优于朴素选择性传输（1.4–1.6× 优势）与 HACK（1.4× 优势），原因在于并行按需传输与投机传输共同消除了网络往返与格式转换开销。
3. **准确率保持**：基于 InfiniGen 和 HATA 的 SmartGen 相对全量缓存基线的准确率保持在 92%–107% 的范围内，远优于 HACK（相对准确率最低至 13%）。
4. **位置相似性验证有效**：Profile-based 策略较 Sequential、Random 分别降低 on-demand ratio 最多 38%/51%，性能已逼近最优选择策略（Optimal）。
5. **自适应性与广泛适用性**：SmartGen 在 15–32 Gbps 网络带宽下均保持优势；带宽越低，相对收益越大（TTST 改进从 2.5× 增至 3.3×）；方法可与不同 KV 选择算法（免训练与可训练）和模型架构无缝集成。
6. **投机性传输的有效性**：Speculative Transfer 能在约 10 个解码迭代内将剩余 KV 全部送达，此后 TBT 与理想情况对齐；10% 的投机比例在速度与干扰之间达到最优平衡。

## 7. 优点与亮点

- **问题定义清晰且实用**：直击自托管云 LLM 场景中的真实痛点（有限带宽 + 大 KV 缓存），有充分的实验数据支撑问题陈述（观察到 4.7×–7.1× 的传输/计算差距）。
- **将动态稀疏性思想迁移到传输阶段**：已有工作利用 KV 稀疏性加速计算（如 InfiniGen、HATA），SmartGen 首次系统地将这一思想推广到跨节点 KV 传输中，开辟了新的优化维度。
- **三分类三路径的设计优雅而完备**：universally important（主动推送）、context-dependent（并行按需）、less important（投机后台传输），覆盖了 KV 条目的全部情况，且每一条路径都基于明确的资源空闲观测，设计动机扎实。
- **工程实现细节考究**：
  - 利用 KV mask + 门铃批处理保证 KV 数据与元数据的一致性；
  - 利用重排序 + RDMA scatter-gather 将离散远程 KV 的 I/O 降低最高 20×；
  - 轻量算子设计使其可无缝嵌入已有 KV 选择流程（无需修改选择算法代码）。
- **与量化方法正交**：作者明确指出 SmartGen 可与 HACK 等量化压缩叠加，具有组合优化的潜力。
- **全面的实验验证**：5 模型 × 4 任务 × 多硬件平台，配合逐项消融与多方面敏感性分析（批量、带宽、序列长度、块粒度、选择比例），研究深度与方法严谨性俱佳。
- **可适配性讨论**：包括周期性/分组式剖析应对负载漂移、无 GDR 云实例的降级方案、动态网络负载下自动退化为全量传输等，提升实际部署价值。

## 8. 不足与局限

- **实验规模有限**：虽然是系统论文中较充分的评估，但仍限于 8B–14B 规模的模型，未验证 70B+ 或 MoE 架构大模型（如 DeepSeek-V3）；输出长度固定 64 tokens，未展示长生成（数百/数千 tokens）下的行为。
- **离线剖析的鲁棒性依赖**：位置相似性假设虽然在多个数据集上成立，但若线上请求分布与校准数据存在显著差异（如不同语言、不同任务领域），重要性矩阵可能偏差。论文提出了周期性与分组剖析作为缓解手段，但未做压力测试。
- **无 GDR 环境下的性能未实测**：对于不支持 GDR 的云实例，论文仅给出

对于不支持 GDR 的云实例，论文仅给出了降级方案（如通过 CPU 中转拷贝或与数据更新合并为一次往返），但并未实测该方案的实际性能开销与稳定性。因此，SmartGen 对 GDR 的依赖可能限制其在部分云环境中的直接部署效果，尤其是那些未提供 RDMA 或 GDR 能力的廉价实例。

- **未深入分析多请求并发与调度交互**：论文实验主要聚焦于单批请求（batch）内的 KV 传输优化，并未讨论多请求并发到达、优先级调度、队列排队等真实服务场景下的交互影响。当多个预填充请求同时竞争解码节点资源时，SmartGen 的三路径传输策略是否会互相干扰、如何与请求级调度器协同，仍有待研究。
- **KV 选择算法本身的误差被继承**：SmartGen 的有效性建立在底层 KV 选择算法（如 InfiniGen、HATA）能准确识别重要条目的前提上。但论文未探讨当选择算法产生误判（例如因训练数据偏差或 prompt 分布漂移而选错 KV）时，SmartGen 如何感知并纠正，这种级联误差可能影响端到端准确率。
- **适用范围仍以稠密 Transformer 为主**：论文测试的模型虽涵盖不同架构与 GQA 等变体，但并未覆盖 MoE 模型（如 DeepSeek-V3）或百万级上下文窗口的稀疏注意力模型。这些模型中 KV 缓存的布局、重要度分布及传输模式可能不同，SmartGen 的结论是否依然成立存在不确定性。
- **部署复杂度与运维成本**：SmartGen 需要额外的离线剖析流程、KV mask 维护、RDMA 传输调度以及多节点状态同步，相比简单的全量传输，系统复杂度显著上升。论文未量化部署 SmartGen 所带来的运维成本（如剖析数据更新周期、故障恢复处理、多版本一致性等），这可能影响其在实际生产环境中的采用意愿。

总体而言，SmartGen 提出了一个优雅且有效的 KV 缓存传输优化框架，实验证据充分，但上述局限性也意味着其普适性与生产级成熟度仍有提升空间。未来工作可以在更大规模模型、更复杂调度场景及无 GDR 环境下做进一步验证与增强。
