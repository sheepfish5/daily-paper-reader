## 摘要
LLM服务系统为满足严格的延迟目标而按峰值负载配置，导致流量低于峰值时大量GPU计算空闲。我们提出DeltaServe，一种宿主无关的协同服务设计，将这种空闲推理容量转化为LoRA微调吞吐量，同时保持推理服务级别目标（SLO）。DeltaServe通过一个紧凑的钩子接口与现有推理引擎集成，仅需支持多LoRA批处理。它利用推理预填充和LoRA微调前向传播的共享执行结构，并使用SLO感知调度器仅在足够推理余量可用时准入和执行微调。该调度器由离线校准并在线优化的CUDA图感知延迟模型驱动。我们将DeltaServe与vLLM、SGLang和S-LoRA集成。在来自X公司的生产轨迹上，DeltaServe在vLLM上实现了比LLMStation高2.9倍的微调吞吐量，推理SLO合规率为100%，而LLMStation为85%。与运行vLLM+torchtune的基线相比，它还实现了39%更高的微调吞吐量，无需额外硬件并保持完全SLO合规。

## Abstract
LLM serving systems are provisioned for peak load to meet strict latency targets, leaving substantial GPU compute idle whenever traffic falls below peak. We present DeltaServe, a host-agnostic co-serving design that converts this idle inference capacity into LoRA fine-tuning throughput while preserving inference service-level objectives (SLOs). DeltaServe integrates with existing inference engines through a compact hook interface that requires only multi-LoRA batching support. It exploits the shared execution structure of inference prefill and LoRA fine-tuning forward passes, and uses an SLO-aware scheduler to admit and execute fine-tuning only when sufficient inference headroom is available. The scheduler is driven by a CUDA-graph-aware latency model calibrated offline and refined online. We integrate DeltaServe with vLLM, SGLang, and S-LoRA. On a production trace from Company X, DeltaServe on vLLM delivers 2.9x higher fine-tuning throughput than LLMStation at 100% inference SLO compliance, versus 85% for LLMStation. It also achieves 39% higher fine-tuning throughput than a baseline running vLLM+torchtune, using no additional hardware and maintaining full SLO compliance.

# DeltaServe 论文中文总结

## 1. 论文的核心问题与整体含义

- **背景动机**：生产环境中的 LLM 推理服务通常按峰值流量配置 GPU 资源，以保证交互式延迟目标（如 TTFT / TPOT）。但实际流量具有强烈的突发性和波动性，导致大多数时间 GPU 利用率远低于峰值。论文给出的 Nutanix 生产推理轨迹显示，平均约 40% 的 GPU 算力处于闲置状态。
- **现有解决思路的不足**：
  - 只优化推理流水线本身（如 Splitwise 分离 prefill/decode，Orca 混合批处理）无法回收“请求流低于峰值”时产生的空闲算力。
  - 传统的 GPU 资源共享（时间切片、MIG、MPS）粒度太粗，无法跟踪亚秒级推理负载波动，也难以在满足 SLO 的前提下利用零散空闲资源。
- **核心问题**：能否在不影响在线推理 SLO、不增加额外硬件的前提下，将推理服务中的空闲 GPU 容量转化为有用的计算工作？
- **论文的答案**：利用 LLM 服务中常见的 **LoRA 参数高效微调（PEFT）** 作为“填充”工作。LoRA 微调与推理共享冻结的基础模型、权重、内核和显存，且微调前向传播与推理 prefill 结构本质上相同，非常适合与推理共服务。
- **整体含义**：DeltaServe 提出了一种“宿主无关（host-agnostic）”的共服务设计，通过紧凑的钩子接口挂载到现有推理引擎（vLLM、SGLang、S-LoRA）上，把推理空闲容量转化为 LoRA 微调吞吐，同时严格保证推理 SLO。

## 2. 论文提出的方法论

### 2.1 核心设计思想

- **宿主无关扩展**：DeltaServe 不是一个全新服务系统，而是附加在现有引擎上的“扩展层”。它将共服务逻辑（SLO 延迟模型、准入策略、解耦反向执行器）封装为可复用核心，仅要求宿主引擎支持 **multi-LoRA batching**（现代吞吐引擎多已支持）。
- **结构复用**：将微调样本视为“单步、仅 prefill、不产生客户端可见输出”的请求，路由到保留的微调 adapter，通过宿主已有的多 LoRA 前向路径执行；微调样本与推理请求合并到同一 batch 中。
- **组件组成**：
  - **Fine-tuning Manager**：管理微调语料、样本顺序、训练进度。
  - **DeltaServe Scheduler**：截获宿主调度循环，在每次形成 batch 前估计延迟余量，决定准入多少微调样本。
  - **Inference-Engine Hooks**：轻量插入宿主前向路径；保存反向所需激活（默认只存每层残差流输入），并记录每步执行时间供模型在线校准。
  - **Backward Subprocess**：独立的 GPU 子进程，在 CUDA MPS 下运行反向传播和优化器更新；通过共享 GPU 内存映射激活缓冲区和模型参数，避免数据拷贝。

### 2.2 关键机制

- **混合前向 batch**：微调样本通过宿主 multi-LoRA 前向路径执行，只额外做激活捕获；微调样本在步完成后立即退役，不进入客户端推理路径。
- **反向子进程**：在独立 CUDA 上下文中运行，避免与推理内核启动路径争用；反向任务执行期间，调度器不准入新微调样本，防止激活覆盖。
- **SLO 预算计算**：
  - 用解析延迟模型预测混合 batch 的执行时间（公式 I / II）。
  - TTFT 预算定义为：`Δ_budget = T_SLO - (t_now - t_arrival)`（公式 III）。
  - 调度器取 TTFT 余量和 TPOT 余量中更紧者作为可用预算 Δ。
- **准入算法（Algorithm 1）**：
  1. 若反向子进程运行、激活缓冲满、微调池为空，或宿主不支持 prefill-decode 混合、当前步仅 decode，则拒绝准入。
  2. 计算 Δ（min(TTFT slack, TPOT slack)）。
  3. 若纯推理 batch 已超出 Δ，则不准入。
  4. 否则按样本 token 长度升序贪心尝试加入微调样本，直到预测的混合 batch 延迟超过 Δ 或激活缓冲容量不足。
  5. 准入后预留缓冲区、从池中移出样本。
- **执行模式感知的延迟模型**：
  - 延迟模型针对 CUDA graph 和 eager 执行分别拟合系数。纯推理 prefill/mixed 步可能用 CUDA graph 重放，而含微调的混合步因激活钩子不能在图内运行而必然是 eager，因此预测时按宿主实际模式选择系数。
- **反向抢占**：反向子进程在每层 transformer 边界检查共享 GPU 授权标志；prefill 到达时清除该标志，反向在层边界让出 GPU，decode 仍可与反向重叠。
- **微调前向中断**：若推理请求在“仅微调”的前向步期间到达，激活钩子在层边界检查 abort 信号，丢弃部分激活，将中断样本放回微调池，立即调度推理。

## 6. 主要结论与发现

- **端到端结果（4×A100）**：
  - Nutanix 轨迹上，DeltaServe-vLLM 微调吞吐为 1418 tok/s，比 LLMStation（489 tok/s）高 **2.9×**，比 vLLM+torchtune（1014 tok/s）高 **39%**；SLO 合规 100%，LLMStation 仅 85.5%。

  - burst-dense：DeltaServe 微调吞吐 1233 tok/s，为 LLMStation 的 2.6×，比 split-pool 高 21%；100% SLO 合规，而 LLMStation 仅 83.3%。
- **可移植性**：
  - DeltaServe-SGLang 在单卡 RTX 5090 上达到 972 tok/s 微调吞吐且 100% SLO 合规；

- **消融结论**：

## 7. 优点

- **宿主无关架构**：通过紧凑钩子接口挂载到多个主流/研究引擎，避免重写服务系统，实用性强。
- **SLO 感知准入**：利用解析模型 + 在线校准，精确估计 batch 级延迟余量，实现亚秒级负载波动的细粒度控制。
- **CUDA graph 感知**：显式区分 graph 与 eager 执行模式，解决了 LLMStation 延迟缓存忽略该区别的问题。
- **结构复用**：将微调前向折叠进推理 prefill，而非独立执行，显著提高吞吐。
- **解耦反向子进程**：反向在独立 CUDA 上下文运行，配合层边界抢占，减小对延迟敏感推理的干扰。
- **设计考虑周全**：包括前向中断、激活缓冲管理、离线校准+在线拟合等工程细节。
- **开源实现**：在三个引擎上实现并开源，便于复现和扩展。

## 8. 不足与局限

- **依赖 multi-LoRA batching**：宿主引擎必须已有该能力；不支持多 LoRA 批处理的引擎需要额外改动才能集成。
- **仅支持 LoRA/PEFT**：无法处理全参数微调（需大量梯度/优化器状态），适用范围受限。
- **延迟模型简化**：解析模型假设延迟与 batch 组成呈线性/二次关系，对极端序列长度分布、异构硬件可能不够精确；在线校准依赖观测数据覆盖。
- **推理延迟有一定代价**：完全 SLO 合规下，Nutanix 轨迹中 DeltaServe 的平均端到端延迟比 split-pool 高约 45%（设计上利用 SLO 余量换取吞吐，是主动选择，但并非零开销）。
- **评估覆盖有限**：仅测了单模型、单数据集、单 LoRA 配置；未充分测试多用户、多 adapter、不同 SLO 组合、超长上下文、多机扩展等场景。
- **反向子进程的 MPS 机制**：CUDA MPS 在部分环境可能有隔离性问题或需要特殊权限，实际部署存在额外运维负担。
- **对比公平性**：LLMStation 和 vLLM+torchtune 的参数细节未完全说明；split-pool 基线固定为 3+1 卡，未探索不同的 GPU 分配比例。
