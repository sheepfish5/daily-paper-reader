## 摘要
高级综合（HLS）将硬件设计的抽象级别从并发寄存器传输级（RTL）程序提高到顺序程序。在HLS利用的并行形式中，流水线需要对流水线结构和冲突解决进行细粒度控制，以实现有竞争力的功耗、性能和面积（PPA）。然而，现有工具要么缺乏这种控制，要么牺牲顺序语义来提供这种控制。我们提出了一种HLS工具，将细粒度流水线控制嵌入到顺序编程模型中，从而支持快速设计空间探索。该工具基于可见性控制，这是一种新颖的编程抽象，统一了冲突解决策略，包括停顿、旁路、推测、延迟提交和寄存器重命名。我们在顺序RISC-V内核、直方图和AES加速器上进行了评估。在RISC-V内核上，我们实现了停顿、旁路、推测和寄存器重命名；在直方图上，我们实现了以前需要RTL或并发编程模型的调度策略。编译后的流水线在顺序语义上优于HLS工具，并实现了与手写RTL相当的PPA。

## Abstract
High-level synthesis (HLS) raises the abstraction of hardware design from concurrent register-transfer level (RTL) programs to sequential programs. Among the forms of parallelism HLS exploits, pipelining demands fine-grained control over pipeline structure and hazard resolution to achieve competitive power, performance, and area (PPA). However, existing tools either lack such control or sacrifice sequential semantics to provide it.   We present an HLS tool that embeds fine-grained pipeline control in a sequential programming model, enabling rapid design-space exploration. The tool builds on visibility control, a novel programming abstraction that unifies hazard resolution strategies including stalling, bypassing, speculation, deferred commit, and register renaming. We evaluate on in-order RISC-V cores, histograms, and an AES accelerator. On RISC-V cores, we implement stall, bypass, speculation, and register renaming; on histograms, we implement scheduling strategies that previously required RTL or concurrent programming models. Compiled pipelines outperform HLS tools with sequential semantics and achieve PPA comparable to hand-written RTL.

- 高级综合（HLS）将硬件设计从并发 RTL 提升到顺序程序，但流水线化需要细粒度控制流水线结构和冲突解决，才能获得有竞争力的 PPA（功耗、性能、面积）。
- 现有工具存在“三难”：
  - 传统 HLS（Vitis HLS、SpecHLS、Dynamatic）：保持顺序语义，但只提供间接控制（如目标 initiation interval），冲突解决策略固定或由编译器决定，**缺乏细粒度控制**。
  - Kanagawa：提供细粒度控制和高效实现，但使用**并发语义**，设计者需手动管理共享状态冲突，策略切换容易引入并发 bug。
  - PDL：试图同时满足三个属性，但因冲突解决被碎片化为若干独立子系统，存在**表达力不足、实现低效、顺序语义保证脆弱**等问题（18 条规则仍不健全）。
- 论文提出一种基于 **可见性控制（Visibility Control）** 的新型 HLS 工具，在**顺序编程模型**中嵌入细粒度流水线控制，统一了停顿、旁路、推测、延迟提交和寄存器重命名等策略，实现快速的流水线设计空间探索，并且生成硬件 PPA 与手写 RTL 相当。

## 2. 论文提出的方法论

### 2.1 核心抽象：可见性控制

- 将每个冲突解决策略归结为两个选择：
  1. **较早指令** 对共享状态上的未决读写暴露多少信息；
  2. **较晚指令** 如何反应。
- 每个指令在共享状态上维护发布状态（published state）：
  - `S_decl`：是否可能发起写；`S_store`：写状态机（⊥ → Declared → Tentative → Sealed）；`S_load`：是否可能读。
  - 操作包括：保守 load、speculative load、commit，根据前序指令的发布状态采取停顿、旁路、转发、直接读写等动作。
- 统一表达了 RAW/WAR/WAW 冲突解决：
  - RAW：保守 load 在 Declared/Tentative 时按地址冲突停顿，Sealed 时旁路；speculative load 可绕过停顿并依赖冲刷恢复。
  - WAW/WAR：commit 在存在前序未决写/读时停顿，保证写提交顺序。

### 2.2 顺序编程实例化

- 基于 Rust 子集：安全 Rust、无堆分配、无并发、循环携带变量用 `Var`/`SpecVar` 包装。
- **Speculative loop pipelining**：每个源循环编译为一条流水线，`sep()` 标记流水线阶段，循环体中的分支编译为 demux/mux，循环推测性发出迭代 token，循环终止时冲刷多余 token。
- **Var 原语**：维护数组语义，提供 `load`、`spec_load`、`try_load` 以及带 `StoreBatch` 的分阶段写协议（`decl`/`store`/`seal`/`drop`）。通过操作在流水线中的位置决定冲突解决策略（如删除 seal 就变为 stall 策略）。
- **SpecVar**：用于建议性状态（如分支历史表），不做冲突解决。
- 支持寄存器重命名：通过组合多个 `Var`（free list、rename table、physical RF）实现，利用 `try_load` 非阻塞探测空闲物理寄存器。

### 2.3 形式化与编译

- 形式化：用 token 抽象定义流水线状态（循环索引、局部变量、发布状态），给出周期级转移规则；正确性证明以 sketch 形式展示：编译后流水线的提交序列 refine 源程序的顺序语义（归纳维护三个不变性质）。
- 编译优化：
  - **程序顺序分析**：利用 token 树结构，多数程序顺序可静态确定，消除动态比较器和循环索引；仅对最内公共循环动态比较。
  - **状态可达性分析**：针对每个 Var 的发布状态进行特化，只保留运行时有意义的分量，生成固定旁路线和旁路多路选择器。
  - 额外优化：局部变量最小化、逻辑简化、以及“eager tentative commit”（满足四条件时直接把 Tentative 值写入共享状态，省去旁路网络）。

## 6. 论文的主要结论与发现

- **三属性同时实现**：提出基于可见性控制的 HLS 工具，首次同时具备细粒度流水线控制、高效实现和顺序语义。
- **RISC-V 结果**：
  - 相比 PDL：运行时降低 1.2–1.8×，面积降低 1.7–3.9×，功耗降低 1.1–1.6×。
  - 相比手写 Sodor：时钟同频下面积相差 +2% 到 +5%，功率相差 −3% 到 +1%，CPI 完全一致；最大频率均为 1250MHz。
- **直方图结果**：三种策略下与 Kanagawa 相比，延迟和资源使用均不劣于（有时显著优于）Kanagawa；同时显著优于 Vitis HLS 和 Dynamatic。
- **AES 结果**：直接移植版与 RTL 参考 LUT/FF 几乎相同，最高频率提高 1.53×；两种优化后（加密/解密路径去重、消除冗余初始化）LUT 减少 1.35×、FF 减少 4.4×。
- **来源差异分析**：PDL 的开销来自多个冗余排序子系统和不必要的运行时比较器；本文通过程序顺序分析和状态可达性分析实现跨模块优化，从而与手写 RTL 持平。

## 7. 优点

- **统一抽象**：可见性控制用一个统一框架表达停顿、旁路、投机、延迟提交和寄存器重命名，极大简化设计空间探索（例如删除两条 `seal` 调用即可从旁路转为停顿）。
- **顺序语义保证**：在类型系统（Rust ownership/typestate）和形式化证明的支持下，策略切换不会引入并发 bug，这是 Kanagawa 和 PDL 做不到的。
- **高效编译**：静态分析消除多数动态比较器和多余流水线寄存器，使生成 RTL 接近手写质量。
- **适用广泛**：案例覆盖处理器（带异常、Zicsr）、数据并行直方图、非流水线型 AES，展示可拓展性。

## 8. 不足与局限

- **任务级并行（TLP）不支持**：论文明确将 TLP 留给未来工作，适用范围限于单流水线内部。
- **乱序执行未支持**：token 保持按序出口，无法表达乱序执行；未来工作才计划扩展。
- **语言约束较严**：仅支持 Rust 安全子集、无堆、无并发、循环携带变量必须用 `Var`/`SpecVar`，对编程风格有额外要求。
- **正式证明是 sketch**，尚未机械化验证；形式化仅覆盖本子集，实践中仍需依赖类型系统保证。
- **评估边界**：未与 SpecHLS 等动态 HLS 在处理器场景对比；与 PDL 相比，PDL 的 LOC 更短且不支持 Zicsr，对比条件不完全等价。
- **场景规模较小**：评估设计均为中等规模（5 级 CPU、直方图、AES），未展示对大型复杂 SoC 的可扩展性。
- **算力信息缺失**：未披露能耗/时间等全面的资源开销，DSE 的实际成本评估不足。
