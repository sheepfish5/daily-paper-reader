## 摘要
重复的提示前缀在 LLM 服务负载中日益常见，出现在系统提示、模板化检索增强生成流水线、智能体框架以及多轮对话中。vLLM 和 TensorRT-LLM 等现代推理运行时提供了跨请求复用先前计算的 KV 缓存状态的机制，但在当代加速器上，前缀复用何时能实质性提升服务性能、何时其收益受限于调度、缓存粒度、并发或内存压力，仍不明确。本文提出 PrefixBench-H100，一个可复现的基准测试与测量框架，用于在单张 NVIDIA H100 上刻画前缀复用。PrefixBench-H100 将受控合成轨迹与聊天式、检索式负载相结合，并在匹配的负载条件下评估两种广泛使用的 LLM 服务运行时。该基准改变共享前缀长度、后缀多样性、请求到达模式、并发、输出长度和缓存配置，同时收集首 token 时间、token 间延迟、端到端延迟、吞吐量、缓存命中统计、GPU 内存使用以及选定的性能分析轨迹。PrefixBench-H100 的目标不是提出新的缓存算法，而是揭示面向 H100 级 LLM 服务的前缀复用的实际运行边界。该研究识别出前缀复用能显著降低首 token 延迟的区间，以及缓存压力会侵蚀这些收益的区间，同时表明缓存有效性本身在很大程度上对并发和输出长度不敏感；仍然存在的跨运行时差异出现在缓存之上，即调度层。

## Abstract
Repeated prompt prefixes are increasingly common in LLM serving workloads, appearing in system prompts, templated retrieval-augmented generation pipelines, agent frameworks, and multi-turn conversations. Modern inference runtimes such as vLLM and TensorRT-LLM provide mechanisms for reusing previously computed KV-cache state across requests, yet it remains unclear when prefix reuse materially improves serving performance on contemporary accelerators and when its benefits are limited by scheduling, cache granularity, concurrency, or memory pressure.   This paper presents PrefixBench-H100, a reproducible benchmark and measurement framework for characterizing prefix reuse on a single NVIDIA H100. PrefixBench-H100 combines controlled synthetic traces with chat-style and retrieval-style workloads, and evaluates two widely used LLM serving runtimes under matched workload conditions. The benchmark varies shared-prefix length, suffix diversity, request arrival pattern, concurrency, output length, and cache configuration, while collecting time-to-first-token, inter-token latency, end-to-end latency, throughput, cache-hit statistics, GPU memory usage, and selected profiling traces.   The goal of PrefixBench-H100 is not to introduce a new caching algorithm, but to expose the practical operating envelope of prefix reuse for H100-class LLM serving. The study identifies the regime where prefix reuse provides substantial first-token latency reductions and the regime where cache pressure erodes them, while showing that cache effectiveness itself is largely insensitive to concurrency and output length; the cross-runtime differences that remain arise above the cache, in the scheduling layer.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：重复提示前缀在 LLM 服务负载中日益普遍，广泛出现于系统提示、模板化 RAG 流水线、Agent 框架与多轮对话中。vLLM 与 TensorRT-LLM 均已默认开启前缀/KV 缓存复用（前者基于 PagedAttention，后者基于 `KvCacheConfig`）。
- **动机**：前缀缓存最初是为 A100 上 KV 内存稀缺的假设设计的；而 H100 NVL 拥有 94 GB HBM3，这一假设已改变。因此问题不再是"前缀复用在 Hopper 上是否有效"，而是"瓶颈迁移到了哪里"。
- **核心问题**：在当代加速器上，前缀复用何时实质改善服务性能、何时其收益被调度、缓存粒度、并发或内存压力所限制？
- **整体含义**：论文定位为**表征性研究（characterization）而非系统构建**——不提出新缓存算法，而是给出 H100 级前缀复用的"实际运行包络（operating envelope）"，为研究者和运维者决定"何时优先做前缀复用、何时转向调度调优或 chunked prefill"提供依据。

## 2. 方法论：核心思想与关键技术细节

- **核心思想**：用**同一套 OpenAI 兼容负载**驱动两个生产级运行时（vLLM、TensorRT-LLM），在匹配条件下分离"前缀复用的内在收益"与"运行时实现差异"。
- **基准组成 PrefixBench-H100**：
  - **合成重复前缀轨迹**：请求形如 `⟨共享前缀⟩ ◦ ⟨唯一后缀⟩`，两段均按 Qwen2 分词器精确构造为指定 token 数；可独立调节共享前缀长度、后缀长度、输出长度、不同前缀数、请求数——使前缀复用成为唯一变量。
  - **真实 RAG 风格模板轨迹**：长系统提示 + 8 篇均匀抽取的检索文档 + 8 个查询模板，用于验证合成结论可迁移到真实后缀多样性场景。
- **负载驱动**：单一异步 Python 驱动（`load_gen.py`，约 300 行，基于 aiohttp），支持 **burst（全量突发）** 与 **fixed-rate（固定速率，请求 i 在 i/QPS 时刻释放）** 两种到达模式；记录 TTFT（首个非空流式 token）、端到端延迟、输出 token 数、HTTP 错误，并在每个 cell 前后抓取 `/metrics` 以计算增量。
- **四组主要 Sweep**：
  1. 顺序复用（并发 1，前缀长度 ∈ {0,512,2048,4096,8192}）；
  2. Burst 并发（前缀固定 4096，并发 ∈ {1,4,8,16,32}）；
  3. Block-size 消融（TRT-LLM `tokens_per_block` ∈ {32,64,128}）；
  4. 真实 RAG（固定速率 ∈ {1,4,8,16} QPS）。
- **指标**：TTFT（p50/p95）、端到端延迟、输出/请求吞吐、前缀缓存命中率、峰值 HBM、代表性 Nsight trace。
- **关键归一化公式（文字说明）**：
  - 缓存有效性统一为"**由缓存服务的输入 token 比例**"：vLLM 用 `prefix_cache_hits_total / prefix_cache_queries_total`（同 block 单位，比值即 token 比例）；TRT-LLM 用 `cached_tokens / prompt_tokens` 的累计值。
  - **无驱逐上限（ceiling）公式**：对从 np 个前缀中均匀抽取 N 个请求的 cell，完美不驱逐缓存的命中率上限为 `1 − np / N`（每个前缀至少首访未命中一次）。用"各 cell 相对自身 ceiling 的缺口"来识别驱逐，避免不同 cell 因重访次数不同而不可比。
- **实验隔离手段**：各 sweep 以随机顺序独立运行以减少残余缓存污染；用 reuse-on/reuse-off 对照锚定绝对收益；用"封顶 KV 容量"来在模型不变的条件下复现驱逐区间。

## 3. 实验设计：场景、Benchmark 与对比对象

- **模型**：
  - 主模型：`Qwen/Qwen2-7B-Instruct`（7.6 B，BF16 权重，32K 上下文）。
  - 压力实验：`Qwen2.5-32B-Instruct`（≈65 GB BF16 权重，KV 池骤减）。
  - 跨架构验证：`Mistral-7B-Instruct-v0.3`（GQA 8 KV heads，对比 Qwen2 的 4）。
- **运行时（作为黑盒，默认推荐配置）**：vLLM 0.21.0 + PyTorch 2.11.0（CUDA 13.0）；TensorRT-LLM 1.2.1 + PyTorch 2.9.1（CUDA 12.8），主用 PyTorch backend，另做一次 engine backend 单 cell 对比。
- **对比维度**：
  - reuse-on vs. reuse-off（`--no-enable-prefix-caching` vs. `enable_block_reuse: false`）；
  - vLLM vs. TensorRT-LLM（跨运行时）；
  - TRT-LLM PyTorch backend vs. TensorRT engine backend；
  - `tokens_per_block` ∈ {32,64,128}；
  - 前缀长度 × 并发度的二维运行图；
  - 输出长度 ∈ {32,128,512}；
  - 缓存压力：不同前缀数 {16,64,128} × 不同模型/封顶容量；
  - 能量（nvidia-smi 4 Hz 采样功率）。
- **公平性设计**：两运行时共享同一 JSONL 负载文件与同一 OpenAI `/v1/completions` 端点，保证提示与调度完全一致；各自独立虚拟环境避免依赖冲突；固定模型、BF16 精度以排除量化干扰。
