## 摘要
LLM 服务通常以共享的多租户服务形式提供，其中来自某个客户端的高需求工作负载可能导致其他客户端违反延迟 SLO。现有的性能隔离解决方案从长期来看会均衡客户端吞吐量，例如通过排队和批处理公平性。然而，这些方法不提供延迟隔离保证；因此，行为良好的客户端仍可能经历其 token 级延迟的显著劣化。在本文中，我们提出 FairInference，它提供了新颖的 δ-token 公平性保证：对于行为良好的客户端，如果某个 token 在隔离环境下在 d 个时间单位内生成，那么在多租户执行中将在 d + δ 个时间单位内生成，从而为 LLM 服务提供强延迟隔离保证。为实现这一点，FairInference 解决了 LLM 服务的一个关键挑战：在不支持细粒度调度或资源分配的情况下，限制因共享 GPU 资源而产生的延迟。在 FairInference 中，调度器强制执行每个 token 的截止时间，同时限制 GPU 计算共享带来的延迟，并考虑 GPU 内存中共享 KV 缓存引入的额外延迟。我们表明，与最先进的 LLM 服务系统相比，FairInference 有效限制了行为良好的客户端的 token 级延迟尖峰，并提高了整体吞吐量。

## Abstract
LLM serving is typically offered as a shared, multi-tenant service, where high-demand workloads from one client can cause latency SLO violations for others. Existing solutions for performance isolation equalize client throughput in the long run, for example through queueing and batching fairness. However, these approaches do not provide latency isolation guarantees; as a result, well-behaved clients can still experience significant degradation to their token-level latencies.   In this paper, we present FairInference, which provides the novel δ-token fairness guarantee: for a well-behaved client, if a token is generated in d time units in isolation, it will be generated within d + δ time units in multi-tenant execution, providing strong latency isolation guarantees for LLM serving. To achieve this, FairInference addresses a key challenge of LLM serving: bounding delays from sharing GPU resources without support for fine-grained scheduling or resource allocation. In FairInference, the scheduler enforces per-token deadlines, while bounding the delays from GPU compute sharing and accounting for the additional delays introduced by the shared KV caching in GPU memory. We show that FairInference effectively bounds token-level latency spikes for well-behaved clients and improves overall throughput compared to state-of-the-art LLM serving systems.

## 1. 核心问题与研究动机

- **背景**：LLM 服务普遍以多租户共享方式部署在 GPU 集群上，以提升利用率、摊薄成本。请求以「prefill（计算密集）+ decode（显存带宽密集）」两阶段流水线执行，并通过 GPU 显存中的共享 KV cache 复用跨请求状态。
- **核心问题**：高需求客户端（高请求率、长 prompt/completion）会挤占共享 GPU 资源，导致行为良好的客户端出现严重延迟劣化。实测中 SGLang 下单客户端可使其他客户端 TTFT 恶化 **60 倍以上**（表 1）。
- **现有方案的不足**：
  - VTC、DLPM、FairServe 等公平调度只做**长期吞吐均衡**（公平排队 + 批处理），不提供延迟隔离保证，TTFT 仍可恶化一个数量级。
  - 传统 CPU / 网络 / 存储的公平机制工作在**请求粒度**：把整条 token 流当作一个请求会破坏 TTFT/TBT；把单个 token 当作请求则延迟**级联传播**，破坏 TTLT。
  - GPU **缺乏细粒度虚拟化与资源分区能力**，无法为客户端分配精确的 1/N 计算份额，也无法可靠抢占长任务。
- **问题特殊性**：LLM 服务的延迟尖峰同时来自**调度**（FIFO 批处理、prefill 优先、decode 被抢占）与**KV cache 共享**（LRU 驱逐导致良好客户端状态被淘汰，需重算或从二级存储回读）。

## 2. 方法论：δ-token 公平性与 FairInference

### 2.1 核心概念：δ-token 公平（Token Latency Fairness）

- 定义：对行为良好（用量低于公平份额）的客户端，若某 token 在**隔离执行**下于 `d` 时间内生成，则在多租户执行中必须在 `d + δ` 内生成，且与其他人负载无关。
- 该性质同时约束三个指标：TTFT、TBT、TTLT（可扩展为 `(δ_TTFT, δ_TBT, δ_TTLT)`）。`δ = ∞` 对应现有无隔离系统，`δ = 0` 对应静态分区隔离。
- 灵感来自存储系统的 Delta Fair Sharing / FairDB，但把请求级隔离推进到 **token 级**，并可与 FairDB 组合成端到端 FairRAG。

### 2.2 关键技术：三步走

1. **计算逐 token 截止时间**：用性能模型估计隔离执行延迟 `T_k^ISO`，令 `d_k = T_k^ISO + δ`。
2. **KV 缓存延迟处理（δ-fair cache）**：
   - 首 token 的延迟预算拆分：`δ_0 = δ_cache + δ_prefill`，截止时间相应扣除 `δ_cache`。
   - 给每个客户端公平份额 `f_i = M/|C|`，估计可在 `δ_cache` 内恢复的 KV 块数 `R_cache_i`，得到**不可驱逐预留** `ρ_i = max(f_i − R_cache_i, 0)`。
   - 驱逐时按客户端的「caching spare」`s_i = max(u_i − ρ_i, 0)` 优先淘汰超额最多的客户端，客户端内部用 LIFO 以减少无效工作；**任何情况下不允许把某客户端降到其预留以下**。
3. **δ-fair 调度器**：
   - 维护按截止时间排序的 `Q_prefill` 与 `R_decode`，采用最早截止优先（EDF）。
   - 准入规则：若接纳某 prefill 会导致运行中 decode 违反截止时间则跳过；优先接纳低于公平份额的客户端请求；非公平客户端仅在显存富余时接纳。
   - 被抢占的 decode 带截止时间重新入队，保证后续优先执行；整体仍保持 prefill 优先以维持利用率。

### 2.3 隔离延迟建模与仿真

- **仿射性能模型**（离线拟合，按硬件/模型配置）：
  - `Δ_prefill(B) = c_p + α_p·S(B) + β_p·M(B) + γ_p·N(B)`
  - `Δ_decode(B) = c_d + α_d·S(B) + β_d·M(B) + γ_d·N(B)`
  - 其中 `S` 为批内总 token 数、`M` 为最长请求长度、`N` 为请求数；隔离设置下线性项乘以用户数 `N`（常数开销不变）。
- **隔离执行模拟器**：独立线程（C 代码，动态链接到 Python 主进程）按时间戳同步，模拟 1/N 资源下的 prefill/decode 排程、排队与内存压力重算，产出逐 token 截止时间。
- **理论保证**：
  - 定理 1：若池化环境下最大 decode 延迟可慢于隔离下的最小 decode 延迟，则任何调度都无法达成 δ 保证；因此系统直接取「池化最大 decode 界 = 隔离最小 decode 界」。
  - 定理 2：prefill 请求速率有上界 `R < δ_decode / [P_p(δ_decode + D_p)]`，即使 `δ → ∞` 该上界仍存在（极限为 `1/P_p`）。

- FairInference 能把良好客户端的 token 级延迟尖峰限制在配置的 δ 内：表 1 中其 TTFT/TBT/TTLT 为 3.2 s / 47 ms / 5.3 s（1×），而 SGLang 为 66×/1.8×/41×，VTC 为 28×/3.1×/18×，DLPM 为 32×/1.7×/20×。

## 9. 总体评价与定位

- **范式转换意义大于单点性能提升**：该工作最有价值之处不在于「比 VTC/DLPM 快多少」，而在于把多租户 LLM 服务的公平性目标从**长期吞吐均衡**重新定义为**相对隔离基线的逐 token 延迟上界**。这一定义使「公平」具备了可验证的定量语义（`d + δ`），并为管理员提供了单一、可解释的调参旋钮（δ），而非一组难以直觉理解的权重或配额。
- **δ 的语义具有层次性**：`δ = 0`（静态分区，隔离最强但吞吐最低）、`δ = ∞`（无隔离，吞吐最高但尾延迟无界）之间构成一条连续的「隔离—利用率」权衡曲线，这与存储/网络领域 Delta Fair Sharing 的定位一致，也说明该工作更适合被视为**服务等级目标（SLO）的实现机制**，而非单纯的调度算法改进。
- **两类延迟源的统一处理是其技术核心**：将「调度排队」与「KV cache 驱逐」纳入同一套截止时间框架，并用不可驱逐预留 `ρ_i` 把缓存公平与调度公平耦合起来，是相较纯排队论方法（VTC/DLPM）的本质差异。这也解释了为何在 Workload 1（前缀匹配差异）这类纯缓存干扰场景中，基线方法几乎无法改善 TTFT。
- **成熟度判断**：作为「ongoing project」，其贡献更偏**问题定义 + 可行原型 + 初步验证**，而非可直接投产的系统。理论结果（定理 1、2）主要起**界定适用边界**的作用，条件较保守，实际部署中需与限流、准入控制配合使用。

## 10. 对后续研究的启示

- **需要更紧的隔离延迟界**：当前对 decode 规模远小于最大值的轻量客户端无法给出紧 δ，根源在于「池化最大 vs 隔离最小」的保守配对。若引入**按客户端分组/分桶建模**或**在线校准**，有望显著收窄该间隙，使 δ 保证对异构负载更普适。
- **限流与隔离的联合设计**：论文已指出 δ 保证依赖 prefill 速率上界，但限流器本身未纳入系统。将速率控制、突发吸收与截止时间抬高策略一体化，是走向实用化的必经一步。
- **与批处理/前缀缓存机制的交互**：δ-fair 调度与连续批处理、RadixAttention 前缀共享之间存在潜在张力（保护预留可能降低前缀复用率），量化这一交互并寻找联合优化点是有价值的开放问题。
- **向多卡与 disaggregated 架构扩展**：在张量并行、PD 分离（prefill/decode 分机）部署下，KV 迁移与跨节点排队会引入新的延迟源，δ 的分解方式（`δ_cache + δ_prefill + δ_transfer`）需要重新设计。
- **端到端组合隔离**：将 token 级 δ 与工具调用/RAG 的各阶段 δ 累加为端到端保证（FairRAG 设想），是把该机制从「单模型服务」推向「agent 流水线」的关键延伸。
- **基准与评估规范**：目前缺乏统一的「多租户隔离」评测协议（干扰源构造、δ 口径、指标定义）。本文的 Workload 1/2 设计可作为起点，但社区仍需标准化基准以避免跨论文结论不可比。

## 11. 一句话结论

本文针对多租户 LLM 服务中「高需求客户端拖垮良好客户端」的问题，提出以逐 token 延迟上界 `d + δ` 为语义的 δ-token 公平性，并通过截止时间驱动的 EDF 调度与带不可驱逐预留的 δ-fair KV cache 策略在 SGLang 上实现 FairInference；实验表明其能在几乎不损失（甚至提升）系统吞吐的前提下，将良好客户端的 p99 TTFT/TBT/TTLT 从基线的数十倍劣化压缩至接近隔离水平，但受限于保守的隔离延迟界、对限流配合的依赖、单卡单模型验证以及缺失的消融与最新 SOTA 对比，其结论的普适性与生产可用性仍有待进一步验证。
