## 摘要
连续批处理提高了大语言模型（LLM）的服务吞吐量，但长提示的预填充可能会延迟解码迭代，并违反令牌间延迟目标。分块预填充缓解了这种干扰，但其块大小通常是固定的：小块能保护解码延迟，但会反复产生启动开销，而大块则提高预填充效率，却会引发延迟峰值。我们提出了SLOWeave，一种在线调度方法，它选择预测能在最早的活跃解码截止时间之前完成的最大预填充块。该决策无需针对工作负载的块大小调整，并通过在单调迭代成本模型上的对数时间搜索来计算。我们证明，只要仅解码迭代可行且成本预测器准确，SLOWeave就能在保留每个活跃请求的下一令牌截止时间的所有决策中，最大化即时预填充进度。我们在一个可重现的事件驱动模拟器和一个迭代级GPU运行时上，对聊天、混合上下文、长上下文和突发工作负载进行了评估。在25毫秒的每输出令牌时间目标下，SLOWeave相对于最强的固定块基线，在混合请求上的有效吞吐量提高了39%，在长上下文请求上提高了38%。在更严格的10毫秒目标下，增益分别上升至3.3倍和2.4倍。这些结果将自适应分块大小作为有用的服务原语，并提供了一个可直接实现的控制器，用于与迭代级LLM运行时集成。

## Abstract
Continuous batching improves large language model (LLM) serving throughput, but long prompt prefills can delay decode iterations and violate inter-token latency objectives. Chunked prefill mitigates this interference, yet its chunk size is normally fixed: small chunks protect decode latency but repeatedly pay launch overhead, while large chunks improve prefill efficiency but create latency spikes. We introduce SLOWeave, an online scheduling method that selects the largest prefill chunk predicted to finish before the earliest active decode deadline. The decision requires no workload-specific chunk-size tuning and is computed by a logarithmic-time search over a monotone iteration-cost model. We prove that, whenever a decode-only iteration is feasible and the cost predictor is accurate, SLOWeave maximizes immediate prefill progress among decisions that preserve every active request's next-token deadline. We evaluate the method in a reproducible event-driven simulator and an iteration-level GPU runtime across chat, mixed-context, long-context, and bursty workloads. Under a 25ms time-per-output-token objective, SLOWeave improves goodput over the strongest fixed-chunk baseline by 39% on mixed requests and 38% on long-context requests. Under a stricter 10ms objective, the gains rise to 3.3$\times$ and 2.4$\times$, respectively. These results isolate adaptive chunk sizing as a useful serving primitive and provide an implementation-ready controller for integration with iteration-level LLM runtimes.

# 截止时间感知的自适应预填充分块（SLOWeave）论文总结

## 一、核心问题与研究动机

- **问题背景**：LLM 服务周期分为 prefill（预填充，并行处理输入提示并构建 KV 缓存）和 decode（解码，逐 token 生成输出）两个阶段。现代运行时采用连续批处理将多个请求混合执行，但长 prefill 会阻塞正在进行的 decode 迭代，导致用户可见的响应停顿，违反“每输出 token 时间”（TPOT）等流式延迟目标。
- **现有方案不足**：
  - **分块预填充**（Chunked Prefill）可缓解 prefill 与 decode 之间的交互干扰，但通常使用**固定块大小**。
  - **小块**：保护 decode 延迟，但多次迭代反复支付调度和内核启动开销，降低吞吐、恶化 TTFT；
  - **大块**：摊销开销、加快单请求首 token 延迟，但会造成延迟尖峰，使部分请求错过 TPOT 截止时间。
- **核心矛盾**：最优块大小取决于 decode 批大小、提示长度、硬件、内核实现以及服务等级目标（SLO），使用单一静态值无法在不同负载和 SLO 下保持鲁棒。
- **口号**：论文主张“自适应的分块大小”是独立于注意力内核、KV 管理、模型并行等手段之外的一种重要的服务原语，并将该决策从人工调参转化为在线、受截止时间约束的调度决策。

## 二、方法论：SLOWeave 算法

### 1. 基本思想
在每个调度迭代中：
- 为每个活跃 decode 请求设定下一 token 截止时间 d_i = 最近一次 token 完成时间 + TPOT 目标 D；
- 取活跃解码集合中**最早的剩余预算** B_t；
- 通过迭代成本预测器，选择**在不早于任一活跃请求截止时间前完成的最大 prefill 块**。
- 当没有活跃 decode 时，则用最大块上限 C_max 加速 TTFT。

### 2. 核心公式与阈值判断
在非空活跃集 A_t 下，选择的块大小满足：

\[
c^*_t = \max\{ c \in \mathbb{Z}_{\ge 0} \mid c \le \min(C_{\max}, L_t),\; \hat{T}(|A_t|, c) + \delta(|A_t|, c) \le B_t\}
\]

其中：
- \(L_t\)：最早等待 prefill 的剩余 token 长度；
- \(B_t = \min_{i \in A_t}(\ell_i + D - s_t)\)，即最早的下一 token 截止时间对应的剩余时间预算；
- \(\hat{T}(n, c)\)：预测的混合迭代耗时（n 个 decode + c 个 prefill token）；
- \(\delta\)：为应对预测误差设定的保守边界（margin）；
- 成本模型只需满足对 c 的单调性，不限定具体形式（可以是查找表、回归器或解析模型）。

### 3. 实现与复杂度
- **算法流程**（每个迭代）：
  1. 若无 pending prefill → 执行 decode-only 迭代；
  2. 否则，取最老待 prefill 请求，且限制长度 L = min(C_max, remaining)；
  3. 若活跃解码为空 → 直接用 L 作为 chunk；
  4. 否则计算最小剩余预算 B；
  5. 对 c ∈ [0, L] 执行二分搜索（binary search），找到满足 \(\hat{T} + \delta \le B\) 的最大 c。
- **复杂度**：二分搜索 O(log C_max) 次代价模型查询；采用堆记录最早截止时间可将扫描活跃集的开销降为 O(log |A|)。
- **批量处理扩展**：算法支持一次迭代容纳多个 prefill 请求（向量化后变成小型背包问题），但实现默认一次一个 pending prefill，以隔离 chunk sizing 的影响。
- **总结安全性证明（Proposition 1）**：若成本预测模型精确且对 c 单调，则 SLOWeave 选出的块既保证在任一活跃解码截止时间前完成，又是所有“安全”块中最大的（实时 prefill 进度最大）。预测误差可通过保留 margin 来部分吸收（如用 P99 残差表）。

### 4. 工程面与兼容性
- 仅需三项最小运行时修改：调度器（调用 SLOWeave）、profiler（测量 T(n,c) 并产生单调查找表）、执行器（接受变长 chunk）；KV 管理器无需调整布局。
- 兼容 vLLM 风格调度：token 预算被当作上界而非固定块长。
- 队列纪律与所选请求的规则独立：可搭配 oldest-first、最短剩余 prefer，或其他公平策略，而安全论证不受影响。
- 支持异构 SLO（per-request 的 D_i）和多优先级类别：只需将 deadline 设为 ℓ_i + D_i 即可。

## 四、主要结论与关键发现

### 1. 核心性能提升（25 ms TPOT）
| 负载 | SLOWeave 相对最强固定基线 goodput 提升 |
|---|---|
| Mixed | 从 42.4 req/s → 59.0 req/s，相对提升 **39%** |
| Long | 从 18.4 → 25.4 req/s，相对提升 **38%** |
| Bursty | 相对提升 ~9%（51.7 → 56.5） |
| Chat | 与其他策略接近（~102 req/s），无明显退化 |

在更严格 10 ms TPOT 目标下，Mixed 和 Long 的相应增益分别上升至 **3.3×** 与 **2.4×**（表 4 的 Summary：Mixed 3.35×，Long 2.45×，Bursty 2.39×）。  
在宽松（50 ms）下，SLOWeave 自动恢复成“整段 prefill”行为，与 Full prefill 持平——表明该方法在不同 deadline 范围内表现均稳健。

### 2. 效果分解
- **增益来源 1**：当 decode 批较小时增大块，摊销固定 prefill 开销；
- **增益来源 2**：在 decode 批增大时缩小块，避免压过 TPTOT 截止时间；
- 固定块策略只覆盖其中一个方向，而 SLOWeave 持续“用满” slack 将 chunk 推到 deadline 边界；P99 TPOT 约等同目标值（~25ms）而非远低于目标，证明绝大多数 slack 转化为 prefill 进度。

### 3. GPU 实测佐证
- A100/8B mixed：SLOWeave goodput 67.1 vs Fixed-1024 52.7（+27%）；P99 TTFT 与请求成功率均有胜出；
- H100/70B-TP8 long：goodput 40.8 vs 31.4（+30%）；energy/valid req 从 73.8 J 降到 58.5 J；
- A100/8B bursty：从 Fixed-512 的 44.2 提升至 50.6 req/s。

## 六、不足与局限

- **论文自行承认的局限**：
  - 迭代真实成本存在非平滑性（内核切换、tensor parallel 通信、内存压力、前缀缓存命中）——用 profiled Lookup-table 加一个高百分位 margin 吸收误差，但没有进行大规模校准漂移研究；

  - 不考虑 preemption 成本和 KV 传输成本；
  - 评估未覆盖多节点 KV 迁移和跨区域服务场景。
- **实验覆盖面限制（外部视角）**：
  - 硬件节点只包含单节点的 A100/H100，虽然覆盖 8B/70B-TP4/TP8，但未开展跨多节点、异质性硬件如 T4/L40S 的扩展性测试；

  - 对“成本模型驱动”的依赖较重：若运行时内核模型漂移超出预设 margin，效果会减弱；论文只给出边界条件下的定量结果，未提供广泛模型/硬件失效边界分析。
- **公平性潜在偏倚**：
  - 论文主动选择“同一 C_max、相同队列纪律、相同连续批处理”来做对比，尚未量化不同队列策略和不同预填充请求选择对 SLA 达成率变动的交互；

## 七、总结

> SLOWeave 是一个轻量、优雅且实现成本极低的调度控制器，以“在每个解码 deadline 之前最大化可安全插入的 prefill 进度”为核心目标，借助单调成本模型实现对可变块大小的在线、免调参决策。其关键价值在于将传统上依赖人工经验去调节的分块策略转化成了一个可持续获得理论保证和实操收益的服务原语，在混合负载与严格 TPOT 场景下相对固定块能带来成倍的好 put 提升。
