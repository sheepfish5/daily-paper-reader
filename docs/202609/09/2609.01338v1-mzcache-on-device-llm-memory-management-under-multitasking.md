## 摘要
移动设备上的大语言模型（LLM）本地推理正受到广泛关注。然而，移动设备运行在高度动态的多任务环境中，用户会频繁在应用之间切换。这会造成内存压力，迫使操作系统将LLM的内存（模型权重和KV缓存）逐出。当新的推理请求到达时，推理系统必须通过缓慢的存储读取来恢复被逐出的内存，或重新计算整个KV缓存，这严重降低了响应速度。为了解决这个问题，我们提出了mzCache，一个针对多任务环境、具有专门内存管理的设备端LLM推理系统。在不可预测的内存压力下，mzCache弹性地逐出LLM内存，并利用移动SoC的统一内存，在CPU端并发进行内存恢复的同时，实现GPU上的零等待推理。mzCache通过面向恢复的内存管理实现这一点：LLM内存被划分为细粒度的共享缓冲区，以支持部分逐出与恢复以及跨处理器的并发访问，同时混合交换（swap）和反向逐出（backward-out）策略确保从任何逐出状态都能实现低延迟恢复。mzCache基于llama.cpp实现，并作为Android应用部署，与基于存储的部分卸载相比，将首令牌时间（Time-to-First-Token）降低了2.1-5.5倍，并在真实多任务场景中展示了其有效性。

## Abstract
On-device mobile Large Language Model (LLM) inference is gaining significant attention. However, mobile devices operate in highly dynamic multitasking environments where users frequently switch between applications. This creates memory pressure, forcing LLM memory (model weights and KV cache) to be evicted by the operating system. When a new inference request arrives, the inference system must restore the evicted memory through slow storage reads or recompute the entire KV cache, severely degrading responsiveness. To address this, we present mzCache, an on-device LLM inference system with specialized memory management for multitasking environments. Under unpredictable memory pressure, mzCache elastically evicts LLM memory and leverages the unified memory of mobile SoCs to enable zero-wait inference on the GPU with concurrent CPU-side restoration. mzCache realizes this through restoration-oriented memory management: LLM memory is partitioned into fine-grained shared buffers to enable partial eviction and restoration with concurrent cross-processor access, while hybrid swap and backward-out eviction policies ensure low-latency restoration from any eviction state. Implemented on llama.cpp and deployed as an Android application, mzCache achieves 2.1-5.5$\times$ reduction in Time-to-First-Token compared to storage-backed partial offload and demonstrates its effectiveness in real multitasking scenarios.

## 1. 论文的核心问题与整体含义（研究动机与背景）

论文聚焦于以下现实矛盾：

- **背景与痛点**：大模型服务正逐渐从“云端计算”转向“端侧推理”。移动设备上用户会频繁切换使用各类应用（如社媒、游戏、相机、视频等），系统会产生高度动态的内存压力。
- **问题的核心**：设备端大模型的运行需要同时占用**模型权重**（如 2.6 GB）与**KV 缓存**（可达 3–4 GB），总体占用常超过 5–7 GB，挤占移动设备有限的物理内存（典型为 12 GB）。
- **系统级困境**：在系统内存压力升高时，操作系统会通过 swap 或回收页面的方式来挤出内存；但由于移动端通用压缩算法（lz4、zstd）对大模型 KV 缓存几乎无效（空间节省仅有 0.2%–9.3%），最终系统无法回收有效内存，只能依靠 Low-Memory Killer（LMK）终止大模型进程。
- **结果**：一旦进程被终止，再次返回大模型应用时需重新从闪存加载模型权重，并从头重新计算 KV 缓存。这一冷启动过程会造成 0.8–16 秒的首 Token 延迟，用户体验被严重损害。
- **核心考察点**：现有移动端大模型推理系统普遍只关注推理过程的加速，却**缺少对大模型内存的分级和受控管理**。系统自身无法在空闲阶段自发释放内存，也无法从上一轮部分驱逐状态中快速恢复，导致多任务场景下响应速度大幅恶化。

由此，论文提出一个全新的系统研究视角——从“面向恢复的内存管理”（restoration-oriented memory management）出发，设计了 **mzCache**。

## 2. 论文提出的方法论：核心思想、关键技术细节与算法流程

论文整体方法可概括为下面的子系统框架：

- **mzCache 的整体状态机与运行阶段**
  - 每个完整周期分为“空闲阶段”（Idle）和“推理阶段”（Inference）。
  - 外部系统可在空闲阶段以“内存释放请求”的方式要求 mzCache 腾出指定大小的内存。
  - 推理请求唤醒系统时，mzCache 首先按顺序恢复被驱逐的部分，同时在“尚未恢复完毕”的情况下就让 GPU 提前开始计算，保证 GPU 无需真正等待恢复完成即可产生首 Token。

- **细粒度的共享缓冲区内存管理**
  - 放弃“一次分配一大块连续缓冲区”（monolithic allocation）的方案。
  - 权重以**每个 Transformer 层**为粒度切分；KV 缓存以**每个 Token 组块**为单位进一步细分（每 256 tokens 为一个 chunk）。
  - 这些数据在 CPU/GPU 间保持共享，mzCache 通过 OpenCL 的 Shared Virtual Memory（SVM）实现共享内存，替代高速互联的独立显存结构，从而充分利用移动端 SoC 的统一内存架构。

- **三级恢复与并行机制**
  - 恢复时 CPU 负责内存分配、读闪存、解压等操作，同时 GPU 可直接读取已恢复的层，执行 Prefill 计算。
  - 由于统一内存天然支持 CPU/GPU 交换数据，系统可以做到“恢复部分”与“推理计算部分”的流水线重叠。
  - mzCache 自行实现了支持连续在线 softmax 的 GPU 注意力 kernel，避免 KV 组块非连续带来的遍历和拼接问题。

- **混合交换（Hybrid Swap）策略**
  - mzCache 不把 KV 缓存全放在内存压缩区或全放在 flash 上，而是为 KV 缓存提供**双交换通道**：内存压缩区（in-memory swap）和存储交换区（storage swap）。
  - 其中模型权重较重且相对无法有效压缩，因此权重只走存储通道；KV 组块具备高压缩潜力，用于平衡两个恢复路径。
  - 采用离线 profiling 方法，一次性测量特定设备上的“解压单块 KV 时间 \(t^{KV}_d\)”和“读单块 KV 时间 \(t^{KV}_r\)”，以及“读取单层权重时间 \(t^W_r\)”。
  - 根据这些时间得到系统能在权重恢复期间处理的 KV 组块数阈值：
    \[
    T = N_{total}^W \cdot \lfloor t^W_r / t^{KV}_d \rfloor
    \]
  - 四个驱逐阶段轮流触发（详细见图 7 中的算法流程）：
    - **阶段 1：仅逐出 KV（KVonly）**——当缓存中 KV 组块数多于阈值 \(T\) 时，优先按两个路径的速度反向配比，将 KV 组块同时交换到“内存压缩区”和“存储区”。
    - **阶段 2：KV 与权重同逐出（KVandW）**——当 KV 组块数量降到阈值后，每从内存中丢弃一个权重层，就相应压缩约 \((t^W_r/t^{KV}_d)\) 个 KV 组块。
    - **阶段 3：仅逐出权重（Wonly）**——如果 KV 组块全部被压缩完仍有内存压力，则开始继续丢权重。
    - **阶段 4：压缩 KV 的二次换出（CompKV）**——此前存入内存压缩区的 KV 都被换到存储以释放全部内存。
  - 上述策略确保不管驱逐停在哪一个阶段，两条路径恢复时都能大致同时完成，因此其联合吞吐最大化。

- **反向逐出、前向恢复的载入策略**
  - 传统 LRU 风格策略会先逐出最早层（第 1 层附近），这意味着即使只被驱逐少量空间，PreFill 也要等待第 1 层恢复后才能启动。
  - mzCache 采用“反向逐出”（backward-out）策略：驱逐时从最后一个 Transformer 层开始向前的顺序逐出；这保证早期层尽量不被逐出，因此只要早期层还在，GPU 就可以提前启动计算。
  - 恢复时则按前向（forward-in）的层顺序恢复，正好与模型逐层执行顺序一致，实现 GPU 和 CPU 同步流水化作业。
  - 同时在内存中采用“栈”结构组织压缩 KV 组块，天然满足 LIFO 换出顺序，扩容和降容成本低。

- **压缩子系统的模块化**
  - 论文默认使用 8-bit 量化压缩 KV，同时（在评测中）支持 CacheGen 压缩，形成模块化可插拔接口。
  - 压缩/解压采用 ARM NEON SIMD 指令集实现，保证手机 CPU 上的低延迟解压。

## 6. 论文的主要结论与发现

- **首要发现**：操作系统对大模型权重和 KV 缓存的内存回收机制非常低效，zRAM 几乎无法压缩 KV Cache，导致 LMK 经常杀掉大模型进程并产生 5–20 倍的 TTFT 膨胀。
- **总体效果**：mzCache 在 Top-level TTFT 上比基于存储的部分卸载快 2.1–5.5 倍；在 GPU 上零等待即可开始 Prefill。
- **组件贡献**：
  - 细粒度共享缓冲区与并行分配使分配速度提升 1.37×；
  - 在 CPU 与 GPU 免拷贝重叠模式下，重载速度提升 2.15×；
  - 自定义注意力核在移动 GPU 上的 Prefill 性能提升 2.33×；
  - 完整重叠带来 1.61× 的总提速。
- **策略贡献**：
  - 反向逐出策略使 GPU 无需等待浅层恢复，有效消除 Prefill 空窗；
  - 混合交换策略让两条恢复路径在任意量级的部分驱逐后都接近负载均衡。
- **压缩比较**：高压缩率的算法（CacheGen）适合大量被逐到存储的场景；更快解压的算法（8-bit 量化）适合内存内恢复场景。压缩算法模块化可依据需求进行取舍。
- **功耗**：mzCache 峰值功率更高（并行使用 GPU、CPU 和存储），但恢复和总完成时间更短，总能量消耗低于 Partial Offload。
- **真实部署**：在真实多应用干扰下 OS 默认机制的进程全部被 LMK 杀死，而 mzCache 以 25 pp 的驱逐量能够保留 KV 缓存并避免冷启动。

## 7. 优点：方法与实验设计上的亮点

- **问题定位精准**
  论文抓住 OS 内存管理与端侧大模型特性间的冲突（压缩率低下、驱逐不可控、恢复路径受限），形成了一个合理的动机闭环。

- **设计具有系统级视角**
  不只停留在硬件核函数加速，而是将“空闲阶段与推理阶段”、CPU/GPU 协同和统一内存特性作整体思考；这种跨层设计在移动端推理领域较新颖。

- **方法具备“恢复导向”的强自洽性**
  从“动态不可预测的恢复量”出发，推导出可应对任何驱逐比例的最优恢复策略（层层递进的混合交换系统），形成严密的逻辑链路。

- **硬件与上层策略结合紧密**
  离线 profiling 与阈值计算公式依据每台设备的真实 I/O 特性而不依赖静态启发式，使方案具备较好的跨设备可迁移性。

- **工程完成度高**：代码以 6k 行在 llama.cpp 上实现，系统具备可直接部署的 Android 应用原型，不是纯仿真论文。

- **实验方法论公正且量化详尽**
  基线（Partial Offload）也被明确扩展以支持部分逐出，从而构造出没有明显“不公平对比”的参照系；并且自报告多角度消融结果、功耗结果、压缩结果以及真实场景结果。

## 8. 不足与局限

- **实验覆盖范围仍有限**
  - 模型只在 0.6B 和 1.2B 两个“轻量级”范围内比较；LLM 部署到手机时，3B 上下会是更常见的界别，缺乏相应的验证。
