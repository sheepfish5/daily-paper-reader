## 摘要
通信已成为大模型分布式训练和推理中的瓶颈。以内核为粒度、在不同流上重叠通信与计算，只能减少其中一部分通信开销。融合内核通常通过在每个输出 tile 一经产生就立即传输来获得更好的性能，但现有融合内核在很大程度上局限于单个 NVLink 域。我们提出 mKernel，一个多 GPU、多节点的融合内核库，可在 tile 粒度上重叠计算、节点内 NVLink 通信和节点间 RDMA。mKernel 将持久化内核的流式多处理器（SM）划分为计算角色和通信角色，并由 GPU 上的控制器在运行时自适应地调整 SM 划分，因为最佳 SM 划分会随内核和输入形状而变化。它采用分层方式组织数据移动，从而最小化穿越节点间网络的数据量。最后，它通过直接基于 RDMA verbs 实现的轻量级命令队列和主机代理，从 GPU 驱动网络，这使得相同的内核可以在任何网络后端上运行（例如 InfiniBand 和 AWS EFA）；我们惊讶地观察到，GPUDirect Async（IBGDA）相比主机辅助的 GPU 发起通信几乎没有带来额外收益。我们实现了五个内核，涵盖张量并行、序列并行和专家并行。在两个 16-GPU H200 集群上，mKernel 在 GEMM+AllReduce 上实现了最高 1.72 倍的加速，在 Ring Attention 上实现了 $1.88\times$ 的加速。

## Abstract
Communication has become a bottleneck in distributed training and inference of large models. Overlapping communication with computation at the granularity of kernels, on separate streams, reduces only part of this communication cost. Fused kernels often have better performance by transmitting each output tile as soon as it is produced, but existing fused kernels are largely confined to a single NVLink domain. We present mKernel, a library of multi-GPU, multi-node fused kernels that overlap computation, intra-node NVLink communication, and inter-node RDMA at tile granularity. mKernel partitions the streaming multiprocessors (SMs) of a persistent kernel into compute and communication roles, and an on-GPU controller tunes the SM partition adaptively at run time, since the best SM partition varies with the kernel and the input shape. It structures data movement hierarchically so that data traversing the inter-node network is minimized. Finally, it drives the network from the GPU through a lightweight command queue and host proxy implemented directly on RDMA verbs, which allows the same kernels to run on any network backend (e.g. InfiniBand and on AWS EFA); we observe, surprisingly, that GPUDirect Async (IBGDA) yields little additional benefit over host-assisted GPU-initiated communication. We implement five kernels spanning tensor, sequence, and expert parallelism. On two 16-GPU H200 clusters, mKernel achieves speedups of up to 1.72x on GEMM+AllReduce and $1.88\times$ on Ring Attention.

- **通信已成为大模型分布式训练与推理的瓶颈**：在生产级 MoE 训练中，通信占前向传播的 43.6%、端到端训练时间的 32%；在主流 MoE 模型与框架中，设备间通信最高占执行时间的 47%。
- **算力与网络带宽的失衡在加剧**：GB300 NVL72 单机架提供 720 PFLOP/s 的 FP8 算力，但每张 GPU 出机架仅靠一条 400–800 Gb/s 的 NIC。跨节点网络带宽约为 NVLink 的 1/9，两个层级无法等同对待。
- **现有重叠方案的粒度不足**：
  - 节点内融合（图 1a）：计算与本地传输重叠，但跨节点通信仍交给独立的集合通信。
  - 双流流水线（图 1b）：按 chunk 重叠，但每个 chunk 只在生产者内核边界才被释放。
  - Tile 级融合（如 Flux、Comet、TileLink 等）：粒度更细，但**大多局限于单节点**，且往往只融合计算、节点内通信、节点间通信中的部分阶段。
- **论文目标**：提出 mKernel，一个**多 GPU、多节点融合内核库**，在 tile 粒度上同时重叠计算、节点内 NVLink 通信与节点间 RDMA，并把 tile 级就绪信号贯穿三个阶段。
- **跨节点融合的额外难点**：带宽不对称；NIC 是独立 PCIe 设备、有独立工作队列，GPUDirect Async 需要 NIC 支持；传输语义不同（InfiniBand RC 保序，而 AWS EFA 的 SRD 不保序，完成标志可能先于数据可见）。

## 2. 方法论

### 2.1 核心思想与四大设计原则

1. **SM 特化（SM specialization）**：持久化内核的线程块被分配为计算、节点内通信、节点间发送、节点间接收四类角色。
2. **分层数据移动（hierarchical data movement）**：先在节点内通过 NVSwitch 做归约/广播，再与"同轨对等体（rail peer，跨节点同 GPU 序号）"交换，最小化穿越节点间网络的流量。
3. **可移植的主机辅助 GPU 发起通信**：内核只向主机内存环形队列写入紧凑命令，由主机代理线程通过 libibverbs 直接提交 RDMA 写，不依赖 NCCL/NVSHMEM，同一套内核可跑 InfiniBand（ConnectX-7）与 AWS EFA。
4. **运行时动态 SM 划分**：由 GPU 上的控制器根据实测进度与剩余工作量调整计算–通信 SM 配比。

### 2.2 关键技术细节

- **粒度解耦**：计算 tile、本地传输、网络 chunk、提交 batch 四者尺寸独立。例如 GEMM+AllReduce 把 4 个本地归约 tile 组成 256 KiB 网络 chunk；Dispatch+GEMM 中接收端按 512 KiB chunk 检查 token 是否到齐。
- **就绪信号分离**：区分"tile 就绪"与"消息就绪"；用 per-chunk 计数器让最后一个完成 tile 发布就绪，无需等待整个 GEMM 结束。
- **命令发布与背压**：发送块在 pinned 主机内存环形缓冲区发布 **48 字节命令**（含 peer、源/目的偏移、字节数、chunk id）；先写命令体再提交头部，代理轮询头部；通过队列信用与未完成请求上限做背压。
- **批量提交但保留 per-chunk 完成**：代理把同一连接最多 8 条就绪命令合并提交，但每条命令保留独立传输与到达通知；支持有界轮询窗口的部分批量提交。
- **传输语义适配**：
  - *InfiniBand*：同一条 RC 连接上先写数据、再写小 flag，接收块轮询 GPU 内存中的 flag（依赖数据先于 flag 的顺序）。
  - *AWS EFA (SRD)*：使用 RDMA write with immediate，immediate 值标识 chunk，由接收端代理在写完成后再发布到达 flag，避免用独立 flag 的到达顺序推断 payload 完成。

### 2.3 关键公式（文字说明）

- **融合内核执行时间模型**：
  `T_fused ≈ max( T_compute · S/(S−Sc), T_NVLink, T_network ) + T_fill/drain + T_sync`
  其中 S 为 SM 总数，Sc 为分配给通信的 SM 数。含义是：通信 SM 越多通信越快、但计算越慢，存在最优折中；同时因带宽差异，T_network 常常成为主导项，这激励了分层通信与自适应分配。
- **自适应 SM 目标值**：控制器用线程块累积的周期计数器估计计算/通信每任务成本，令两类角色预测完成时间相等，得到目标通信块数
  `n*_s = B · (R_s/C_s) / (R_p/C_p + R_s/C_s)`
  其中 B 为总块数，R_p、R_s 为剩余计算/通信任务数，C_p、C_s 为估计成本。当通信为计算提供输入时，等待输入的块可临时协助通信。

## 6. 主要结论与发现

- 在 16-GPU H200 集群上，相对"cuBLAS/FlashAttention + NCCL"的非融合基线：
  - **AllGather+GEMM**：最高 1.41×（EFA）/ 1.34×（ConnectX-7）
  - **GEMM+AllReduce**：最高 1.53×（EFA）/ **1.72×**（ConnectX-7）
  - **GEMM+ReduceScatter**：大问题（M ≥ 16K）下 1.02–1.27×
  - **MoE Dispatch+GEMM**：EFA 上相对 all-to-all+GEMM 加速 3.1–4.5×
  - **Ring Attention**：最高 1.78×（EFA）/ **1.88×**（ConnectX-7）
- 与融合基线相比：Ring Attention 相对 MagiAttention 快 1.4–3.3×、相对 ring-flash-attention 快 2.3–5.6×、相对 Mercury 快 2.2–8.6×、相对 Triton-distributed 快 1.1–1.7×（后者在最长序列上失败）。
- **自适应 SM 划分有效**：不同内核/问题规模的最优通信 SM 数在 2–64 之间变化；最差的 AllReduce 静态划分比最优慢约 25×；自适应控制器无需逐形状调参即可达到静态最优固定划分的几何平均 1.18×。
- **一个反直觉发现**：在测试场景下，**GPUDirect Async（IBGDA）相对主机辅助 GPU 发起通信几乎没有性能收益**（吞吐比约 0.91–1.03）。原因是主机代理可重叠提交并批量下发，而 IBGDA 每个 chunk 需要昂贵的 system-scoped GPU fence 与 doorbell。

## 7. 优点

- **问题定位准确且前沿**：明确指出"融合内核止步于单 NVLink 域"这一空白，并给出跨节点融合的系统性约束分析（C1–C5）。
- **粒度解耦设计优雅**：将计算 tile / 本地传输 / 网络 chunk / 提交 batch 四层粒度独立化，既保留 tile 级早期发送，又摊销了 RDMA 每消息开销。
- **可移植性强**：直接基于 libibverbs 实现，不依赖 NCCL/NVSHMEM，同一套内核同时支持 InfiniBand 与 AWS EFA，并针对两者不同的顺序语义给出各自的完成通知方案。
- **自适应控制器轻量且有效**：仅用周期计数器估计成本，目标公式简单，能达到静态最优的 1.18× 几何平均，避免了逐形状 profiling 与维护成本。
- **工程贡献扎实且开源**：五个真实内核（TP/SP/EP）实现 + 开源代码 + 多基线实测；对 IBGDA 的负面/中性结论也具有实际工程参考价值。
- **实验方法学较为严谨**：以最慢 rank 计时、预热、末尾单次同步，符合分布式内核评测惯例。

- **对比对象选择有偏向**：跨节点发起路径只对比了 IBGDA 与主机辅助两条路线，未与 NVSHMEM 的完整路径（含其信号/同步机制）做端到端对照，因此"不依赖 NCCL/NVSHMEM"的可移植性优势缺少同口径的性能证据。
- **通用性与可扩展性论证不足**：五个内核均为特定通信模式的手写实现，论文对库级编程模型、抽象接口、扩展到新算子（如 EP 的 Combine、流水线并行的 P2P、序列并行的其他变体）的成本描述较少，难以判断该方法是"通用框架"还是"五个高质量内核的集合"。
- **容错与鲁棒性未涉及**：未讨论 NIC/链路故障、命令队列溢出、代理线程异常等生产环境下的降级与恢复策略。

## 9. 可复现性

- **有利因素**：代码开源；硬件与软件栈交代清楚（2 节点 × 8 H200、NVLink/NVSwitch 450 GB/s、CUDA 12.9、sm_90a、每 GPU 一进程）；网络配置（ConnectX-7 8×400 Gb/s、EFA 16×200 Gb/s）与基线版本均明确；计时方法（预热、最慢 rank、末尾单次同步）描述规范。
- **不利因素**：AWS EFA 集群为特定云资源，跨平台引用 ConnectX-7 数据的做法使部分图表难以严格复现；MoE 基线假设均匀路由，实际 MoE 负载的路由分布会显著影响结论；自适应实验依赖 H100 单节点环境，与主实验平台不一致。
- **总体判断**：核心机制与主要趋势（跨节点融合的有效性、自适应的必要性、IBGDA 收益有限）具备较强可复现性；但具体加速比数字在换硬件/换负载分布后可能明显漂移。

## 10. 总体评价与对领域的意义

- **定位**：mKernel 是把"tile 级融合"这一单节点成熟范式系统性地推进到多节点、多传输层级的早期代表性工作之一，填补了"融合内核止步于 NVLink 域"的空白。
- **方法论层面的可借鉴点**：
  1. **粒度解耦**（计算 tile / 本地传输 / 网络 chunk / 提交 batch 四层独立）是一条通用经验——它同时解决了"早期发送"与"摊销每消息开销"两个相互冲突的目标，可迁移到其他通信密集算子。
  2. **SM 特化 + 运行时自适应划分**给出了一种低成本的负载均衡路径，其"用周期计数器估计成本、令两侧预测完成时间相等"的思路简单且不依赖 profiling。
  3. **传输语义适配**（IB RC 的顺序依赖 vs. EFA SRD 的非顺序完成）提醒后续工作在跨厂商网络上必须显式处理完成通知语义，而不能沿用单一假设。
- **对工程实践的启示**：IBGDA 在"主机可重叠提交并批量下发"的场景下并无优势，这一反直觉结论对"是否值得为 GPUDirect Async 投入工程成本"具有直接参考价值。
- **主要保留意见**：结论建立在 2 节点、16 GPU 的微基准之上，缺少端到端验证与更大规模拓扑检验；部分基线对比口径不完全一致，加速比应视为上界估计。因此本文更适合被读作"跨节点融合内核可行性与设计空间的系统性探索"，而非"已被端到端验证的生产方案"。
- **后续可期待方向**：扩展到 ≥4 节点的 ring forwarding、端到端训练/推理集成、多节点下的自适应控制器验证、以及更完整的消融与正确性验证。
