## 摘要
现代 AI 系统建立在 Transformer 架构之上，其核心操作——注意力——占据了大部分计算和内存开销。研究人员不断提出新的注意力变体，以提升质量、效率或上下文长度，但每个变体目前都需要专家编写的 GPU 代码才能以可用速度运行。PyTorch 最近的 flex_attention 让研究人员可以用 Python 描述自定义注意力模式，并将其编译为融合内核，但其设计仅限于在核心矩阵乘法之后应用的修改，排除了 Rotary Position Embedding（RoPE）——每个主流 LLM 都使用的位置编码。我们提出 AttnFuse，一个用于注意力的轻量级 DSL，使 RoPE 等乘法前变换成为一等操作。研究人员组合十个高层构建块来描述一个变体，AttnFuse 的编译器会为整个计算生成单个融合 GPU 内核。在 RTX 3090 上，AttnFuse 在 RoPE+causal 模式上相比 flex_attention 实现了 2.10× 加速。在 H100 上，它运行完整的 Llama-3-8B 训练步骤，性能与 PyTorch 手工调优后端相差在 5% 以内。我们的研究揭示了旋转演算（Rotation Calculus）：是融合 RoPE 还是单独应用 RoPE，取决于 GPU 的计算与带宽之比，并推导出一个与测量结果吻合的交叉点。AttnFuse 表明，一个小型、面向注意力的编译器可以弥合灵活研究代码与生产内核之间的差距。

## Abstract
Modern AI systems are built on the Transformer architecture, whose core operation, attention, accounts for the majority of computation and memory cost. Researchers continually propose new attention variants to improve quality, efficiency, or context length, but each variant currently requires expert-written GPU code to run at usable speeds. PyTorch's recent flex\_attention lets researchers describe custom attention patterns in Python and compile them to fused kernels, but its design is limited to modifications applied after the central matrix multiplication, excluding Rotary Position Embedding (RoPE), the positional encoding used by every major LLM.   We introduce AttnFuse, a small DSL for attention that makes pre-multiplication transformations like RoPE first-class operations. Researchers compose ten high-level building blocks to describe a variant, and AttnFuse's compiler emits a single fused GPU kernel for the entire computation. On an RTX 3090, AttnFuse achieves a 2.10$\times$ speedup over flex\_attention on the RoPE+causal pattern. On an H100, it runs a full Llama-3-8B training step within 5\% of PyTorch's hand-tuned backend. Our investigation reveals the Rotation Calculus: whether to fuse RoPE or apply it separately depends on the GPU's compute-to-bandwidth ratio, with a derived crossover that matches measurement. AttnFuse demonstrates that a small, attention-specific compiler can close the gap between flexible research code and production kernels.

## 1. 核心问题与研究动机

- **注意力瓶颈**：Transformer 是现代 AI 系统的核心，而注意力操作占据其中大部分计算与显存开销。注意力本质上是访存密集型操作，朴素实现会把完整的 N×N 分数矩阵写入片外显存，长序列下开销难以承受。
- **融合内核的价值与局限**：FlashAttention 通过在线 softmax（online softmax）与分块执行，将中间状态保留在寄存器中，把片外访存从 O(N²) 降到 O(N)，但它固定且不灵活。
- **研究者的两难**：研究者不断提出滑动窗口、线性偏置、稀疏模式等新变体，但每个变体都需要专家手写 GPU 代码才能高效运行，形成"高层 Python 灵活但慢、生产内核快但死板"的鸿沟。
- **flex_attention 的关键缺陷**：PyTorch 2.5 的 flex_attention 让研究者用 Python 的 `score_mod` 描述自定义注意力，但其修改函数作用于 QKᵀ **之后**。RoPE（被 LLaMA、Mistral、Qwen、DeepSeek 等所有主流 LLM 采用的位置编码）在乘前对 Q、K 分别旋转，无法用乘后修改表达，只能退化为单独 kernel 预旋转，付出两次额外访存往返。
- **论文整体含义**：AttnFuse 是一个注意力专用的可组合 DSL，将 RoPE 等**乘前变换**设为一等操作，在抽象层面严格比 flex_attention 更通用，并证明小型领域专用编译器可以同时兼顾研究灵活性与生产性能。

## 2. 方法论

### 2.1 核心思想
- 用十个高层组合子（combinator）声明式描述注意力变体，编译器保证**任意良构程序都融合为单个 GPU 内核**。
- 十个组合子：`scaled dot product`、`rope`、`causal`、`sliding window`、`full`、`block sparse`、`alibi`、`additive bias`、`softmax`、`relu attention`。
- 典型写法：`softmax(causal(rope(Q, K))) @ V`，其中 `rope()` 是乘前操作。
- DSL 刻意"窄化"：不能表达 flex_attention 那种任意 `score_mod` 回调——正是这种窄化使编译器能对显存行为与内核结构给出强保证。

### 2.2 四层编译流水线
`用户 DSL → 高层 IR → Triton 内核 → 运行时调度`

- **Fuse 遍**：识别规范注意力模式（分数计算、掩码、归一化、值聚合），验证图可融合。
- **Tile 遍**：依据目标 GPU 架构与变体选择 tile 尺寸（block 维度、warp 数、流水级数），调优表来自预先扫描。
- **Lower 遍**：将图转换为扁平的 `TiledKernel` 记录，携带全部代码生成常量。
- **Codegen 遍**：生成 Triton 源码，无运行时分支，变体逻辑在编译期经 `constexpr` 解析。

### 2.3 IR 与缓存
- 高层 IR 含六种节点：`TensorSym`（输入张量）、`ScoreOp`（分数计算）、`MaskOp`/`BiasOp`（修改）、`NormOp`（softmax 变体）、`MatMulPV`（值聚合）。
- 每张图计算 SHA-1 结构签名，作为编译内核的缓存键。
- 低层 IR 记录 tile 形状、架构标志及 `ROPE_KIND`、`MASK_KIND`、`SAVE_L` 等常量。

### 2.4 运行时调度与关键优化
- 调度开销 < 1 μs，含三条快速路径：
  - **Flash Decoding**：Q 批大小为 1（自回归推理）时把 KV cache 切分到多个 program；GQA 下将每 program 的 query head 循环复制填充至 16，K/V 每 program 只加载一次。两阶段：并行计算部分 (m, ℓ, acc) → 用 log-sum-exp 合并。
  - **块稀疏**：用户提供块坐标谓词，`create_block_mask` 求值一次并返回 CSR 风格 `BlockMask`，前向与反向均只迭代活跃块，产生真正亚二次 FLOPs。
  - **Hopper spike**：H100 上因果注意力的 tile 扫描调优变体。
- **融合 RoPE 实现**：query 矩阵在外层循环前旋转一次，每个 key tile 在内层循环中即时旋转（NeoX 约定），用预计算的索引偏移与符号乘子访问向量的旋转半部分。
- **反向传播**：沿用 FlashAttention-2 设计，拆成三个 kernel（行梯度预处理、K/V 梯度累加、Q 梯度累加），避免原子累加；前向每 query 行只保存一个标量 `L = m + log ℓ`。

### 2.5 旋转演算（Rotation Calculus）
- 判断 RoPE 应融合还是预旋转，取决于平台的**计算-带宽比**。
- 预旋转代价：`T_pre = 4BHND · 2/BW` 秒（读 Q、K，写 Q′、K′）。
- 融合内旋转代价：`T_fused ≈ N_tiles · c_rot`，其中 `N_tiles = BHN²/(B_M·B_N)`，`c_rot` 为每 tile 旋转周期数（Hopper 上约 800 cycles）。
- 令二者相等推导交叉点：**N\* ≈ √(8D · B_M · B_N · (FLOPS/BW) / c_rot)**。
- 代入 H100 NVL 参数（BW = 3.9 TB/s、FLOPS = 10¹⁵、B_M = B_N = 128、D = 64、c_rot = 800）得 N\* ≈ 6000，与实测 4k–8k 之间的交叉一致（文中摘要记为 N\* ≈ 5,500）。

## 6. 主要结论与发现

- **融合 RoPE 的收益**：RTX 3090 上 RoPE+causal 在 N=4096 相比 flex_attention+预旋转加速 **2.10×**，全部 12 个 RoPE 单元均胜出（1.65–2.10×）。
- **旋转演算成立**：融合是否划算取决于 GPU 计算-带宽比。带宽受限的 Ampere（脊点约 152 FLOPs/byte）上融合决定性胜出；计算充裕的 Hopper（脊点约 300 FLOPs/byte）上交叉点在 N≈5,500–6,000，N≥8k 时预旋转更优（H100 上 N=16384 时融合反而慢至 0.69×）。
- **Hopper 不需要 WGMMA 也能接近上限**：flex_attention 在 H100 上 HMMA pipe 仅 32.6%，受 FA-2 非矩阵乘部分（在线 softmax、掩码、地址运算）结构性约束，而非 WGMMA/HMMA 代码生成选择；仅靠 tile 选择（BLOCK_N=64、num_warps=8、num_stages=3）即达 29.4%，闭合 85% 差距（0.931 ms → 0.488 ms vs. flex 0.443 ms）。
- **Hopper 调优经验**：稀疏表启发式在 Hopper 上反转（Ampere 偏好 BLOCK_N=32，Hopper 偏好 64/128）；num_warps=8 严格优于 4（后者慢 2–3×）；num_stages=3 与 4 基本持平。
- **解码与稀疏优势**：Flash Decoding 在 Llama-3-70B + 32k cache 上把延迟从 3,153 μs 降到 184 μs（**17×**），优于 flex 的 196 μs；BigBird 块稀疏在 N=4096 为 84 μs vs. flex 270 μs（**3.21×**），优势是结构性的（flex 仍付全 O(N²) FLOPs）。
- **端到端生产性能**：H100 上 Llama-3-8B 仅前向 N=2048 仅落后 SDPA 51 μs（+1.8%），N=4096 在 8% 以内；完整训练步 N=2048 在 5.2% 以内、N=4096 在 14.7% 以内；RTX 3090 训练步达 SDPA 的 1.06×，且因 flex 在 HEAD_DIM=128 时 OOM，AttnFuse 是唯一能在消费级 Ampere 上跑 Llama-3-8B 训练的 Triton 注意力编译器。
- **负面结果**：Triton 3.3.1 在 sm 90 上把 `tl.reshape + tl.permute + tl.split + tl.join` 链降级为 SMEM 往返而非寄存器级 warp shuffle，导致长记分板停顿从 17.45%
