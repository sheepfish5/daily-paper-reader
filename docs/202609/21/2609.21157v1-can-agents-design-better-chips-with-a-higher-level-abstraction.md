## 摘要
大语言模型（LLM）智能体正日益被探索用于芯片设计，但现有方法大多直接在 RTL 层面操作。我们探究智能体能否通过利用更高层次的抽象来设计出更好的芯片。我们比较了直接 RTL 设计、基于智能体的 HLS 设计、编译器后 HLS 优化以及 HLS 后 RTL 优化，并将基于智能体的 HLS 设计与 HLS 后 RTL 优化相结合，称为带 RTL 优化的基于智能体的 HLS（AHRR）。我们使用 FPGA 作为实用且易于部署的平台进行端到端评估，但指出我们研究的设计流程权衡在很大程度上与目标技术无关。在一个包含 11 个任务的多样化基准测试套件上，AHRR 相较于直接 RTL 设计取得了 2.6 倍的几何平均加速。案例研究表明，HLS 将设计知识提炼为智能体可以利用的抽象，而 RTL 优化则重新发掘了底层优化机会。总之，这些结果使 AHRR 成为面向智能体芯片设计的一种有前景的工作流程。代码和评估产物可在 https://github.com/ZijD/AHRR 获取。

## Abstract
Large Language Model (LLM) agents are increasingly being explored for chip design, but most existing approaches operate directly at RTL. We ask whether agents can design better chips by leveraging higher-level abstractions. We compare Direct RTL Design, Agent-based HLS Design, Post-Compiler HLS Refinement, and Post-HLS RTL Refinement, and combine Agent-based HLS Design with Post-HLS RTL Refinement as Agent-based HLS with RTL Refinement (AHRR). We use FPGAs as a practical, easy-to-deploy platform for end-to-end evaluation, but note that the design-flow tradeoffs we study are largely independent of the target technology. Across a diverse 11-tasks benchmark suite, AHRR achieves a 2.6$\times$ geometric-mean speedup over Direct RTL Design across our benchmark suite. Case studies show that HLS distills design knowledge into abstractions that agents can leverage, while RTL refinement recovers lower-level optimization opportunities. Together, these results make AHRR a promising workflow for agentic chip design. The code and evaluation artifacts are available at https://github.com/ZijD/AHRR.

## 1. 核心问题与研究动机

- **背景**：LLM 智能体已被广泛探索用于芯片设计（硬件生成、调试、验证、优化），并已进入商业设计流程。但绝大多数工作把智能体直接放在 **RTL（寄存器传输级）** 层面操作。
- **核心问题**：RTL 并非智能体与硬件设计流程交互的唯一接口。高层次综合（HLS）允许用 C/C++ 表达计算，把调度、流水、RTL 生成交给编译器；领域专用 HLS 编译器（AutoSA、StreamHLS 等）进一步提供参数化架构模板。那么——**智能体在更高抽象层次上工作，能否设计出更好的芯片？抽象本身是否带来收益？**
- **两类方案的张力**：
  - 直接 RTL 生成给智能体完全控制权，但需显式构造并行结构；
  - HLS 与领域专用编译器把设计空间限制在一个通常较优的子集内，但可能遗漏底层优化机会。
- **整体含义**：论文系统比较了四种设计流程，提出将「智能体 HLS 设计」与「HLS 后 RTL 精炼」结合为 **AHRR**，主张把**机器智能（前沿 LLM）**与**人类智能（HLS 及领域编译器沉淀的设计知识）**结合，是智能体时代芯片设计的可行范式。

## 2. 方法论

### 2.1 核心思想
- 让同一智能体、在同一任务规格与评测框架下，分别在不同抽象层次上设计，从而隔离「抽象层次」这一变量；并允许跨层次组合（先在 HLS 层做架构级探索，再在 RTL 层做周期精确的微调）。

### 2.2 四种设计流程
1. **(i) Direct RTL Design**：智能体直接根据规格书写 Verilog。
2. **(ii) Agent-based HLS Design**：智能体写 HLS C/C++，由 Vitis HLS 综合出 RTL。
3. **(iii) Post-HLS RTL Refinement**：智能体以 HLS 生成的 Verilog 为起点，继续在 RTL 层优化。
4. **(iv) Post-Compiler HLS Refinement**：由领域专用编译器（AutoSA / StreamHLS）先生成 HLS C++，智能体再改写；其产出的 RTL 可作为流程 (iii) 的输入。
- **AHRR = (ii) + (iii)**：智能体先做 HLS 级设计，再精炼 HLS 生成的 RTL。

### 2.3 关键技术细节
- **智能体循环**：沿用标准迭代式编码智能体循环，使用开源编码智能体 **pi**（未做修改）；**会话跨轮次保持**，每轮 prompt 报告**前 3 轮**的评测结果；prompt 极简，只给优化目标、资源预算、接口要求与提交协议。每轮最多 1 小时开发提交。
- **规格驱动设计**（流程 i/ii）：起点为同一任务规格、任务包（含一个正确但未优化的 C++ 实现、一个测试激励、固定接口契约）与评测框架；RTL 流程额外获得端口规格与 AXI wrapper。
- **工具生成设计的精炼**（流程 iii/iv）：除起点产物与抽象层次不同外，优化循环与评测流程完全一致。
- **隐藏测试平台**：公开测试台仅提供单一激励用于本地开发；正确性用**隐藏测试台**（更广输入 + 由规格推导的边界情况）评估。测试台被强化至 C++ 参考实现达到 **100% 分支覆盖率**，并对参考 RTL 实现额外测量语句/分支覆盖率。
- **有效性判据**：通过隐藏测试台 + 布线成功 + 资源占用不超过上限。
- **性能度量**：执行时间 = 仿真周期数 × max(布线后时钟周期, 目标时钟周期)。

## 6. 主要结论与发现

- **HLS 抽象本身带来收益**：Agent-based HLS Design 相对 Direct RTL Design 取得 **2.31× 几何平均加速**。
- **AHRR 最优**：叠加 Post-HLS RTL Refinement 后提升至 **2.62× 几何平均加速**（n=13）。
- **Post-HLS RTL 精炼有效但幅度有限**：在 16 个有效案例上相对 HLS 生成的 RTL 起点平均提升 **1.17×**；大多数成功轮次是局部编辑（周期数变化 < 1.15×），**所有较大的延迟改善都来自"完全重写"**（如 ROB1、ROB3 获得 2–4× 加速）。
- **编译器后精炼仍有机会**：SHL2 上 Gemini/GPT 分别把 StreamHLS 提升 **3.3×/1.7×**（周期数 539,726→209,297，BRAM 224→2）；GEM1 上把 AutoSA 提升 **1.3×/1.2×**（周期数变化 <2%，收益来自时序改进）；SHL1 两者均无改善，主因是初始设计仿真时间已接近超时上限。
- **抽象"蒸馏"设计知识**：ROB1 案例中，HLS 仅用两个 pragma（ARRAY_PARTITION 到 256 bank + PIPELINE II=1）就实现 256 路并行（127K 周期），而直接 RTL 只做到 32 路 argmax + 8 路抑制扫描（1.86M 周期）；跨 6 个任务，**弱模型在 RTL 侧只能达到强模型的 0.40×，在 HLS 侧可达 0.95×**——HLS 显著拉平了模型能力差距。
- **RTL 层仍可恢复底层机会**：MEM3 中智能体把 min/max 选择移到乘法之前，DSP 64→32、LUT 4,868→2,228；ROB1 中把 `union < 2·intersection` 改写为 `a+b < 3·intersection`，去掉关键路径上的减法器，时钟周期 3.60→3.31 ns。
- **分工图景**：编译器/高层抽象完成"大步"（giant steps），智能体完成案例相关的"小步"（baby steps），二者互补。
- **更广的意义**：智能体不受既有 RTL 设计惯性束缚，又能读懂 HLS 生成的 RTL，有望**加速 HLS 方法学的产业采纳**；作者提及 OpenAI 的 Jalapeño 芯片（2026 年 8 月）已采用 AI 智能体 + HLS。

## 7. 优点

- **问题设定清晰且有价值**：把"抽象层次"作为受控变量，系统对比四种流程，直接回答"智能体能否借更高抽象设计更好芯片"。
- **公平性设计扎实**：同任务同模型比较加速比、隐藏测试台、测试台覆盖率驱动强化、统一资源上限与时钟目标、统一超时预算。
- **跨层次组合思路实用**：AHRR 把"架构级探索"与"周期精确控制"结合，兼顾 HLS 的构造正确性与 RTL 的精细优化。
- **案例研究有说服力**：ROB1、SHL2、MEM3、ROB1(GPT) 等案例具体展示了"HLS 暴露设计知识"与"RTL 恢复底层机会"两种互补机制，并给出量化收益。
- **弱/强模型交叉对比**提供了一个有洞察力的发现（HLS 能压缩模型能力差距），对实际部署有参考意义。
- **可复现**：代码与评估产物已开源（github.com/ZijD/AHRR）。

## 8. 不足与局限

- **统计严谨性不足**：每个配置仅运行一次，无重复实验、无方差/置信区间，几何平均加速比的稳健性存疑；对 prompt 敏感（作者亦承认简单 prompt 改动可能显著改变两侧结果）。
- **流程覆盖不均衡**：Post-Compiler HLS Refinement 只在 3 个设计上验证，AHRR 的 n=13 小于 Direct RTL 对比的 n=15；SHL1 上的失败被归因于仿真超时而非能力上限，缺乏更充分证据。
- **规模与平台限制**：仅在单一 FPGA（Alveo U55C）与单一工具链（Vitis 2025.2）上评估；部分任务被缩放（LLM2 缩至 12 tokens、ROB2 粗化 pillar、ROB3 缩放图像），结论在真实规模下的可迁移性未验证。作者虽声称流程权衡"与目标技术基本无关"，但未在 ASIC 流程上验证。

- **缺少人类基线**：论文没有引入人类专家（或人类工程师 + 传统 HLS 流程）作为参照，因此"2.62× 加速"只说明智能体内部跨抽象层次的相对增益，无法回答"智能体是否已接近/超过人类设计者"这一更受关注的问题。
- **只报延迟与资源，不报能效**：度量口径为"周期数 × 布线后时钟周期"，资源以 60% 上限做约束，但未报告功耗、能效（GOPS/W）或面积—延迟积，而这三者在真实芯片设计决策中往往与延迟同等重要；资源上限设为固定比例也掩盖了"用更多资源换延迟"这类折中策略的效果。
- **提示与流程的超参数未做敏感性分析**：只回传前 3 轮评测结果、每轮 60 min、最多 5 轮、单轮单次提交等设定都是硬编码的，论文既未做消融，也未讨论这些选择对收敛曲线的影响；作者虽坦承 prompt 敏感，但未给出任何量化证据。
- **失败与退化案例的刻画偏薄**：除 SHL1（仿真超时）外，论文较少系统性地报告失败轮次、无效编辑、回归（性能变差）的比例与模式，读者难以判断智能体循环在多大比例上"空转"。
- **可复现性的隐性成本**：虽然代码开源，但复现需要 Vitis 2025.2、Alveo U55C 板卡以及两个闭源前沿模型的 API 访问权限，第三方独立复现的门槛与成本较高。

## 9. 总体评价与启示

- **定位**：这是一篇"提出问题比给出答案更有价值"的系统性实证研究。它没有提出新的模型或算法，而是把**抽象层次**这一在硬件设计中被长期讨论、但在 LLM 智能体语境下尚未被严格隔离的变量，放进受控对比框架中检验，并给出一个可操作的工程配方（AHRR）。
- **核心洞见可归纳为三点**：
  1. **抽象是"知识蒸馏器"**：HLS 与领域编译器把人类数十年沉淀的并行化、流水化、存储分块经验封装成少数几行 pragma/模板参数，使智能体无需自行推导即可获得大规模并行结构，同时显著压缩了不同能力模型之间的差距（RTL 侧 0.40× vs HLS 侧 0.95×）。这意味着**抽象层次的选择本身是一种"能力放大/均衡"手段**，对低成本模型的实际部署尤具意义。
  2. **抽象是"机会过滤器"而非"机会消灭器"**：HLS 会遗漏位宽选择、比较器改写、算子重排等与实现强相关的优化，但这些恰恰是智能体在 RTL 层可以重新捡回的（MEM3 的 DSP 64→32、ROB1 的 3.60→3.31 ns）。因此最优策略不是"选一个层次"，而是**分层接力**。
  3. **两种智能互补而非替代**：编译器负责"大步"（结构级、构造正确性），智能体负责"小步"（案例相关的局部改写，且大改动往往来自完全重写而非增量微调）。这为"人机/机机协作"的芯片设计流程提供了一个可量化的分工假设。
- **实践启示**：对希望引入智能体的团队而言，先在高抽象层（HLS/DSL）建立可工作的正确实现、再让智能体在 RTL 层做周期精确精炼，比直接让智能体从零写 RTL 更稳妥也更快；同时应把"评测基础设施"（隐藏测试台、覆盖率强化、统一资源/时钟约束）当作方法的一部分来建设，而非附属品。
- **后续值得做的研究**：(a) 多轮重复实验与置信区间，以及对 prompt/轮数/回传历史长度的消融；(b) 引入人类专家基线与功耗/能效度量；(c) 扩展到 ASIC 流程与其他抽象层（如 SystemC、Chisel、领域 DSL）以验证结论的可迁移性；(d) 探索"抽象层次的自适应选择"——让智能体自行决定何时上移（换架构模板）何时下移（改 RTL）；(e) 用 HLS 延迟估计器替代完整 RTL 仿真来解除迭代瓶颈，从而让长仿真任务（如 SHL1）也能进入公平比较。
- **一句话总结**：在智能体时代，"给智能体一个更好的抽象"与"给智能体更强的模型"同样重要——HLS 提供了前者，RTL 精炼保留了后者的用武之地，而 AHRR 正是把二者串起来的务实范式。
