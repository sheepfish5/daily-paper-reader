## 摘要
GPU 内存带宽和容量限制了大语言模型（LLM）推理的吞吐量。GPU 内存系统由主层级的高带宽内存（HBM）和次级层级的主机内存组成，后者通过 CPU 到 GPU 互连连接。当前的服务系统以分层方式对待这些层级：当数据能放入 HBM 时，仅从 HBM 提供服务；否则在使用前将数据从主机内存预取到 HBM。在这两种情况下，主机内存带宽都从未得到充分利用。预取通过利用主机内存扩展了容量，但会消耗 HBM 带宽用于写入，从而减少可用于按需加载的带宽。我们观察到，要充分利用主机内存和 HBM 的带宽，需要每一波 GPU 线程块并发地访问两个层级，并按它们的带宽比例进行访问。现有的带宽比例放置策略无法提供并发性，因为它们不了解 GPU 波次以及较大的 2MB GPU 页大小。本文提出 BOOST，这是首个提供对两个 GPU 内存层级的并发且按比例访问的运行时系统，在不修改内核的情况下为 LLM 推理提取主机内存和 HBM 的组合带宽。BOOST 的关键见解是利用内核访问模式使页面分配和运行时数据管理具有波次感知能力。对于静态模型权重，BOOST 应用基于模运算的页面放置，以消除访问比例差异；对于动态提供的注意力键值（KV）对，它使空闲 KV 页池具有波次感知能力。我们将 BOOST 集成到 vLLM 中，并在 Grace Hopper 系统上进行了评估。在相同批次大小下，BOOST 将每输出令牌时间（TPOT）相比仅 HBM 服务提高了 4.3%，而预取使 TPOT 降低了 6%。在高吞吐量服务中，BOOST 平均将吞吐量提高了 31%，比预取高出 15%。

## Abstract
GPU memory bandwidth and capacity limit throughput in large language model (LLM) inference. The GPU memory system consists of a primary tier of high-bandwidth memory (HBM) and a secondary tier of host memory connected via CPU-to-GPU interconnect. Current serving systems treat the tiers hierarchically: they serve exclusively from HBM when data fits, and otherwise prefetch data from host memory to HBM before use. In both cases, the host memory bandwidth is never well utilized. Prefetching expands capacity by utilizing host memory, but consumes HBM bandwidth for writes, reducing the bandwidth available for demand loads. We observe that fully utilizing both host and HBM bandwidth requires each wave of GPU threadblocks to access both tiers concurrently and in proportion to their bandwidth ratio. Existing bandwidth-proportional placement strategies fail to provide concurrency because they are not aware of GPU waves, and the large 2MB GPU page size.   This paper presents BOOST, the first runtime system that provides concurrent and proportional access to both GPU memory tiers, extracting the combined bandwidth of host memory and HBM for LLM inference without kernel changes. The key insight in BOOST is to use kernel access patterns to make page allocation and runtime data management wave-aware. For static model weights, BOOST applies modulo-based page placement that eliminates access-ratio variance; for dynamically provisioned attention key-value (KV) pairs, it makes the free KV page pool wave-aware. We integrate BOOST into vLLM and evaluate on a Grace Hopper system. At iso-batch size, BOOST improves Time-per-Output-Token (TPOT) by 4.3% over HBM-only serving, whereas prefetching degrades TPOT by 6%. In high-throughput serving, BOOST improves throughput by 31% on average, outperforming prefetching by 15%.

## 1. 核心问题与研究动机

- **背景**：LLM 解码阶段是自回归的、**内存带宽受限**（部分场景还受容量限制）。每轮迭代都要重新读取数百 GB 的模型权重与注意力 KV 缓存（如 DeepSeek R1 权重 670GB，32K 上下文每用户 KV 再加 1GB）。
- **硬件现状**：GPU 内存系统是异构两层——主层 HBM，次层主机 CPU 内存，通过 CPU-to-GPU（C2G，如 NVLink C2C）缓存一致互连连接。GH200 上主机内存带宽约为 HBM 的 **9%–11%**（记为 α）。
- **现有系统的问题**：
  - **仅 HBM 服务**：数据放得下时只从 HBM 取，主机内存带宽完全闲置。
  - **预取（prefetch）**：放不下时把数据先迁到 HBM 再用。每次预取都产生 **HBM 写**，挤占按需读带宽，即使完美重叠也只能得到 (1−α) 而非 (1+α) 的有效带宽；在 α=10% 时两者相差约 22%。实测预取使 SM 可用带宽下降 211GB/s、TPOT 反而恶化。
  - **CUDA Unified Memory**：工作集超出 HBM 后退化为"页缓存颠簸"，实测吞吐下降 **5×**。
  - **BAPP-R（带宽感知随机放置）**：为 4KB 页时代设计，当年一"波"触及数千页，随机比例自然近似成立；现代 GPU 用 **2MB 大页**，一波只触及几十页，导致**每波访问比例方差极大**（全核 10%±1.5%，单波 10%±3.6%），反而比仅 HBM 慢 3.5%。
  - **Linux 加权交织（set_mempolicy）**：确定性条带但**不了解消费者**（哪个内核/CTA 读哪页），会跨内核边界，且分配时固定、无法应对运行时 KV 页的创建/释放。
- **核心洞察**：要拿到 HBM+主机的**叠加带宽**，访问必须同时满足两个属性——
  - **并发性（Concurrency）**：每一波访问都要同时打到两层；
  - **比例性（Proportionality）**：打到主机的访问比例应恰为 α/(1+α)（例如 10%）。
  - 二者合称 **CAP（Concurrent and Proportional）**。违反比例性（主机份额过高）会被主机带宽拖住而 HBM 闲置，导致净减速。

## 2. 方法论

### 2.1 总体思路

- BOOST 是**首个面向 LLM 推理、无需修改内核**即可实现 CAP 的运行时系统，集成在**服务系统（vLLM）内部**而非 OS/驱动层，因为只有服务系统同时掌握内核访问模式、张量分配和 KV 池管理信息。
- 不做任何运行时数据迁移，所有访问都是到某一层的**缓存一致按需加载**；同时天然扩展可用容量。
- 两个组件（均运行在 CPU，不新增 GPU 代码）：
  - **PAM（Page Allocation Manager）**：分配时的页放置（静态权重）。
  - **DSR（Data Shape Remapper）**：运行时的 KV 数据管理（动态数据）。

### 2.2 三条关键洞察与对应技术

- **洞察一：波感知的取模页放置（MPP, Modulo-based Page Placement）**
  - 针对**静态模型权重**（expert/MLP 内核）。这类内核的线程块访问虚拟连续内存。
  - 规则：设 HBM 与主机带宽比为 K=1/α，则**每 K 个页放 HBM、第 (K+1) 个页放主机**。α=10% 时 11 页即可精确匹配比例。
  - 效果：在每个 CTA 波内**消除比例方差**，把 BAPP-R 的随机性变成确定性收益（实验中 BAPP-R 平均减速最多 25%，MPP 与 BAPP-R 的最好情况持平且方差极小）。
  - **按张量分别分配**，使放置模式在每个张量处重启，保证单个内核的主机访问份额不超过 α。

- **洞察二：CTA 级波感知（CTA specialization）**
  - 粒度刻画（GH200，Qwen3-Next 80B）：CTA 大小低方差（4 或 8 warp），但**每波活跃 CTA 数变化剧烈**（每波固定 264K 活跃线程）。
  - 结论：**线程级**划分导致 warp 分歧、破坏访存合并；**warp 级**划分过粗（4-warp CTA 只能表达 0.25 倍数的带宽比）；**SM 级**（限定部分 SM 只访主机）降低访存并行度。
  - **CTA 级**最优：把主机访问**限制在 α 比例的 CTA 上**，其余 CTA 独占 HBM。若单个 CTA 跨两层，主机的慢加载会拖住同发的 HBM 加载、损失 HBM 带宽。
  - 效果：CTA 级放置获得 7.1% 加速，达 CAP 理论上界（7.4%）的 96%；手写改内核版本 7.3%（99%），差距仅 0.2 个点，不值得改内核。
  - **超页（superpage）**：当 CTA 足迹不整除 2MB 页（如 Llama-70B down-projection 单 CTA 跨 1.75 页）时，按 CTA 足迹与页大小的**最小公倍数**（如 LCM(3.5MB, 2MB)=14MB）构造超页，每个超页只落一层，再在超页间应用 MPP，避免 CTA 访问被劈成两层。

- **洞察三：KV head chunk 映射（动态数据）**
  - 难点：PagedAttention 在虚拟内存与线程块数据之间插入了**空闲 KV 页池**，页在运行时被反复分配/释放，虚拟地址到波的映射近似随机，任何静态放置策略都失效。
  - 观察：FlashAttention-3 / FlashInfer 等把**每个 KV head 分给不同线程块**，并把上下文按 head 切 chunk，因此同一波中的 CTA 处理不同的 **KV head chunk**。
  - 设计：两层机制
    - **LPP（Linear Page Placement）**：把虚拟地址空间**连续**分段，前 1/(α+1) 页映射 HBM，后 α/(α+1) 映射主机；使页所在层成为虚拟地址的固定函数，DSR 便可**通过选择虚拟地址来控制物理放置**。
    - **波感知块供给（greedy block fulfillment）**：定义两类块——`single-head-host`（1 个 head 落主机，其余落 HBM）与 `all-local`（全落 HBM）。目标主机占比 1/M、head 数 H 时，保持两类块比例为 H : (M−H)。新请求到来时，若空闲 single-head-host 块比例超过 H/M 就分配该类，否则分配 all-local。同一请求的所有块类型一致（sticky），降低跨波时序方差。
    - 边界处理：single-head-host 列表空 → 退化为 all-local（低于 α，只损失收益、不引入减速）；all-local 列表空 → 向 all-local 请求追加 single-head-host 块，把混合限制在该请求内；内存压力极大时交回服务系统调度器。
  - **张量布局重排**：单个 KV 块（16 token × 全部层与 head）约 2.5MB，与 2MB 页不对齐，故把 **head 重排为最外层维度**，使每个 head 的数据连续并对齐 LPP 分区；利用 vLLM 内核以 base pointer + 维度长度 + stride 描述张量、允许非连续虚拟内存的特性，不改变访问规律。H > M 时混合 ⌊H/M⌋ 与 ⌈H/M⌉ 个主机 head 的块。

### 2.3 实现细节

- 集成于 **vLLM v0.17.0**，改动约 **800 行**（Python + PyTorch）。
- PAM 在 `model_loader` 中实现：GH200 缓存一致，OS 把 GPU 内存暴露为 NUMA 节点；对每个 2MB 区域用 `mmap(MAP_HUGETLB)` + `mbind` 选节点 + `cudaHostRegister` 暴露给 GPU，再清零强制物理落盘。
- K=1/α 非整数时取 K=⌈1/α⌉，使主机份额**低于** α（高于 α 会减速）。
- 残留方差来源：内核最后一波 CTA 数较少；消除它需要预先知道波数，而参数化 CUTLASS 内核目前不暴露该信息。
- DSR 扩展 KV block manager 维护两条空闲链表，无需逐页跟踪、无需改动内核分配逻辑。
