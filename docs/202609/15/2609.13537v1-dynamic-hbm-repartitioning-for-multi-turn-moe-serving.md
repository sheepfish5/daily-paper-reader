## 摘要
长时间运行的多轮请求会累积可复用的键值（KV）状态。一旦该状态超过固定的 GPU KV 缓存分配，服务系统就会逐出可复用的前缀、重复执行预填充工作，并可能抢占请求。这种压力对于专家混合（MoE）模型尤为严峻：其专家权重占据了大部分 GPU 高带宽内存（HBM），尽管每个 token 仅激活稀疏的一部分专家。权重与 KV 缓存之间的静态边界，使得服务系统无法随着对话增长而利用专家内存来保存可复用状态。我们提出 VAMP，一个在运行时改变这一 HBM 边界的 MoE 服务框架。当 KV 分配无法满足时，VAMP 会比较三种备选方案的预估未来工作量：从主机内存暂存专家权重、逐出可能需要重新预填充的已缓存前缀，或抢占并重新调度请求。当某一操作具有最低预估代价时，它便将一块有界的专家权重区域转换为 KV 缓存容量。CUDA 虚拟内存管理（CUDA Virtual Memory Management）的页重映射可在不复制常驻 KV 数据的情况下完成这一转换。我们在 vLLM 服务引擎中实现了 VAMP，并在记录的和受控的多轮工作负载上评估 Qwen3-Next-80B。在对一个记录的 2,103 轮 SWE-bench 智能体工作负载的五次重放中，采用 15% 最大专家卸载比例的 VAMP 将首 token 时间（TTFT）p90 从 26.1 秒降至 1.10 秒（23.6 倍），并将请求吞吐量相对于未修改的 vLLM 提高 20.7%，同时将每输出 token 时间（TPOT）增加 31.1%。

## Abstract
Long-running multi-turn requests accumulate reusable key-value (KV) state. Once this state exceeds a fixed GPU KV-cache allocation, serving systems evict reusable prefixes, repeat prefill work, and may preempt requests. This pressure is particularly acute for Mixture-of-Experts (MoE) models: their expert weights occupy most GPU high-bandwidth memory (HBM), even though each token activates only a sparse subset of experts. A static boundary between weights and the KV cache prevents serving systems from using expert memory to preserve reusable state as conversations grow.   We present VAMP, an MoE serving framework that changes this HBM boundary at runtime. When a KV allocation cannot be satisfied, VAMP compares the estimated future work of three alternatives: staging expert weights from host memory, evicting cached prefixes that may require re-prefill, or preempting and rescheduling requests. It then converts a bounded expert-weight region into KV-cache capacity when that action has the lowest estimated penalty. CUDA Virtual Memory Management page remapping performs this conversion without copying resident KV data.   We implement VAMP in the vLLM serving engine and evaluate Qwen3-Next-80B on recorded and controlled multi-turn workloads. Across five replays of a recorded 2,103-turn SWE-bench agent workload, VAMP with a 15% maximum expert-offloading ratio reduces time-to-first-token (TTFT) p90 from 26.1 s to 1.10 s (23.6 times) and increases request throughput by 20.7% relative to unmodified vLLM, while increasing time per output token (TPOT) by 31.1%.

# 论文总结：Dynamic HBM Repartitioning for Multi-Turn MoE Serving

## 1. 核心问题与整体含义

- **研究背景**：LLM 服务系统依赖两大策略——批处理与 KV 缓存复用，两者共同对 GPU HBM 形成巨大压力。现有系统（如 vLLM）在引擎初始化时固定划分「模型权重池」与「KV 缓存池」，两者运行时互不借用。
- **被打破的两个假设**：
  - 假设一：权重只占 HBM 一小部分。MoE 架构通过稀疏激活把总参数量与单 token 计算解耦（Mixtral-8x7B 47B 总参/13B 激活；DeepSeek-V3 671B/37B；Qwen3-Next-80B 80B/3B），导致**专家权重主导 HBM**——H100 单卡 94 GiB 中专家权重占 72.0 GiB，KV 池仅 8.02 GiB。
  - 假设二：KV 需求不超过预分配池。多轮 Agent 场景中上下文累积增长（平均 157 轮、32.7k token，个别超 1M），KV 长期接近饱和，触发反复驱逐与重预填充。
- **核心现象——前缀缓存悬崖（prefix-cache cliff）**：当可复用前缀足迹超出 KV 容量，前缀命中率骤降、TTFT 陡升。这是**阈值型突变**而非渐进退化。
- **整体含义**：静态 HBM 边界让专家权重内存无法在 KV 压力下被回收，导致「驱逐—重计算—更严重驱逐」的级联。论文主张在运行时打破该边界，将专家权重 HBM 转为 KV 容量，把悬崖推向更高并发。

## 2. 方法论（VAMP）

- **核心思想**：把 GPU HBM 视为**专家权重与 KV 缓存共享的统一资源池**；当 KV 分配无法满足时，比较三种动作（及组合动作）的**预估未来代价**，选择代价最低者执行；用 CUDA VMM 页重映射在**不拷贝常驻 KV 数据**的前提下完成物理页归属转换。
- **三大组件**：
  1. **价值感知动作选择（三方成本模型）**
  2. **动态资源编排器**：在专家权重区与 KV 池之间按页粒度重划分
  3. **批处理感知专家卸载**：双缓冲暂存 + 拷贝/计算重叠
- **成本模型（文字说明）**：
  - **缓存块驱逐代价 Cc**：先以滑动窗口前缀命中率 `r_hit` 与 LRU 队首候选块年龄 `age` 估计有效复用概率 `p_eff = α·r_hit/(1+age/τ)`；再乘上重预填充代价 `C_c = p_eff·(n_tok·t_prefill + t_overhead)`。以 LRU 队首年龄近似整个回收集，倾向于**低估**驱逐代价而非过度保护缓存。
  - **专家卸载代价 Ce**：卸载期间每步都要在 MoE 执行前暂存该层被卸载区（与 router 实际选择无关），故代价按连续解码步数 `w` 累计：`C_e(n_cand) = min(n_cand, E)·c_eff·w`，其中 `n_cand` 为候选扩容量、`E` 为每层本 rank 的本地专家分片数、`w` 为运行请求中最小剩余解码预算（钳制在 1–64 步）。
  - **请求抢占代价 Cp**：单次抢占 `C_p^(1) = t_sched + t_queue + n_partial·t_prefill`（仅最后一个未填满块能立刻提供未缓存块）；覆盖 G 个块缺口时 `C_p = C_p^(1)·G`。
  - **组合动作 Cb**：专家扩容以固定粒度进行，取整后残余缺口用缓存驱逐补齐：`C_b = C_e^floor + C_c^remainder`。
  - 控制器从 {Ce, Cc, Cp, Cb} 中选最低代价可行方案；达到卸载上限后仅剩 Cc 与 Cp。
- **动态 HBM 重划分**：
  - 引入**专家组（expert group）**作为最小页对齐重映射单元，由 rank 本地分片大小与 CUDA VMM 分配粒度推导（Qwen3-Next 下每组 6 MiB = 3×2 MiB 页）。
  - 用 CUDA VMM **unmap 物理页并 remap 到 KV 池**，专家张量虚拟地址范围保留，常驻权重地址不变；各 TP rank 取最小可扩容块数保持容量一致。
  - **卸载上限**：每 rank 每层最多卸载 `E_buffer` 个分片（受暂存缓冲容量与配置上限 VAMP-r 约束），层内保留低索引常驻区、卸载连续高索引区。
- **批处理感知卸载**：因单个模型步内 batch 的专家并集可能达 262–494（远大于 top-k=10），逐专家按需抓取不可行；VAMP 改为**每层整体暂存整个卸载区**，并用**双缓冲**在层 N 计算时异步预取层 N+1 的权重，与 MoE kernel、dense、router 计算重叠；第一层保持全常驻（无前序计算可重叠）。TP2 下 gate/up GEMM 可在权重拷贝完成后立即启动。

## 6. 主要结论与发现

- **KV 池扩展**：H100 上 VAMP-15/20 把 8.0 GiB 基线 KV 池扩到 **18.5 / 21.8 GiB**（2.30× / 2.71×）。
- **记录回放（2,103 轮，n=5）**：
  - TTFT p90 从 **26.1 s → 1.10 s（23.6×）**；TTFT p99 从 32.7 s → 3.48 s（9.4×）
  - 请求吞吐 **+20.7%**（0.596 → 0.720 req/s）
  - 前缀缓存命中率 **0.19% → 89.8%**；平均排队时间 15.1 s → 21 ms；抢占 562.7 → 0.18 次/千轮
  - **代价**：TPOT **+31.1%**（170.9 → 224.0 ms）
- **闭环执行**：基线 6 小时内累计 7,227±495 次抢占、前缀命中率跌破 0.2%、末段 30 分钟平均 TTFT 142.5 s、KV 利用率 0.967；VAMP-15 无排队、几乎零抢占、平均 TTFT 2.63 s。
- **容量边界前移**：H100 上基线在 c=16 即越界（TTFT p99 22.1 s），VAMP-25 在 c≤28 仍保持 3.0–3.9 s；H200 上基线在 c=32 越界（92.8 s），VAMP-20 仅 9.1 s（**10.2×** 降低）。
- **卸载比例非越大越好**：VAMP-20 相比 VAMP-15 在部分负载下 TTFT 相当但 TPOT 更高、吞吐更低；过大的比例甚至会因传输开销先行越界（VAMP-15 在 H100 c=24 时比基线还差约 26%）。
- **无配置全局最优**：SLO 网格显示，P=150ms 时全部配置吞吐 <0.13 req/s；P=200ms 时 vLLM/VAMP-10 领先；P≥250ms 时 VAMP-15 全面领先。

## 7. 优点

- **问题切中要害**：准确识别「静态 HBM 分区 + MoE 权重膨胀 + 多轮累积」三者叠加导致的阈值型悬崖，并用前缀缓存命中率崩溃作为可观测证据。
- **决策机制有前瞻性**：三方成本模型同时权衡卸载传输、重预填充与抢占重调度，把「哪些数据更值得留在 HBM」这一价值判断形式化；用 LRU 队首年龄近似回收集，偏差方向明确且保守。
- **零拷贝重划分**：用 CUDA VMM 页重映射而非数据搬运完成专家 HBM → KV 池的转换，避免了重分区路径上的拷贝停顿，是可落地的系统级工程方案。
- **批处理感知设计**：识别到 batch 内专家并集远大于 top-k（262–494/512）这一关键事实，从而放弃 LRU 专家缓存，改用整区暂存 + 双缓冲，保留 router 结果不改变模型输出。
- **实验组织审慎**：区分闭环（生态效度高）与回放（严格对照）两类范式；报告 mean ± SD；对闭环结果明确声明为「观察到的服务模式」；附录用三次独立运行验证基线崩溃的可重复性。
- **工程完整度高**：7,100 行集成进 vLLM，同时支持 TP2/TP4，成本系数在开发时一次性设定后跨负载跨平台不重调
