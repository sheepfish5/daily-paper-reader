# Abstract 

Serving a large language model (LLM) is limited by memory capacity. High-Bandwidth Flash (HBF) stacks NAND flash inside the accelerator package, one tier below high-bandwidth memory (HBM); the specification was published on August 3, 2026, and the first inference devices are expected to sample in early 2027. Decisions about capacity and data placement cannot wait for silicon. No existing method settles those de-cisions: a storage simulator replaying a recorded access se-quence never executes the workload, a GPU simulator does not run the real compute kernels, and a cycle-accurate simula-tor cannot finish one LLM inference run. We present HBFSim, the first evaluation platform that applies HBF timing, capacity, and thermal effects to a real inference workload while that workload executes on a real GPU. HBFSim rewrites PTX, the intermediate code NVIDIA’s compiler emits, and gates kernel launches; issue is separated from consumption, so real hardware supplies the computation that hides an access. Tim-ing comes from measurements of a real device rather than a parameter sheet, and junction temperature sets both the rate HBF sustains and the retention deadline that forces refresh writes. HBFSim matches the measured device exactly at all six calibration breakpoints, with zero unsafe launches, and an un-modified vLLM 0.15.1 serving Qwen3-30B-A3B returns the token identifiers of the uninstrumented baseline. The device fast path serves the same Qwen3-30B-A3B case in 2.014352 s against 44.469 s on the detailed reference path, 20.8 times faster, and a workload over a 110 GiB logical range backed by a 2 GiB HBM page cache returns the baseline checksum on a 97,887 MiB GPU. Before HBF parts sample, HBFSim lets a designer measure a capacity or placement decision under a real workload instead of assuming one. 

# 1 Introduction 

Serving a large language model (LLM) is limited more and more by memory bandwidth and memory capacity [35, 48]. High-bandwidth memory (HBM), DRAM stacked inside the accelerator package, is what the industry built to serve that load, and HBM delivers high bandwidth at low energy per bit. But HBM does not keep up with the models it serves: the standard caps one HBM4 cube at 64 GB [13], and the number of parameters in large models has grown by a factor of 410 every two years while the memory on a single GPU has grown by a factor of 2 over the same two years [7]. High-Bandwidth Flash (HBF), NAND flash stacked inside the same package, is a response to those limits: Sandisk and SK hynix are the primary contributors to its specification, and Google and Tenstorrent joined the consortium during standardization and contributed to validating the technology and to establishing the standard [37]. Sandisk states that HBF offers 8 to 16 times the capacity of HBM at similar bandwidth and similar cost [36]. HBF is the first open standard that defines stackable NAND flash as a memory tier inside the package of an xPU, published through the Open Compute Project in August 2026. The spec-ification gives this tier 8× the capacity of HBM [5], at roughly the same read bandwidth. Stacking memory inside the pack-age is not new; HBM has stacked DRAM dies inside the package for years. What is new is the medium: the stacked die holds non-volatile NAND rather than DRAM. NAND makes a write far more expensive than a read, and every write uses up part of the limited number of times a flash cell can be rewritten. Only part of what an inference server keeps in mem-ory therefore belongs in this tier. The data suited to HBF is data written once and read many times: model weights above all, and the part of the key-value cache that several requests share, such as a system prompt every request repeats. HBF is not a replacement for HBM; HBF is a new tier below HBM. The choices a system designer faces cannot wait for HBF silicon to arrive. The first HBF devices for inference are ex-pected to reach customers as samples in early 2027, and sev-eral questions are open now: whether the frequently used and the rarely used experts of a mixture-of-experts model can be prefetched from HBF, which access patterns pay most for HBF latency, how an LLM’s model weights and key-value cache are split between the two tiers, what sustained load 1arXiv:2609.09800v1 [cs.AR] 9 Sep 2026 costs in heat and device lifetime, and more. A mixture-of-experts model holds many separate groups of weights and uses a small network called a router to choose a few groups for each token, and the router chooses only while the model runs, so there is no time left to fetch the chosen weights before they are used. No existing method answers those questions: real devices cannot be obtained, and a storage simulator that replays a recorded access sequence [19, 27, 40] never exe-cutes the workload, so a slower read cannot change what the program issues next. A GPU memory simulator [4, 22, 39] does not run the real compute kernels, and a cycle-accurate simulator [6] cannot finish one LLM inference run. Opinion on HBF splits into two opposing camps. SK hynix, Sandisk, and Joungho Kim of KAIST, widely known as the “father of HBM” [33], hold that HBF can take over a large part of the capacity problem that HBM carries today [9, 18, 25, 37]. Micron and others hold the opposite, that NAND’s own limits will hold HBF back and leave it worse than the media already in use [34]. Real parts that could settle the argument do not exist yet, so the open questions and the disagreement both call for a simulator that favors neither side, that covers a whole inference run, and that finishes fast enough to be used. Two candidates fail: an HBF module in GPGPU-Sim, and GPU trace replay against an HBF simulator. Simulating one inference run takes far too long, and the computation and prefetching that hide HBF latency exist only in a real work-load. On a real GPU a slow access stalls in a back end that instruction issue never sees, below the code a rewriter can reach, where neither physical registers nor dependences are fixed. We therefore split issue from consumption: a rewritten access allocates a device future, a record of the modeled com-pletion, and waits at the first instruction that consumes the value. The computation that hides HBF latency then comes from the real hardware, not from our model. Building this platform runs into many difficulties. First, every HBF access is served inside the accelerator package, where earlier simulators have no interception point, so a de-vice effect can only be written into the instruction stream of the program under test. Second, how long one access takes depends on the accesses that came before, while the timing model has to be evaluated once per access inside the GPU code of the workload itself, so accuracy and cost work against each other. Third, HBF is NAND flash, which is sensitive to temperature, and it shares a package with a GPU that draws high power throughout the run, so the rate HBF sustains is set by temperature, not by the nominal peak. We present HBFSim, which simulates HBF as separate lay-ers rather than as one device and joins the layers into one loop. The GPU layer is not simulated at all: the workload runs as usual on a real GPU, and rewritten PTX, the intermediate code NVIDIA’s compiler emits, routes accesses inside a registered address range into HBFSim. Timing comes from two mea-sured sources: a curve calibrated on a real device, and a flash media model that receives requests while the workload runs. A capacity layer gives the workload a logical range with no physical GPU memory behind it, paged in on demand through a cache in HBM. The workload also draws power, and a first-order thermal response model turns that power into a curve of junction temperature over time, the temperature inside the die, which runs hotter than the package surface. Junction temper-ature then sets the thermal-management state, and that state changes two things: how fast HBF serves requests, and how long written data stays readable. Blocks past their retention deadline have to be rewritten, which adds forced refresh traf-fic. HBFSim is the first evaluation platform that applies the timing, the capacity, and the thermal effects of HBF to a real inference workload while that workload executes on a real GPU. Because the GPU layer is not simulated, three proper-ties hold at once. The workload is real: unmodified vLLM 0.15.1 serving Qwen3-30B-A3B runs under injected HBF timing and emits token identifiers identical to the baseline run. The feedback is real: the program is actually waiting, so a slower access changes what the program issues next. The heat is real: on one BF16 8192 ×8192 matrix multiply the GPU sustains 379.117 TFLOP/s cold and 348.427 TFLOP/s hot, a difference of 8.10%, and the fitted first-order thermal time constants are 13.1 s for the GPU and 12.4 s for the NVMe device used for calibration, so temperature changes within the span of a single inference run. 

# 2 Background 

HBF places NAND flash dies inside the accelerator package and gives them a memory-style interface. The specification defines a 16-die NAND stack [5], and that stack is why HBF read bandwidth is far higher than an ordinary SSD’s. NAND has two clear drawbacks next to DRAM, and HBF inherits both of them. ➀ NAND wears out and cannot be overwritten in place: a block tolerates a limited number of program/erase cycles and must be erased before it is rewritten, and a write to page 0 of a block makes HBF erase that whole block internally [5]. ➁ NAND is also slow next to memory: published work assumes up to 20 μs for a page read [17], against about 272.8 ns for one global-memory access on a GPU with HBM [30]. Either property would keep NAND out of a memory tier if the workload wrote often and needed each byte on demand. Large language model inference does neither. Every operator of the decode stage, where the model emits one token at a time, is bounded by memory bandwidth rather than arithmetic [48]. Three published studies that disagree about HBF still classify model weights the same way, as written once and read many times [28, 34, 43]; the one that offloads only the key-value cache never tests weights in HBF, so it says nothing about whether weights suit HBF. A prefix of the key-value cache shared across requests, such as a system prompt every request repeats, is also written once and read many times [20]; the key-value cache a request generates for 2itself is not. A talk at Hot Chips 2026 reports that about 93 percent of the bytes of one trillion-parameter model, 1.45 TB, are mixture-of-experts expert weights, the weight matrices a router picks a few of for each token; the speakers argue that HBF suits the expert pool and key-value cache offload while HBM handles attention weights and hot data [1, 21]. 

Observation 1: Almost every byte an inference server moves through accelerator memory is read rather than written. 

Transformer decoding walks the layers in a fixed order, so which weights a token reads is settled before that token starts to compute. We compute the lead time for Llama 3 8B ourselves, using the HBM bandwidth NVIDIA states for an H100 SXM5 card [8, 32]: reading one layer of weights takes 130.211 μs, the lead time that computing layer i leaves for reading the weights of layer i+1, and 6.51 times the as-sumed 20 μs NAND page read [17]. Three results narrow that factor: the same lead time covers a 50 μs random read only 2.60 times [24]; prefetching inside a single matrix multiplica-tion kernel, where the lead time is far shorter, already slows execution 3 to 4 times at 20 μs [17]; and for the experts of a mixture-of-experts model the lead time is zero, because choosing the experts and running them sit back to back inside the same block [11]. 

Observation 2: The predictable execution path of trans-former inference leaves a long lead time for prefetching. 

Accelerators that order transfers in the compiler, TPUs and Huawei’s DaVinci NPU among them [15, 16, 29], can issue a fetch earlier than a GPU, which hides latency with run-time concurrency [14]. TPUv4i states that “DRAM backs Vector Memory so that the pair form a compiler-controlled memory hierarchy” [15]. We note the longer lead time there. What belongs in HBF is data written once, read many times, and addressed before it is needed, model weights first of all and the prefix of the key-value cache shared across requests. The key-value cache a request generates for itself, activations, and the gradients and optimizer state of training do not: they are written often and carry no lead time. One row of Table 1 sets HBF apart from HBM4 and the enterprise SSD: retention, not bandwidth or latency. HBM keeps nothing without power, an enterprise-class drive keeps written data for three months at 40 ◦C without power, and HBF guarantees 24 hours at 85 ◦C only while powered [5], so HBF is neither a slower memory nor a faster drive. Cells with no citation come from a published industry analysis of HBF [2], except in the CXL column, where they are values typical of that class of device; a tilde marks an estimate rather than a specified or measured value. The 272.8 ns given earlier is our own conversion of the 478.8 clock cycles reported for a global-memory access at 1755 MHz on an H800 PCIe card [30], not the H100 SXM5 card used for the lead time. The specification writes temperature into the host interface: values the host reads, thresholds the host sets, and states the host has to respond to. The operating window is a junction temperature of 0 to 105 ◦C, and the four thermal states are normal operation, light throttling at the LTT threshold, which lowers the clock, heavy throttling at the STT threshold, and shutdown [5]. How much faster retention loss runs at one temperature than at another is set by the activation energy Ea,a constant that depends on the manufacturing process. Section 4.2 of HeatWatch measures Ea for 3D NAND, the medium HBF stacks, and reports Ea = 1.04 eV, with a 95% confidence interval of 1.01 to 1.08 eV and a coefficient of determination 

R2 = 0.76 [31]. Rewriting memory instructions in PTX, the intermediate code NVIDIA’s compiler emits, changes neither the appli-cation source nor the kernel source. Production inference frameworks ship many of their operators as cubin, the already-built code for one GPU architecture, and those operators fall outside the rewriting layer we chose. 

# 3 Motivation 

How HBF should be used, and whether HBF is worth building at all, are both open in public today, and no published method settles either question. Neither disagreement can be closed by writing another architecture paper: five evaluations of HBF have been published and none of the five, on our reading, con-tains a measurement on silicon [9, 10, 17, 34, 43], the Micron study describing itself as “The analytically modeled platform (no silicon measurement)”. One number decides which side of the disagreement is right, and the specification never gives that number. The bandwidth the specification states is measured at the UCIe interface, not at the flash: “Total Effective BW per Cube = 3072 GB/s” (Table 2). Challenge 1: HBF sits inside the accelerator package and every access to HBF is served without leaving that package, so none of the interception points that earlier simulators rely on exists here. 

An interception point is a place outside the program under test through which every memory access must pass and where an experimenter is free to add waiting time. The word outside carries the weight: not one byte of the binary of the program under test changes, and the added delay is supplied by some other layer of the machine. Four places outside the program under test exist on the host processor side, and all four are unavailable for HBF: the page fault taken through operating-system page tables, the extended page table of a virtual machine (the route Cylon takes [47]), sampling with processor performance counters (the route CXLMemSim takes [46]), and binding the data to a remote NUMA node, whose access latency is already higher. Persistent memory and CXL memory were emulated this way not because the researchers who did so were more clever, but because those media attach to the host processor’s memory path, which ships with all four places already built in, while an HBF access is issued by GPU load/store units and served inside the package, so the host processor never participates. On the GPU side, fault handling through the GPU page table, as offered by NVIDIA unified memory and by XNACK on AMD MI300A, really is outside the program under test, but the cost of fault handling lands inside the very range HBF-Sim has to resolve: 16 μs for a minor fault and 18 μs for a major fault, against HBF page read latencies that published work places between 1 and 20 μs [17], and a page throughput ceiling of about 37 GB/s [42], 10 to 83 times below the three bandwidths the specification states. Purpose-built hardware inserted on a link outside the package has nowhere to sit in-side an HBF package, but should a development board expose HBF together with a programmable delay element, such a board would be a more direct instrument than the approach HBFSim takes. Placing the entire execution inside a model instead fails elsewhere: such a model produces no temper-ature, whereas Challenge 3 below requires temperature to change the service rate while the run proceeds, and a modeled instruction stream carries no feedback from one slow read to what the program issues next; a reviewer who only wants to know how page read latency affects a matrix multiplication is well served by cycle-level simulation, and the advantage of HBFSim is confined to real execution and to temperature. What decides whether an access can be intercepted is the three properties—which unit translates the address, where the access is served, and whether the path admits third-party hardware—and replacing UCIe with a silicon interposer, an on-chip network, or NVLink changes none of the three. The instruction stream, finally, is not where the cost of an access is defined, and that limit holds for NVBit exactly as the limit holds for HBFSim [41]. Leaving Challenge 1 unaddressed produces one specific wrong number rather than a vague loss of fidelity. In one real vLLM [26] run, of 23,210 coverage decisions, 12,626 touched no registered memory, 10,584 touched registered memory but were admitted and marked untimed because the module arrived as a compiled binary with no rewritable intermediate representation, and 0 were timed successfully. Were those 10,584 accesses allowed to proceed at HBM speed with no record left in the report, the end-to-end slowdown measured would come out close to 1.0 ×, and a reader would take the tier to be nearly free. Registering more memory does not close the gap: registering the full 61,064,245,248 bytes would make the profiling phase of vLLM issue a number of synchronous requests that cannot be served. Capacity belongs to the same challenge, because a capacity range hands out addresses that no physical GPU memory backs, so a kernel the PTX pass could not rewrite faults the first time execution reaches such an address, and a run in that mode has to be refused rather than admitted. Capacity is also the entire reason HBF exists: our present evidence is a 110 GiB logical range backed by a 2 GiB HBM page cache, under which the workload runs to completion with the checksum over 128 accesses identical to the baseline, and confining the working set to what fits in GPU memory measures something other than the problem HBF exists to solve. Challenge 2: The timing model for HBF has to be accu-rate and cheap at the same time, and in this setting the two requirements work against each other. 

Accuracy and cheapness each mean something definite here. Accuracy means that the model can express one particu-lar dependence: how long an access takes depends on which page the earlier accesses left in the cache buffers of HBF, so the model has to advance while carrying the record of which page each cache buffer holds. Cheapness means that the same model has to be evaluated once for every access, inside the GPU code of the program under test. One access, however, has two units that do not line up. On the side of the program under test, one access is one memory instruction executing on the GPU whose target address falls in a range registered as HBF. On the side of HBF, the specification fixes the units at 64 bytes for a read and 4 KiB for a write, and how many 64-byte requests one memory instruction expands into follows from the addresses the 32 lanes of a warp computed at that moment rather than from the parameters of the instruction. That a device carries internal state, and that the cost of one access depends on that state, is not what Challenge 2 claims as new, since storage simulators have modeled such state for decades; what the accurate end claims is narrower and con-cerns the shape of a measured curve, which the cost form in current use cannot express. Writing the cost of one access as a fixed latency plus a byte count divided by a bandwidth makes the cost linear in the byte count, so the marginal cost per page is a constant by construc-tion. The measured marginal cost is not a constant. Table 2 gives the measured cumulative service time at six transfer sizes together with the marginal cost per page in each seg-ment. The third column is computed by subtracting adjacent breakpoints and dividing by the number of pages the segment adds. The shape rises and then falls back: the marginal cost per page rises by about a factor of five between 16 pages and 64 pages, and falls back across the rest of the measured range. Pages later in a transfer are not uniformly more expensive than pages earlier in the same transfer, and HBFSim makes no such claim. Held against the fixed-latency-plus-bandwidth form, the deviation widens monotonically with size: the model is faster than the measurement by 10.11% at one page and by 99.93% at 512 pages. Replacing that form with a constant-per-page model, the simplest repair available, still leaves a deviation of 71.86% at 512 pages, so the deviation is not a fixed offset that one constant removes; the form of the model cannot express the shape. What the six measurements calibrate has to be stated ex-actly, because the measured path is not the NAND medium. The six numbers come from one complete host software pag-ing path terminating in a Dell CD8P NVMe solid-state drive, and the source record states that these numbers make no in-dependent prediction on a different workload, and that the Dell CD8P is not a CXL device. The defensible statement at the accurate end is therefore one about the expressive power of a model form: whatever class of hardware supplies the calibration, a fixed latency plus a byte count divided by a bandwidth cannot express the measured shape. Calling the shape a property of the NAND medium would claim more than the measurement supports. The cheap end carries a measured price of its own. On one deterministic test case, the detailed reference path, which is the path able to carry state, takes 44.469 s for one generation, while the fast path, which can be evaluated on the device once per access, takes 2.014352 s, a factor of 20.8. We measured both numbers ourselves on our own two paths rather than taking either from another publication, and the source record states that “This is emulator wall time, not a hardware HBF projection.” The reason the two ends pull against each other here, and not in earlier work, is where the timing model is evaluated. A storage simulator built before HBF had to be accurate only, because its timing model runs in time of its own: refining the state machine costs the experimenter more waiting and changes nothing the workload observes. The timing model of HBFSim is evaluated inside the GPU code of the program under test and in the wall-clock time of that same program. The program really waits, and one stretch of real waiting time holds both the modeled media latency and the cost of evaluating the model, so what can be observed is a single sum. Separating the two would require knowing when the access would have completed had nothing been injected, and that quantity is the instant at which the access truly reaches the medium, which no instrumentation level observes. Failing at the accurate end makes the tier come out systematically faster than measurement on large transfers, and failing at the cheap end makes a reported slowdown factor say nothing about HBF. At the accurate end, the shape of the curve has so far been measured on one machine and one software path; at the cheap 5end, 20.8 is one measurement on one deterministic test case and moves with the workload and with the machine. The conflict as a whole rests on one premise, that the timing model can only be evaluated in the wall-clock time of the program under test. 

Challenge 3: The medium of HBF is a stack of temperature-sensitive NAND flash that shares a package with the GPU, so the rate HBF sustains over a long run is set by temperature rather than by the nominal peak. 

The wrong result that follows from leaving Challenge 3 unaddressed is that the nominal peak bandwidth of the vendor is read as a rate the device can hold. The three nominal band-widths in the specification, 0.4 to 3.0 TB/s, are short-term values: the workload itself raises the junction temperature, the temperature at the actual heat source inside the die, and above the thresholds the specification defines, HBF first lowers its clock, then stops accepting new commands, and shuts down if the temperature keeps climbing. The four thermal states and the three thresholds the spec-ification defines, whose rising and falling directions differ, are given in Section 2. Those four states set a long-run rate rather than any one instantaneous rate, because within a sin-gle run HBF moves back and forth among the four states as the temperature crosses one threshold after another. The long-run average rate is the rate of each state weighted by the time spent in that state, and the time spent in each state follows from the three thresholds, from where the two hys-teresis bands sit, and from how fast the workload heats the part. What keeps that rate from being computed is therefore not a missing formula but a missing premise, namely that the program is really running: temperature is accumulated by all the execution that came before, so recording an access sequence and replaying it afterwards yields no conversion from traffic to temperature to rate. Our measured evidence so far concerns the time scale on which temperature moves, and the boundary of that evidence is stated here alongside the numbers. Fitting a first-order ther-mal response, meaning a model that describes with a single time constant how quickly a temperature approaches its steady value, gives 13.1 s for the GPU and 12.4 s for the Dell CD8P solid-state drive, so temperature changes appreciably within the duration of one inference run. On one GPU with exclusive access, a cold run reaches 379.117 TFLOP/s and a hot run 348.427 TFLOP/s, a drop of 8.10%, with the sampled SM clock falling from about 2,062 MHz to 1,642 MHz and the driver’s cumulative software thermal slowdown counter rising from 0 to 8,279,678 microseconds; the scalar checksum of all three runs is 66.5, so the workload itself did not change. Those percentages measure the compute die of the accelerator throttling itself as the die heats, an effect that exists today and is independent of whether HBF is present; the same percent-ages are not evidence that the service rate of HBF varies with junction temperature. For comparison, the solid-state drive in the same run served reads only, wrote zero bytes, and rose by about 3.2 ◦C, far short of its own 77.0 ◦C warning point. Together the two sets of numbers fix that time scale at sec-onds. A quantity that moves within a run is a run-time state, which is why HBFSim reads junction temperature while the workload executes instead of fixing one value before the run begins. Simulators are not unable to model temperature, since ther-mal modeling inside architectural simulation is an established line of work [3]; the accurate statement is that the parameters of a thermal model have themselves to be calibrated on a real machine. What we measure is the temperature of a GPU and of a solid-state drive, not the temperature of HBF, which does not exist yet: we use the measured thermal response of a real GPU under a real workload as the boundary condition of the HBF stack, while the HBF side remains a model. Section 4 answers Challenge 1 with D1, D2, and D6, an-swers Challenge 2 with D3 and D2, and answers Challenge 3 with D4 and D5. The correspondence runs in both directions without being one to one: one challenge may be answered by several design responses, and one design response may answer several challenges. 

# 4 Design 

HBFSim closes the loop between a running GPU program and a modeled HBF device. The workload executes on an unmodified GPU software stack; a PTX pass rewrites only accesses for which it can preserve the program’s semantics. At run time, the generated helpers classify the effective ad-dress against explicit HBF ranges and route the HBF portion through either a detailed reference path or a device-resident fast path. Both paths consume the same generation-stamped thermal state and the same deterministic refresh plan. This sec-tion first defines that execution boundary and then describes timing, temperature, retention, and capacity as one coupled system. Figure 1 shows where each part of that feedback loop executes. The seven parts below answer the three challenges of Sec-tion 3. D1 and D6 answer C1: D1 decides which accesses a run covers and refuses the launch when the declared run con-tract is not met, and the same coverage decision is a precondi-tion for D6, because a capacity range hands out addresses that no physical GPU memory backs, so a kernel the PTX pass could not rewrite would fault on reaching such an address. D3 answers C2 with a detailed reference path and a device-resident fast path, and D4 and D5 answer C3 by closing the loop from traffic to temperature and from temperature to re-tention, refresh, and wear. D2 answers C1 and C2 together: once a device effect has to be applied inside the workload’s own code, splitting issue from consumption is what keeps the asynchrony the GPU already provides, and splitting issue from consumption is also what allows the timing model to be evaluated in the workload’s own wall-clock time, since rewrit-6ing an instruction into a blocking host call would serialize behavior that the GPU executes asynchronously. 

# 4.1 D1: An Explicit and Fail-Closed Boundary 

D1 answers C1. Applications register virtual-address intervals as HBF timing or capacity ranges. Registration is intentionally explicit: neither a PTX instruction nor a TensorMap descriptor says which physical tier will back its address at run time. Each range records its base, length, access permissions, page geom-etry, stream, and backing-file offset. The runtime publishes a sorted immutable snapshot, and a device helper classifies the effective address produced by the executing instruction. An address outside every registered range follows the native HBM path. An in-range access is modeled only if the com-plete byte span and its permissions are valid; an ambiguous or partially out-of-range access fails rather than silently running as HBM. This dynamic classification is essential for Tensor Memory Accelerator (TMA) operations. A TensorMap is a host-created descriptor whose base, dimensions, strides, box shape, ele-ment format, and out-of-bounds policy are values, not PTX constants. The runtime binds a hash of the exact 128-byte de-scriptor to a decoded and generation-stamped representation. At issue, HBFSim enumerates the tile’s effective element ad-dresses and partitions it into HBM, HBF, and out-of-bounds bytes. Unicast and multicast use the same partition; multicast adds one tracked destination per selected cluster rank and completes its barrier only after both native TMA and every modeled HBF segment complete. Consequently, a tile that crosses the HBM–HBF boundary is modeled byte for byte rather than assigned wholesale to either tier. The same principle limits coverage. The pass instruments PTX modules and records an admission artifact containing the original and transformed hashes, the helper ABI, and the instruction coverage. A precompiled cubin has no PTX to rewrite, so HBFSim does not claim to observe it. Exact runs are admitted only when every access required by the declared run contract is covered; otherwise the launch is refused and the reason is recorded. This turns incomplete instrumentation from an implicit source of optimistic results into an explicit experimental boundary. 

# 4.2 D2: Preserving GPU Asynchrony 

D2 answers C1 and C2. Rewriting an instruction into a block-ing host call would serialize behavior that the GPU executes asynchronously. HBFSim instead splits issue from consump-tion. An ordinary load or store allocates a small device future and continues; the first dependent use polls or waits for its modeled completion. TMA issue creates a deferred object keyed by the barrier, CTA group, cluster, and generation. Na-tive completion and modeled completion are conjunctive: neither alone releases the barrier. Every object has exactly one terminal transition, and stale generations, leaks, and faults are reported. The fast path also models the SM120 routing resources hidden below PTX. A measured routing profile maps the issu-ing SM, warp/SMSP proxy, operation class, and relative CTA rank to one of four GNIC channels and one of two GPC arbiter channels. Per-SM channel tails and queue depths determine service. Selection therefore occurs from run-time execution identity, while the PTX pass merely inserts the call site. This separation is what allows instrumentation above register al-location and instruction scheduling to reproduce a calibrated queueing consequence without pretending to reconstruct an unknown SASS schedule.

The workload does not run ahead of the model: a synchronous consumer waits imme-diately, whereas a future or TMA object waits only at its ar-chitectural dependency. The fast path avoids the host crossing. It combines the calibrated per-access curve with channel-tail reservations in device memory. Hybrid mode samples whole warp instructions into the reference path, never individual lanes, and uses those samples to expose drift between the paths. Both paths apply thermal service exactly once. # 4.7 D7: Speculative Prefetcher 

A dense LLM reads its weights in the same order on every token, so an HBF tier can fetch the pages a layer needs before that layer runs. D7 therefore predicts from the accesses already served: HBFSim fetches the pages that follow a served page fault. On a synthetic Mixture-of-Experts stream, 8 pages per ex-pert, 256 frames and 1033 distinct pages, the share of accesses served without a media read rises from 17.97% to 89.16% ,and the media reads an access still has to wait for fall by 

86.79% , from 840 to 111. The speculative prefetcher builds no media plan and never enters the detailed timing path, so it adds no modeled latency, queueing, or contention. Entering the timing path is future work, and this paper claims no run-time performance benefit from D7. 

# 5 Implementation 

The implementation is 9,302 lines of C, C++ and CUDA under src/ and include/ , with a further 3,250 lines added afterwards for the measured calibration work. Three parts are reused: the flash media model of MQSim, the CUDA call interception path of bpftime, and the inference frameworks themselves, whose source is not modified. The parts we add are the range table and its registration interface, the PTX rewriting pass, the shared control region and the interface across it, the device-side fast timing model, the thermal and retention model, and the page cache and backing store of the capacity mode. Four dependencies are pinned by commit: bpftime at

The GPU is an NVIDIA RTX PRO 6000 Blackwell Server Edition with driver 595.84, compute capability 12.0 — the version number CUDA uses to identify a GPU architecture generation — and 97,887 MiB of memory; the CUDA toolkit is 13.0.88, and PTX is assembled with the ptxas of CUDA 12.8. The flash and thermal reference device is a Dell DC NVMe CD8P E3.S 1.92 TB on PCIe 5.0 at 32 GT/s x4, attached to NUMA node 1; it supplies real flash and thermal behaviour and is not an HBF device. Section 6 describes the same machine. Host and device share one control region. It is carried in an anonymous memory file, a region of memory that has a file descriptor but no file on disk, which is then sealed against any change of size, mapped, and registered so that the device can reach it, which yields a device-side address for the same bytes. The seal is what makes the region usable from a GPU thread: the device side reaches the request ring and the completion slots at fixed offsets, and those offsets hold only if the size cannot change while the run is in progress. The other allocation route was not taken because it does not yield a file descriptor that can be mapped again after a change of process. A timed access reserves a request slot and, at the same index, the completion slot that will answer it. The reservation sequence number is written into the request and is also the ticket the caller keeps; a waiter consumes only the completion slot its own ticket names, so a completion is never taken by another access. 9The daemon publishes its first heartbeat, a counter it up-dates to show that it is still running, only after the configu-ration, the timing engine and the dispatcher have been con-structed. That first heartbeat is the readiness boundary: until it appears, no access is served. One-time initialisation is al-lowed 10 seconds, and from then on the heartbeat is updated at least once every 10 milliseconds. The device side does not subtract a host clock reading from a GPU clock reading, be-cause the two clocks are not guaranteed to share a time origin. It records the last heartbeat value it observed together with the local GPU time at which that value changed, and decides from those two whether the daemon is still running; a run whose heartbeat stops ends rather than continuing untimed. Four kinds of time are counted separately: the delay the model asked for, the wait an access actually observed, the time the host spent serving it, and the part of wall-clock time that the modeled delay does not account for. They are car-ried in four counters, modeled_ns , wall_ns , service_ns 

and overhead_ns . The reason is that a simulator which ap-plies its effects inside a real execution can be functionally correct and still spend more time in its own software path than the device latency it is modeling; a slowdown reported without that split says nothing about the device. Section 6 reports the split for every workload. Every failure ends the run, and nothing is downgraded silently. A request ends in one of eight states: PENDING ,

READY , IO_ERROR , COPY_ERROR , CHECKSUM_ERROR ,

TIMEOUT , UNSUPPORTED and DAEMON_LOST ; the six er-ror states among them end the run. When the dispatcher or the timing engine fails, two steps happen in a fixed order. A terminal error completion is first posted to the reserved ticket of every request that has been admitted, is in flight, or is still queued, and only then is the global failure word published. In that order, a waiter that observes the failure word also finds a terminal state in the completion slot its own ticket names, so no thread is left waiting on a completion that will never arrive.

HBFSim is evaluated on the questions a reader has to settle be-fore trusting any number it reports: whether the emulated run is still the same program (Section 6.2), whether the calibrated timing model returns the device measurements it was built from (Section 6.3), how the observed time divides between the modeled device and the emulator itself (Section 6.4), what the fast path costs against the reference path (Section 6.5), whether a working set larger than device memory runs at all (Section 6.6), and how far temperature moves inside one run (Section 6.7). Section 6.8 then puts the platform to the use it is built for and asks which HBF die geometry a designer should ask for. In the runs of Sections 6.2 through 6.7 the workload executes on a real GPU and HBFSim applies the device effects while it executes, so every time reported there is the wall-clock time of a real execution rather than the output of a simulated processor.

The device-resident fast path returns the reference path’s result on the same deterministic case and finishes 20.8 times sooner. # 6.7 Temperature Within One Run 

Temperature moves far enough inside a single run to change delivered performance, so a thermal state fixed once before 11 the run starts describes a different machine. Fitting a first-order thermal response gives a time constant of 13.1 s for the GPU and 12.4 s for the Dell CD8P solid-state drive, both shorter than one inference run. The same BF16 8192 ×8192 matrix multiplication was measured in three thermal states: • cold, with exclusive use of the GPU, 35 to 70 ◦C: 379.117 TFLOP/s; • concurrent with reads on the CD8P, 51 to 83 ◦C: 371.601 TFLOP/s, 1.98% below the cold run; • hot, with exclusive use of the GPU, 61 to 85 ◦C: 348.427 TFLOP/s, 8.10% below the cold run. The scalar checksum of all three runs is 66.5, so the work-load itself did not change. In the hot run the sampled SM clock falls from about 2,062 MHz to 1,642 MHz and the driver’s cu-mulative software thermal slowdown counter rises from 0 to 8,279,678 microseconds, with no hardware thermal slowdown and no power brake event recorded. The solid-state drive in the same runs delivered 7,586 MB/s alone and 7,587 MB/s while the GPU was loaded, with a p99 completion latency of 1,270 microseconds in both cases. What these runs measure is the compute die of the accel-erator and a solid-state drive rather than HBF, which cannot yet be bought, and what they establish is the time scale on which the thermal state of a loaded package moves. # 6.8 When Does Die Geometry Matter? 

Die geometry is the only variable this sweep changes: dies per channel (dpc) and the per-die capacity that follows from it, with modeled capacity (2 TiB), channel count (16), NAND page size (4 KiB) and all other flash parameters held fixed, so that any movement in HBF tail latency is attributable to geometry alone. We issue 4 KiB random reads under a closed-loop queue depth (QD) and vary dpc across six MQSim PAGE_LEVEL allocation orders. The reduced sweep uses five seeds per cell. The QD64 dpc1-to-dpc2 comparisons use 30 paired seeds and 95% confidence intervals from 10,000 paired percentile-bootstrap resamples. P99 is the primary met-ric. Geometry leaves the tail untouched until offered concur-rency passes the channel count. GPGPU-Sim [4] and Accel-Sim [22] advance a modeled instruction stream instead of executing the compute kernels of the work-load, so what is measured is the model, not the kernels a production inference server dispatches. HBFSim differs in the first two columns of Table 4: the kernels run on a real GPU and the timing model is a curve measured on a real device. eGPU [45] places code inside a running GPU kernel and is the direct predecessor of the instrumentation route HBFSim uses; HBFSim applies that ability to the timing and the capac-ity behaviour of a device that does not exist yet. NVBit [41] rewrites GPU binaries at the SASS level, the machine code the driver produces, whereas the PTX pass of HBFSim works one level above SASS, so NVBit reaches kernels that HBF-Sim cannot rewrite. NVBit contains no model of a storage medium and carries no temperature state. 

Simulating a device that cannot be obtained. Three sys-tems at other tiers simulate a device that cannot be obtained, and HBFSim differs from each on three axes. Cylon [47] emulates a CXL-attached solid-state drive presented as a byte-addressable memory tier, and acts on the CPU side through vir-tualization. CXLMemSim [44,46] simulates a pooled memory tier by attaching to an unmodified running program, observ-ing memory accesses with hardware performance counters and kernel instrumentation, and injecting delay once per fixed interval of execution. FlashAccel [43] is a hardware–software co-design of an inference system built on HBF, evaluated with an event-driven simulator. The device HBFSim simulates is flash inside the accelerator package, read at 64 bytes and writ-ten at 4 KiB, with the wear and retention limits a DRAM pool does not have. Accesses are observed and delayed in rewrit-ten intermediate code on the GPU, not at the virtual machine layer or in CPU performance counters. The third axis is the loop from temperature to reliability: none of the three makes temperature part of the device interface, whereas the HBF specification defines temperature as values the host reads, thresholds the host sets and states the host has to respond to. 

Full-system simulation before the silicon exists. A full-system simulator that already supports a new memory tech-nology is the obvious alternative to HBFSim, and the history of HBM support in gem5 [6] shows what such support consists of while the parts are still unavailable. The HBM configura-tions added to gem5 in September 2015 are timing values fed 13 to the ordinary DDR controller; the commit message gives “Timing extrapolated from existing LPDDR configurations” as one of three sources for those values, and adds, “Will adjust once specs become available.” A memory controller written for HBM itself, with pseudo channels, arrived only in May 2022, six years after HBM2 shipped with the P100. Before the silicon exists, the answer a full-system simulator gives is therefore itself extrapolated from a neighbouring standard. Speed is the weakest of the three reasons HBFSim does not take the cycle-level route, because a workload can be shrunk until a cycle-level simulator finishes within an acceptable time. Shrinking the workload supplies neither a temperature state that changes the service rate and the retention deadline nor the feedback path along which a read that returns late changes which requests the program issues next. 

# 8 Discussion 

The calibrated curve is measured on a complete host paging path, a software route that presents an NVMe solid-state drive as memory through the device node /dev/vmem0 . One access along that route carries a page fault, the driver, page-cache insertion and a user-space scan, so the profile is named an end-to-end vmem model rather than a media model. The curve is fitted at 1, 4, 16, 64, 256 and 512 pages, and past 512 pages continues on the slope of the last measured segment. Random, reverse, repeated and cross-operation accesses reset the burst length to one and are charged the single-page cost of 11,133 ns, so the non-linear rise measured between 64 and 512 pages shapes sequential bursts alone. An HBF stack inside the package pays no page fault, no driver crossing and no page-cache insertion, and the second timing source is built for the difference: foreground requests enter an online MQSim media model on the host along the reference path, or are evaluated once per access on the device along the fast path. The two paths generate the same token identifiers on one deterministic Qwen3-30B-A3B case (Sec-tion 6.5). A question about the medium is therefore answered with the media model, and a question about a host-attached deployment with the calibrated end-to-end curve. Coverage is a property of each run rather than a fixed ceiling. Under vLLM the registered span is the first 16,384 bytes of model.layers.0.mlp.experts.w13_weight ,over which the run makes 24 modeled launches out of 2,304 and records 10,339 coverage decisions (Section 6.2); registering the full 61,064,245,248 bytes is ruled out by the profiling pass of vLLM itself (Section 3). Kernels that arrive already built are covered at the level of the whole program, where injected modeled time enters the end-to-end time and the output is unchanged. Results therefore carry to accesses inside registered ranges of rewritable kernels, and widening that set is a question of registration and of the rewriting layer, not of the timing model. Hardware parameters that move are data rather than code. The three synthetic timing profiles are conservative.json ,

nominal.json and aggressive.json ; the aggressive pro-file tops out at 1 TB/s and 1 TiB, while the published spec-ification gives about 3.0 TB/s and 512 GB per stack [5], so re-anchoring the profile to the published figures edits a data file. The thermal measurements come from one GPU and one Dell CD8P solid-state drive, since HBF parts cannot yet be obtained, and the simulated-warning profile crosses the configured GPU and SSD warning points at 30 s and 42 s by extrapolation, with no physical device taken there, so figures using that profile mark the two crossings as computed values. Retention deadlines follow the Arrhenius equation anchored on Ea = 1.04 eV, measured for 3D NAND after 10,000 pro-gram/erase cycles [31]; a medium with a different activation energy moves every deadline and the refresh traffic each dead-line forces, which is why a run reports a sweep over activation energy rather than one lifetime. 

# 9 Conclusion 

HBFSim lets a real inference workload run on a real GPU while the timing and the capacity effects of an HBF device are applied during that execution. The timing comes from a curve measured on real hardware rather than from parameter-sheet values substituted into a formula, and junction temperature enters the model as a state that changes the service rate and, through the retention deadline, the volume of refresh traffic the device has to write. The evaluation gives one result for fidelity, one for speed, and one for capacity. At all six calibra-tion sizes the calibrated profile delivers the measured service time inside a real kernel, with zero unsafe launches and zero unsupported instructions. The device fast path completes the same deterministic case 20.8 times faster than the detailed ref-erence path. A 110 GiB logical range served by a 2 GiB HBM page cache finishes with checksum 14245581564465502923 ,the value the baseline run also produces. Before HBF parts sample, HBFSim lets someone designing an inference sys-tem measure a capacity or placement decision under a real workload instead of assuming one; the source, the calibra-tion profiles, and the measurement scripts are available at 

https://github.com/SlugLab/HBFSim .
