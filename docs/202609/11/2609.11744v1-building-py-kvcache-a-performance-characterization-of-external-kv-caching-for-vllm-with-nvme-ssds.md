## 摘要
前缀缓存可以通过复用先前计算出的键值（KV）状态，降低长上下文 LLM 请求的首 token 时间（TTFT），但对于短前缀或快速 GPU，重新计算可能比从外部缓存加载更快。我们使用合成工作负载、长上下文基准和生产追踪，在 vLLM 中跨 GPU、CPU 和 NVMe 层级刻画了这一权衡，并发现缓存性能不仅取决于设备带宽，还取决于传输粒度、中间内存使用以及传输何时进入请求调度。这些发现促成了 py-kvcache：一个 vLLM KV Offload 连接器，具备异步直接 I/O、有界共享暂存和调度器感知预加载，它能在请求仍在等待时启动磁盘读取，并与计算重叠。在 80k tokens 时，py-kvcache 从磁盘加载比 LMCache 快 2.0 倍，其中预加载贡献了 1.34 倍。在启用 GPU、CPU 和磁盘缓存后，它比 LMCache 快 1.23 倍，并与原生 vLLM KV Offload 实现的差距在约 4% 以内。LongBench 和 SCBench 表明，这些收益可扩展到不规则前缀链和多轮工作负载。Bailian trace 回放可在较弱 GPU 上改善 TTFT，但在 H100 上，平均请求低于盈亏平衡点，且仅 GPU 内存就保留了足够的前缀。因此，外部 KV 缓存应被视为一种取决于具体设置的准入决策。py-kvcache 实现见：https://github.com/atlarge-research/py-kvcache。

## Abstract
Prefix caching can reduce the time to first token (TTFT) of long-context LLM requests by reusing previously computed key-value (KV) states, but for short prefixes or fast GPUs, recomputation can be faster than loading from an external cache. We characterize this tradeoff in vLLM across GPU, CPU, and NVMe tiers using synthetic workloads, long-context benchmarks, production traces, and find that cache performance depends on transfer granularity, intermediate memory use, and when transfers enter the request schedule, not only on device bandwidth. These findings motivate py-kvcache, a vLLM KV Offload connector with asynchronous direct I/O, bounded shared staging, and scheduler-aware preloading, which starts disk reads while requests are still waiting, overlapping with compute. At 80k tokens, py-kvcache loading from disk is 2.0x faster than LMCache, with preloading contributing 1.34x. With GPU, CPU, and disk caching enabled, it is 1.23x faster than LMCache and within approximately 4% of the native vLLM KV Offload implementation. LongBench and SCBench show that these benefits extend to irregular prefix chains and multi-turn workloads. Bailian trace replays improve TTFT on a weaker GPU, but on an H100 the average request falls below the break-even point and GPU memory alone retains enough prefixes. External KV caching should therefore be treated as a setup specific admission decision. The py-kvcacheimplementation is available at: https://github.com/atlarge-research/py-kvcache.

# 论文总结：py-kvcache——基于 NVMe SSD 的 vLLM 外部 KV 缓存性能表征

## 1. 核心问题与整体含义

- **背景**：现代 LLM 服务中，Transformer 注意力在 prefill 阶段随上下文长度呈二次增长；KV 缓存虽可避免重复计算，但其规模随上下文长度、批量、模型宽度和层数线性增长，长上下文工作负载同时受限于二次 prefill 计算与 KV 容量/传输速率。
- **动机**：前缀缓存是极具吸引力的优化（相同文档、多轮对话、RAG 重复段落、共享前缀的批评估等），外部 KV 缓存可将 KV 块卸载到 CPU DRAM、本地 NVMe、共享文件系统甚至远程 KV 存储。但**外部缓存并非自动有益**：一次缓存命中会以"缓存查找 + 磁盘/主机内存读取 + CPU↔GPU 传输 + 调度同步"替换 GPU prefill 计算；对短前缀、低命中率或快速 GPU，这些成本可能超过重算时间。
- **核心问题**：现有系统提供了跨层存取 KV 块的机制，却配套**固定策略**，把每次前缀命中都当作收益；缺少"何时查找才划算"的决策策略。论文的核心提问不是"外部 KV 缓存能否工作"，而是"**何时应该使用它**"。
- **整体含义**：将外部 KV 缓存理解为一种**关键路径优化**，而非单纯的内存层级扩展。峰值存储带宽决定数据移动速度，但不决定移动何时开始、预留多少中间内存、以及加载是否比重算更快；调度与资源管理决策常与存储介质本身同等重要，这解释了为何更慢的来源有时反而产生更低的 TTFT。

## 2. 方法论

### 2.1 核心思想

通过代码路径追踪与跨层表征，识别 TTFT 关键路径上的主导开销，据此设计 py-kvcache——一个面向 vLLM 的 Python 外部 KV 缓存后端，针对文件系统/NVMe 存储。四条设计原则：

- 使用普通文件系统布局，便于部署与跨多个 vLLM 实例共享；
- 对块式服务引擎产生的大块连续 KV 对象保持高效 I/O，避免过度 worker 线程协调；
- 显式限制中间 CPU 内存，不随请求大小增长；
- 缓存策略感知硬件与工作负载，低于实测盈亏平衡点则绕过外部复用。

### 2.2 关键技术细节

- **接口选择**：基于 vLLM 的 **KV Offload API**（相比 KV Transfer API 更简洁，只需 `prepare_load`/`prepare_store`/`transfer_async` 等少量操作），并复用其**异步执行模型**——将 store 工作从引擎迭代 N 推迟到 N+1，使 GPU→CPU 拷贝与后续 forward 重叠。
- **I/O 路径**：放弃 xNVMe/SPDK 与 GPUDirect Storage（KvikIO）原型，最终采用**普通文件 + 直接 I/O + io_uring**（liburing Python 库）。以**单 reactor 线程**提交和收割多个未完成操作，由**可配置 I/O 深度**而非线程数控制并发。
- **有界共享暂存**：一个连续、对齐、pinned 的 CPU 分配池；每个存储块占一个固定槽位，I/O 与 GPU 传输完成后释放。请求大于池容量时**增量处理**而非为整个 KV 对象预留内存；load/store/preload 共用同一池；池可选保留完成槽位（LRU/ARC），兼作 DRAM 缓存。
- **流水线传输**：load 时按存储块流水化——先通过 io_uring 发起异步 `openat`（独立 lookahead 深度），就绪后立即排队 CPU→GPU 传输，单次 reactor 迭代中所有就绪映射**融合为一次 `swap_blocks_batch`** 在专用 CUDA stream 上启动；store 为反向流水线，每个槽位独立 CUDA stream。
- **调度感知预加载**：Manager 检查有界 lookahead 的等待请求，向 worker 发送 preload plan，在请求被调度前将匹配前缀读入 CPU 暂存池；请求进入执行时加入进行中的读或认领已暂存块，关键路径上只剩 CPU→GPU 提升。为此在 vLLM fork 中新增 `on_preload_candidates` 调度回调与对应 worker 钩子。预加载**从属于按需流量**：优先调度按需读、按需 load/store，最后才做投机预加载；预留等于 I/O 深度的槽位给前台工作；若按需 load 在投机读进行中出现，则关闭该描述符并重新排队；相同前缀的多个预加载候选**共享一次磁盘读与一个引用计数槽位**。
- **共享文件系统布局**：沿用 llm-d 的层次化哈希寻址布局；store 先写唯一命名的临时文件，完成后用**硬链接**创建最终哈希名并删除临时名——链接创建原子且失败即表示他人已发布，形成 first-writer-wins 协议；读者只打开最终名，条目要么不存在要么完整。
- **盈亏平衡门（break-even gate）**：离线按节点和模型做一次 Pareto 前沿标定，生成各来源层的盈亏平衡前缀长度文件；服务时不测量、不拟合。查找时若可复用前缀低于该来源层阈值，Manager **拒绝加载**并让 vLLM 重算，从而避免外部缓存成为回归。

### 2.3 公式与算法流程

- **缓存是否划算的判定**：设 D 为文档总 token 数，P 为缓存前缀 token 数，f(x) 为冷 TTFT（全量计算），g(x) 为命中 TTFT。当

  **g(P) + f(D − P) < f(D)**

  时缓存才有价值；由此可计算盈亏平衡 Pareto 前沿及最小盈亏平衡传输带宽。

- **盈亏平衡带宽预算**：`max_io(D) = f(D) − (g(D) − t_copy(D))`，其中 t_copy(D) 为把 KV 数据移入 GPU 的时间（取自 profiler 追踪的中位传输时长）。用文档 KV 字节数除以该预算，得到让全缓存前缀追平重算所需维持的吞吐量。
- **KV 体积**：`bytes per token = layers × 2 × KV heads × head dim × datatype size`；Llama 3.2 3B 每 token 为 112–114,688 字节，80k 上下文约 8.75 GiB。
