## 摘要
外部缓存传输可能成功，而混合语言模型却从不一致状态恢复。我们考察完整的 45 层 GLM-5.3-Flash 模型，使用 RedHatAI/GLM-5.3-Flash-NVFP4 量化检查点，在四路张量并行下结合 vLLM 和 LMCache。一次完全命中恢复不匹配为完整提示恢复了状态，而调度器却少计入了一个 token。我们通过严格前缀查找对齐恢复，并利用共享计算校正、匹配检查点调度和固定的每 rank 内核配置建立了数值比较。在包含九种长度的串行工作负载中，与修改后的重计算对照的一致性从 34/36 提升到 36/36 次生成，每次生成包含 64 个 token ID。一次单独插桩运行通过了记录的传输页、有效尾部与延迟保存检查。三个额外的合成模板在两次全新容器运行中通过了 72 对 256 个 token 的续写。随后的一项串行性能研究在 120 个请求中保持了输出相等；在测量的试验中，相对于修改后的冷重计算，CPU reload 将首 token 时间缩短了 46–64%，总请求时间缩短了 1.9–7.0%。本工作的贡献是一项经过实验验证的集成修复，应用了已有的检查点对齐原则。证据仅限于一个模型版本和受控配置；它不能确立一般确定性、任务质量等价性、并发服务收益或超出 GPU 内存的容量。

## Abstract
External cache transfers can succeed while a hybrid language model resumes from an inconsistent state. We examine the full 45-layer GLM-5.3-Flash model, using the RedHatAI/ GLM-5.3-Flash-NVFP4 quantized checkpoint with vLLM and LMCache under four-way tensor parallelism. A complete-hit recovery mismatch restored state for the full prompt while the scheduler credited one fewer token. We aligned recovery through strict-prefix lookup and established a numerical comparison using shared computation corrections, matched checkpoint scheduling, and fixed per-rank kernel configurations. In a nine-length serial workload, agreement with the modified recomputation control improved from 34/36 to 36/36 generations, each containing 64 token IDs. A separate instrumented run passed recorded transfer-page, effective-tail, and delayed-save checks. Three additional synthetic templates passed 72 paired 256-token continuations across two fresh-container runs. A subsequent serial performance study preserved output equality across 120 requests; among the measured trials, CPU reload reduced time to first token by 46-64% and total request time by 1.9-7.0% relative to modified cold recomputation. The contribution is an experimentally validated integration repair applying an existing checkpoint-alignment principle. The evidence is confined to one model revision and controlled configuration; it does not establish general determinism, task-quality equivalence, concurrent-serving gains, or capacity beyond GPU memory.

# 论文总结：使用 vLLM 和 LMCache 验证 GLM-5.3-Flash 的混合状态缓存恢复

## 1. 核心问题与整体含义（研究动机与背景）

- **核心问题**：外部缓存传输"成功"并不等于模型从正确状态恢复。论文观察到一种"完全命中恢复不匹配"（complete-hit recovery mismatch）现象：在提示长度为 3,584 token 时，四个传输 worker 报告已为全部 3,584 个 token 恢复了缓存检查点，但 vLLM 调度器只计入 3,583 个 token，并额外调度了一个输入 token，导致续写结果与无连接器对照在第 11 个生成 token 处出现分歧。
- **为何重要**：混合语言模型（同时含稀疏注意力与线性注意力）的缓存中，部分状态是**原地更新（in-place）的循环状态**，而非仅仅是注意力历史。简单地把调度器 token 计数减一，**无法回滚已加载的循环状态**。因此"缓存命中计数为正"不能说明计算是否从正确的逻辑位置恢复。
- **整体含义**：这是一项**集成修复（integration repair）**，而非新算法。作者将已有的"可复用注意力前缀需与循环检查点对齐"原则（见 Marconi 等工作）应用到一个具体的 vLLM + LMCache 集成故障上，并给出了受控条件下的实验验证。

## 2. 方法论：核心思想、关键技术细节与流程

- **核心思想——状态边界 B 与调度器位置 p 必须对齐**：
  - 设提示长度为 N，检查点间隔 C=1,792，B 为恢复检查点所代表的逻辑前缀，p 为调度器已计入的 token 数。
  - 状态表示前缀 `[0, B)` 时，支持从 B 继续计算；只有 `p = B` 才对齐。
  - 对于完全缓存提示，把查找范围限制为**去掉最后一个 token 的提示**，可选出 `B = C · floor((N−1)/C)`，调度器随后计算非空后缀 `[B, N)`。
- **故障机制**：归档的连接器把对齐查找结果保留在请求追踪器中，但后续"完整提示分支"又把计入调度器的数量减一，导致出现 `B = N`、`p = N−1` 的不一致（快照选的是完整边界，而非较短前缀的快照）。
- **修复手段**：在两个 GLM 查找入口点**排除最后一个已知 token 再查找**（严格前缀查找），使选择与查找记账处于同一边界。修复后 N=3,584 时加载 `B=1,792`、重算 1,792 token 后缀；N=5,376 时加载 `B=3,584`、重算同样长度后缀。
- **建立数值对照的关键技术**：
  - **共享计算校正**：两臂共享除外部缓存路径外的相同计算修改。
  - **匹配检查点调度**：消除早前"无连接器 3,583 token 预填 vs 连接器拆成 1,792+1,791"的批处理差异。
  - **固定每 rank FLA 内核配置**：记录基线运行中 Flash Linear Attention 自动调优器实际选出的 **7 个配置**，在每个 rank 上分别固定并清空选择缓存，拒绝调用未记录的调优器；后续运行还校验实际选中的配置。
  - 说明：该 profile 是"7 个配置的联合干预"，**单一内核消融无法证明某个 tile 大小或 warp 数单独导致分歧**。
- **累积功能补丁**：跨 LMCache 与 vLLM 修改 **11 个文件**，涵盖布局与快照处理、保存完成、检查点行为、稳定选择/打包等；最终严格前缀干预只改了两个 GLM 查找入口点。
- **观察有效性修正**：早期尾部检查报告"全零页相等"，后来发现检查的是无效地址/步幅；修正寻址后暴露出非零尾部数据与传输差异。保存也必须区分"提交"与"完成"，集成改为等待真正的 `DeviceMessagingFuture`。

## 3. 实验设计：场景、Benchmark 与对比方法

- **主工作负载（九长度边界矩阵）**：提示长度 `{3,583, 3,584, 3,585, 3,587, 3,588, 3,589, 5,375, 5,376, 5,377}`，围绕检查点边界选取。
  - 每个用例执行 **5 个串行操作**：冷状态生成目标 → 生成两个 interposer 请求 → 重置 GPU 缓存但保留外部缓存 → 重新生成目标。
  - 每个配对臂共执行 **45 个操作**（36 次生成 + 9 次重置）。
  - 输入为 27 条不同 token 序列，源自同一个**中文密码检索与解释模板**（目标与 interposer 变体仅开头文档标签不同，并非独立应用领域）。
  - **输出判据**：逐请求比较全部 64 个生成 token ID，temperature 0、seed 42、忽略 EOS；记录中无 EOS、无抢占（preemption）。
- **插桩回归**：同一修复候选加上字节观察器、H2D 前目标投毒（destination poisoning）、注入 500 ms 保存延迟。
- **内容扩展（预注册）**：三个额外合成模板——英文账本算术、中文有序规则应用、英文 Python 代码推理；长度 `{3,583, 3,584, 5,376}`，每请求生成 256 token；每臂 50 个操作、9,472 输出 token；两个全新容器各跑一对引擎。
- **性能研究（预注册、独立）**：串行流式补全，N ∈ {3,583, 3,584, 5,376}，128 token 续写；两个全新容器以相反顺序（OFF→ON、ON→OFF）运行；每长度 1 次热身 + 3 次测量；OFF 做冷启动与立即重复，ON 额外做"仅 GPU 重置后的 CPU reload"。
- **对比方法**：
  - 主要对照是**修改后的重计算控制（modified cold recomputation control）**，即共享计算校正下的无连接器路径。
  - 明确**不是**"连接器补丁 vs 未改动的生产可执行文件"的对比。
  - 性能对比是"修复后 reload vs 修改后冷重算"，**不是**与错误的前缀修复路径比延迟。

## 6. 主要结论与发现

- **修复有效**：九长度矩阵中，与修改后重计算控制的一致生成从 **34/36 提升至 36/36**；所有 9 个目标冷/重载比较一致；36 个对照生成在修复前后也彼此一致。两个此前失败的长度（N=3,584 与 N=5,376）均被修复。
- **传输元数据佐证**：修复后所有 9 次重载在四个 rank 上均记录正向 H2D 传输；N=3,584 时每 rank 传输字节从 69,625,856 降至 54,809,600，N=5,376 时从 84,442,112 降至 69,625,856，印证所选检查点发生变化。
- **插桩检查通过**：字节比较、非零尾部、延迟保存等待均通过；候选与归档对照的 36 次生成一致。
- **内容扩展通过**：两容器各 40 次续写比较全部通过；四 rank reload 元数据满足 `B = C·floor((N−1)/C)`、`computed = B`、`scheduled = N − B`，首批零 draft token；无 EOS、无抢占；每轮导出 49 个文件经独立 SHA 校验。
- **性能收益**：120 个请求输出完全一致；CPU reload 相对修改后冷重算，**TTFT 降低 46–64%**（比值 1.85–2.80），**总请求时间降低 1.9–7.0%**（比值 1.019–1.076）；ON-cold/OFF-cold 的 TTFT 比值为 1.01–1.04。
- **明确定位**：贡献是"应用已有检查点对齐原则的、经实验验证的集成修复"，**不**主张通用确定性、任务质量等价、并发服务收益或超出 GPU 显存的容量。

## 7. 优点

- **数值对照构建严谨**：清晰区分"重复执行可复现"与"跨批处理/前缀切分不变性"，指出固定随机种子无法解决浮点归约几何变化，并用固定的 FLA profile 作为具体对照锚点。
- **故障归因有实证链**：不依赖单一指标，而是用实际传输记录与批处理记录证明 `B = N`、`p = N−1` 的机制，而非仅从命中率推断。
- **观察有效性自我纠错**：主动披露早期"全零页相等"实为无效地址检查，并将其重新归类为"观察失败"而非验证通过。
- **保守且诚实的主张边界**：反复声明证据限于一个模型 revision、一个四 rank 配置、合成模板、有限续写、串行请求；明确保留失败运行的断言与非零退出码。
