## 摘要
解耦式 LLM 服务将计算密集的 prefill 和内存密集的 decode 放在不同的 GPU 资源池上。DistServe、Splitwise 和 Mooncake 等系统使这种分离变得高效，但路由仍然决定每个请求由哪些实例处理。我们研究了一种路由器，它利用精确的提示长度、预测的输出长度、准入后的 KV 缓存压力以及 SLO 类别来估计每个实例上的额外完成时间。我们在离散事件模拟器中开发该策略，并在八块 NVIDIA A40 GPU 上进行验证，每块 GPU 运行一个 vLLM 引擎，并由 NIXL 在池之间传输 KV 缓存。所有工作负载均在实测饱和状态下运行。在三条混合、突发到达的请求轨迹上，经校准的路由器实现了最高的平均有效吞吐（goodput），为 0.864，而轮询、最少负载和一种长度启发式方法为 0.835 至 0.847。它在不同轨迹间的方差也最低。它在三条轨迹上都优于轮询和长度启发式，并在两条轨迹上优于最少负载。在第三条轨迹上，它落后 0.003，处于逐次运行的噪声范围内。硬件校准很重要：由模拟器推导出的常数会损失 4.5 个有效吞吐点，并损失约 40% 的尾部延迟优势，使评分器几乎退化为仅统计队列长度。这些收益随 decode 池规模和流量异质性的增加而增大，但在只有三个实例的池中会消失，因为此时队列计数通常已经足够。在极度稀缺的情况下，贪心成本最小化会将请求集中到成本评分最低的实例上，而盲目分散表现更好。在成本经过校准的情况下，学习型路由器使用六块 GPU 即可达到轮询使用七块 GPU 的有效吞吐。

## Abstract
Disaggregated LLM serving places compute heavy prefill and memory heavy decode on separate GPU pools. Systems such as DistServe, Splitwise, and Mooncake make this separation fast, but routing still determines which instances handle each request. We study a router that estimates the additional completion time on each instance using exact prompt length, predicted output length, post admission KV cache pressure, and SLO class. We develop the policy in a discrete event simulator and validate it on eight NVIDIA A40 GPUs, each running a vLLM engine, with NIXL transferring KV caches between pools. All workloads run at measured saturation. Across three mixed, bursty arrival traces, the calibrated router achieves the highest mean goodput at 0.864, compared with 0.835 to 0.847 for round robin, least loaded, and a length heuristic. It also shows the lowest variance across traces. It beats round robin and the length heuristic on all three traces and least loaded on two. On the third, it trails by 0.003, within run to run noise. Hardware calibration matters: simulator derived constants cost 4.5 goodput points and roughly 40 percent of the tail latency advantage, reducing the scorer to little more than queue counting. Benefits grow with decode pool size and traffic heterogeneity but disappear in pools with three instances, where queue counts are often enough. Under extreme scarcity, greedy cost minimization concentrates requests on the cheapest scored instance, and blind spreading performs better. With calibrated costs, the learned router matches the goodput of round robin using six GPUs instead of seven.

## 1. 核心问题与整体含义

- **背景**：解耦式（disaggregated）LLM 服务把计算密集的 prefill 阶段与内存密集的 decode 阶段拆到不同 GPU 池，DistServe、Splitwise、Mooncake 等系统已让这一机制足够快。
- **核心问题**：机制本身**不决定放置**。每个请求仍需各自选一个 prefill 实例和一个 decode 实例，而生产系统普遍用对请求内容"视而不见"的策略（轮询、最短队列）来做这一选择。
- **为何重要**：一句聊天和一串千 token 推理轨迹，在轮询/JSQ 眼里都是"一个请求"，但占用 decode 槽位的时长可差两个数量级。若把长请求发给"看起来空闲"的实例，它自身及其后排队请求的 SLO 都会违约。
- **可用信号**：准入时刻所需信息几乎免费可得——prompt 长度精确、输出长度可预测、每实例 KV 缓存占用一次 metrics 轮询即可、SLO 类别随请求到达。
- **研究问题**：用这四类信号为放置定价的学习型路由器，能否在真实硬件上击败计数式放置？收益多大？优势边界在哪？哪个信号贡献最大？

## 2. 方法论

### 2.1 核心思想：边际成本评分

- 对每个候选 decode 实例 `d`，估计请求 `r` 在该实例上会经历的**额外完成时间**，取 argmin 放置。
- 评分公式：
  `cost(d) = w_b · backlog(d) · σ(s_r) + w_s · (ô_r / τ_dec) · (1 + ρ · press⁺(d)) · σ(s_r) + w_q · queue(d)`
  - `backlog(d)`：已提交给 d 的剩余工作量（秒）；
  - `τ_dec`：该硬件每 token 解码时间；`ô_r`：预测输出长度；
  - `press⁺(d)`：准入 r 后的缓存压力；
  - `σ(s_r)`：对紧 SLO 请求放大负载项；
  - 第三项 `queue(d)` 为队列计数项。
- prefill 候选池用类似方式评分，把 `ô_r/τ_dec` 换成 `p_r/τ_pre`。
- 算法流程（Algorithm 1，逐请求准入）：预测输出长度 → 选 prefill 实例 → 选 decode 实例 → 执行 prefill → 传 KV → 在 decode 实例上生成 → 记录结果。

### 2.2 关键技术细节

- **"校准即方法"**：`backlog` 以真实秒观测，而请求自身工作量用 `τ_pre`、`τ_dec` 定价。若常数与部署硬件不符，两项单位不一致，size-aware 项被"静音"，评分器退化为队列计数。因此路由器被定义为"构造即校准"。
- **校准流程**：对目标集群做 5 分钟基准（prefill 延迟曲线、并发下 decode 速率），据此设定 `τ_pre`、`τ_dec` 与 SLO 目标，再进行任何路由。实测中模拟器推导的 `τ_dec` 比实测值小 7.4 倍。
- **输出长度预测器**：刻意保持简单，被视为**可替换组件**；其质量不约束系统其他部分，因此用注入噪声（最高 150% 相对误差）来评估。
- **开发在模拟器、评估在硬件**：策略与特征在确定性离散事件模拟器中开发，但论文所有数字均来自硬件实测；模拟与实测的分歧本身也被报告。
