## 摘要
与先前智能体服务系统所针对的秒级工具调用暂停不同，智能体式LLM请求在等待人类审批时可能被挂起数分钟至数小时。我们研究挂起与恢复如何影响GPU服务性能，并制定一种保留策略，在不确定的审批等待中权衡主动服务容量与未来重计算。核心矛盾十分严峻：保留挂起的KV可实现快速恢复，但可能消耗大量GPU容量，使主动服务的有效吞吐量降低41%；而将其驱逐则避免了驻留成本，但在请求返回时会导致恢复延迟高出近10倍。我们围绕GPU机会成本开发了一种分层保留控制器，该控制器以统一的GPU时间成本来表达保留或重建挂起请求KV状态所消耗的服务容量。在主机内存中，控制器利用校准等待样本，在无限期保留与基于负载的过期之间进行选择，而无需对每个请求进行等待预测。在人类规模的审批工作负载上，我们的控制器相对于vLLM基线将主动请求的有效吞吐量提升了23-51%，相对于MORI提升了22-29%，相对于Continuum提升了41-52%。

## Abstract
Unlike the seconds-scale tool-call pauses targeted by prior agent-serving systems, agentic LLM requests can be suspended for minutes or hours while waiting for human approval. We study how suspension and resumption affect GPU serving performance and develop a retention policy that balances active-serving capacity against future recomputation under uncertain approval waits. The central tension is severe because retaining suspended KV preserves fast resume but can consume enough GPU capacity to reduce active-serving goodput by 41%, while evicting it avoids that residency cost at the expense of nearly $10\times$ higher resume latency when the request returns. We develop a tiered retention controller around GPU opportunity cost, which expresses the serving capacity consumed by preserving or reconstructing a suspended request's KV state in a common GPU-time cost. Within host memory, the controller selects between indefinite retention and load-indexed expiration using calibration wait samples, without requiring per-request wait prediction. On human-scale approval workloads, our controller improves active-request goodput by 23-51% over the vLLM baselines, 22-29% over MORI, and 41-52% over Continuum.

## 1. 论文的核心问题与整体含义

- **背景与动机**：现有的智能体服务系统（如 MORI、Continuum）主要面向**秒级工具调用**的暂停（例如 1–2 秒）。但真正意义上的**人类审批**——如 AI 编程助手等待用户确认发送邮件、修改文件或执行命令——往往持续**数分钟乃至数小时**。在这个时间尺度上，如何管理挂起请求的 KV 缓存成为一个全新的系统问题。
- **核心矛盾**：保留挂起请求的 KV 缓存（尤其在 GPU HBM 上）可以实现快速恢复，但会占用本可用于活跃请求的服务容量；实验显示强制驻留可使活跃请求 Goodput 下降约 **41%**。若将 KV 从 GPU 驱逐/丢弃，虽消除了驻留开销，但恢复时需重新计算，Resume TTFT 增大约 **10 倍**（从 66–75 ms 升至 687–705 ms）。
- **更深层的意义**：作者指出，在人类审批时间尺度下，**Resume 延迟本身已不重要**（1 秒的恢复阻塞在 30 分钟等待中只占 0.06%），关键是**驻留状态的 GPU 机会成本随时间持续累积**。因此，KV 保留不再是一个简单的缓存命中率问题，而是一个**容量分配（capacity allocation）** 问题：每一项保留决策都意味着牺牲可能为其他活跃请求提供服务的 GPU 时间。
- **核心洞察**：不存在对所有审批等待分布都最优的固定保留计时器。若等待呈无记忆性分布（如指数分布），时间流逝不提供信息，设置过期只会徒增抖动；若等待群体中同时存在短等待与长等待的异质性用户，则“已等待的时间”能帮助区分哪些 KV 更可能在近期恢复——从而需要**面向分布选择策略（regime-aware）**。

## 2. 方法论

### 2.1 核心思想：GPU 机会成本统一度量

- 论文把“保留/重建挂起请求 KV 状态”所消耗的服务容量统一表达为 **GPU 时间（GPU-seconds）**，即 GPU 机会成本模型。
- 三种状态类型：**GPU HBM（GPU 驻留）**、**Host DRAM（主机内存驻留）**、**Discard（丢弃后重算）**。每种状态定义了：
  - α_j：每秒持有成本（holding cost）
  - β_j：一次性恢复成本（resume cost）

### 2.2 核心成本模型公式

对于在状态 j 中等待 ℓ 秒的请求：

\[
C_j(\ell) = \alpha_j \ell + \beta_j
\]

- HBM：α₁ > 0，β₁ = 0（驻留期间持续占用 GPU，恢复时无额外成本）
- Host DRAM：α₂ = 0（只要主机容量充足），β₂ > 0（恢复时需从主机拷贝到 GPU）
- Discard：α₃ = 0，β₃ > 0（恢复时需重新 prefill 已丢弃的 suffix）

**关键断点**：
- HBM 与主机 DRAM 的均衡点：t₁ = β₂ / α₁
- HBM 与丢弃重算的均衡点：t* = β₃ / α₁

### 2.3 主机拥塞与负载索引过期

一旦主机 DRAM 容量受限，主机驻留本身也要计价：基于 **Little's Law**（N = λW），推导主机层饱和点 λ_crit = C₂ / W_ref。超过该负载后引入平均场拥塞价格：

\[
\alpha_2(\lambda) = \max(0, \lambda - \lambda_{crit}) \cdot \beta_3 / C_2
\]

进而得出负载索引的 DRAM–Discard 阈值：

\[
t_2(\lambda) =
\begin{cases}
\infty, & \lambda \leq \lambda_{crit} \\
(\beta_3 - \beta_2) / \alpha_2(\lambda), & \lambda > \lambda_{crit}
\end{cases}
\]

### 2.4 两阶段保留控制器（Regime-Aware Controller）

- **阶段 1（GPU → Host 卸载）**：由于 t₁ ≈ 1s 极短，请求挂起时 KV 立刻从 GPU 卸载到主机 DRAM。
- **阶段 2（主机层保留策略选择）**：给定校准数据，在 **无限期保留（host-retain）** 与 **负载索引过期 cpu_ttl(λ)** 两条策略分支之间做选择：
  - 方法：从独立校准样本中分别用两种模式重放，计算各自总 GPU 机会成本，选择成本更低的策略分支并冻结（freeze）用于正式服务。
  - 运行时只需观测负载 λ，即可计算 t₂(λ)；无需预测每个请求的具体等待时长。

### 2.5 校准方法

- 通过平台测量获得三个常数：(α₁, β₂, β₃)；
- α₁ 通过 KV 池占用来计算（如每挂起 suffix 占总 KV 池 Token 比例，乘以 4 张 GPU）；
- β₂ 只计 GPU 端调度与同步开销（约 0.02 GPU-s），不计可重叠的 DMA 传输时间；
- β₃ 通过带共享前缀缓存的 suffix 重 prefill 实测得到（客户端侧 E2E TTFT × 4 GPU Ranks，约 1.91 GPU-s）。

## 6. 主要结论与发现

- **保留有代价**：强制 KV 驻留最多让活跃 Goodput 下降 41%；驱逐则使恢复延迟提升约 10×。
- **在人类审批尺度下，决策应面向“容量分配”而非“缓存命中”**；Resume TTFT 在 30 分钟等待中只占 0.06%，焦点应放在 GPU 容量的机会成本。
- **没有单一的最佳主机保留计时器**：不同等待分布下 host-retain 和 ttl（过期）策略各有优势。本文控制器通过校准选择正确分支。
- **性能提升**：在 2λ_crit 的端到端服务中，相对 vLLM 基线提升 23–51%；相对 MORI 提升 22–29%；相对 Continuum 提升 41–52%。在混合等待分布上，即便 MORI 保留更多 KV（21.9% vs. 17.6%），仍低于本方法 Goodput（0.83 vs. 1.07 req/s）。
- **crossover 规则**：在固定负载与校准参数下，TTL 策略 vs. host-retain 的优劣势在 P(W ≤ t*) ≈ 0.39 处发生切换：当很短等待占比升高时过期策略更好，否则保留更优。
- **可迁移性**：不同 GPU 平台校准出的 α₁ 与 t* 差异很大（t* 范围 43.5–112 s），但在各自平台重放后的策略优选顺序一致——说明校准方法可以跨平台迁移，但阈值本身必须本机测量而非直接复用。

## 7. 优点

- **问题驱动扎实**：从“人类审批”这一实际痛点出发，使用真实的 τ²-bench 写操作门控轨迹、真实人类邮件延迟统计作为依据，支撑了长尺度等待的动机。
- **模型简洁统一**：用 GPU 机会成本把持有/恢复/重算三种状态的代价统一为一个 GPU 时间标度，方法上属于**系统推理而非纯启发式**，清晰而优雅。
- **参数少且透明**：只需校准三个平台系数（α₁、β₂、β₃），不需要每请求预测，易于在实际部署时做平台自校准。
- **策略选择可靠**：直接在使用之前做成本最小的分支选择，固定选择后部署，大大降低运行期复杂度，且对负载变化和校准错误有一定容忍。
- **实验设计好**：不仅测端到端 Goodput，还通过归一化 TTFT 区分“resident”、“recomputed”状态，解释力强；对全系统施压采用 victim-exclusion patch 做受控实验。
- **开源合规与可复现**：对 vLLM 的 patch、详细校准协议、CPU-only 重放和 trace 生成、外部资产生成过程都给出实施办法；附录对基线实现细节作了一定交代，安全考量完善。
