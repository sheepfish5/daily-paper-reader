## 摘要
推演（rollout）推理往往主导大规模强化学习（RL）的挂钟时间。在智能体RL中，每条轨迹在多个回合中交替进行模型生成与环境交互。因此，异步轨迹会在其他轨迹仍处于解码（D）阶段时引入新的预填充（P）工作，使得P/D共存成为推演的持续属性，而非一次性提示词摄入事件。在共享加速器上，持续P/D共存可能使预填充干扰对延迟敏感的解码，并延长推演完成时间。P/D分离（disaggregation）避免了这种共置，但需要独立的设备池和KV缓存传输。原位复用（in-place multiplexing）保留共享设备与KV状态，但现有设计缺乏大规模MoE部署所需的通信隔离——这些部署将注意力TP/DP与分布式专家执行结合。在实际实现中，P和D可能以不一致的跨秩顺序发出相交的集合通信；DeepEP的P和D路径也共享可变协议状态。我们提出AInfer-PD，将原位P/D复用扩展到分布式MoE推演。AInfer-PD跨秩协调P/D集合通信顺序，并为DeepEP的两条路径提供独立通信状态，使交叉的ADP/ATP和DeepEP路径在并发P/D执行下保持安全。该设计在共享模型权重和KV存储的同时，在同一设备上协调P和D。在重复的单节点prefill密集型工作负载上，相对于禁用P/D复用的同一AInfer引擎，AInfer-PD将固定工作负载的推演完成时间减少7.1%-22.5%；相对于SGLang减少24.8%-32.9%。在两节点上，降低幅度分别为18.0%-35.3%和18.3%-31.8%。在同引擎消融中，细粒度边界相比整个epoch的异步入队进一步将完成时间降低8.6%-19.8%。

## Abstract
Rollout inference often dominates the wall-clock time of large-scale reinforcement learning (RL). In agentic RL, each trajectory alternates between model generation and environment interaction over multiple turns. Asynchronous trajectories consequently introduce new prefill (P) work while other trajectories remain in decode (D), making P/D coexistence a persistent property of the rollout rather than a one-time prompt-ingestion event.   On shared accelerators, persistent P/D coexistence can make prefill interfere with latency-sensitive decode and prolong rollout completion. P/D disaggregation avoids this co-location but requires separate device pools and KV-cache transfers. In-place multiplexing retains shared devices and KV state, but existing designs lack the communication isolation needed for large MoE deployments that combine attention TP/DP with distributed expert execution. In practical implementations, P and D can issue intersecting collectives in inconsistent cross-rank orders; DeepEP's P and D paths also share mutable protocol state.   We present AInfer-PD, which extends in-place P/D multiplexing to distributed MoE rollouts. AInfer-PD coordinates P/D collective order across ranks and gives the two DeepEP paths independent communication state, making crossed ADP/ATP and DeepEP paths safe for concurrent P/D execution. The design retains shared model weights and KV storage while coordinating P and D on the same devices. Across repeated single-node prefill-intensive workloads, AInfer-PD reduces fixed-workload rollout completion time by 7.1-22.5% relative to the same AInfer engine with P/D multiplexing disabled and by 24.8-32.9% relative to SGLang. On two nodes, the reductions are 18.0-35.3% and 18.3-31.8%, respectively. In a same-engine ablation, fine-grained boundaries reduce completion time by a further 8.6-19.8% over whole-epoch asynchronous enqueue.

## 1. 论文的核心问题与整体含义

- **研究动因（背景）**：在大规模强化学习（RL）中，rollout 推理阶段常常是训练挂钟时间的主要瓶颈；而 agentic RL 的轨迹是多回合的——每一回合中模型生成动作后等待环境/工具响应，响应回来后再附带新增上下文进行 prefill，然后继续解码。由于各异步轨迹回合长短不一，导致“新的 prefill（P）持续混入仍有 decode（D）执行”的现象，P/D 共存是系统性的持续状态，而非一次性 prompt 处理事件。
- **核心问题**：在共享 GPU 设备上，prefill 与延迟敏感的 decode 相互竞争计算与通信资源，会拖慢整个固定轨迹集合的完成时间。解决方法主要有两类：
  - **P/D 分离（disaggregation）**：使用独立部署池，需要额外设备、跨池 KV 传输、协调机制，成本高。
  - **原位复用（in-place multiplexing）**：共享设备/模型权重/KV 状态，原有工作缺乏大规模 MoE 部署下 P 与 D 之间的通信隔离能力（例如“attention TP/DP 与分布式专家执行”组合的路径中，P 与 D 可能以不一致的跨 rank 顺序发出相交集合通信；DeepEP 中 P 正常路径与 D 低延迟路径会共享可变协议状态，难以并发）。
- **整体含义**：本论文提出 **AInfer-PD**，将安全的通信隔离引入“原位 P/D 复用”模式，使其适用于分布式 MoE rollout 引擎，既避免额外设备或 KV 转移，又消除并发 P/D 引发的分布式死锁/通信竞争，从而加速整个 rollout 完成时间。

## 2. 方法论：核心思想、关键技术细节与算法流程

- **核心思想**：沿用 AInfer 引擎，将 P/D 安排在同一设备/模型/KV 资源上运行，但引入两类针对大规模 MoE 部署的增强：
  1. 跨 rank 的 P/D 集合通信排序机制；
  2. 面向 DeepEP 的两条执行路径（正常模式 vs 低延迟模式）的独立通信状态隔离，使其能并发安全执行。
- **关键技术细节与技术方案**：
  - **In-place P/D 执行与段式交错**：P 任务较长，会被拆分为多个由后端发布的“通信安全边界”（communication boundaries）所划分的段。调度器维护 rank-shared 调度计划，每个 turnstile round 中：先让所有 rank 一致地**enqueue 一整个 D 迭代**，再让 **P 执行一个段**，直到下一通信边界。此前提交的 P GPU 工作继续异步执行，从而在长时间 P 执行过程中不断穿插推进 D。
  - **ADP/ATP 交叉集合通信的排序协议**：解决 P 中 full-group TP AllReduce 与 D 的 DP-attention ReduceScatter/AllGather 在相交进程组中“跨 rank 乱序”导致的分布式进度环死锁。
    - 通过分布式转门（turnstile）：在每次 D 调度前，所有 rank 先进行两段 CPU 控制相位（`PreDRendezvous` 与 `PostDRendezvous`）来保证 P 已发布到边界且 D 能被一致地入队；
    - 通过**选择性流路径**，把与 D 冲突的 P 集合通信放到 D 的图启动流上，从而在设备执行顺序层面建立一致的 D→P 顺序（受 CUDA stream FIFO 保证），只约束冲突的路由调用，不约束其他 P 计算和非交集通信；
    - 该协议不会等待 P GPU 整体完成：D 插入各边界之间即可推进。
  - **DeepEP 状态隔离（phase-owned state）**：
    - 一个进程级 DeepEP/NVSHMEM 运行时，但 P 与 D 分别单独拥有缓冲区、计数器、workspace、流、事件和 QP 范围；共享模型权重/KV/物理连接等；
    - 将 DeepEP 正常模式的 dispatch 拆分为：专家通知 →（此时暴露边界）接收计数 + 数据搬运；P 在后台获取 receive-count，随后在获得计数与转门许可之后才提交数据移动；D 继续走其低延迟低延迟路径；
    - 分离通信-SM 预算，避免跨相位围栅（fence），保证取消操作/生命周期清理的安全性。
- **算法/控制流程（简化文字版）**：
  1. 给定 P epoch e，预设许可端点 p、跨度 K；
  2. P 提交段，并在每个边界处发布边界标识 i，直到结束报告 TaskDone；
  3. 转门：若 p=0，先等 D 入队；进入前置 rendezvous → 发布 D 的 registered calls → 进入后置 rendezvous → p ← p+K → 释放下一段 P；
  4. 在交叉路径上执行“D→P”的设备顺序约束；
  5. 对 DeepEP 路径，P 等待 receive-count 后再提交数据移动，保证与 D 的低延迟通信状态互不干扰。

## 8. 不足与局限性

- **硬件规模有限，缺乏大规模集群验证**：实验仅覆盖单节点 4/8 卡与两节点 16 卡 H20-3E，H200 仅用于 RQ3 机制诊断；对真实生产级大规模 MoE rollout（如数百卡、跨多机架）的通信竞争、NVLink/Switches 层级拥塞、DeepEP 跨节点低延迟路径的表现，尚未充分验证。论文论点涉及分布式死锁，最好在更广的节点规模和拓扑（如 3D torus、多机多交换机）下做压力测试，而目前结论主要依赖小规模、单/双节点场景。
- **RL 轨迹真实性与多样性受限**：轨迹来自匿名化内部 RL 推理日志，虽保留了多回合结构，但论文未说明这些请求所依托的基座模型、采样参数、工具环境分布，也未公开轨迹数据或提取特征的直方图，因此外部读者无法独立评估其分布的代表性与泛化性。
- **缺乏与 P/D 分离（disaggregation）方案的直接量化对比**：文中反复强调避免额外设备与跨池 KV 传输，但只在同引擎内与“Normal”（无复用）和整系统外基线 SGLang 做比较，没有提供将 P/D 分离到独立 GPU 池时在相同模型与固定预算下的对比实验（时间、吞吐、GPU 成本）；这使“原位复用更优”这一核心主张缺少直接数据支撑。
- **live-RL 实验作为证据的效力有限**：两次运行虽然是真实端到端训练，但每次只一次运行、轨迹随训练进程变化，存在训练发散或其他配置差异的混淆因素；论文没有将其作为严格的受控 A/B，也没有延长训练时长考察长期稳定性与采样质量影响，严谨性受影响。
- **某些机制性结论的通用性不足**：交叉序死锁的复现与修复、DeepEP 状态隔离均在特定 NCCL/DeepEP 版本与特定拓扑组合下验证；NCCL 与 DeepEP 的协议变化（如新的 PT2A、RDMA 保护带、SM 调度）可能使文中提出的边界和 phase-owned state 设计需要重新适配。
- **指标层面对延迟与公平性刻画不够深**：对 p99 TTFT、逐请求 QoS 的分析较浅；在不同轨迹并发/优先级场景下，P/D 交错如何影响各回合完成时间稳定性和公平性（是否有请求被系统性地推迟）没有展开讨论。
- **复现所需细节披露不充分**：调度器关键参数（时钟轮询间隔、enqueue 阈值、片段大小选择策略的具体公式、DeepEP 的 NVSHMEM 配置细节）未完整公开；也未给出最终版本代码/伪代码的产物链接或附录中的代码片段，这限制了复现性。

## 9. 我的个人评价与后续思考

- **对问题选择的评价**：这是切中实际系统痛点的选题。Agentic/多回合 RL 推理负载使“持续有新 prefill 混入 decode”成为常态，而绝大多数推理引擎的调度器和集合通信库并未针对这种持续混合设计。将“原位复用”重新提出，并用分布式通信排序去解决此前未被专门定义的死锁类别，研究思路具备真实价值。
- **对技术路线的思考**：将同步负担从 GPU 移到 CPU、用细粒度“通信边界”切分 P 而非整 epoch 等待，是整个方案中最巧妙且性价比最高的一步。因为它直接回应了此前 P/D 复用方案的痛点（长 P 阻塞 D 或全带宽竞争），同时不引入昂贵的全局栅栏。选择性限制冲突通信（而非全局串行化）也体现了良好的系统化权衡功力。
- **对局限的反思**：若需在更多场景验证该方法，应优先考虑三件事：
  1）在更广泛的硬件拓扑上运行相同的 trace，以检验死锁避免协议在大规模下是否仍然有界；
  2）与 P/D 分离（在不同 GPU 上额外部署 prefill worker 与 decode worker）做严格的成本—时延对照；
  3）将 AInfer-PD 作为 rollout 服务接入真实的 RLHF/RLVR 训练回路中，观察多轮训练间的长期稳定性与采样质量影响。
- **对可改进处的一点设想**：将来可考虑将通信隔离与调度策略下推到集合通信库层的抽象接口（如提供“low-latency lane”与“throughput lane”双通道的统一 API），使得 KV/权重复用之外的各类新算子也能直接受益，而不必每次针对特定库（如本节针对 DeepEP）重新实现隔离协议——这也可能是从经验方案迈向通用系统抽象的关键一步。

## 10. 总结

AInfer-PD 面对多回合 agentic RL 推理中“prefill 与 decode 在同一设备上持续共存”的现实，指出现有原位复用方案的两个薄弱环节：跨 rank 的 ADP/ATP 通信顺序不稳定，以及 DeepEP 双模式状态共享导致并发风险。它通过主机侧转门协议、选择性设备流路径，以及面向 DeepEP 的 phase-owned 状态隔离，仅约束冲突路径而保留大量并行性，在不增加 GPU 的前提下，将固定轨迹集合的端到端完成时间进一步压缩。整体实验覆盖单/双节点、多种并行拓扑、MTP 启停、FP8/BF16 与 DeepEP 前后端，数据充分、内部对照设计扎实，且性能收益明确。局限在于验证规模较小、缺少与 P/D 分离的直接成本对比，以及复现细节与长期稳定性的证据不够完整。

从系统角度看，论文展示了一条务实而有效的路径：不追求新一代硬件专门化，也不引入通用调度框架的大规模改造，而是靠细致梳理冲突子集、在关键资源上做状态隔离来让已有的硬件与模型架构变为可用，并保留可观的并行余量。它为多回合 agentic 推理场景下的 P/D 共处的工程实现提供了有价值的参考基线，也为后续研究如何在更普遍意义上抽象“低延迟通信通道与吞吐通道的安全复用”留下了开放的方向。
