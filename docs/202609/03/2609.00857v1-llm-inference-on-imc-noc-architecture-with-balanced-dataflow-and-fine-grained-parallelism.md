## 摘要
LLM推理已成为一项基本服务，但它对内存带宽、计算密度和通信效率提出了前所未有的要求。虽然IMC是解决内存墙问题的一种有前景的方案，但LLM的异构数据动态性需要互补资源来处理运行期间生成的中间数据。此外，LLM中数量庞大的参数需要扩展架构，其中片上数据移动通常是主要的性能瓶颈。本文提出了一个硬件-软件协同设计框架，将分布式计算、内存和通信统一到一个无缝的处理-通信结构中。在硬件方面，我们提出了一种名为LEAP的可扩展架构，它集成了IMC PE、NMC PE和INC。这使得每个硬件层能够执行专门的任务：IMC用于静态权重，NMC用于动态数据，INC用于部分结果归约。在软件方面，我们介绍了一种针对LLM服务中关键指标（包括吞吐量和延迟）优化的分区、映射和调度框架。为了解决预填充和解码阶段的不同计算强度，我们提出了一种预填充-解码分离方法，该方法动态重新配置PE组织以最大化资源利用率。与商业GPU平台相比，所提出的架构分别提供了≥1.52倍的吞吐量提升和24.91倍的能效提升。

## Abstract
LLM inference has become an essential service, yet it imposes unprecedented demands on memory bandwidth, computational density, and communication efficiency. While IMC is a promising solution to the memory wall issue, the heterogeneous data dynamicity of LLM requires complementary resources to handle intermediate data generated during run-time. Furthermore, the massive number of parameters in LLM necessitates scale-up architectures where on-chip data movement is often the primary performance bottleneck. This article presents a hardware-software co-design framework that unifies distributed compute, memory, and communication into a seamless processing-communication fabric. On the hardware side, we propose a scalable architecture, named LEAP, that integrates IMC PE, NMC PE, and INC. This allows each hardware layer to execute specialized tasks: IMC for static weights, NMC for dynamic data, and INC for partial result reduction. On the software side, we introduce a partitioning, mapping, and scheduling framework optimized for key metrics in LLM serving, including throughput and latency. To address the distinct computational intensities of the prefill and decode phases, we present a prefill-decode disaggregation approach that dynamically reconfigures PE organizations to maximize resource utilization. Compared to commercial GPU platforms, the proposed architecture provides a throughput and an energy efficiency improvement of $\geq{}1.52\times$ and $24.91\times$, respectively.

## 论文总结

### 1. 核心问题与研究动机

- **大语言模型（LLM）推理的硬件瓶颈**：LLM 推理对内存带宽、计算密度和通信效率提出了极高要求。尽管存内计算（IMC）能有效缓解"内存墙"问题，但 LLM 数据具有"静态预训练权重 + 运行期动态中间数据"的混合特性，单一 IMC 无法高效处理动态激活数据。
- **分布式 IMC 扩展带来的通信瓶颈**：单个 IMC 交乘阵列（crossbar）容量有限（KB 级），支撑数十亿参数模型必然涉及大规模空间扩展；此时片上网络（NoC）中部分结果的聚合与归约成为主要性能瓶颈。
- **prefill 与 decode 阶段的计算强度悬殊**：prefill 阶段属于计算密集型（compute-bound），decode 阶段属于带宽密集型（bandwidth-bound），二者对硬件的需求截然不同，统一调度会造成资源利用率下降。
- **软件层协同调度的缺失**：现有工作多侧重于纯硬件设计或纯软件调度，缺少面向"IMC+X"分布式异构架构的端到端软硬件协同优化框架。

### 2. 方法论

#### 核心思想

提出 LEAP 架构，将三类核心资源集成到统一的处理-通信结构（processing-communication fabric）中，使每个硬件层次各司其职：
- **IMC PE**：专门执行静态权重与动态输入之间的矩阵乘法（DSMM）；
- **NMC PE / 路由器内 scratchpad**：存储动态数据并执行动态矩阵间的乘法（DDMM）；
- **INC（in-network computing）**：在 NoC 路由器内部集成算术逻辑（IRCU），用于部分结果归约与动态数据的矩阵运算。

#### 关键部件与流程

1. **硬件模板（Hardware Template）**：采用 2D Mesh NoC 结构，每个 "macro" 由 PE 与路由器构成。路由器内包含 NMC 资源（scratchpad + 矩阵乘法逻辑）与 INC 资源（归约逻辑）。

2. **两种工作模式**：
   - **LEAP-A（聚合模式）**：所有 macro 同构配置，prefill 和 decode 共享硬件资源；
   - **LEAP-D（分离模式）**：prefill 区域保留 IMC PE 与路由器资源，decode 区域移除 IMC PE 但扩展 scratchpad 容量。

3. **矩阵划分（Partitioning）**：静态权重矩阵按行和列维度分割后映射到 IMC crossbar；动态矩阵（Q/K/V）的切分受 IRCU 带宽和 scratchpad 容量约束。划分粗粒度上类似 GPU 场景的 tensor parallelism + context parallelism，但粒度更细。

4. **空间映射（Mapping）**：
   - 启发式约束：同源子矩阵映射到连续区域、区域尽量呈矩形、按行主序/列主序展开以降低数据流不规则性；
   - 层间映射采用蛇形拓扑（serpentine topology），以高效实现各解码器之间的自回归中继；
   - KV 缓存采用循环存储（cyclic storage）策略以适配解码阶段不断增长的上下文长度。

5. **数据流模式（Dataflow Patterns）**：定义三类集体通信原语——Broadcast、Reduce、ReduceScatter，以及衍生的 AllReduce、AllGather、E-ReduceScatter 等。所有数据流在编译阶段即可确定，运行期无需仲裁，降低控制开销。

6. **PD 分离（Prefill-Decode Disaggregation）**：针对 prefill 与 decode 的计算/内存需求差异：
   - LEAP-D 将 KV 缓存从 prefill 区域传输到 decode 区域，但通过与 AllGather 等步骤重叠执行，KV 传输不位于关键路径上，无额外时间开销；
   - 对比现有工作：与 DistServe（GPU 上依赖网络带宽过配）、Adrenaline（操作级分离）不同，LEAP 利用细粒度计算-通信调度在中等带宽下实现低延迟。

7. **批处理（Sequence Batching）**：分析了两个请求并发时的调度冲突并定义了仲裁策略——当两个请求竞争访问 IMC 中静态权重时，以单层粒度协调调度。

### 6. 主要结论与发现

1. 相比 A100，LEAP-A 吞吐量提升 ≥ 2.55×，能效提升 ≥ 71.94×；相比 H100，LEAP-D 吞吐量提升 ≥ 1.52×，能效提升 ≥ 24.91×。
2. decode 吞吐天然比 prefill 低 4–6×，但通过 LEAP-D 的 PD 分离设计可显著缩小这一差距。
3. LEAP 的吞吐下降速度远低于模型参数增长速度（如 1B→8B 模型量增约 8× 时吞吐并不按比例下降），原因在于关键路径只随行/列方向扩展而增长，而非随总面积扩展增长。
4. 关键路径开销主要集中于通信（IRCU 内的数据移动与 DDMM），IMC 侧运算很少成为瓶颈——验证了"数据移动是主要性能瓶颈"这一设计假设。
5. batching 并非总是最优策略：batching 有助于降低 TTFT，但会增加 TPOT；两种模式应互为补充，根据应用需求（交互式 vs. 长文本生成）灵活选择。
6. 路由器虽是面积小头（占 macro 的 17.51%），却是功耗大头（占 56.32%），有效证明了片上通信优化的价值。

### 8. 不足与局限

- **与已有加速器的比较仅定性**：表 I 的对比基于功能特性而非实测数据，无法确认 LEAP 实际相对这些 SOTA 加速器的优势。

- **使用 128×128 RRAM 假设**：IMC 的参数来自特定文献，RRAM 良率、精度、写入开销、工艺变化等实际物理约束未充分讨论，可能低估端到端实现的复杂度。
- **KV cache 传输的能效代价未被单独量化**：虽然文中声称 KV 转移与现有通信重叠、无关键路径开销，但传输带来的额外能耗没有被剥离分析。
