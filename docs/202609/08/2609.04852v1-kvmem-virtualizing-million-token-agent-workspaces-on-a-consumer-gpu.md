## 摘要
现代LLM智能体在持久工作空间中运行，其累积的历史可能超过GPU KV容量和模型原生上下文窗口。现有系统通常将较旧的上下文压缩为摘要或稍后作为文本检索，这要么丢失了细粒度的执行证据，要么重复预填充模型已经处理过的内容。我们提出KVMem，一种KV上下文虚拟化系统，它将溢出工作空间历史作为分页KV状态，分布在GPU内存、主机内存和NVMe上。KVMem使用轻量级的、模型原生的注意力空间索引来选择相关的历史块，并实现一个受模型原生上下文窗口约束的、依赖于查询的执行视图。在长达一百万Token历史的长上下文智能体基准上的广泛评估（包括LongMemEval、MemoryAgentBench和AgentLongBench）表明，KVMem通常比基于压缩的方法（处理上下文溢出的事实标准）获得更高的任务效用和更高的推理效率。在使用Qwen3.8-27B的DeepSWE长上下文测试中，KVMem将任务成功率从仅压缩上下文管理的43.8%提高到48.4%。在我们的本地部署评估中，KVMem在配备24GB RTX 5090笔记本电脑GPU的现成笔记本电脑上运行Qwen3.6/3.8-27B NVFP4与MTP，虚拟化高达100万Token的智能体工作空间——是模型原生256K Token上下文窗口的四倍。在单会话设置中，KVMem生成约50 Token/s，为本地智能体执行提供交互式响应。更广泛地说，通过将可寻址工作空间大小与LLM的原生上下文窗口解耦，KVMem为工作空间可以超越该窗口增长的长运行智能体提供了一条实用路径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

# KVMem 论文详细中文总结

## 1. 核心问题与研究背景

- **问题根源**：现代 LLM 智能体在持久化"工作空间"（workspace）中运行，会持续累积大量任务上下文（历史对话、文件内容、工具输出、日志等）。这一积累面临双重限制：
  - **内存限制**：即便历史总量在模型原生上下文窗口内，其全部 KV 状态也无法同时驻留在 GPU 显存中（模型权重、运行时缓冲等竞争同一份显存），导致实际可用上下文远小于广告窗口。
  - **窗口限制**：长时间运行后，累积工作区本身可能超过模型原生上下文窗口（例如 Qwen3.6-27B 原生窗口为 256K tokens，但长上下文智能体基准的轨迹可达数百万 token）。
- **现有方案的缺陷**：
  - **压缩（Compaction）**：将旧历史压缩为摘要，在压缩时就需预判未来相关性，存在信息丢失风险（论文用不可区分性论证：两个不同历史可映射到同一摘要，导致未来查询无法恢复区分性信息）。
  - **文本检索（Text Retrieval）**：检索到的文本需重新做全量 prefill，重复计算模型已经处理过的内容，造成推理效率低下。
- **核心洞察**：当历史离开活动上下文时，模型已经将其编码为 KV 状态；溢出并不意味着 KV 状态必须被丢弃。借鉴操作系统虚拟内存思想，应将**智能体可寻址的 KV 工作空间大小**与**GPU 上物理驻留的 KV 状态量**解耦——溢出历史可以以分页 KV 形式保存在更大的后备存储中，按需选择性物化。
- **总体含义**：KVMem 使可寻址工作区能够远超模型原生窗口和 GPU KV 容量，为长时运行智能体在消费级硬件上提供高保真、低开销的历史访问路径。

## 2. 方法论

### 2.1 核心架构抽象

- 将工作区历史按逻辑块（默认 32 tokens/块）切分，作为检索评分、选择和 KV 移动的单位。
- 区分三个容量层：模型原生上下文窗口（B_model）、GPU KV 预算（B_gpu）、主机内存+NVMe 后备工作区（B_m）。有效活动上下文预算为 Ba = min(B_model, B_gpu)，后备容量 Bm 可远大于 Ba。

### 2.2 三大核心机制

**机制一：步骤级内存调度（Step-Level Memory Scheduling，解决"何时召回"）**

- 实证依据：在 8 个 OpenHands SWE-bench Lite 轨迹上分析滑动窗口注意力分布的 KL 散度，发现同一 agent step 内相邻窗口的平均 KL 仅为 0.070 bits，而跨 step 边界则高达 2.59 bits（相差 37.3 倍）。
- 设计：每个 agent step 只在 **prefill 完成后、decode 开始前**执行一次工作集更新；整个 decode 期间工作集保持不变，新生成的 KV 追加在执行视图尾部。

**机制二：查询条件化的 KV 检索（Query-Conditioned KV Retrieval，解决"召回什么"）**

- 实证依据：滑动窗口平均涉及 103.1 个历史块，但 top-8 块就覆盖 66.5% 的历史注意力，top-16 覆盖 77.0%——说明只需召回少量高相关块。
- **Mean-K 索引构建**：对每个历史 KV 块，先去除 K 向量中的 RoPE 位置编码获得位置无关的 ˜k，再对每个层和 KV head 取均值得到块级表示：
  
  k̄_{l,b,g} = (1/|b|) Σ_{i∈b} ˜k_{l,i,g}
  
  这使得索引大小远小于完整 KV 状态。
- **相关性评分公式**：对每个候选块 b，用当前查询向量与 Mean-K 做缩放点积，并在候选块上做 softmax 归一化：

  R_b = Σ_m mean_{l,h} softmax_{b'∈C}( q^T_{l,m,h} k̄_{l,b',g(h)} / √d )_b

  即对每个 query token，在层和头上取平均；默认保留 sink 与 recent 区域后，以该分数填充剩余预算。
- **可扩展性设计**：完整索引驻留主机内存，仅将固定大小的 tile 流式加载到 GPU 上评分，使检索的 GPU 内存占用与工作区规模解耦。

**机制三：分层 KV 管理（Tiered KV Management，解决"如何召回"）**

- 区分两个视图：**仓库视图**记录每个历史块的副本位置（GPU 页池 / 主机 / NVMe）；**执行视图**仅包含当前 step 选中的块，按时间顺序排列并通过页表映射到紧凑注意力窗口（免拷贝装配）。
- **位置一致性恢复**：RoPE 编码的 K 只在原位置有效，KVMem 以位置无关的 raw K 为真源，对进入执行视图的块按其新位置重新施加 RoPE（re-RoPE）；V 不依赖位置可直接复制。
- 三个优化：
  - **主动移出（Proactive Stage-out）**：在 chunked prefill 的 chunk 间隙异步将已完成块的 KV 复制到主机/NVMe，使下个工作集切换时可立即回收 GPU 页，移出操作不落在关键路径上。
  - **检索感知的分层复用**：将工作集转移分解为保留集 R_t = W_t ∩ W_{t-1}、进入集 L_t = W_t \ W_{t-1}、移出集 E_t = W_{t-1} \ W_t；GPU 上已有物理页的块免于加载，只加载 L_physical = W_t \ G_{t-1}。重复调用的块优先留在主机内存（而非 LRU 那样按最近使用驱逐），避免频繁的 NVMe 重载。GPU 页复用须通过 re-RoPE 处理 K 的位置变化，且设置 delta re-RoPE 次数阈值，超过后从 raw K 完全重建以限制数值误差累积。
  - **打包与流水线化的 KV 重物化（Packed & Pipelined Rematerialization）**：将分散的块在主机固定内存缓冲中聚合成连续批次，批量 H2D 传输至 GPU staging 缓冲，再由 GPU kernel 散射到目标 KV 页并施加 re-RoPE。三个阶段（CPU 聚合 → H2D 传输 → GPU 散射 + re-RoPE）通过双重缓冲和 CUDA 事件重叠执行，将大量细碎传输转化为批量数据移动。

### 2.3 执行生命周期

每步先 prefill 新查询（期间收集 Mean-K 索引增量），然后执行一次工作集重选与恢复，再把当前查询在新执行视图上重新 prefill（避免旧上下文导致的注意力偏差），最后 decode。系统实现为原生 C++/CUDA 推理引擎 QW3（无法在现有 vLLM/SGLang 等引擎中直接扩展实现），支持分页 KV、连续批处理、前缀复用和 MTP 推测解码。

## 6. 主要结论与发现

- **效用提升**：KVM EM 优于 Sliding Window 与 Compact-only；在 LongMemEval-S 上达 85.6% 精度，几乎追平 Full Context（86.6%）；在 AgentLongBench ≤256K 上以 60.87% 超过 Full Context（59.54%）；超过模型原生窗口后优势更显著（MemoryAgentBench 40.99% vs Compact+RAG 34.80%；AgentLongBench 1M 时 50.0% vs 42.0%）。
- **效率提升**：pre-answer 延迟仅为 0.38~1.81 秒，而 Compact+RAG 需 26.63~416.38 秒；即使排除摘要生成时间，KVM EM 仍比其快 11.4~53.8 倍。KVM EM 的"全新 prefill"输入仅 0.08K tokens（与 Full Context 一致），而 Compact+RAG 需 31K tokens。
- **端到端 DeepSWE 提升**：Pass@1 从 43.8% 提升至 48.4%（绝对 +4.7 个百分点），Pass@4 从 81.3% 提升至 93.8%（绝对 +12.5 个百分点，15/16 任务至少一次成功）；prefill 时间降低 55.1%（2.23 倍加速），请求墙钟时间降低 15.4%，解码量降低 18.7%。
- **消费级可行性**：24GB 笔记本 GPU 上实现 80K token 执行视图 + 1M token 虚拟工作区（原生窗口的 4 倍），单会话约 50 token/s，保持交互响应性（对照：vLLM 仅支持约 10K 上下文，llama.cpp 约 80K 且无虚拟化）。
- **横向扩展**：服务器平台 10M-token 工作区（64K 执行视图不变）运行时 GPU 显存占用保持约 34-35 GiB 不变，TTFT 仅从 0.43s（256K）增至 1.60s（10M）。

## 7. 优点

1. **视角有新意**：把 agent 累积上下文上升为系统层可虚拟化资源，明确区分可寻址工作区、模型可见执行窗口与 GPU 驻留 KV 集三层边界——相比传统摘要化上下文管理，是对系统架构架构级别的重新定义。
2. **"KV 即内存"的硬件资源分层利用**：将 KV cache 建模成分页虚拟内存系统（GPU→主机内存→NVMe 的换入换出），打开了一条利用推理而非训练侧手段来扩充上下文处理空间的新路线。
3. **洞察扎实**：基于实际轨迹（OpenHands 8 个 rollout）的注意力分布 KL 散度与 top-k 覆盖度做调度/检索频度设计，让"步级调度""只需 8-16 个块"等设计有实验依据支持。
4. **务实处理"位置一致性"难题**：Raw K（无 RoPE）+ re-RoPE 方案对 KV 复用中的位置失配问题提出了系统化的处理方案。
5. **实验严谨性好**：受控基准 + 全轨迹评估两层互补设计；保留 Full Context 参考以确认虚拟化的潜在"长上下文退化缓解"效果；统一对比较为公平。
6. **针对真实约束给出结果**：消费级 24GB GPU + 1M 工作区 + 50 tokens/s 的单会话演示，展示应用可能性。

## 8. 不足与局限

1. **KV 复用保真度有理论缺口**：论文自身承认复用 KV 并不等于在新上下文下对文本重算——K 受到原因果上下文限制，重物化后未完全消除跨块因果偏差；缺少针对不同任务类型对 KV 复用误差敏感度的系统分析。
2. **检索漏检风险依然存在**：step 级调度 + 有限的检索预算意味着某些关键历史块仍可能被漏选；当工作区规模膨胀时，检索的权威性取决于 Mean-K 表示的区分能力，论文不过多讨论对细粒度工具输出或精确数值的盲点。
3. **存储开销高**：KV 状态远大于对应文本（10M-token 工作区需 324 GiB NVMe）。论文并未给出 KV 空间开销与复算成本之间的盈亏平衡分析，也未对压缩文本与 paged KV 之间的混合存贮做优化探索。
4. **不能透明叠加于黑盒 API**：实现需要端到端控制 KV 分配/检索/位置恢复/跨层移动，所以无法在 closed-source API 上运行；扩展到多用户并发、多 workspace 竞争共享存储资源也是开放问题。
5. **实验范围与统计性**：受控基准主要是"已固定历史回放"而非真实完整 agent 轨迹，对 KVMem 在运行中上下文管理对后续推理/工具使用效果的耦合缺乏多任务覆盖；DeepSWE 仅 16 任务×4 次采样且未做显著性检验；缺少独立消融（如不同块大小 32 vs 128、softmax 打分 vs 向量相似度、调度频率调整等的单独影响）。
6

6. **场景适用范围与失败模式未被充分刻画**：KVMem 的有效性高度依赖"注意力天然稀疏、且相关历史集中在少数块中"这一实证前提。对于需要同时综合极宽范围上下文的任务（例如要求跨数千个分散块做精确数值匹配、多跳逻辑引用、或对时间细节零容错的场景），有限的 top-k 召回是否依然可靠、失败概率如何随工作区规模增长、以及是否应有针对低置信度的兜底策略（如自动回退到整段重 prefill），论文均未给出定量刻画或失败案例分析。此外，方法对模型架构的假设——Mean-K 作为检索键的区分力、KV 状态的可独立移动性等——也未跨不同系列（如非 RoPE 位置编码模型、专家混合架构、长上下文微调差异显著的模型）验证，其泛化边界尚待进一步探索。

---

## 9. 总结评价

总体而言，KVMem 是一篇系统性较强的系统研究论文。它将长期运行智能体的上下文膨胀问题以"虚拟内存"为隐喻重新定义，把 KV cache 从被动的推理缓存提升为主内存管理与调度的一等公民，并围绕 *何时召回、召回什么、如何召回* 三个子问题给出了层次分明、实现完整的技术方案（步骤级调度、Query 条件化 Mean-K 检索、GPU/内存/NVMe 三层存储与流水线化重物化）。这一"用系统手段而非摘要手段解决长上下文"的思路，对社区后续在检索式 KV 复用方向的工作具有较清晰的参考价值。

但论文也有明确的局限：理论保真度（KV 复用与全量重算的因果一致性差距）缺少数学刻画；实验过度集中在少数几类注意力稀疏场景，消融深度不足；DeepSWE 的统计功效偏低，尚不足以证明端到端收益的稳健性；且作为闭源 API 无法复用的深度定制系统，落地门槛较高。若后续研究能补齐检索失败率边界分析、跨任务/跨模型泛化验证与盈亏平衡分析，这条技术路线会更具有说服力。
