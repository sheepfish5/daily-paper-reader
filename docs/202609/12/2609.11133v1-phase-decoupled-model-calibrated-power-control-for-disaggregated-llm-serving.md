## 摘要
数据中心 GPU 功耗是 LLM 服务容量的刚性约束，生产服务已转向预填充/解码（PD）解耦。在解耦式 B200 系统上部署 NVIDIA 的 Max-Q 推理配置时，我们发现其实际收益有限（+8.6% tokens/J）、依赖模型，并带来平均端到端延迟代价（+5.2%），而仅看吞吐的评估无法揭示这一点；该配置还对运行在相反硬件工况下的预填充和解码 GPU 采用同一种设置。我们假设，最优功耗设置是所部署（模型、量化、引擎、硬件）组合的属性，而非 GPU 类别的属性；每条通道都应有自己的配置；并且要安全地将 SLO 余量转化为能效，需要在运行时 SLO 保护下进行受延迟门控的校准，而不是采用固定配方。我们提出一种阶段解耦、模型校准的控制器：预填充通道运行在 SM 时钟窗口下，其下限从构造上即为延迟保证；解码通道运行在自动校准所设定的功耗上限下，该上限刚好高于实测的吞吐/延迟悬崖。由于解耦式解码通道消耗平稳的、受内存限制的功耗，该上限会持续生效，导致 POLCA 拒绝设置功耗上限的反应式过冲缺陷不复存在，并且 GPU 自身的功耗管理器能在该上限下保持吞吐。在 8x B200 节点上，以智能体负载服务 Qwen3-Coder-480B（FP8）时，我们的均衡模式在平均端到端延迟增加 +3.5% 的情况下实现 +20.4% tokens/J，而 Max-Q 为 +5.2% 延迟代价下 +8.6%，在两个维度上均实现帕累托改进。在 Qwen3-235B-A22B（NVFP4）上，每种运行模式在每次重复中均满足 ITL-p99 SLO；而两种厂商配置均未满足。一项解码执行器 A/B 测试表明，校准后的功耗上限优于静态时钟锁定；一次为期三天的持续运行节省了一对通道 32.3% 的电能。两个模型均为 MoE；稠密模型可获得的收益大约只有其 1/5，因此我们将结论范围限定于 MoE 服务。

## Abstract
Datacenter GPU power is the binding constraint on LLM serving capacity, and production serving has shifted to prefill/decode (PD) disaggregation. Deploying NVIDIA's Max-Q inference profile on a disaggregated B200 system, we found its realized gain modest (+8.6% tokens/J), model-dependent, and carrying a mean end-to-end latency cost (+5.2%) that throughput-only evaluation does not surface; the profile also applies one setting to prefill and decode GPUs that operate in opposite hardware regimes. We hypothesize that the optimal power setting is a property of the deployed (model, quantization, engine, hardware) combination rather than of the GPU class, that each lane warrants its own profile, and that converting SLO headroom into energy safely requires latency-gated calibration under a runtime SLO guard rather than a fixed recipe. We present a phase-decoupled, model-calibrated controller: the prefill lane runs under an SM-clock window whose floor is a latency guarantee by construction, and the decode lane under a power cap placed by automatic calibration just above a measured throughput/latency cliff. Because a disaggregated decode lane draws flat, memory-bound power, the cap binds continuously, the reactive-overshoot weakness that led POLCA to reject capping is absent, and the GPU's own power manager retains throughput under the cap. On an 8x B200 node serving Qwen3-Coder-480B (FP8) under agentic load, our balanced mode delivers +20.4% tokens/J at +3.5% mean e2e versus +8.6% at +5.2% for Max-Q, a Pareto improvement on both axes. On Qwen3-235B-A22B (NVFP4) every operating mode meets the ITL-p99 SLO in every repetition; both vendor profiles miss it. A decode-actuator A/B shows the calibrated cap beats static clock locks, and a three-day sustained run saves 32.3% of a lane pair's electricity. Both models are MoE; a dense model recovers roughly 5x less, so we scope our claims to MoE serving.

## 1. 核心问题与整体含义

- **背景约束**：数据中心 GPU 功耗已成为 LLM 服务容量的刚性约束，集群往往先耗尽电力预算而非机架空间；因此每节省一瓦功耗都直接转化为可部署容量。
- **生产范式转变**：生产服务已普遍采用预填充/解码（PD）解耦架构，将两种硬件特征相反的阶段（prefill 计算密集、功耗高；decode 内存带宽受限、功耗平稳且远低于 TDP）分置到独立 GPU 池。
- **核心矛盾**：现有三类主流方案均未从被服务的具体组合推导功耗设置：
  - **厂商静态配置**（NVIDIA Max-Q）：按 GPU 类别统一套用同一多旋钮配方，对 prefill 与 decode 采用相同设置，属"阶段盲"。
  - **集群功耗管理框架**（POLCA、TAPAS）：POLCA 明确拒绝功耗上限，认为其反应式、不可预测，主张时钟锁定。
  - **阶段感知 DVFS 控制器**（VoltanaLLM、DualScale、GreenLLM 等）：虽识别 PD 不对称性，但执行器一律为频率选择，且未在解耦场景下重新审视机制选择。
- **关键观察**：在解耦 B200 系统上部署 Max-Q，实际仅获 +8.6% tokens/J，却带来 +5.2% 平均端到端延迟代价（吞吐评估无法揭示），且该配置对两个相反硬件工况的 GPU 使用同一种设置。
- **核心假设**：
  - **H1**：最优功耗设置是（模型、量化、引擎、硬件）组合的属性，而非 GPU 类别属性，需按组合测量，故校准必须自动化。
  - **H2**：PD 解耦下 prefill 与 decode 通道应有各自独立配置。
  - **H3**：安全转化 SLO 余量需延迟门控校准 + 运行时 SLO 保护，而非固定配方。
- **整体含义**：解耦将原先需在时间维度追逐的瞬态阶段区分，转变为 GPU 通道的静态空间属性；本文据此提出阶段解耦、模型校准的功耗控制器，并发现两通道需要不同**机制**（而非仅不同设置）。

## 2. 方法论

### 2.1 核心思想

- **问题形式化**：给定尾延迟 SLO Λ（ITL-p99 约束），控制器求解
  - 目标：max_(c,W) tokens/J，s.t. ITL-p99 ≤ Λ
  - 其中 c 为 decode 功耗上限，W=[f_lo, f_hi] 为 prefill SM 时钟窗口，二者取自按（模型、量化、引擎、硬件）索引的校准产物 A。
- **机制分工**（由测量而非直觉决定，与初始设计相反）：
  - **Prefill 通道 → SM 时钟窗口**：计算密集（β≈1），功耗与时钟近似成正比，窗口下限即延迟保证；窗口跨度约可达时钟范围的 20-30%，最节能模式下限接近最大时钟一半。
  - **Decode 通道 → 校准功耗上限**：内存带宽受限（β≪1），功耗平坦；上限置于实测吞吐/延迟悬崖之上，由 GPU 自身功耗管理器在微秒级自适应分配 SM/内存频率。

### 2.2 关键理论依据

- CMOS 功耗模型：P ≈ A + B·f^(1+α)（α>0，电压随频率协同缩放）
- 执行时间 T ∼ f^(-β)，β∈[0,1] 为算术强度系数
- 单位工作量能耗：E = P·T ∼ A·f^(-β) + B·f^(1+α-β)
- 推论：prefill（β≈1）时钟下限天然构成延迟保证；decode（β≪1）存在带宽饱和悬崖，且 β 随批占用上升，最优频率随负载移动，静态锁频必须保守高置，而功耗上限通过委托 GPU 自身管理器连续重解分配，无需软件预测模型。

### 2.3 系统组件

- **执行器**（§3.1）：每通道异构机制（prefill：DVFS 窗口阶梯；decode：校准功耗上限）；窗口内轻量运行时控制器随负载调整时钟（速率受限）。
- **运行模式阶梯**（§3.2）：三种风险姿态，均源自同一校准产物，单调且受同一 SLO 保护：
  - **PERF**：decode 上限≈自然功耗，prefill 窗口高位，近乎不限流。
  - **BAL**：中间校准设定点，默认推荐。
  - **EFF**：最深的 SLO 可接受设定点（decode 上限刚高于悬崖，prefill 窗口下限即延迟保证）。
- **自动校准**（§3.3）：约 1 小时离线自动完成，输出各通道自然功耗、各模式 decode 上限、prefill 窗口边界，并记录引擎指纹（CUDA-graph 配置、KV 传输后端、引擎版本）。
- **算法流程**：
  - **算法 1（运行时模式执行）**：读取校准产物 A[m]，应用 decode 上限、限制 prefill 时钟窗口；每控制周期观测尾延迟，若违反 Λ 则将通道设定点释放向硬件默认，恢复合规后再重新应用；窗口内运行时控制器随负载移动时钟。
  - **算法 2（校准接受门）**：以多重复、抗噪的参考吞吐 T_ref 为基准，仅当候选设定点满足吞吐 ≥ (1-ε)T_ref **且** ITL-p99 ≤ Λ 时接受；引擎指纹变化即作废 A 并触发重新校准。

### 2.4 关键设计原则

- 策略的每个要素（机制、设定点、验证指标）都应从被部署栈的测量中推导。
- 校准必须自动且引擎感知：同一模型同一 GPU 上，不同引擎配置的自然 decode 功耗可移动约 3%，ITL 随引擎版本漂移。
- 延迟感知接受不可省略：仅按吞吐接受曾导致 ITL-p99 在大比例重复中越界。
